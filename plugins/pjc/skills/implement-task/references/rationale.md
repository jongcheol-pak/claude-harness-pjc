# Rationale — implement-task 규칙의 배경

> **이 파일은 규칙이 아니다.** 규칙의 정본은 `SKILL.md`이며, 여기 서술과 충돌하면 **`SKILL.md`가 우선한다.**
>
> 여기 담는 것은 "이 규칙이 왜 지금 형태가 됐는가"의 이력·근거뿐이다 — 판정 조건·수치 임계·금지/의무 문장·예외 경계는 담지 않는다(그것을 옮기면 본문만 읽는 실행 경로에서 규칙이 사라진다).
>
> **읽는 시점**: 규칙을 그대로 따를 때는 읽지 않아도 된다. 규칙이 반직관적으로 보여 그대로 적용해도 되는지 판단이 필요할 때, 또는 규칙을 바꾸려 할 때만 참조한다.

## Phase V — pre-review 커밋을 만드는 이유

리뷰어는 `git diff <BASE_SHA> <HEAD_SHA>`로 변경을 본다. 구현 변경이 워킹트리에만 있고 미커밋이면(과거 결함) HEAD가 직전 `checkpoint: T<N> start`(빈 커밋)를 가리켜, 리뷰어가 **빈 diff**를 보고 거짓 BLOCKER를 내거나 임의로 워킹트리 diff를 쓰게 된다. pre-review 커밋으로 리뷰 대상 스냅숏을 고정하면 결정적·재현 가능해진다.

## Fast-Path — Type C에서 V-6(품질 리뷰)이 기본이 된 경위

종전에는 Type C가 `(quality-review)` 플래그 없이는 V-6을 생략했다. 그 기본값이 **대부분의 코드를 품질 검토 0회로 통과**시켰기 때문에 반전했다(v1.122.0). 그래서 지금은 Type C/D의 실행 단계가 동일하고, 둘의 차이는 실행이 아니라 계획 단계에 있다.

## V-5 — Type B prefilter의 ESCALATE를 전건 Type C로 격상하는 근거

ESCALATE는 "trivial 아님" 판정이다(prefilter의 판단 기준이 "확신 없으면 ESCALATE"이므로). 종전에는 이때도 spec 단독 검증만 적용돼, **오분류가 가장 의심되는 순간에 가장 약한 검증이 걸리는 역설**이 있었다. 전건 격상은 그 역설을 없앤다.

## 호출 시점 주입 — 리뷰어 정의 파일의 금지 규칙만으로 실패한 경위

V-5·V-6이 Bash 쓰기 금지와 판정문 요구를 **호출 프롬프트에** 붙이는 이유다. 리뷰어 정의
파일에도 같은 금지가 있었지만 v1.173.0 T7에서 `code-quality-reviewer`가 그 규칙을 보유한
채 `git checkout <BASE_SHA> -- .`를 실행해 워킹트리를 되돌렸다(자기 보고로 발각 — 없었으면
다음 task의 편집이 조용히 유실될 뻔했다). 주입 후 T8·T10·T11 리뷰에서 위반 0건이지만
**표본 3회로 작다.** 같은 결론이 vault `decisions.md` [2026-08-15]에도 있다 — *"결함은 문구의
부재가 아니라 정의 파일 하단의 규칙이 조사 도중 상기되지 않는 것"*이라 문장을 더 넣는 대신
위치를 바꾸는 쪽이 답이다(v1.179.0 T1이 리뷰어 「실행 예산」 절을 **최상단**에 둔 근거이기도 하다).

## 검증 매핑 표의 위치 — V-2 조건부 축소 게이트가 "또는 그것이 지목하는 문서"까지 보는 이유

`AGENTS.md`는 세션 주입 상한(16KB) 때문에 표 본체를 별도 문서로 밀어낼 수 있다. 그때 게이트가
"AGENTS.md 안에 있는가"만 보면 조건이 거짓이 되어 **축소가 조용히 꺼진다** — 표를 옮긴 것뿐인데
매 task가 전체 스위트로 회귀한다. 문서 이동이 동작 변경이 되는 자리라, 게이트 문면을 넓게 잡았다.
