# 최종 보고 양식 (implement-task)

> SKILL.md "최종 보고" 섹션에서 참조. Phase F 통과 후(PRD 있으면 Phase G까지 통과 후) 아래 양식을 그대로 사용한다. 권한 경계(push·main 병합·태그·릴리즈·PR은 루프 권한 밖 — 별도 승인)는 SKILL.md 절대 규칙 12와 최종 보고 섹션 참조.

## 분량 지침

최종 보고는 **사용자가 다음에 무엇을 할지 정하는 데 필요한 것만** 담는다. 커밋 메시지·plan.md·git log에 이미 있는 내용을 다시 풀어쓰지 않는다(그쪽이 정본이고, 보고는 그것을 가리키면 된다).

- **task별 서술**: 한 줄. 무엇을 했는지는 커밋 제목이 이미 말한다.
- **검증 결과**: 명령과 수치만(`419/419 OK`). 로그 원문을 옮기지 않는다.
- **길게 써야 하는 곳은 정해져 있다** — 사용자의 판단이 필요한 것: Halt 사유, 검증하지 못한 항목과 그 이유, 승인이 필요한 외부 작업, follow-up.

요약하면 **완료된 것은 짧게, 미완·불확실한 것은 자세히** 쓴다. 반대로 쓰면 보고가 길어지면서 정작 사용자가 알아야 할 것이 묻힌다.

## 제목 분기 (F-8 결과에 따라)

| F-8 상태 | 제목 |
|---|---|
| N/A(분해 섹션 없음) 또는 `⏳ 미확인` 0건 **이면서 인벤토리 미달 0건** | `## 🎉 모든 task 완료 + Phase F 통과 (+ Phase G 통과, PRD 있을 때)` |
| **`⏳ 미확인` 1건 이상 잔존** | `## ⏸️ 구현 완료 — 확인 대기` |
| **인벤토리 미달(수용된 ❌) 1건 이상** — `⏳`가 0건이어도 | `## ⏸️ 구현 완료 — 확인 대기` |

> **미확인이 남으면 `🎉` 제목을 쓸 수 없다** — 시각 검증이 끝나지 않았는데 "완료"를 선언하는 것이 F-8이 막으려는 바로 그 결함이다(`phase-f-detail.md` F-8).
>
> **인벤토리 미달도 같다 (세 번째 행).** 인벤토리 행은 정적 축이라 `⏳`를 만들지 않으므로(`phase-v9-detail.md` 4), **`⏳` 조건만 두면 "항목·문구가 원본과 다른데 시각 미확인은 0건"인 상태가 `🎉`로 빠져나간다** — 화면 이식만 하는 작업(시각 속성 표를 생략한 plan)의 정상 형태가 정확히 그 상태다. 두 조건은 병렬이며, 기존 `⏳` 행의 조건·동작은 변하지 않는다.
>
> **`⏸️` 분기의 본문은 아래 양식과 동일하다** — Tasks 완료 수·변경 요약·Phase F/G 결과(PRD 있으면 G-1 충족표 전체 + Must 충족률 100% 명시 그대로)·Plan 변경 내역·Execution stats·Follow-ups를 모두 유지한다. **확인 보류가 PRD 보고를 삭제하지 않는다.** 다른 점은 셋뿐이다: ① 제목 ② **상단 안내 1줄** ③ **확인 요청 목록**(미확인 행·미달 행 + 사용자가 무엇을 어디서 봐야 하는지 — 화면 이름·진입 경로·볼 항목)을 Follow-ups 앞에 배치. 마지막의 "여기서 멈춥니다" 고지도 그대로 둔다.
>
> **상단 안내 1줄에는 미달 건수를 축별로 적는다** — 예: `인벤토리 3건 미달 / 시각 5건 미확인`. 상세 목록은 위 ③대로 Follow-ups 앞에 두되, **건수와 축 구분은 상단에서 바로 보이게** 한다(하단에만 있으면 읽히지 않은 채 완료로 받아들여진다). **"동일하게 만들었다"류 단정은 인벤토리 전 행이 ✅일 때만** 쓸 수 있고, 미달이 있으면 축을 나눠 서술한다(`phase-f-detail.md` F-8 5).

```markdown
**Plan**: <plan.md 경로>
**Tasks**: <N>/<TOTAL> 완료

**Summary of changes**

**Phase F 결과**
- F-2 전체 빌드: OK
- F-2 전체 테스트: <X/Y passed>
- F-7 plan-completion-reviewer: OK (또는 MINOR n개 follow-up 등록)

**Phase G 결과 (PRD 있을 때만 — G-1 충족표 전체 포함)**
- Must: <n>/<n> 충족 (기계 검증)
- 재루프: <0-2>회
- ⏳ 사용자 확인 필요 (HUMAN-VERIFY): <FR-x UI 체감, ...> ← 기계 검증 불가 항목, 직접 확인 부탁

**Plan 변경 내역** (구현 중 plan.md에 가해진 수정 — 사용자가 plan.md를 열지 않고도 계획이 잘 갱신됐는지 검수할 수 있게. 아래 4줄 중 변경이 하나도 없으면 전체를 "계획 원안대로 완료 (plan 수정 없음)" 1줄로 대체)
- 추가된 task: <구현 중 추가된 T<N> + 사유 (Phase G 갭, F 결함 보강, caller 연쇄 등) — 없으면 "없음">
- Files 추가: <P-3 caller 누락 발견 등으로 task Files에 추가된 파일 — 없으면 "없음">
- 신규 Deferred / Decisions: <구현 중 새로 생긴 항목 요약 (상세는 아래 Follow-ups) — 없으면 "없음"> (미처리 Deferred가 있으면 `docs/plans/deferred.md` 대장 반영 확인 — F-6.5 규정)
- 체크박스: <N>/<N> [x] 확인

**Execution stats**
- Type 분포: A=<n>, B=<n>, C=<n>, D=<n>
- Prefilter PASS율 (Type B): <n/n>

**Follow-ups** (있으면)

> **각 항목에 사유를 반드시 붙인다 — `기존 문제` / `범위 밖` / `개선 제안` 셋 중 하나.** 이 셋은 `implement-task` 규칙 4-1이 **이연 가능하다고 정한 것의 전부**이므로, 사유를 못 붙이는 항목은 이연 대상이 아니라 **이번에 고쳤어야 할 것**이다(자기 유발). 표기가 없으면 사용자는 *"왜 이게 남았는가"* 를 알 수 없고, 실제로 그 질문을 받았다.

     — SKILL 규칙 4-1. 그것은 같은 루프에서 고쳤거나(정상) 범위를 넘어 Halt한 것이지, 완료 보고의 잔여 항목이 아니다.

- <항목 1> (`기존 문제` | `범위 밖` | `개선 제안`)

**다음 회차 인계** (이연·등재한 항목이 있어 다음 착수가 정해질 때 — 사용자가 "새 세션에서 이어가게 해달라"고 하면 **필수**)

> **산출물은 새 세션 입력창에 그대로 붙여넣을 프롬프트다 — 코드블록으로 낸다.** 대장 등재와 plan `## Next Steps` 갱신은 함께 하되 **그것으로 대체하지 않는다**: 새 세션은 대장 수십~수백 건 중 *무엇부터*인지, *무엇을 먼저 판정해야* 하는지 모른다. 문서만 갱신하고 "새 세션이 대장을 열면 된다"고 안내하는 것은 인계가 아니라 **인계를 사용자에게 떠넘기는 것**이다(실제로 그렇게 처리해 지적받았다).
- 담을 것 넷: ① **착수 대상**(대장 항목이면 `[등록일] 제목`을 그대로 인용 — 새 세션이 그 문자열로 찾는다) ② **배경 1~2줄**(직전 회차가 무엇을 끝냈고 왜 이것이 다음인가) ③ **착수 전 판정할 것** — *직전 회차 방식을 그대로 복사하면 틀리는 지점*. 이 줄이 없으면 새 세션이 전례를 그대로 베껴 "고쳤는데 원 결함은 그대로"가 된다 ④ **현황 재측정 명령**(그 항목의 규모·상태를 즉시 재는 한 줄).
- 부수 항목은 **별도 코드블록**으로 나눠, 함께 넣을지 사용자가 고르게 한다(묶어 주면 범위를 못 고른다).
- 다음 착수가 정해지지 않았으면(이연 0건이거나 판단이 사용자 몫) 이 절을 생략한다 — 억지로 만들지 않는다.

**미룬 승인 항목** (루프가 「완료 후 일괄 승인」으로 미룬 것이 있을 때만 — `## Progress Log`에서 모은다)

> 자율 루프가 **승인이 필요하지만 지금 받지 않아도 되는 것**으로 판정해 **하지 않고 지나간** 작업들이다(정본은 `halt-conditions.md` 「위임 경계」 4번째 행 — 판정 기준은 *"그 작업 없이 그 task의 acceptance가 충족되는가"*). 각 항목에 **무엇을 · 왜 미뤘는지 · 지금 하면 무엇이 바뀌는지**를 한 줄로 적어 사용자가 채택 여부를 고르게 한다.
- **0건이면 이 블록 자체를 내지 않는다**(빈 목록·"해당 없음" 줄도 만들지 않는다 — 과잉 방지).
- **외부 작업 승인(아래 「여기서 멈춥니다」)과 섞지 않는다** — 그쪽은 push·병합·태그·릴리즈·PR이라 **행위를 이름으로 적어 `## ⏸️ 외부 작업 승인 요청` 헤더로 따로** 묻는 별개 요청이다. 이 블록은 루프가 이미 지나온 부수 작업의 사후 채택 여부이고, 승인하지 않아도 이번 회차의 완료 판정은 그대로다.

**여기서 멈춥니다.** push·main 병합·태그·릴리즈·PR 등 외부로 나가는 작업은 자율 루프 권한 밖이라 각각 별도 승인이 필요합니다 — 필요하면 그 행위를 이름으로 적어 따로 여쭙겠습니다 (예: "이제 push·v1.x.x 릴리즈 할까요?"). 어떻게 진행할지 알려주세요.
```
