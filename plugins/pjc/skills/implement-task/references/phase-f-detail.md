## F-1. plan Goal 재확인 (자체 검증)

- plan.md의 `## Goal` 문장을 다시 읽고, 누적된 diff 전체가 그것을 충족하는지 자문
- Goal에 있는 단어/개념마다 diff 어디에서 충족되는지 지목
- 미충족 발견 → 추가 task로 보강하거나 follow-up 등록

## F-2. 전체 빌드 + 전체 테스트 (per-task 아닌 전체)

- **빌드 중복 제거**: 마지막 task의 V-1 빌드가 성공했고 그 이후 **코드 변경이 전혀 없으면** (commit만 했고 추가 수정 없음) 전체 빌드를 **skip**한다. 이미 최신 빌드 상태이므로 재빌드는 무의미.
  - 단 마지막 task 이후 어떤 파일이라도 수정했다면 빌드 다시 실행.
  - 확신이 안 서면 빌드 실행 (안전 우선).
- AGENTS.md의 test 명령 실행. 전체 통과 수 기록. **(테스트는 항상 전체 1회 실행 — 누적 회귀 최종 확인)**
- per-task에서 통과했던 테스트가 누적 변경 후에도 여전히 통과하는지 확인.

## F-3. Impact Analysis 회귀 점검 (자체 검증)

  - 실제 처리되었는지 grep으로 재확인
  - 명시되었으나 흔적이 없으면 사유 확인 또는 follow-up 등록

## F-4. Follow-ups 완전성 확인

- 모든 commit 메시지에서 "follow-up", "TODO", "MINOR" 언급된 사항이 plan.md `## Deferred / Follow-up`에 기록되었는지
- 누락 시 plan.md 갱신
- **각 항목이 자기 유발인지 기존 문제인지 분류돼 있는가 (SKILL 규칙 4-1)** — 이번 plan의 변경이 **원인이 되어 생긴 것**(회귀·깨진 호출부·어긋난 문서/규약·무효화된 동작)이 Deferred에 남아 있으면 **F-4는 그 상태로 Phase F를 통과시키지 않는다**: 추가 task로 해소하거나, 고치는 것이 범위를 넘으면(파괴적·외부/비가역·공개 API·5개 파일 이상 연쇄) 이연이 아니라 **Halt**한다. 이연 가능한 것은 규칙 4-1의 셋(기존 문제·범위 밖·개선 제안)뿐이다.

## F-6. 자기 정직성 최종 체크

**V-8 자기점검(SKILL Phase V)을 plan 전체 diff에 1회 재적용**한다 — per-task가 아닌 plan-wide 관점:
- [ ] plan의 **모든** acceptance가 diff에서 충족됨을 지목할 수 있는가 (도중 약화·축소한 acceptance는 없는가)
- [ ] 빌드/테스트 출력을 직접 봤는가 (commit 메시지만 의존하지 않음)
- [ ] "거의 동작함" 같은 모호한 표현으로 마무리하지 않았는가

F-1 ~ F-6 중 어느 하나라도 결함 발견 → **추가 task 등록 후 Phase P 재진입** 또는 **사용자 보고 (Halt)**.

## F-6.5. 문서 갱신 (README) + 회차 서사 커밋

검증 통과 후, 완료된 작업을 문서에 반영한다. (공통 지침 CLAUDE.md의 "문서 관리"를 따르되, 회차 서사 처리는 다음을 명시한다.)

**회차 서사 커밋**: 개별 task 커밋은 *그 task가 무엇을 했는지*를 담지만, **여러 task를 관통하는 흐름은 어느 커밋에도 남지 않는다.** 그 공백만을 커밋 하나로 메운다 — **커밋 메시지 본문이 이미 담는 것(`Type`·`Build`·`Tests`·`Review`·`Caller-recheck`·`Self-honesty`)은 반복하지 않는다**(git이 정본). 담을 것은 둘뿐이다:
- **ⓐ 여러 task를 관통하는 맥락·경위** — 커밋 하나로는 보이지 않는 흐름(이 회차의 실질이 무엇이었는지).
- **ⓑ 회차 수준의 결정 배경** — 개별 task 커밋에 없는 것. 무엇을 했는지가 아니라 **왜 그렇게 했는지·무엇을 기각했는지**.
- **`## Deferred / Follow-up`은 여기 적지 않는다** — 아래 **Deferred 대장이 정본**이며, 서사에 중복 기재하면 두 곳이 갈린다.

**ⓒ 커밋 명령**:
```bash
git commit --allow-empty -m "문서: Phase F 통과 기록" -m "<서사 본문 — ⓐ·ⓑ>"
```
**`--allow-empty`가 필수다** — `plan.md`가 gitignore인 레포에서는 F-6.5 산출물이 git에 보이지 않아 staged가 0이고, 일반 커밋은 `nothing to commit`으로 실패한다(`checkpoint: T<N> start` 빈 커밋과 동일 선례). README를 함께 고친 회차라면 그 변경이 같은 커밋에 담긴다.

**제목 문구는 고정이다** — 부제가 필요하면 `문서: Phase F 통과 기록 — <부제>`처럼 뒤에 잇고, `병합:` 등 **다른 접두어로 대체하지 않는다.** 이 커밋과 아래 ⓒ-2의 병합 커밋은 같은 회차를 가리키지만 **자리가 다르다**(작업 브랜치 / main). 제목까지 같게 만들면 `git log --oneline`에 동일한 줄이 연달아 두 번 나타나 어느 쪽이 서사 커밋인지 구별되지 않는다 — v1.183.0에서 실제로 그렇게 됐다(`ad78d7d`가 `병합: … (v1.183.0)` 제목의 빈 커밋으로 남았고, 정작 병합 커밋 `b04b23a`는 본문 없이 제목 한 줄뿐이었다).

**ⓒ-2 병합 커밋도 같은 서사를 싣는다 (승인 후 수행 — 메시지 규약의 정본은 여기다)**: main 병합은 루프 권한 밖이라 사용자 승인 뒤에 수행하지만(규칙 12), 그때 만드는 커밋의 **메시지 형태는 이 절이 정한다** — 승인 시점에 즉석으로 짜면 회차마다 갈린다.

```bash
git merge --no-ff task/<id>-<slug> -m "병합: <회차 제목> (v<버전>)" -m "<서사 본문 — ⓒ와 같은 ⓐ·ⓑ>"
```

**둘째 `-m`을 빠뜨리지 말 것** — 서사 커밋은 병합으로 도달 가능하니 사라지지는 않지만, `git log --first-parent`로 **회차 단위로 훑을 때는 병합 커밋 본문만 보인다**. 본문이 비면 그 회차만 제목 한 줄로 비어 보인다. 최근 병합 6건 중 2건(`4b4bca6`·`b04b23a`)이 그 상태이므로 우연한 누락이 아니라 **규정이 없어서 생긴 반복**으로 본다.

**ⓓ 수행 시점**: **F-7(·F-8) 통과 후, `SKILL.md` Phase F가 Phase Ledger를 갱신하는 지점에서 1회.** PRD 연결 plan은 **Phase G 통과 후 최종 보고 직전 1회**다. F-6.5는 서사를 **작성**하는 자리이고 커밋은 통과가 확정된 뒤에 만든다 — 아래 「큐 자동 소비」 ⓑ가 *"1회의 기준은 세션이 아니라 최종 보고"*로 같은 구조를 쓴다.
- **F-7 앵커가 없는 회차 — 진입 조건표 1행(1 task + Type A, Phase F 생략)과 2행(1 task + Type B, F-6.5는 돌지만 F-7 없음)**: **이 분기는 `**PRD**:` 줄이 없는 회차에만 적용된다** — PRD 연결 plan은 F-7 유무와 무관하게 위 「Phase G 통과 후」 경로(G-4에서 ⓒ의 신규 커밋)를 쓴다. PRD 없는 회차에서는 "Phase F 통과 기록" 커밋이 성립하지 않으므로 **마지막 task 완료 커밋(`T<N>:`) 본문에 서사를 병합**한다. **그 커밋은 Phase D 「커밋」에서 이미 만들어져 있으므로 신규 커밋이 아니라 `git commit --amend`로 본문에 덧붙인다** — ⓒ의 `--allow-empty` 명령은 F-7이 있는 주 경로 전용이다(Phase D 「커밋」의 amend 분기와 같은 수단이며, 로컬 작업 브랜치의 미push 커밋이라 규칙 10의 history rewrite에 해당하지 않는다).
- **ⓔ Halt로 끝난 회차는 대상이 아니다** — F-6.5에 닿지 못했으므로 남길 서사도 확정되지 않았다.
- **ⓕ 재진입·재루프 회차는 최종 1회** — F-7 BLOCKER로 Phase P 재진입(아래 F-7, 최대 3회)하든 Phase G의 G-2 재루프(`phase-g-detail.md`, 최대 2회)를 돌든, F-6.5가 여러 번 실행돼도 **커밋은 최종 통과 시 하나만** 만든다. 서사는 재진입·재루프에서 얻은 내용까지 합쳐 **마지막에 한 번** 쓴다 — 통과 전에 *"Phase F 통과 기록"* 커밋이 먼저 남으면 그 제목이 거짓이 된다.

**Deferred 대장 반영 (`docs/plans/deferred.md` — 형식 정본은 이 절)**: plan에 미처리 `## Deferred / Follow-up` 항목이 있으면 `docs/plans/deferred.md`의 `## 대기` 섹션에 1줄씩 append한다 — plan.md는 다음 작업 때 교체되고 레포에 따라 gitignore이기도 해서 이월이 수작업이 되고 유실되기 쉬우므로, **커밋되는 단일 대장**이 Deferred 추적의 **유일한 정본**이다.
- **등재 게이트 (등재 전에 먼저 판정한다 — 형식보다 앞선다)**: 대장은 append만 하면 단조 증가하므로 **올릴 것과 그 자리에서 끝낼 것을 등재 시점에 가른다.** 실측 근거: 어느 두 회차의 신규 등재 7건 중 **5건이 리뷰어 배출물**이었고 그중 2건은 리뷰어 스스로 확신이 낮다고 표시한 것이었다(같은 기간 대기가 120 → 129로 늘었고, "소진"을 표방한 회차조차 순증이었다).
  - **⚠ 규칙 4-1(자기 유발)이 이 게이트에 우선한다.** 자기 유발 결함은 **심각도 라벨·범위와 무관하게 게이트 대상이 아니며**, **범위 안이면 고치고 범위 밖이면 Halt**한다(어느 쪽도 등재가 아니다 — `SKILL.md` 규칙 4-1). **자기 유발 판정은 여기서 끝나고 아래 거르는 범주로 내려가지 않는다** — 같은 분기를 게이트 안에 다시 적으면 "게이트 대상 아님"과 "게이트의 분기임"을 동시에 주장하게 된다.
  - **거르는 범주 다섯 — 비자기유발 지적에만 적용된다**:
    - **ⓐ 판정 유보** — 리뷰어가 `(판정 유보)`로 표시한 것은 등재하지 않는다. 리뷰어가 확신이 낮다고 **스스로 밝힌** 것이라 정말 결함이면 다음 회차에 다시 관측된다. **배출 규정은 그대로다** — `agents/plan-completion-reviewer.md`의 *"침묵하지 말고 배출"* 은 리뷰어의 의무이고 이 게이트는 **메인의 등재 판정**이라 층이 다르다(배출된 지적은 커밋 메시지에 남으므로 정보가 사라지지 않는다).
    - **ⓑ 범위 안** — **① 수정 대상이 그 task의 `Files` 목록 안이고 ② plan의 `Verification Strategy`에 이미 있는 명령으로 재검증되면** 등재하지 않고 **그 자리에서 고친다.** 둘 중 하나라도 아니면 등재한다. **"5분이면 된다" 같은 시간·체감 기준을 쓰지 않는다** — 그런 축은 *"이건 5분 넘어 보인다"*·*"새 측정이 필요하다"* 로 언제든 자기 정당화되므로, **plan 문서에 이미 적힌 두 값**으로만 판정한다.
    - **ⓒ 증상만 막는 수정** — 지적을 등재하기 전에 *"이 지적이 가리키는 **원인**이 어디 있는가"* 를 본다. **원인이 이 task의 `Files` 안이면 등재 불가이며 그 자리에서 원인을 고친다** — 증상만 막아 두고 원인을 대장에 올리면 다음 회차에 같은 증상이 다른 얼굴로 돌아온다(사용자 표현: *"근본적인 해결 방법보다 일부만 수정해서 현재 상태에서만 문제가 발생하지 않도록"*). 원인이 Files 밖이면 종전대로 ⓑ의 판정을 따른다.
      - **원인의 위치는 이렇게 특정한다** — **리뷰 지적 본문이 지목한 코드 지점**, 또는 그것이 없으면 **증상에서 grep으로 직접 추적되는 지점**이다. 둘 중 어느 것으로도 원인을 특정할 수 없으면 이 축은 발동하지 않는다(추측으로 "원인이 안에 있다"고 판정하지 않는다).
      - **새 주관 축을 만들지 않는다** — *"이게 근본 해결인가"* 를 감으로 묻는 것이 아니라, **원인의 위치가 Files 안인가**라는 ⓑ와 같은 객관 축으로 판정한다. 증상과 원인이 같은 자리면 애초에 이 축이 발동하지 않는다.
    - **ⓓ 외부 사건 트리거 조건부** — 원 지적이 **착수 조건을 외부 사건에 걸고 있으면**(*"…가 관측되면"* 류) 등재하지 않는다. 그 사건이 일어나는 날이 곧 근거를 갖춘 새 등재 시점이라 대기에 두어도 착수를 앞당기지 못한다. **이 축은 새 기준이 아니라 아래 「대장 소진 batch 규약」 ②의 기각 주력을 등재 시점으로 앞당긴 것**이다 — 그 축이 batch에서 이미 12건 이상을 `기각(기록성)`으로 종결해 왔고, 그렇다면 **등재 → 대기 체류 → batch 판정 → 기각의 왕복 전체가 낭비**다.
      - **판정 어휘·예시·예외는 ②의 두 ⚠ 가 정본이며 여기 복제하지 않는다** — 트리거 문구 목록·「이미 판단이 내려진 것」 예시·**⚠ 관측 경로가 없는 것은 유지**(fail-open 미탐처럼 실패가 조용한 것)·**⚠ 원문에 없던 트리거를 판정자가 부여하지 않는다** 전부 그렇다. **같은 목록을 두 곳에 적으면 한쪽만 고쳐져 갈린다** — 이 절의 초안이 실제로 `"(선택)"` 항목을 빠뜨려 **신설 즉시** 드리프트를 냈다(v1.185.0 T1 quality M1).
      - **⚠ `SUGGEST`와의 우선순위 (ⓓ·ⓔ 공통)**: `SUGGEST` 라벨은 그 자체로 ⓓ·ⓔ 면제가 아니다. 그러나 **ⓓ의 두 분기 모두 원 지적 본문에 그 문면이 실제로 적혀 있을 때만 적용한다** — 「이미 판단이 내려진 것」은 **판단 결론**이 적혀 있어야 하고, 「외부 사건 트리거」는 **위 ⚠(원문에 없던 트리거 부여 금지)가 그대로 적용된다**. 결론도 트리거도 없이 개선을 제안하는 `SUGGEST`는 아래 「거르지 않는 것」에 따라 **종전대로 등재한다**. **ⓔ도 같다** — 관찰만 적은 `SUGGEST`라도 ⓔ의 2조건 AND를 통과해야 미등재이며, `SUGGEST` 라벨이 ⓔ를 자동 발동시키지도 자동 면제하지도 않는다.
    - **ⓔ 액션이 아닌 기록성 관측** — 원 지적이 **관측·교훈**이고 액션이 아니면 등재하지 않고 **회차 서사 커밋 본문에만 남긴다**(위 F-6.5 ⓒ가 그 자리다 — ⓐ와 같은 논리로 정보가 사라지지 않는다). **범주 자체는 소진 batch 규약 ④(기록성 항목은 기각 범주)에서 승계하되, 판정 축은 등재 시점용으로 새로 정의한다** — ⓓ가 어휘·예시·예외까지 ②에 위임하는 것과 달리 여기는 *"무엇을 기록성으로 볼 것인가"* 를 아래 2조건으로 규정한다(④ 쪽은 항목의 **성격**을 보고 여기는 원 지적의 **문면**을 본다 — ④ 말미가 같은 구분을 적는다).
      - **판정은 원 지적의 문면에 대한 2조건 AND다** — **ⓐ 수정 대상과 그 수정 동작이 한 절에 함께 적혀 있지 않다** · **ⓑ 액션 동사가 없다** — `고친다`·`추가한다`·`바꾼다`·`넣는다`·`정정한다`·`명문화한다` 등이며 **이것은 예시이고 이에 준하는 지시형 서술을 포함한다**. 둘 중 하나라도 아니면 등재한다.
      - **⚠ 경로가 나온다고 「명시」가 아니다** — 대장 항목 대다수가 **관측 지점·근거 인용**으로 `경로:라인`을 담는다(아래 소진 batch 규약 ③가 종결 근거로 그것을 의무화하기 때문이다). 그것은 *"어디서 보였는가"* 이지 *"거기를 어떻게 고친다"* 가 아니므로 ⓐ의 「명시」에 해당하지 않는다. **경로와 수정 동작이 같은 절에서 짝을 이룰 때만** 명시로 본다.
      - **⚠ ⓐ와 ⓑ은 독립 조건이 아니라 같은 짝을 두 각도에서 보는 것이다** — **특정 대상을 향하지 않는 일반 원칙·교훈형 당위 서술**(*"…할 때는 …해야 한다"*·*"…를 전부 돌려야 한다"*)은 ⓑ의 지시형에 **포함하지 않는다**. ⓐ가 요구하는 **대상-동작 짝이 없으면 그 당위 서술은 액션이 아니다.** 이 단서가 없으면 기록성 교훈이 거의 예외 없이 당위형으로 끝나므로 ⓑ에서 통째로 등재로 흘러가 이 범주가 이름만 남는다.
      - **⚠ 판정이 갈리면 등재한다** — ⓔ는 미등재 판정이라 애매할 때의 안전 방향이 ⓑ·ⓒ와 **반대**다(그쪽은 「고친다」라 되돌릴 수 있지만 미등재는 아무 데도 남지 않는다). 소진 batch 규약 ②의 *"판정이 애매하면 유지"* 와 같은 방향이다.
      - **⚠ 원 지적이 「반영할 정본 문서」를 적었으면 그것은 액션이다** — 규약화 대상을 지목한 것이므로 종전대로 등재한다. **판정자가 「지목할 수 있다」고 선언하는 것이 아니라 원 지적이 그 문서를 적었는지를 본다**(ⓒ가 못 박은 「새 주관 축을 만들지 않는다」와 같은 층 — 판정자의 시도 성패에 의존하는 축은 반증할 수 없다).

  - **원인 귀속 × 범위 4조합** (위 둘을 합치면 전건이 정해진다):

    | | **범위 안**(①② 충족) | **범위 밖** |
    |---|---|---|
    | **자기 유발** | 고침 · 미등재 (규칙 4-1) | **Halt** (`SKILL.md` 4-1) |
    | **비자기유발** | **고침 · 미등재** (ⓑ) | 등재 (ⓑ) — 단 **원인이 Files 안이면 등재 불가·고침**(ⓒ) · **ⓓ·ⓔ에 걸리면 미등재** |

  - **거르지 않는 것**: `SUGGEST`(설계 소견)·표현·문면 지적은 **종전대로 등재 가능**하다. 이 게이트는 *"MINOR는 다 버린다"* 가 아니다 — 그렇게 읽으면 문서 품질이 서서히 떨어진다.
  - **세 규정은 층이 다르다**: 이 게이트는 **등재 시점의 필터**, 아래 「중복 억제」는 **동일 요지의 재등재 방지**, 「항목 수 상한·자동 만료 없음」은 **`## 대기`에 등재된 미처리 항목의 삭제 금지**다(**종결된 항목의 사유별 정리와는 층이 다르다** — 아래 「종결 처리 3분기」의 표가 그것을 규정한다). 서로를 대체하지 않는다. **⒪의 「절대 상한」은 또 다른 층이다** — 그것은 항목을 지우는 상한이 아니라 **batch를 여는 트리거**라, 여기 「항목 수 상한을 두지 않는다」와 어휘만 겹칠 뿐 대상이 다르다.
- **형식**: `## 대기`에 `- [YYYY-MM-DD] {요지 1줄} (출처: {plan slug 또는 버전})`, `## 종결`에 `- [등록일 → 종결일] {요지} — {반영(버전·T#)|기각(사유)}` 또는 `— 병합 — 「<등록일 제목>」에 흡수`(**병합만 이중 대시형** — 기존 항목 전건이 이 표기다). **이 줄 형식이 대조기 계수 정규식의 짝이자 아래 3분기 판정 규칙 ①의 근거**이므로 임의로 바꾸지 않는다(소급 정리가 끝나면 `## 종결`에는 기각만 남지만, 정리 전에는 세 사유가 공존하므로 열거를 좁히지 않는다).
- **종결 처리 3분기 (사유가 처리를 결정한다)**: 종결은 일률적 이동이 아니다 — **근거가 커밋에 남는 것은 삭제하고, 대장이 유일한 근거처인 것만 보존**한다.

    | 사유 | 처리 | 근거처 |
    |---|---|---|
    | **반영** | 항목 **삭제**(삭제 누계에 반영 — 값 규칙은 대장 「카운트 기준」) | 대응 커밋(해시 또는 `vN T#`)을 **삭제 커밋 본문에 지목** |
    | **병합** | 항목 **삭제**(동상) | 삭제 커밋 본문(흡수처를 **등록일 + 제목**으로 지목) |
    | **기각** | `## 종결`로 **이동**(이력 보존 — decisions.md 항목 불변 관례와 동형) | 대장 항목 자신 |

  - **기각만 보존하는 이유**: 기각은 *"아니라고 판단했다"* 는 결론이라 **대장 밖에 근거가 없다.** 지우면 같은 항목이 다음 회차에 다시 등재되고 같은 조사가 반복된다 — 실제로 `## 대기`에는 「미탐 예외 신설 시 직전 batch **기각분**을 1회 재훑을지」처럼 **기각 이력의 소급 재조회를 상정한 항목**이 있다.
  - **판정 규칙 (사유 문자열은 상호배타가 아니다 — 실측 근거로 도입)**: 종결 항목 줄에 사유 단어가 본문 어디에나 등장해 단순 포함 검색은 **총수를 초과**하고 겹침이 실재한다(반영∩기각·반영∩병합). 그러므로 —
    - **① 판정 대상은 항목 말미의 사유 필드**(`— 반영(…)`·`— 병합 — …`·`— 기각(…)`)뿐이다. 본문 중 단어 등장은 근거가 아니다.
    - **② 한 항목에 기각이 섞이면 보존한다.** 오삭제는 비가역이고 잔존 비용은 한 줄이다.
    - **③ 여러 사유로 읽혀 모호하면 보존**하고 다음 batch가 다시 본다.
    - **④ 사유 표기가 아예 없는 항목은 "모호"가 아니라 "미판정"이다 — 보존이 아니라 사유를 부여한다.** 종결 항목은 이미 종결된 것이므로 **그 회차 커밋에서 사유를 확인해 부여**한 뒤 ①~③을 적용한다. **회차 커밋은 항목의 `(출처: …)` 필드로 특정하고, 그것이 없으면 종결일 근방의 `git log`로 찾는다**(특정 방법을 적지 않으면 수행자마다 다르게 해석한다). 확인해도 판별되지 않을 때만 보존한다. ③으로 흘리면 형식이 통일되지 않은 과거 항목이 통째로 영구 잔존해 정리가 절반에서 멈춘다.
    - **적용 순서**: **④ 사유 부여 → ①②③ 분류 → 반영·병합만 아래 「삭제 전 대응 커밋 지목이 의무다」 확인 → 삭제**. 둘 다 회차 커밋을 보러 가므로 순서를 정하지 않으면 같은 커밋을 두 번 판정하게 된다.
  - **삭제 전 대응 커밋 지목이 의무다**: 반영·병합을 삭제할 때는 **그 항목의 요지가 대응 커밋 본문에 실재함을 확인**하고 해시(또는 `vN T#`)를 삭제 커밋에 적는다. **지목이 불가능하면 그 항목은 보존**한다(삭제 대상에서 뺀다) — 근거가 커밋에 있다는 전제가 항목마다 참인지는 그 항목을 봐야 알 수 있고, 전제가 거짓인 항목만 남기는 것이 이 확인의 목적이다.
- **`## 대기`의 주제별 그룹 (v1.148.0~)**: 대기 항목이 많아지면 `### ` 소제목으로 주제를 나눈다 — 현행 5그룹은 **대장 운영 / hook · 안전망(차단·경고·골든 러너) / 하니스 스킬(implement-task · plan-feature · 리뷰어 · 템플릿) / llm-wiki · vault / eval · 측정**. append 시 **해당 그룹 안에** 넣는다(그룹이 없으면 만들거나 가장 가까운 그룹에). 이 구조의 목적은 `plan-feature` Step 1의 `## 대기` 조회에서 **이번 작업과 관련된 항목만 골라 읽을 수 있게** 하는 것이다 — 그룹이 없으면 수십 건을 훑다가 상단 몇 건만 보고 넘어가게 된다. **항목 수 상한·자동 만료는 두지 않는다**(미처리 항목의 자동 삭제는 대장의 존재 이유와 충돌).
- **재확인 표기**: 오래된 항목을 실측 판정했는데 **여전히 유효하면**(해소도 기각도 아님) 항목 끝에 `(YYYY-MM-DD 재확인: 유지 — {근거 1구})`를 덧붙인다. 유지 판정은 그냥 두면 산출물에 흔적이 남지 않아 **누가 언제 확인했는지 알 수 없고 다음 세션이 같은 조사를 반복**한다.
- **생성 조건**: Deferred 항목이 실제 있을 때만 파일을 생성한다(없으면 대장을 만들지 않고 조용히 통과 — 무관 프로젝트에 빈 파일을 만들지 않는다). `docs/plans/` 디렉터리가 없으면 함께 만들고, 대장에 `## 종결` 섹션이 없으면 추가한다.
- **중복 억제**: 같은 요지의 항목이 이미 `## 대기`에 있으면 append를 생략한다.
- **종결 처리**: 이번 작업이 기존 `## 대기` 항목을 해소(구현·검토 종결·기각)했으면 **위 「종결 처리 3분기」 표에 따라** 처리한다 — 사유를 붙이는 것은 공통이고, 반영·병합은 삭제(+누계), 기각은 `## 종결`로 이동이다.
- **위키 [DECISION] 큐와 병존**: 아래 [DECISION] 큐잉(SKILL 본문 규정)은 크로스 프로젝트 결정 이력(위키 decisions.md)용, 이 대장은 레포 내 작업 추적용 — 목적이 달라 둘 다 수행한다.

### 대장 소진 batch 규약 (등재의 짝 — 여기가 정본)

위 규정이 **쌓는 쪽**이라면 이것은 **비우는 쪽**이다. 대장은 append만 하면 단조 증가하므로 주기적으로 소진하지 않으면 `plan-feature` Step 1에서 아무도 끝까지 읽지 않는 목록이 된다. 소진은 **별도 task로 명시적으로 착수**한다(F-6.5가 매번 자동 수행하는 것이 아니다 — 등재는 상시, 소진은 batch).

- **⓪ 착수 조건 — 언제 batch를 여는가.** `## 대기`가 **100건을 넘고 그중 「직전 batch 이후 신규 등재분」이 30건 이상**이거나(두 조건이 **AND**다 — 잔량만으로는 열지 않는다), `## 대기` 항목의 **"마지막으로 판정된 날"의 최솟값이 30일을 넘거나**, **`## 대기`가 절대 상한(현행 130건)을 넘으면** 다음 plan에 batch task를 넣는다(**세 축은 OR**다). 그 날짜는 **그 항목이 마지막으로 판정된 날**이다 — `(YYYY-MM-DD 재확인: 유지 …)` 표기가 대표 형태이고, **날짜 접두에 부기가 붙은 형식**(`[등록일, **vN에서 부분 해소**]`)은 **그 부기가 가리키는 회차의 날짜**가 판정일이며, 둘 다 없으면 등록일이다. **등록일만 보면 안 된다**: 유지 판정은 항목을 대기에 남기므로 등록일이 영원히 갱신되지 않아, 어제 전건 재확인한 항목 때문에 오늘 또 batch가 열린다(*"정리했는데 또 열린다"* 는 이 규약이 막으려던 바로 그 현상이 스케줄에서 재현된다). **부기 형식을 빼먹으면 같은 일이 반대편에서 벌어진다** — 표기 정규식만 돌리면 그 항목들이 등록일로 읽혀, v1.188.0 실측에서 **어제 판정된 2건이 39일 방치로 잡혀 batch가 잘못 열렸다**(세 축을 다시 재니 전부 미달이었다). 이 조건은 **`plan-feature` Step 1의 대장 조회 지점에서 확인한다** — 그곳이 대장을 여는 유일한 정기 지점이므로, 규정을 이 파일에만 두면 **판정할 사람이 그것을 보지 않는다.** **현재 날짜를 확인할 수 없으면 잔량 축만 적용**한다(날짜를 못 읽는 것은 정당한 skip이지 판정 누락이 아니다 — 잔량은 날짜와 무관하게 셀 수 있으므로 그 축만으로 batch를 연다).
  - **「직전 batch 이후 신규 등재분」은 이렇게 센다**: **현재 `## 대기` 건수 − 직전 batch 기록의 「정리 직후 N건」**(아래 규칙 ⑥이 batch 종료 시 남기는 값). **도출 방법을 적지 않으면 아무도 계산하지 않고 조용히 건너뛴다** — 그러면 AND가 무의미해지고 날짜 축만 작동한다(바로 아래 날짜 축이 같은 이유로 도출 방법을 함께 적고 있다). 직전 batch 기록이 없으면(첫 batch) 이 조건은 충족된 것으로 본다.
    - **이 델타는 「순증분」이지 「순수 신규 등재분」이 아니다** — 두 batch 사이에 개별 task가 「종결 처리」로 항목을 삭제하면 그만큼 상쇄돼 **실제 등재보다 작게 나온다**(등재가 급증해도 축이 안 열릴 수 있다). 값이 기대보다 낮으면 그 구간의 개별 종결 건수를 더해 보정하고, 보정한 값과 근거를 판정에 함께 적는다.
  - **잔량 축에 순증분 조건을 AND로 건 이유**: 잔량 100건은 **한 번 넘으면 계속 참**이라, 전건을 재확인한 다음 날에도 그대로 열린다 — 실측으로 114건 전건 재확인 다음 날 123건으로 재발동했고, *"정리했는데 또 열린다"*는 이 규약이 막으려던 현상이 스케줄에서 재현됐다. 날짜 축이 `(재확인: 유지)` 표기로 재발동을 막는 것과 같은 장치를 잔량 축에도 둔다. **날짜 축(최고령 30일)은 OR로 남긴다** — 순증분이 없어도 오래 방치된 항목은 열려야 하므로, AND를 두 축 모두에 걸면 batch가 영영 열리지 않는다.
  - **절대 상한 축(세 번째 OR) — 값의 도출 규칙**: 잔량이 임계를 넘고도 AND 조건 때문에 **방치되는 상태**를 닫는 축이다(실측: 잔량 138인데 신규 등재분이 11건이라 세 축 모두 미달로 batch가 열리지 않았다 — v1.185.0). 상한은 다음 **세 값을 모두 넘는 가장 낮은 10 단위**로 정한다 — ⓐ **123**(AND를 건 이유인 재발동 실측 — 바로 위 불릿) ⓑ **100**(기존 잔량 임계 — 이보다 낮으면 AND가 무의미해진다) ⓒ **그 시점의 정리 직후 잔량**(이보다 낮으면 도입 즉시 상시 참이 되어 *"정리했는데 또 열린다"* 가 재현된다). **현행 130은 v1.185.0 T2의 정리 직후 잔량 125로 도출했다** — `max(123, 100, 125) = 125`를 넘는 가장 낮은 10 단위이고, 최소성은 `130 - 10 = 120 ≤ 125`로 확인된다.
    - **⚠ ⓒ는 상한을 「최초 확정」할 때만 쓴다 — 재도출에는 쓰지 않는다.** 규칙이 `정리 직후 잔량 초과`를 포함하므로 상한은 정의상 언제나 그 시점 잔량 위인데, 매 회차 재도출을 허용하면 **소진이 부진할수록 상한이 함께 올라가** 축이 영영 열리지 않는다 — *"대장이 부풀수록 늦게 열린다"* 는 역방향 인센티브이고, 이 축이 고치려는 상태를 그대로 재생산한다. **재도출은 값을 낮추는 방향으로만 허용한다**(재도출 값이 현재 상한보다 크면 채택하지 않는다). ⓒ를 뺀 재도출은 항상 `max(123, 100)` → 130이므로 **상한은 130을 바닥으로 하향 수렴**하고 올라갈 경로가 없다. **재도출은 ⓐ·ⓑ의 값 자체가 바뀔 때만 한다** — 재발동 실측(ⓐ)이 갱신되거나 기존 잔량 임계(ⓑ)를 조정하는 회차가 그 시점이다. 그 밖에는 상한이 고정이며 **매 batch마다 재도출하지 않는다**(발동 시점을 적지 않으면 이 규약이 ⒪를 신설한 이유 — *"어떻게는 정밀하게 규정하면서 언제를 규정하지 않았다"* — 와 같은 공백이 여기 생긴다).
  - **최고령은 잔량 앵커에서 얻을 수 없다** — 앵커 줄은 `대기 N / 종결 M / 정리 삭제 누계 K / 총 등재 누계 T`라 **개수만 담고 날짜를 담지 않으며**, 대기 항목의 날짜는 5개 주제 그룹에 흩어진 채 **그룹 내에서도 정렬돼 있지 않다.** 그래서 `## 대기` 구간을 훑어 **위 규칙(재확인 표기가 있으면 그 날짜, 없으면 등록일)으로 항목마다 날짜를 정하고 그 최솟값을 취한다.** ⚠ **대장 「카운트 기준」의 `^- \[\d{4}-…` 정규식을 그대로 쓰면 안 된다** — 그것은 **등록일**만 보므로 재확인 표기도 **부기 형식도** 무시해 위 규칙이 무효가 된다(그 정규식은 개수를 세는 용도다). 도출 방법을 함께 적지 않으면 아무도 계산하지 않고 조용히 건너뛴다.
  - **왜 조건이 필요한가**: 이 규약은 아래 ①~⑥으로 *"어떻게"* 는 정밀하게 규정하면서 ***"언제"* 를 규정하지 않았다.** 그 공백 때문에 3차 batch(2026-08-05) 이후 세 회차 동안 batch가 **0회**였고 그 사이 대기가 94 → 129건으로 늘었다 — 규약이 있는데도 실행되지 않은 것이지 규약이 없던 것이 아니다.
- **① 착수 단위는 날짜 구간이다.** `## 대기`에서 **가장 오래된 등록일부터** 한 구간(통상 1주, 25~35건)을 잡아 그 구간 **전건**을 판정한다. 주제별로 골라 처리하면 남은 것이 계속 뒤로 밀려 대장이 비지 않는다. **착수 시 구간 건수를 먼저 재계수**해 계획의 예상치와 대조하고, 어긋나면 정정을 기록한다. **작업 연관 항목만 선별 종결한 경우는 batch가 아니다** — 그렇게 처리했으면 "구간 batch는 미실행"이라고 명시해 다음 세션이 그 구간을 건너뛰지 않게 한다.
- **② 판정은 3분류이고, 묻는 것은 "여전히 유효한가"가 아니라 "조건 없이 지금 착수할 수 있는 액션인가"다.** 전자로 물으면 대장이 비지 않는다 — 대상 코드가 그대로면 전부 유지로 넘어가기 때문이다(실측: 같은 29건이 종전 기준 1차 batch에서는 종결 1건, 새 기준 5차 batch에서는 15건이 정리됐다). **종결(반영)** — 해소됨 / **기각** — 전제가 사라졌거나 애초에 액션 아이템이 아님 / **유지 재확인** — 여전히 유효. **셋 다 산출물에 흔적을 남기고, 판정이 애매하면 유지한다** — 잘못 종결하면 근거가 사라지지만 유지는 다음 batch가 다시 본다.
  - **⚠ 기각의 주력은 "외부 사건이 트리거인 항목"이다** — *"…가 관측되면"·"근거가 생기면"·"데이터가 축적되면"·"…를 쓰는 워크플로가 생길 때"* 로 착수 조건을 단 것, 그리고 **이미 판단이 내려진 것**(*"비용>효과라 보류"*·*"의도적으로 인라인 유지"*·*"(선택)"*)이 여기 속한다. 전자는 **그 사건이 일어나는 날이 곧 근거를 갖춘 새 등재 시점**이라 대기에 두어도 착수를 앞당기지 못하고, 후자는 결론이 난 것을 매 batch마다 다시 검토하게 만든다. 이 범주를 쓰지 않으면 그런 항목이 영원히 남아 잔량을 부풀린다(④의 기록성 기각을 트리거 축으로 확장한 것). **이 축은 위 F-6.5 「등재 게이트」 ⓓ가 1차로 거르므로, 여기 남는 것은 그 게이트 신설(v1.185.0) 이전에 등재된 것이다** — 판정 어휘·예시·예외의 정본은 이 불릿과 바로 아래 ⚠ 이며, 게이트 쪽은 그것을 가리키기만 한다.
  - **⚠ 단 "관측되면"이 붙었다고 기계적으로 기각하지 않는다 — 판정 기준은 "그 관측이 실제로 일어나는가"다.** 오탐·성능 저하·빌드 실패는 사용자나 CI가 즉시 알아채 재등재되지만, **차단 hook의 미탐(fail-open)처럼 실패가 조용한 것**은 위험 명령이 그냥 성공할 뿐 아무도 신고하지 않아 *"관측되면 다시 등재된다"* 는 전제가 성립하지 않는다 → **유지**한다. 이 예외는 **"관측 경로가 없는 것"에 한정**되며, 같은 hook 파일의 항목이라도 오탐·성능처럼 드러나는 것은 기각 대상 그대로다(예외를 그룹 단위로 넓히면 ⓐ의 기각 축이 통째로 무력화된다). 그리고 **원문에 없던 트리거를 판정자가 부여하지 않는다**(원 항목이 *"차기 정비 때 검토"* 라고 적었으면 그것은 조건 없는 액션이다 — 5차 batch에서 실제로 이 오분류가 나왔다).
  - **⚠ 병합은 3분류와 나란한 정식 수단이다** — 같은 뿌리의 항목을 하나로 합쳐 **착수 단위**를 만든다. **흡수된 항목은 「종결 처리 3분기」의 병합 행에 따라 삭제한다**(삭제 누계 반영 — 값 규칙은 대장 「카운트 기준」)(사유 `병합 — 「<등록일 제목>」에 흡수`는 **삭제 커밋 본문**에 적는다) — **누계에 가산되므로 아래 「무손실 대조」의 불변식은 유지된다.** 종전에는 `## 종결`로 옮기게 했는데, 그것은 누계 필드가 없어 삭제가 곧 총수 손실이던 시절의 규정이다(5차 batch가 실제로 총수를 깨뜨린 것도 **누계 없이** 지웠기 때문이다). 근거 형식은 ③의 예외(`경로:라인` 대신 등록일+제목). 5·6·7차 batch에서 제거된 41건 중 **19건이 병합**이었고, 특히 문면 정비 지적은 개별로는 착수되지 않아(하나 고칠 때마다 예산 표 재측정·정합 검사가 붙어 **착수 비용이 내용보다 크다**) 두 구간에 걸쳐 9건까지 자라 있었다. **항목 자신이 *"함께 검토/설계"* 라고 적어 둔 것**이 1순위 후보다. 셋 다 산출물에 흔적을 남긴다(유지도 `(YYYY-MM-DD 재확인: 유지 — 근거)` 표기 — 위 「재확인 표기」). **판정이 애매하면 유지**로 둔다. 잘못 종결하면 근거가 사라지지만 유지는 다음 batch가 다시 본다.
- **③ 종결 근거에는 백틱 `경로:라인`이 필수다.** *"해소된 것 같다"*·*"이제 그렇게 안 한다"* 로 종결하지 않는다 — 실제로 grep/Read로 확인한 **지점을 지목**한다(예: ``recovery.md:88``). 대장 항목 자체가 다음 세션의 근거이므로, 추측 종결은 잘못된 근거를 남기는 것이고 그 오류는 **종결됐다는 이유로 다시 검토되지 않는다**. **단 병합은 예외다** — 흡수 대상이 같은 대장 안의 항목이므로 **등록일 + 제목으로 지목한다**(라인 번호는 대장을 편집할 때마다 어긋나고, 병합은 정의상 항목을 옮기는 작업이라 그 자리에서 이미 낡는다). **삭제되는 항목(반영·병합)도 이 근거 의무를 면제받지 않는다** — 근거처가 대장 항목이 아니라 **삭제 커밋 본문**으로 옮겨갈 뿐이다(위 「삭제 전 대응 커밋 지목이 의무다」). 근거 없이 지우면 잘못된 삭제를 사후에 판별할 수단이 사라진다.
- **④ 기록성 항목은 기각 범주다.** 등재 당시 이미 *"정정 불가·기록만"* 으로 결론난 항목처럼 **애초에 액션 아이템이 아닌 것**은 해소도 전제 소멸도 아니지만 기각으로 종결한다. 이 범주가 없으면 그런 항목이 영원히 `## 대기`에 남아 잔량을 부풀린다. **이 축도 위 F-6.5 「등재 게이트」 ⓔ가 1차로 거른다** — 다만 **판정 축이 달라**(게이트는 원 지적의 **문면**을, 여기는 항목의 **성격**을 본다. 각각의 기준은 그 자리에 있고 여기 옮겨 적지 않는다) 게이트를 통과해 등재된 것도 batch에서 이 범주로 걸릴 수 있다.
- **⑤ 아직 실행되지 않은 task를 근거로 인용할 때는 3요소를 지킨다.** ⓐ 괄호로 실행 여부 명시(`계획 단계`·`아직 미실행`) ⓑ 완료 동사(`해결했다`·`실증한다`) 대신 계획·시도 동사(`채택했다`·`시도한다`·`설계다`) ⓒ 검증 시점을 미래로 조건화(`실행 후 확인하면`). 같은 시제 오류가 batch 안에서 task를 건너 연속 재발한 적이 있다 — 미래를 완료형으로 적으면 다음 세션이 그것을 확정 사실로 읽는다.
- **⑥ 잔량은 "정리 직후"와 "현행"을 분리 표기한다.** batch가 끝나면 그 자리에서 `정리 직후 N건 / 현행 M건`으로 적고, **같은 세션의 F-6.5가 신규 등재를 하면 현행 값을 즉시 갱신**한다. 정리 직후 값만 적고 등재분을 반영하지 않는 것이 이 대장의 **반복 실수**다 — 한 번은 그 값이 나흘 동안 굳어 대장이 실제보다 작아 보였다. 기계 대조 대상인 **전용 앵커 줄**(`**▶ 현행 잔량(기계 대조 대상)**: 대기 N / 종결 M / 정리 삭제 누계 K / 총 등재 누계 T`)도 같은 시점에 갱신한다 — 과거 batch 기록 안의 *"현행 N건"* 문자열들은 그 시점의 사실이므로 **고치지 않는다**. **어느 연산이 어느 필드를 얼마나 움직이는지(등재·삭제·이동·복원)는 여기 적지 않는다 — 대장 「카운트 기준」 블록이 정본**이며, 그 값 규칙을 이 파일에 복제하면 대장↔대조기와 달리 **어떤 기계 검사도 지키지 않아 조용히 낡는다**.
- **무손실 대조**: 불변식은 **`대기 + 종결 + 정리 삭제 누계 == 총 등재 누계`**이며, **사람이 세는 절차가 아니라 `check-harness-consistency.py`가 매 실행 검사한다**(종전에는 batch 전후로 `대기 + 종결` 총수를 사람이 대조했는데, 3분기 도입으로 삭제가 정상 경로가 되면서 파일에 남지 않는 삭제분을 누계가 대신 센다). **⚠ 그 대조기는 하니스 레포 자신의 자산이다** — 대조기도 앵커도 없는 프로젝트에서는 **batch 전후로 `대기 + 종결 + 삭제 수` 총수가 불변인지 사람이 대조한다.** 기계 검사를 유일한 수단으로 적으면 그 자산이 없는 곳에서 폴백이 사라진다 — 3분기로 삭제가 정상 경로가 된 만큼 손실 위험은 오히려 커졌다. **세는 규칙(구간별 정규식)·연산 규칙·불변식은 모두 대장 자신의 「카운트 기준」 블록이 정본**이다 — 그 블록은 기계 대조기와 짝을 이루므로 여기 옮겨 적으면 한쪽만 고쳐져 갈린다.
- **컨텍스트가 임계에 닿으면** 판정한 데까지 기록하고 잔여를 "다음 batch 대상"으로 남긴다. **절단은 항목 경계에서만** 한다.

**민감 정보**: notes·archive·README 어디에도 실제 IP·계정·비밀번호·토큰을 적지 않는다 (절대 규칙 6-1). 일반 표현 또는 환경변수 이름만 기록.

**위키 반영 능동 확인 (llm-wiki 사용 중 + 프로젝트 등록 시)**: 최종 완료 보고 시, 이번 작업에 **위키에 남길 내용이 있으면 사용자에게 능동적으로 묻는다** (Next Steps 목록에 한 줄로 묻어두지 말 것).

> **"프로젝트 등록 여부" 판단(read-only)**: vault가 설정돼 있으면(미설정이면 이 단계 자체를 건너뜀 — **단 "미설정" 판정은 `pjc:llm-wiki` 절차 K 1의 `⚠ 판정 게이트`를 거친 확인 결과여야 한다**: 그 확인 없이 단정하면 등록된 프로젝트의 위키 반영 기회가 통째로 사라지고 그 사실조차 남지 않는다. 주입된 vault 상태 라인이 있으면 그것으로 갈음하되 **라인의 부재는 판정 근거가 아니다**) vault의 `20_projects/{personal|work}/`에 이 프로젝트 허브가 있는지 Glob/grep 1회로 확인한다(위키 직접 수정 없음). 있으면 "등록됨" → 아래 조건 시 능동 질문. 없으면(미등록 — 신규 개발 등) 이번 작업 반영은 묻지 않되, 위키 등록이 가치 있어 보이면 "이 프로젝트를 위키에 등록(절차 A)할까요?"만 1회 제안할 수 있다(강요 아님 — 과잉 방지).

묻는 조건은 다음 중 하나라도 해당할 때:
- 기능·구현·동작이 바뀌어 feature 페이지 갱신이 필요하다.
- 다른 프로젝트에도 적용될 **재사용 가능한 개선 교훈**이 있다 (llm-wiki 절차 B-2 2-1의 patterns 추출 후보).

질문 형식 예: *"이번 작업에 위키에 반영할 내용이 있습니다: [한 줄 요약 — 무엇을/어떤 교훈]. 별도 위키 세션에서 `pjc:llm-wiki` 절차 B로 반영할까요?"* 사용자가 동의하면 별도 세션에서 진행한다 — **ingest(절차 B)는 여전히 구현 세션이 수행하지 않는다**(레포 대조·본문 편집이 필요하다). 단 아래 「큐 자동 소비」가 규정하는 `[DECISION]`·`[PROJECT-FACT]` 소비와 「`[SKILL-IMPROVE]` 해소분 제거」(하네스 레포 전용)는 그 예외이며, **구현 세션의 위키 쓰기는 그 셋으로 한정된다**.

**미이행 시 큐잉 (묻고 끝내지 않는다)**: 위 질문에 사용자가 **미루거나(“나중에”·“다음에”) 답하지 않으면**, 그 사실을 `pjc:llm-wiki` 절차 K 5의 `[K-DRIFT]` 큐에 1줄 남긴다 — `- [YYYY-MM-DD] [K-DRIFT] {프로젝트}: v{버전} 구현분 위키 미반영 (ingest 대기)`. **묻기만 하고 끝내면 미반영 사실이 대화와 함께 사라져** 위키가 조용히 뒤처지고(그 뒤처짐은 lint §7-26이 나중에 발견하지만, 위키 세션을 열어야 보인다) 아무도 추적하지 못한다 — 큐가 그 유일한 전달 매체다(소비는 위키 세션의 B-1 0 / F-0).
- **하네스(플러그인) 레포 자신도 예외 없이 큐잉한다.** 절차 K 5-1~5-5(SKILL-IMPROVE·DECISION·PROJECT-FACT·K-MISS·SYMPTOM)에는 "하네스 레포면 큐 대신 plan 기록" 예외가 있지만 **K 5(K-DRIFT)에는 없다** — 그 예외의 근거는 "자기 레포의 개선은 그 레포 세션에서 일어나므로 큐를 거칠 이유가 없다"인데, **위키 ingest는 하네스 세션이 아니라 위키 세션에서만 일어나므로** 큐를 건너뛰면 전달 경로가 사라진다.
- **중복 억제**: 같은 프로젝트의 위키 미반영 항목이 이미 큐에 있으면 **버전이 달라도 append를 생략**한다(K 5의 중복 억제 준용). 큐 항목의 버전 표기가 낡아도 소비 결과는 같다 — ingest(절차 B)는 허브 `updated` 이후 델타를 **그 시점 HEAD까지** 반영하므로, "v1.118 미반영"이라 적힌 항목을 소비해도 그 뒤 쌓인 버전까지 함께 반영된다.
- **명시적 거절은 큐잉하지 않는다** — "반영 안 함"은 결정이지 미이행이 아니다(큐가 거절 항목으로 차면 잔량 20건 경고가 무의미해진다).
- vault 미설정·append 실패 시 폴백은 절차 K **5-1** 규약을 따른다(보고 + plan.md 1줄 — K 5 블록이 아니라 5-1에 폴백·판정 조문이 있다. "미설정" 판정 자체는 K 1의 `⚠ 판정 게이트`).

**단, 묻지 않는 경우**: 문서·설정 변경(Type A)이나 trivial 단일 수정처럼 위키에 남길 가치가 없는 작업은 묻지 않는다 (질문 남발 방지). 위키 반영 가치가 명확할 때만 능동 질문한다. **묻지 않은 작업은 큐잉 대상도 아니다**(반영할 내용이 없으므로 미반영도 없다).

**큐 자동 소비 (`[DECISION]`·`[PROJECT-FACT]`)**: 위 큐잉이 **쌓기만** 하는 쪽이라면 이것은 **비우는 쪽**이다. 코드 세션이 큐를 쌓고 소비는 사용자가 위키 세션을 열어야만 일어나던 구조에서는, 그 세션이 열리지 않으면 큐가 무한히 자라고 잔량 경고만 반복됐다.

- **ⓐ 발동 조건**: 위키 vault가 설정돼 있고 `pending.md`에 **이 세션 대상 프로젝트의** `[DECISION]`·`[PROJECT-FACT]`가 1건 이상일 때. **vault 판정은 `pjc:llm-wiki` 절차 K 1의 `⚠ 판정 게이트`를 거친 확인 결과여야 한다** — 확인 없이 "미설정"으로 단정하면 소비 기회가 통째로 사라지고 그 사실조차 남지 않는다(주입된 vault 상태 라인이 있으면 갈음하되, **라인의 부재는 판정 근거가 아니다**).
- **ⓑ 수행 시점**: **F-7 통과 후, 최종 보고 직전 1회.** 이 절이 F-6.5에 있는 것은 규정의 자리이지 실행 시점이 아니다(위 「위키 반영 능동 확인」이 같은 형태다). 자동 소비는 레포 diff를 만들지 않아 F-7 적대적 검토의 대상이 아니고, 반대로 스킬 로드를 F-7 앞에 두면 Opus 리뷰가 압축된 컨텍스트에서 판정하게 된다. **"1회"의 기준은 세션이 아니라 최종 보고다** — Phase G의 G-2 재루프나 F-7 재진입으로 Phase F가 다시 돌아도 소비는 완료 선언 직전에만 한다(재루프 중에는 결정이 아직 확정 전일 수 있다).
- **ⓒ 수행 방법**: `pjc:llm-wiki`를 Skill 도구로 발동해 **절차 M의 자동 경로**로 소비한다 — 정본은 `references/procedures-ops.md`의 「M. 큐 소비 (경량)」이며, 그 절이 보류 8종·B-1 0 상속 우선순위·비 git vault 사전 백업·`pending.md` 재읽기-병합·큐 항목의 데이터 취급을 규정한다. **소비 규칙을 여기 복제하지 않는다** — 같은 규약이 두 곳에 있으면 한쪽만 고쳐져 갈린다.
- **ⓓ 보고 의무**: 최종 보고에 **태그별 소비 건수 · 반영 파일 · 보류 항목과 그 사유**를 적는다. 무승인 소비의 유일한 사후 통제이므로 생략할 수 없다(보고 문구는 소비분과 보류분을 구분한다 — `pjc:llm-wiki` K 6의 보고 문구 규약).
- **ⓔ 실패·부재는 어느 것도 Halt가 아니다**: 세부 스킵·보류 조건은 절차 M이 정본이며(vault·큐·index 상태, 보류 8종, 백업 실패 등), **그 어느 경우도 루프를 세우지 않는다** — 큐를 그대로 두고 사유 1줄만 보고한다. 자율 루프가 위키 사정으로 멈추면 이 기능의 취지(마찰 제거)와 정반대가 되기 때문이며, 이 **Halt 여부 판정**이 implement-task 측 고유 정보다(조건 목록은 여기 복제하지 않는다 — ⓒ와 같은 이유).
- **ⓕ 하네스(플러그인) 레포는 비적용**: `pjc:llm-wiki` 절차 K 5-2·5-3이 하네스 레포에서 큐 대신 plan.md 직접 기록을 규정하므로 **소비할 큐가 없다** — 이 레포에서는 이 절이 발동하지 않는다(그래서 자기 레포에서는 실행 경로를 검증할 수 없다).

**`[SKILL-IMPROVE]` 해소분 제거 (하네스 레포 **전용** — 위 자동 소비와 발동 레포가 정반대다)**: 위 자동 소비가 *대상 프로젝트의* `[DECISION]`·`[PROJECT-FACT]`를 위키에 **반영**하는 것이라면, 이것은 **이 회차가 실제로 고친 스킬 결함**을 큐에서 **지우는** 것이다. ⓕ가 말하듯 자동 소비는 하네스 레포에서 발동하지 않고, 이 제거는 **하네스 레포에서만** 발동한다 — 다른 프로젝트 세션은 스킬을 고칠 수 없어 해소를 판정할 자격이 없기 때문이다. 이 경로가 없으면 큐는 **유입만 되고 비워지지 않는다**(실측: 이미 해소된 항목이 `(보고됨)` 표식만 단 채 남아 있었다).

- **발동 조건**: 이 회차가 pjc 스킬·hook·리뷰어 정의를 고쳤고 vault 루트 `skill-feedback.md`에 항목이 1건 이상일 때. **vault 판정은 `pjc:llm-wiki` 절차 K 1의 `⚠ 판정 게이트`를 거친 확인 결과여야 한다**(위 ⓐ와 같은 요구).
- **판정 근거 — 추정 제거 금지**: 항목마다 *"이 회차의 변경이 그 항목이 적은 증상을 실제로 없앴는가"* 를 묻고, **그 근거를 이 회차의 커밋·파일로 지목할 수 있을 때만** 제거한다. 지목하지 못하면 **남긴다** — 잔존은 다음 회차가 다시 보지만 **오제거는 회수 불가**다. 부분 해소(증상 일부만 닫힘)도 남긴다.
- **수행 시점·방법**: 위 자동 소비와 같은 지점(**F-7 통과 후 최종 보고 직전 1회**). 해당 줄을 지우고 vault에 커밋한다(커밋 메시지 형식·push 시점은 `pjc:llm-wiki`의 git 자동 반영 규약).
- **대장 짝 처리**: 같은 건이 `docs/plans/deferred.md`에도 있으면(이중 관리 — 대장 `[2026-08-15]` 항목이 그 실태를 기록한다) **그 짝도 같은 판정으로 함께 처리**한다. 한쪽만 지우면 다음 회차가 이미 닫힌 것을 다시 판정한다.
- **보고**: 제거한 항목과 **어느 변경이 그것을 닫았는지**를 최종 보고에 1줄씩 적는다. 무승인 삭제의 유일한 사후 통제다.

## F-7. plan-completion-reviewer subagent (필수)

위 자체 검증 통과 후 **`plan-completion-reviewer` subagent에 적대적 검토 위임.** 자체 검토만으로 마무리 금지 — **예외는 호출 자체가 불가한 환경뿐이며 그때는 `recovery.md` "Reviewer 호출 실패 대응" B 분기**(체크리스트 대체 + 의무 3종). **reviewer가 HTTP 오류 없이 정상 응답으로 검토를 거절한 경우는 그 절의 C 분기**(범위를 좁혀 1회 재의뢰 → 그래도 거절되면 B 절차를 쓰되 사유를 "거절 — 미검토 범위"로 기재)를 따른다. **B 분기로 F-7을 대체하면 Phase G가 active Must FR 전체를 보완 재대조한다**(`phase-g-detail.md` G-1 예외 ② — 대체 경로가 Sonnet 대체보다 얕으므로 사후 검증을 느슨하게 두지 않는다). 호출은 **동기 호출**(`run_in_background: false`) — 검토 결과를 받아 판정한 뒤에만 완료 선언으로 간다.

호출 시 전달:
- plan.md 경로
- BASE_SHA (implement-task 시작 전 커밋)
- HEAD_SHA (마지막 task 완료 후 커밋)
- AGENTS.md 위치
- **Bash 쓰기 금지 1구**: *"조사 금지: `git checkout`·`stash`·`reset` 등 워킹트리·인덱스를 바꾸는 명령 — 과거 상태는 `git show <sha>:<path>`로 읽을 것."* — `plan-completion-reviewer`도 Bash를 보유한다. 근거·이력은 `implement-task/SKILL.md` V-5의 같은 항목.
- **이전 라운드 이력** (F-7 재호출일 때만 — `| 라운드 | 지적 | 심각도 | 반영 방식 |` 4열 표). `plan-completion-reviewer`의 「재리뷰 규약」이 이 표를 전제하며, 없으면 이전 BLOCKER 해소 여부를 판정할 수 없어 지적이 라운드마다 뒤집힐 수 있다. 첫 호출에는 전달하지 않는다.
- **PRD 경로** (plan.md 상단 `**PRD**:` 줄이 있을 때) — 이 경우 F-7은 plan Goal 검토에 더해 **PRD의 FR/NFR 전수 대조**를 수행한다(plan-completion-reviewer 역할에 포함). **Phase G가 이 F-7 대조 결과를 재사용**하므로(phase-g-detail G-1), PRD가 있으면 이 전달을 빠뜨리지 않는다.

F-7 검토에는 **요구 커버리지 대조**(plan `## 요구 이해` ↔ 산출물 — plan-completion-reviewer 항목 2.5)가 포함된다. **PRD 없는 plan에서 승인 게이트 이후 유일한 사후 요구 재검증 지점**이므로 생략하지 않는다(요구 이해 섹션이 없는 구 plan은 reviewer가 자동 skip).

결과 처리:
- **BLOCKER** 있음 → 추가 task 등록 후 Phase P 재진입 (이슈 0까지, 최대 3회 — 재진입 횟수는 plan.md `## Retry Ledger`에 기록해 압축·재개 후 이어 센다, 정본 `recovery.md`)
- **MAJOR** 있음 → 동일 (또는 사용자 보고)
- **MINOR** 있음 → plan.md follow-up에 기록하고 진행
- **재호출 3회 연속 동일 BLOCKER** → Halt → 사용자에게 보고

재진입(추가 task) 완료 후 최소 재실행 세트는 **Phase G G-2와 동형**이다 — **F-2 전체 테스트 1회 + F-7 재호출**(BLOCKER 해소 확인 — F-7은 지적 당사자이므로 G-2의 "F-7 Opus 면제"가 여기엔 적용되지 않는다). F-1~F-6 전체 반복은 불요. F-7 재호출도 **동기 호출**(`run_in_background: false`) — 결과 수신 전 진행 금지. **재호출에는 위 전달 목록의 「이전 라운드 이력」 표를 함께 넘긴다**(진동 차단). 반환된 `### CONFLICT` 섹션은 `references/recovery.md` 「리뷰 결과 처리 (재리뷰 범위 · 이력 전달 · CONFLICT · incomplete · 이의)」대로 소비한다 — Verdict가 OK여도 소비 전에는 통과로 보지 않는다.

## F-8. 시각 충실도·참조 정합 최종 관문 (디자인 정합·화면 이식 작업만)

**발동 조건**: plan에 `## 시각 요소 분해` 섹션이 있을 때만 (V-9와 동일 트리거). **섹션이 없으면 N/A** — 비디자인 작업은 이 단계를 통째로 건너뛴다.

**수행 위치 — 완료 선언 직전 1회.**

| plan 구성 | F-8 수행 시점 |
|---|---|
| PRD 없음 | **F-7 통과 후** (= 최종 보고 직전) |
| PRD 연결 (`**PRD**:` 줄 있음) | **Phase G 통과 후** (G-4의 Phase Ledger 기록과 최종 보고 사이) |

> PRD가 있으면 Phase G가 **자율 재루프**로 새 task를 추가할 수 있고(G-2), 그 task가 시각 요소를 다시 바꿀 수 있다. F-8을 Phase F 말미에 두면 재루프마다 반복 수행되므로, **선언 직전 1회**로 모은다. F-8은 검증 단계가 아니라 **선언 게이트**다.

**절차**:

1. **V-9가 인계한 `⏳ 미확인` 행을 모은다** — plan `## 시각 요소 분해` 섹션에서 각 task의 V-9가 남긴 미확인 표기를 전 task에 걸쳐 취합한다. (V-9는 task마다 돌지만 이 관문은 전체를 한 번에 본다.)
   - **취합 범위는 섹션 전체다 — 표를 구분해 좁히지 않는다.** 실제로 `⏳`가 나오는 것은 `### 시각 속성` 표 행이고, `### 참조 정합 인벤토리` 행은 전부 정적 축이라 `⏳`가 발생하지 않는다(대조 불가는 `phase-v9-detail.md` 4에 따라 Halt). **그럼에도 인벤토리 행에 `⏳`가 발견되면 그것은 규칙 위반이므로 취합·완료 보류 대상**이다 — 취합 대상을 시각 속성 표로 한정하면 그 위반 행이 이 관문에도 제목 분기에도 안 걸려 `🎉`로 종결되고, V-9가 세운 "게이트 리터럴을 우회하는 경로를 만들지 않는다"는 원칙이 정반대로 뒤집힌다.
   - 인벤토리의 **주 게이트는 `⏳` 취합이 아니라 아래 5의 "동일" 선언 게이트**다. 두 표는 이 관문에서 역할이 다르다.
2. **미확인 0건 + 인벤토리 미달 0건** → 조용히 통과. 최종 보고는 정상 완료 양식(`🎉`).
   - **미확인은 0건인데 인벤토리 미달(사용자가 수용한 ❌)이 남았으면 `🎉`를 쓸 수 없다** — 아래 5의 선언 게이트로 가고 제목은 `⏸️`다(`final-report-template.md` 제목 분기가 정본). 이때 **Halt는 아니다**(이미 사용자가 보고 수용한 상태이므로 다시 세우지 않는다). **이 단서가 없으면 게이트가 통째로 샌다** — 인벤토리 행은 정적 축이라 `⏳`를 만들지 않으므로, 취합(절차 1)과 Halt(절차 3)가 모두 `⏳`에만 걸려 있는 이 관문에서 "항목·문구가 원본과 다른데 미확인은 0건"인 상태가 정상 완료로 빠져나간다. 화면 이식만 하는 작업의 정상 형태가 정확히 그 상태다.
3. **미확인 1건 이상** → **완료 선언을 보류하고 Halt**한다. 아래를 제시하고 사용자의 화면 확인을 기다린다:
   - 분해 표 (미확인 행을 `⏳`로 표시, 확인된 행은 diff 위치 포함)
   - **확인 요청 목록** — 사용자가 무엇을 어디서 봐야 하는지(화면 이름·진입 경로·볼 항목). "화면을 확인해 주세요"만으로는 부족하다.
   - 확인 불가 사유 1줄 (데스크톱 UI라 자동 캡처 불가 / 캡처 도구 부재 등)
   - 최종 보고는 `## ⏸️ 구현 완료 — 확인 대기` 양식(`references/final-report-template.md`)
4. **사용자 응답 처리**: 어긋난 부분을 지적하면 그 항목으로 Phase P/I 재진입해 수정 후 F-8을 다시 탄다. "이대로 완료" 응답이면 그 지시를 plan `## Progress Log`에 기록하고 종결한다 — **F-8은 강제 수정 게이트가 아니라 확인 게이트**이므로 사용자가 수용하면 그것으로 끝난다.

5. **"동일" 선언 게이트 (인벤토리 표가 있을 때).** 최종 보고에서 **원본과의 동등성을 단정하는 모든 표현은 인벤토리 표의 전 행이 ✅일 때만** 쓸 수 있다. 미달이 남으면 그 표현을 쓰지 않고 실제 상태로 서술한다.
   - **판정 기준은 특정 단어가 아니라 "대응 사실이 없는데 동등성을 암시하는가"다.** "동일하게 만들었다"·"똑같이 구성했다"뿐 아니라 "1:1로 재현", "완전 이식", "원본 그대로", "A 프로젝트 기준으로 구현 완료" 같은 완곡한 표현도 같은 인상을 주면 대상이다 — 어휘 목록을 피해 가는 것이 목적이 되면 게이트가 무의미해진다.
   - **미달이 보고까지 도달하는 경로**: 정상 경로에서 ❌는 최종 보고에 오지 않는다(`phase-v9-detail.md` 7에 따라 Phase I 복귀 대상). 도달하는 경우는 **Halt 후 사용자가 "이대로 완료"를 지시한 때뿐**이며, 그때도 "동일" 표현은 금지하고 수용된 미달 항목을 명시한다 — **사용자의 수용이 사실 서술을 바꾸지는 않는다.**
   - **축을 나눠 서술한다.** 가장 흔한 상태는 *인벤토리 전 행 ✅ + 시각 축 `⏳` 잔존*이다. 이때는 "항목 구성은 원본과 일치(전 행 소스 대조 확인), 시각 배치는 미확인"처럼 **두 축을 구분해** 적는다. 뭉뚱그려 "대체로 동일"로 쓰면 개선 전으로 돌아간다 — 사용자가 겪은 문제가 정확히 그 뭉뚱그림이었다.
   - **미달 사실은 보고 상단에 드러낸다.** 배치는 `references/final-report-template.md`가 정본이다: 상세 목록은 종전대로 Follow-ups 앞에 두고, **미달 건수와 축 구분은 상단 안내 1줄**에 넣는다. 하단에만 적으면 사용자가 읽지 않은 채 완료로 받아들인다(이 관문이 존재하는 이유와 같다).

**이 관문이 존재하는 이유**: 종전에는 V-9가 "렌더 확인 불가 → 멈추지 말고 진행 + 보고에 명시"였다. 데스크톱 UI는 자동 캡처 수단이 없어 **항상** 그 경로로 떨어졌고, 결과적으로 "시각 검증을 하지 않고 완료 보고"가 정상 경로가 됐다. 보고에 적는 것만으로는 부족하다 — 사용자가 그 줄을 읽지 않으면 미검증이 완료로 묻히기 때문이다. F-8은 **읽지 않으면 넘어가지 못하게** 한다.
