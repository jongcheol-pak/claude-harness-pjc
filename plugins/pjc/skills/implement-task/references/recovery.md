# Recovery Mechanism — implement-task

Phase V 실패 시 복구 절차. 그리고 **하니스 전 스킬이 공유하는 subagent 호출 공통 규약**(정상 경로의 동기 실행 + 호출 실패 대응)을 담는다 — 아래 두 절은 `implement-task`뿐 아니라 `plan-feature`·`pjc-systematic-debugging`이 포인터로 참조하는 정본이다 — **다만 스킬마다 참조하는 절은 다르다**(`plan-feature`는 두 절 모두, `pjc-systematic-debugging`은 「Subagent 호출 규약」만 참조한다). `llm-wiki`는 자기 정본 `references/wiki-schema.md` §9에 같은 취지 규약을 둔다.

## 절차

Phase V에서 회복 불가 판단 시:

```bash
git reset --hard <checkpoint hash>
```

**순서 주의 (카운터 유실 방지)**: `git reset --hard`는 **추적(tracked) plan.md도 checkpoint 시점으로 되돌린다**. 따라서 Retry Ledger 카운트 증가·"Failed attempts" 기록은 **반드시 reset 이후에** 수행한다 — reset 전에 적으면 바로 그 reset이 방금 센 카운트를 지워, "checkpoint 복구 2회 → Halt" 가드가 매 복구마다 0으로 리셋돼 **영원히 발동하지 못한다**(무한 복구 루프). 순서: ① `git reset --hard <checkpoint>` → ② plan.md `## Retry Ledger` 복구 카운트 +1 및 해당 task에 실패 원인 기록 → ③ Phase P부터 다른 접근으로 재시도. (plan.md가 gitignore인 repo에선 reset이 plan.md를 안 건드리므로 순서 무관 — SKILL.md의 stale `[x]` 주석과 반대 방향의 같은 원리.)

## 한계

- 동일 task에서 **2회 복구 발생 시 Halt** (자동 중단 → 사용자 보고).
- 같은 BLOCKER/MAJOR가 **3회 연속 지적** → Halt (reviewer의 RECURRING 태그도 이 카운터에 포함).
- 같은 task에서 **리뷰 지적(BLOCKER/MAJOR) 수정 사이클이 누적 5회** → Halt. 매 사이클 지적이 서로 달라 '동일 3회'에 안 걸려도, 5번 고치고도 새 결함이 계속 나오면 구현 방향이 근본적으로 틀린 신호다(무한 수정 루프 방지).
- 빌드/테스트 **5회 연속 실패**, 원인 미상 → Halt.
- 한 task에서 **빌드·수정 사이클 10회 이상** 반복하고도 미완 → Halt (무한 그라인딩). 위 두 캡이 못 잡는 시나리오를 막는다 — 빌드 5회 캡은 "원인 미상"이어야 걸리고 수정 사이클 5회 캡은 "리뷰 지적"에만 걸리므로, **원인은 매번 파악되지만 끝나지 않는** 그라인딩은 이 상한이 유일하게 잡는다.
- **위 카운터들 사이에 `auto-debug pass`가 1회 끼어든다 (Halt 직전 구제).** 동일 BLOCKER 2회 시점에 fresh context 진단을 1회 받는 단계이며, **어떤 Halt 카운터도 증감시키지 않고** 자체 상한 `1/1`만 갖는다 — 즉 위 상한들의 도달 시점은 그대로다. 정본은 이 파일의 「auto-debug pass (동일 BLOCKER 2회 — Halt 직전 구제)」.
- **카운터 영속화 (압축 생존, G5).** 다음 카운터는 대화 컨텍스트에만 두면 auto-compact·재개 시 리셋된다 → **발생 시 plan.md `## Retry Ledger`에 카운트를 기록**하고, 압축·재개 후 그 값에서 이어 센다 (SKILL.md 재시도 한계와 동일 규칙):
  - **task 단위**: checkpoint 복구 2회·동일 BLOCKER/MAJOR 3회·수정 사이클 누적 5회·**빌드·수정 사이클 10회(무한 그라인딩)**·**같은 지점 `[CONFLICT]` 2회**·**`auto-debug <task> 1/1`**(Halt 카운터는 아니지만 재개 시 소진 여부 판정에 필요해 같은 곳에 남긴다 — 아래 「auto-debug pass」 절). (checkpoint 복구 카운트는 **reset 후에** 기록해야 생존한다 — 위 "순서 주의".) `[CONFLICT]`는 기록 형식이 다르다 — **지점 식별자와 판정 내용을 같은 줄에** 둬야 "같은 지점 2회" 판정이 재개 후에도 성립한다. **형식 리터럴은 이 파일의 「리뷰 결과 처리 (재리뷰 범위 · 이력 전달 · CONFLICT · incomplete · 이의)」가 정본이며 여기 복제하지 않는다** — 같은 문자열을 두 곳에 두면 한쪽만 고쳐져 드리프트가 난다.
  - **Phase 단위 재루프**: Phase G 재루프 최대 2회(`phase-g-detail.md` G-3)·Phase F-7 재진입 최대 3회(`phase-f-detail.md` F-7). 이 둘도 컨텍스트 관리 규칙 4의 "압축 통과" 시나리오 안에서 도는 루프이므로 함께 영속화하지 않으면 압축이 카운트를 0으로 리셋해 "최대 2회·3회" 무한루프 가드가 무력화된다.
  아래 "Failed attempts"가 무엇이 왜 실패했는지를 남긴다면, Retry Ledger는 몇 번째인지(카운트)를 남겨 둘이 보완한다.

## checkpoint 구조

각 task의 Phase I 시작 시 `git commit --allow-empty -m "checkpoint: T<N> start"`(빈 커밋) 생성.
구현 완료 후 Phase V 진입 직전 `git commit -m "checkpoint: T<N> pre-review"`(실변경 — 리뷰 대상 diff 고정, SKILL Phase V 서두) 생성.
pre-review 이후의 수정분(리뷰 지적·V-1~V-3 실패 수정)은 `git commit -m "checkpoint: T<N> review-fix"`로 이어 커밋(재리뷰 HEAD 갱신 — SKILL Phase V 서두·Phase D 「판정」의 신호).
중간에 큰 변경 후 추가 checkpoint 가능:

```bash
git commit -m "checkpoint: T<N> partial — <어디까지>"
```

**복구 reset 대상**: 회복 불가 판단 시점에 따라 다르다 — 구현 자체를 폐기하고 다시 짜야 하면 `checkpoint: T<N> start`(빈 커밋)로, 리뷰 지적 수정이 꼬여 pre-review 시점으로만 되돌리면 되는 경우엔 `checkpoint: T<N> pre-review`로 reset한다(가장 최근의 적절한 checkpoint). 그 이후 변경은 모두 폐기.

## 복구 후 행동

1. 실패 원인을 plan.md의 해당 task에 "Failed attempts" 섹션으로 기록
2. Phase P 재진입 (사용자에게 묻지 않음)
3. 다른 접근법 시도

이는 자율 루프의 일부이므로 사용자 개입 없이 자동 진행.

## Subagent 호출 규약 (공통) — 동기 실행

reviewer·explorer·위임 에이전트 등 **이 하니스가 호출하는 모든 subagent는 동기 호출한다 — 결과를 받아 판정한 뒤에만 다음 단계로 간다**(현 하니스에서는 `run_in_background: false`). 하니스의 subagent 호출은 전부 "결과가 곧 통과/차단 판정"이거나 "결과를 받아야 다음 조사·기록이 성립"하는 게이트라, 결과 없이 다음으로 넘어가면 그 게이트가 통째로 무력화된다.

**스킬 발동이 곧 subagent 호출 요청이다 — 리뷰 호출에 별도 승인을 구하지 않는다.** 세션 지침·상위 정책이 *"사용자가 요청하지 않으면 에이전트를 호출하지 말라"*고 규정하더라도, 사용자가 **plan을 승인하고 이 스킬을 발동한 시점에 그 스킬 규약이 규정한 reviewer·explorer 호출은 이미 요청된 것**이다 — plan.md = 전체 작업의 위임장이고, 리뷰 게이트는 그 plan에 명시돼 사용자가 보고 승인한 절차다. 따라서 자율 루프는 **묻지 않고 정상 호출로 진행**하며, 이 상황을 아래 B 분기(체크리스트 대체)로 강등하지도 않는다. 되묻는 것이 안 되는 이유는 둘이다: ① 리뷰가 규정된 plan을 승인해 놓고 그 리뷰 호출만 다시 승인받는 **순환**이 되고, ② 자율 루프의 근간인 *"task 사이에 사용자에게 묻지 않는다"*가 리뷰 지점마다 무너져 **루프가 첫 task에서 멈춘다**(이 규약을 명문화한 계기가 실제로 그 정지였다).

**"병렬"과 "비동기"는 다른 개념이다.** 하니스 문서 곳곳의 "한 turn 동시 호출"·"병렬 호출"은 **동기 호출 여러 개를 한 메시지에 함께 보내는 것**을 뜻한다 — 동시에 실행돼 대기 시간이 줄고, 전부 끝난 뒤 결과가 함께 돌아온다. **백그라운드로 띄워 두고 결과를 나중에 받는 것이 아니다.** 이 구분을 명시하는 이유는 호출 도구의 **기본값이 백그라운드**이기 때문이다 — 명시하지 않으면 기본값으로 나가 리뷰 결과 없이 루프가 전진한다.

**백그라운드 실행은 결과 시점만 바꾸는 게 아니라 subagent의 도구를 줄인다.** 공식 sub-agents 문서에 따르면 백그라운드로 띄운 subagent는 **내장 도구가 축소되며 그 허용 목록에 `LSP`가 없다** — 정의로 이동·참조 찾기 같은 정적 분석을 쓰던 reviewer가 **경고 없이** 그 능력을 잃은 채 판정하게 된다. 즉 백그라운드 호출은 "같은 리뷰를 나중에 받는 것"이 아니라 **더 얕은 리뷰를 받는 것**이다. 도구 축소가 조용히 일어나 결과만 보면 알아챌 수 없으므로, 동기 호출은 게이트 무력화 방지뿐 아니라 **검증 깊이 보존**을 위해서도 지켜야 한다.

## Reviewer 호출 실패 대응 (과부하·도구 불가·거절·빈 응답) — 모든 subagent 호출 공통

reviewer subagent 호출이 실패하면 **실패 유형으로 분기**한다 (V-5/V-6, Phase F-7, plan-feature의 plan-reviewer 등 모든 reviewer 호출에 적용). 유형을 나누는 이유는 대응이 서로 다르기 때문이다 — **과부하는 기다리면 풀리므로 재시도가 1순위**지만, **도구 자체를 못 쓰는 환경은 몇 번을 재시도해도 같으므로 즉시 대체 절차로 가고**, **거절은 같은 입력을 다시 보내면 같은 결과가 나오므로 입력을 바꿔야 하며**, **빈 응답은 조사가 이미 끝나 있으므로 판정문만 다시 받으면 된다**.

### A. 과부하 (HTTP 529)

1. **짧게 대기 후 재시도** (최대 2회). 일시적 과부하는 대부분 재시도로 해소된다.
2. 재시도도 계속 529면 **모델 등급에 따라 분기**:
   - **Opus reviewer**(`plan-reviewer`, `plan-completion-reviewer`): **Sonnet으로 대체 실행 가능**. 단 *"Opus 과부하로 Sonnet 대체 실행 — 검증 깊이가 평소보다 낮을 수 있음"*을 사용자에게 **명시**하고, 그 reviewer의 결과/완료 보고에 ⚠️ 표시를 남긴다. 중요 게이트(F-7 등)를 건너뛰지 않기 위함이며, 대체로 통과해도 "Opus 미검증 영역 가능"을 plan.md Next Steps에 기록한다.
   - **Sonnet reviewer**(`spec-compliance-reviewer`, `code-quality-reviewer`): **Haiku 대체 금지** (검증 신뢰도가 크게 떨어짐). 재시도가 모두 실패하면 사용자에게 *"검증 subagent가 과부하로 실행 불가 — 잠시 후 재시도 / 이번은 자체 검증으로 진행 / 대기"* 중 선택을 요청한다. **이 요청은 `## ⏸️ 리뷰 인프라 선택 요청` 헤더로 출력한다** — Strong 마커가 없으면 `require-evidence` 검사 4가 이 정당한 정지를 위반으로 판정할 수 있다(정본: SKILL.md 금지 표현 예외 목록의 마커 규약). 자체 검증으로 진행하더라도 그 사실을 보고에 명시한다.
   - **Haiku reviewer**(`spec-prefilter`, `explorer`): 재시도만. 계속 실패하면 해당 단계의 상위 흐름(Sonnet reviewer 직접 호출 등)으로 진행한다.
3. **모델 대체·검증 생략은 항상 사실을 명시한다** (투명성). 검증이 평소보다 약화됐다는 신호를 사용자가 알 수 있어야 한다 — 조용히 대체하지 않는다.

### B. 도구 사용 불가 (subagent 호출 자체가 불가능)

**발동 조건 (좁게 한정)**: subagent 호출이 **물리적으로 불가능**할 때만이다 — 도구가 제공되지 않거나, 호출이 즉시 거부되거나, 환경상 실행되지 않는 경우. **"리뷰가 과한 것 같다", "이 정도는 안 봐도 된다" 같은 판단은 발동 조건이 아니다** — 그 판단으로 여는 순간 이 분기는 검증을 건너뛰는 통로가 된다. 조건이 애매하면 발동하지 않고 Halt해 사용자에게 묻는다.

**세션 정책이 "사용자 요청 없는 에이전트 호출"을 금지하는 상황은 이 분기가 아니다.** 위 「Subagent 호출 규약」대로 **스킬 발동 자체가 그 요청**이므로 묻지도, 체크리스트로 강등하지도 않고 **정상 호출**한다. 이 분기는 **승인이 있어도 열리지 않는 환경**(도구 부재·즉시 거부)만 다룬다 — 정책 상황까지 여기로 보내면 검증이 조용히 강등되고, 승인 요청으로 보내면 자율 루프가 리뷰 지점마다 멈춘다.


1. **재시도는 2회까지만** 하고(A와 같은 한도 — 일시적 오류와 구분하기 위함) 더 반복하지 않는다. 환경이 원인이면 재시도로 바뀌지 않는다.
2. **대체 절차**: 메인이 해당 reviewer의 **정의 파일(`agents/<이름>.md`)을 Read해 그 판정 항목을 체크리스트로 삼아 직접 대조**하고, **항목별 판정 결과를 남긴다**. 요약이 아니라 항목 단위 기록이어야 한다 — "대체로 괜찮다" 식의 뭉뚱그린 통과는 이 절차의 목적(무엇을 못 봤는지 드러내기)을 없앤다.
3. **의무 3종 (전부 필수)**:
   - 사용자에게 **그 자리에서 보고**한다("reviewer 호출 불가 → 체크리스트 대조로 대체").
   - plan.md `## Progress Log`에 대체 사실을 기록한다(압축·재개 후에도 남게).
   - **최종 보고에 "검증 깊이 저하 — reviewer 미실행"을 명시**한다. 이 표시가 없으면 사용자는 적대적 검토를 받은 산출물로 오인한다.
4. **Phase G 연동**: F-7을 이 분기로 대체했으면 **PRD 대조의 신뢰도가 낮아진 상태**이므로, `phase-g-detail.md` G-1 예외 ②(Sonnet 대체 시)와 **동일하게 active Must FR 전체를 메인이 보완 재대조**한다 — 체크리스트 대체는 Sonnet 대체보다 검증 깊이가 **더** 낮으므로 더 약한 경로가 더 느슨한 사후 검증을 받는 역전을 막는다.

> **이것은 "생략"이 아니라 "대체"다.** 안티패턴 표의 *"Review subagent 생략 — 절대 금지"*는 **호출할 수 있는데 안 하는 것**을 금지한다. 이 분기는 호출이 불가능한 환경에서 검증을 **다른 수단으로 수행하고 그 약화를 공시**하는 절차이므로 그 금지와 충돌하지 않는다.

### C. 안전 분류기 거절 (refusal)

**식별**: reviewer가 HTTP 오류 없이 **정상 응답으로 돌아오지만 검토를 거부**한 경우다(응답의 `stop_reason`이 거절을 나타내거나, 본문이 판정 대신 거부 사유만 담고 있다). A(529)와 달리 **전송 계층은 성공**했으므로 재시도 로직이 그대로 돌면 실패로 보이지도 않는다.

**재시도는 무의미하다.** 529는 서버 혼잡이라 기다리면 풀리지만, 거절은 **같은 입력에 대한 일관된 판단**이다 — 같은 diff·같은 프롬프트를 다시 보내면 같은 거절이 돌아온다. 그래서 A의 "짧게 대기 후 재시도"를 여기 적용하지 않는다.

**처리**:
1. **거절 사유를 그대로 확인**한다. 리뷰 대상 diff에 안전 분류기를 건드리는 내용(예: 자격증명처럼 보이는 문자열·공격 코드 형태의 테스트 픽스처)이 있는지 본다. 하니스 자신의 골든 픽스처가 그런 형태인 경우가 실제로 있다.
2. **입력을 바꿔 1회 재의뢰**한다 — 범위를 파일 단위로 좁히거나(거절을 유발한 파일 제외), 그 파일이 테스트 픽스처임을 프롬프트에 명시한다. **diff 자체를 고쳐 통과시키려 하지 않는다**(검증을 통과시키려고 대상을 바꾸는 것은 본말전도). **파일을 빼고 재의뢰해 통과했다면 그 파일은 검토되지 않은 것이므로, 최종 보고에 "미검토 범위: `<파일>`"을 남긴다** — 좁힌 범위의 OK를 전체의 OK로 보고하면 4번을 우회하는 셈이 된다.
3. 좁힌 재의뢰도 거절되면 **B 분기의 대체 절차를 그대로 적용**한다(정의 파일 체크리스트 대조 + 의무 3종, **그리고 B-4의 Phase G 연동까지** — 검증 깊이가 낮아진 사실은 원인이 거절이든 도구 불가든 같으므로 사후 보완도 같아야 한다). 다만 최종 보고에는 "도구 불가"가 아니라 **"reviewer 거절 — 미검토 범위: `<파일>`"**로 사유와 범위를 정확히 적는다. 무엇이 검토되지 않았는지가 사용자에게 필요한 정보다.
4. **거절을 통과로 해석하지 않는다.** "리뷰어가 문제 삼지 않았다"가 아니라 "리뷰어가 보지 않았다"이며, 이 둘을 뭉개는 것이 이 분기를 두는 이유다.

### D. 빈 최종 텍스트 (호출 성공 · 판정문 없음)

**식별**: 호출이 성공하고 **도구 호출도 정상적으로 기록**됐는데(30여 회 쓴 경우가 관측됐다) **최종 텍스트가 비어** 돌아온 경우다. 조사 서술만 하다 **판정문에 이르기 전에** 끊긴 형태도 여기 포함된다.

**`incomplete`와의 경계는 "판정문이 하나라도 나왔는가"다.** Verdict·지적 항목이 **일부라도** 출력됐으면 — 그 뒤가 절단됐더라도 — **incomplete**이며(아래 「리뷰 결과 처리」 절의 incomplete 처리 경로: 미검토분을 메인이 대조하거나 재호출), **판정문이 하나도 없으면** D다. 이 기준으로 잡는 이유는 둘의 처리가 다르기 때문이다: incomplete는 **무엇을 못 봤는지가 응답에 남아 있어** 그 부족분만 지목해 메우면 되지만, D는 **메울 대상조차 없어** 판정 자체를 다시 받아야 한다. 애매하면 **incomplete로 본다**(부족분 지목이 더 엄격한 경로다). A(과부하)와도 다르다: 전송 계층이 성공했고 재시도할 이유가 없다(모델이 조사를 이미 마쳤다). C(거절)와도 다르다: 거부 의사가 아니라 **출력만 유실**된 것이므로 입력을 바꿀 필요가 없다.

**처리**:
1. **같은 에이전트에 판정문만 재요청한다 (1회).** 새 조사를 요구하지 말고 *"방금 조사한 내용으로 판정만 출력하라"*고 요청한다 — 그 에이전트의 컨텍스트에 조사 결과가 남아 있어 **추가 도구 호출 없이 즉시 응답**한다(실측: 4회 관측 전건이 이 방법으로 해소, 재조사 비용 0).
2. **재요청도 비어 오면 B 분기의 대체 절차로 수렴한다**(정의 파일 체크리스트 대조 + 의무 3종, 사유는 "빈 응답 — 판정문 미수신"). 무한 재요청은 루프를 세우므로 **재요청은 1회로 끝낸다** — C 분기가 "좁힌 재의뢰 1회 후 B로 수렴"하는 것과 같은 구조다.
3. **재요청 사실을 plan.md `## Progress Log`에 남긴다.** 검증 깊이가 낮아진 것은 아니지만(같은 에이전트의 같은 조사 결과다), 재요청이 잦아지면 그 자체가 신호이므로 기록해 관측 가능하게 둔다.
4. **빈 응답을 통과로 해석하지 않는다.** C 분기와 같은 이유다 — 판정문이 없는 것은 "지적이 없다"가 아니라 "판정을 받지 못했다"다.

> **왜 별 분기인가**: 이 형태는 A/B/C 어디에도 해당하지 않아 관측될 때마다 즉흥 대응해야 했다(T1 2회 + T2 1회 + T3 1회 = **4회**). 대응은 매번 같았고 매번 통했으므로, 그 방법을 규약으로 고정한다.

## 재개 진입 (중간 체크포인트에서 이어하기)

**plan-feature를 거치지 않고** implement-task로 들어오는 **모든 진입**에 적용한다 — `"T6부터 계속"` 같은 명시적 재개뿐 아니라, 새 세션에서 `"구현해"`·`"진행"`처럼 **이번 대화에 Step 1이 없는 경우 전부**다. **발동 조건을 명시적 재개 문구 형태로 좁게 읽지 않는다**: 아래 5번(경량 위키 참조)이 메우려는 공백은 *"plan-feature Step 1을 거치지 않아 위키 지식이 빠지는 것"* 인데, 그 공백은 **요청 문구가 아니라 진입 경로**에서 생기므로 좁게 읽으면 같은 공백이 그대로 남는다.

1. plan.md의 `## Progress Log`를 읽어 완료 task 파악
2. `git log`로 마지막 commit 상태 확인
3. plan.md의 task 체크박스로 미완료 task 식별
4. **첫 Phase P 진입 전 Phase 0(사전 승인 일괄 확인)을 1회 수행** — 새 세션 재개는 이번 대화에 plan 승인이 없으므로 재확인 분기(위 Phase 0). 그 뒤 지정된 task(또는 첫 미완료 task)부터 Phase P 시작
5. **경량 위키 참조 (절차 K, 세션당 1회)**: 첫 Phase P 진입 전, `pjc:llm-wiki` 절차 K(read-only)로 이번 plan과 관련된 feature/recipe/patterns를 참조한다 — 재개 세션은 plan-feature Step 1(위키 참조)을 거치지 않아 위키의 재사용 레시피·함정 지식이 빠지기 쉽다. vault가 있으면 index 기능별 인덱스·`30_knowledge/patterns/`에서 관련 항목만 식별해 Read하고(전체 정독 금지), vault가 없거나 관련 자료가 없으면 조용히 통과한다(K 준용 — vault·자료 없으면 조용히 통과, 무매칭 시 합성 금지). **단 "vault가 없다"는 판정은 절차 K 1의 `⚠ 판정 게이트`를 거친 확인 결과여야 한다** — 그 확인 없이 미설정으로 단정하고 통과하지 않는다(주입된 vault 상태 라인이 있으면 그것으로 갈음, **라인의 부재는 판정 근거가 아니다**). 건너뛴 경우의 기록도 K 1 형식을 따른다. **plan.md Investigation Log에 `위키 참조:` 기록이 있으면 그 페이지들을 우선 식별 대상으로 삼는다**(계획 세션이 이미 찾아둔 근거 — 인덱스 재검색 생략). 동일 세션에서 plan-feature를 막 거쳐온 경우(Step 1에서 이미 참조)는 중복이므로 생략한다 — **이 절 서두의 진입 조건("plan-feature를 거치지 않은 진입")과 표면상 겹쳐 보이지만 중복이 아니라 백스톱이다**: 압축으로 Step 1이 대화에서 안 보이게 되면 진입 조건은 만족하는데 실제로는 이미 참조를 마친 상태가 되며, 그 경우를 이 문장이 잡는다(중복으로 보고 지우지 말 것).
6. 이전 task 상세는 Progress Log + git으로만 참조 (전체 history 불필요)

**세 신호(Progress Log·git log·체크박스)가 어긋나면 git log를 신뢰한다.** git log는 매 task commit(`T<N>: ...`)으로 항상 최신이고, Progress Log는 2 task마다, 체크박스는 갱신 누락 가능성이 있다. 또 지정 task의 선행(`Depends on`) task가 git log에 안 보이면 그 선행부터 다시 확인한 뒤 진행한다.

**task 내부 재개 판정 (checkpoint 커밋으로).** git log 마지막 커밋이 그 task의 완료 커밋(`T<N>: ...`)이 아니라 checkpoint면 task가 미완료 중단된 것이다 — `checkpoint: T<N> start`(빈 커밋)면 구현부터, **`checkpoint: T<N> pre-review`면 구현은 끝났고 V-5/V-6 리뷰가 미완료**인 것으로 보고 그 task의 Phase V부터 재개한다(구현을 다시 하지 않는다). **`checkpoint: T<N> review-fix`면 수정분까지 커밋됐고 재리뷰가 미확인** — 그 HEAD로 V-5/V-6 재리뷰부터 재개한다(직전에 재리뷰가 이미 통과했을 가능성은 있으나 중복 리뷰를 감수한다 — 무회귀 우선, pre-review 재개와 동일 철학). **`checkpoint: T<N> partial`이면 구현 중 중단** — Phase I를 이어 진행한다. 제목이 checkpoint 계열도 완료 커밋도 아니면(수동 개입 등) `checkpoint: T<N> pre-review`의 존재 여부로 폴백한다(있으면 Phase V부터, 없으면 구현부터). Phase Ledger 마커는 Phase F/G 위치만 다루므로, task 내부의 이 판정은 마지막 checkpoint 커밋 종류로 한다.

**Phase Ledger로 진행 위치 판정 (Phase F/G 중복 실행 방지).** plan.md에 `## Phase Ledger` 줄이 있으면 그것으로 **어느 Phase까지 왔는지**(예: `전 task 완료` / `Phase F 통과 (HEAD <sha>)` / `Phase G 재루프 N회차`)를 판정한다. **이미 Phase F를 통과한 상태로 재개하면**(예: Phase G가 추가한 task를 처리하다 압축된 경우) 남은 task만 P→I→V→D로 처리하고 **Phase F(F-7 Opus 포함)를 재실행하지 않는다** — Phase G 재루프는 완료 task 후 G-1 재대조만 하지 Phase F 전체를 다시 돌지 않기 때문이다(phase-g-detail G-2). 마커가 **없는** 기존 plan은 안전하게 "처음부터(전 미완료 task + Phase F/G)"로 폴백한다(무회귀). 마커가 git log·체크박스와 어긋나면 task 완료 판정은 git log를 신뢰하되, **Phase 진행 위치**는 마커 + Progress Log로 판정한다.

**재개도 완전 자율 루프다.** "T6부터 계속"은 "T6 하나만"이 아니라 **"T6부터 마지막 task까지 + Phase F/G까지"를 의미한다.** 첫 세션의 T1 시작과 재개 세션의 T6 시작은 시작점만 다를 뿐 동일한 루프이며, 금지 표현 규칙("T7 진행할까요?" 금지)도 동일하게 적용된다. task 사이에 멈춰 사용자에게 묻는 것은 재개 세션에서도 위반이다. 단일 task만 실행하는 경우는 사용자가 "T6만" 처럼 명시적으로 한정했을 때뿐이다.

**분할 plan 호출**: plan이 2개로 분할된 경우(plan-feature "긴 plan 분할" — `docs/plans/...-part1.md`/`-part2.md`), 각 part는 **plan 경로를 명시해 호출**한다(예: "`docs/plans/<날짜>-<slug>-part2.md` 구현"). `docs/plans` 복수 파일은 자동 plan 해소가 모호하므로 경로를 지정한다. 각 분할 plan은 자기 안에서 T1부터 시작하며(분할은 각 plan을 독립 실행), part1 완료 최종 보고가 part2 경로를 안내한다. **plan 상단에 `## 이전 part 핸드오프` 섹션이 있으면 첫 task 전에 먼저 읽는다** — 이전 part 세션이 남긴 함정·기각된 접근·검증 지름길(final-report-template.md의 분할 안내가 생성)로, `/clear`로 유실된 암묵지를 회수한다.

## 리뷰 결과 처리 (재리뷰 범위 · 이력 전달 · CONFLICT · incomplete · 이의)

> `implement-task` V-5/V-6에서 **리뷰 결과를 받은 뒤** 적용하는 절차다. 첫 리뷰가 OK로 끝나면 이 절을 읽을 일이 없어 본체에서 이리로 옮겼다 — 본체에는 판정선만 남아 있다.
>
> **소비자가 셋인 불릿은 둘뿐이다** — 아래 **「수정을 시작하기 전에 …」**(맨 앞)와 **「`[CONFLICT]` 수신」**은 `implement-task` F-7과 `plan-feature` Step 9도 정본으로 참조한다. **증분 재리뷰·이력 전달·incomplete**는 **V-5/V-6 전용**이며 그 두 경로는 각자 자체 규정을 갖는다. 이 구분이 없으면 병렬 2-리뷰 전제의 서술이 단일 리뷰 경로에도 적용되는 것으로 읽힌다.
>
> **「지적 이의 절차」의 스코프는 정해져 있지 않다** — F-7·Step 9에 대응 규정이 **없고**(실측) 이 절의 그 불릿도 스코프를 한정하지 않는다. 위 열거에서 뺀 것은 *"저쪽에 자체 규정이 있다"* 가 사실이 아니기 때문이며, **어느 범위인지의 판정은 이 회차가 하지 않는다**.

- **수정을 시작하기 전에 고칠 자리를 먼저 센다 (전수 스캔 → 일괄 수정 → 재스캔).** 지적을 받으면 **지목된 자리부터 손대지 않는다** — 같은 결함이 있는 자리를 전수로 세어 목록을 만들고, 그 목록을 한 번에 고친 뒤, 재스캔으로 잔존 0을 확인한다.
  - **발동 조건은 둘이고 어느 하나만 충족해도 발동한다**: ① `Where`가 **자리를 둘 이상** 지목한 지적 ② 지적이 문면·규약의 **통일·정합을 요구**하는 경우(자리 수와 무관). ②의 판정 어휘는 **통일 · 정합 · 일관 · 전부 · 모든**이며, 지적문에 그런 요구가 있는지만 보면 되므로 판정이 지적문 안에서 닫힌다. **발동하지 않는 예**: *"이 한 줄의 조건이 틀렸다"* 처럼 한 자리의 내용만 다투는 지적.
  - **②가 없으면 실제 재발 사건이 트리거되지 않는다.** v1.193.0 F-7 2R의 반영 커밋 제목이 `아키텍처 소속을 16자리 전수 통일`인데, **그 16자리는 메인이 스캔해서 센 수이지 리뷰어가 열거한 수가 아니다** — 지적은 소속이 어긋난다는 정합 요구였고 고칠 대상이 그 개념의 모든 출현이었다. ①만 두면 이 형태가 그대로 빠져나간다.
  - **왜 순서를 뒤집는가**: 지목된 자리를 먼저 고치기 시작하면 **나머지가 시야에서 사라진다.** v1.193.0 T3에서 1R quality가 `SKILL.md:176, 180` 두 줄을 한 지적에 담았는데 `:176`만 고쳐 같은 축이 3R까지 반복됐고 동일 MAJOR 3회로 Halt까지 갔다. `auto-debug` 진단이 원인을 「지목된 곳만 국소 수정」으로 확정한 **뒤에도** 같은 회차의 F-7 2R에서 재발했다 — 원인을 아는 것만으로는 닫히지 않아 절차로 세운다.
  - **넓히지 않은 경계 (관측이 착수 조건이다)**: ⓐ *"복제 가능성이 있으면 전건 스캔"* 은 판정이 주관에 열려 채택하지 않았다 ⓑ **같은 축의 결함이 여러 지적으로 쪼개져 각각 자리 하나씩 오는 형태**는 지적 단위 트리거로 잡히지 않는다 — 관측이 없어 지금 넓히지 않되, 그런 구멍이 있다는 것은 적어 둔다.
  - **기록**: 수행 결과를 완료 커밋 `Review:` 줄에 남긴다 — `전수 <N>자리 → 수정 <N> · 잔존 0`. **발동하지 않은 라운드도 `전수 N/A(자리 1)` 로 짧게 적는다**(무기록으로 두면 *"세었더니 자리가 하나였다"* 와 *"세지 않아 하나로 보였다"* 가 구분되지 않아 이 기록의 목적이 사라진다).
  - **아래 「②의 복제 규약 예외」와 축이 다르다** — 그쪽은 수정한 **뒤** 재리뷰를 어디까지 돌릴지의 판정이고, 이 절차는 수정하기 **전** 어디까지 고칠지의 판정이다.
- **재리뷰 범위 — 수정의 성격에 비례한다 (증분 재리뷰).** 수정 후 무조건 전량을 다시 돌리지 않는다. `review-fix` diff를 보고 **메인이** 아래 3단계로 판정하며, **판정 축은 `code-quality-reviewer`의 「표현 지적의 심각도 상한」이 쓰는 것과 같다** — *"그 문장을 고치지 않으면 실행 결과·절차 경로가 달라지는가"*:

  | 수정 성격 | 재리뷰 범위 |
  |---|---|
  | ① **실행 결과·절차 경로에 영향이 없는 순수 표현**(오탈자·용어 통일·서식 다듬기) | **재리뷰 생략** |
  | ② 지적된 파일 내부의 국소 수정 | **그 파일만** 재리뷰 |
  | ③ 그 외(판정 조건·절차 경로 변경·시그니처·구조 변경·신규 파일) | **전량 재리뷰** |

  - **①에서 제외되는 것** — 그 리뷰어 정의의 carve-out 4종과 동일하다: **stale 주석** · **판정 조건이 바뀌는 문면**(규칙·게이트의 조건이 좁아지거나 넓어지는 것, 그리고 절차 경로가 불명확해지는 것 포함) · **사용자 노출 UI 문구** · **acceptance 충족 여부**. **마크다운이 곧 실행 규칙인 프로젝트에서는 문서 문면 수정도 이 축으로 판정한다** — "코드 라인 0줄"은 기준이 되지 못한다(그런 프로젝트에서는 거의 모든 수정이 그 조건을 만족해 재리뷰가 통째로 사라진다).
  - **②의 복제 규약 예외**: **동일 문면을 복제 보유하는 파일군**(공유 상수 · 정본/사본 관계 · 동기화 각주가 달린 절)의 수정은 **국소여도 ③(전량)으로 판정**한다 — 파일 단위 축소는 복제본 간 드리프트를 볼 수 있는 유일한 시야를 없앤다.
  - **직전 리뷰가 `incomplete`였으면 ①·②를 쓰지 않는다**(미검토분이 남아 있으므로 전량).
  - **판정 근거를 완료 커밋 `Review:` 줄에 남긴다** (예: `Review: spec OK, quality OK (재리뷰 생략 — 오탈자 2곳, 판정 조건 무관)`). 리뷰 여부를 리뷰어가 정하는 순환을 막기 위해 판정은 메인이 한다.
  - **재개 시 생략 판정은 승계하지 않는다** — 근거가 완료 커밋에 남으므로 `checkpoint: T<N> review-fix`에서 재개하면 존재하지 않는다. 그때는 전량 재리뷰로 폴백한다('재개 진입'의 중복 리뷰 감수 원칙과 정합).
  - **자기 유발 MINOR**(규칙 4-1의 수정 대상)를 고친 경우도 이 표를 따른다 — ①에 해당하면 **재리뷰 없이 V-7로 진행**한다.
- **재리뷰 시 이전 라운드 이력을 전달한다 (의무).** 재호출하는 리뷰어에게 `| 라운드 | 지적 | 심각도 | 반영 방식 |` 4열 표로 이전 라운드의 지적과 그 반영 내역을 넘긴다 — 이 표가 없으면 리뷰어는 이전 판정을 알 수 없고, **같은 지점이 라운드마다 뒤집히는 진동**이 생겨 수정과 재수정이 반복된다(리뷰어 정의의 「재리뷰 규약」이 이 표를 전제한다). **첫 호출에는 전달하지 않는다**(그때는 이력이 없다).
- **`[CONFLICT]` 수신 — 통과 조건이 아니라 소비 대상이다.** 리뷰어가 이전 지적과 상충한다고 판단하면 Verdict가 아니라 `### CONFLICT` 섹션으로 보고한다. **Verdict가 OK/MINOR여도 `[CONFLICT]`가 있으면 통과로 보지 않는다** — 아래 판정을 마치고 결과를 기록한 뒤에만 다음 단계로 간다(위 `incomplete` 처리와 같은 원리: 리뷰어가 정직하게 올린 신호를 소비하지 않으면 그 보고가 무의미해진다).
  - **판정**: 메인이 이전 지적 근거와 이번 지적 근거를 대조해 ⓐ **이번 지적 채택**(되돌림) 또는 ⓑ **이전 유지**(반증 근거를 첨부해 같은 리뷰어 재호출 — 아래 「지적 이의 절차」 재사용)를 정한다. 판정 권한이 메인에 있는 이유는 리뷰어에게 이전 라운드의 맥락이 이력 표 이상으로 없기 때문이다.
  - **기록**: 판정 결과를 plan.md `## Retry Ledger`에 `CONFLICT <지점> N회 — <채택|유지> <근거 1줄>` 형식으로 남긴다(압축·재개 생존 — 정본 `references/recovery.md` 카운터 영속화).
  - **종결**: 같은 지점에 `[CONFLICT]`가 **2회** 발생하면 Halt해 사용자 판단을 받는다. 새 상한 값을 도입한 것이 아니라 checkpoint 복구·Phase G 재루프와 **같은 2**다(`references/halt-conditions.md`).
- 두 리뷰는 **첫 판정 시 최종 diff에 전체 수행** — 어느 것도 생략·약화하지 않는다. **예외는 둘뿐이다**: ⓐ 위 **증분 재리뷰 ①·②**(재리뷰에만 적용 — 첫 리뷰는 항상 전량) ⓑ "Reviewer 호출 실패 대응"의 **A(과부하 529)·B(도구 불가)·C(거절)** fallback. **어느 쪽이든 축소·약화 사실을 반드시 명시한다**(ⓐ는 커밋 `Review:` 줄, ⓑ는 보고와 Progress Log). **D(빈 응답)는 이 열거에 넣지 않는다** — 같은 에이전트에 같은 조사 결과의 판정문만 다시 받는 것이라 리뷰가 축소되지 않으며, 재요청이 실패해 B로 수렴하면 **그때 B가 이 예외에 걸린다**(D 자체가 아니라 수렴처가 예외다). 실패 경로에서 V-6이 재실행되는 토큰 비용은 품질 우선으로 감수한다.
- **529 과부하는 각 reviewer에 독립 적용** — 병렬 중 한쪽만 529면 그 reviewer만 "Reviewer 호출 실패 대응" A 분기를 따른다 (다른 쪽 결과 유지).
- **reviewer가 "incomplete"(turn 예산 소진 등으로 acceptance 일부만 검토)로 응답하면 통과(OK)로 보지 않는다** — 해소 경로는 리뷰 종류로 갈린다: **V-5(spec) incomplete**는 미검토 항목을 메인이 diff에서 직접 대조(해당 acceptance가 충족되는 위치 지목 — 기계적 대조라 허용)하거나 reviewer를 재호출한다. **V-6(quality) incomplete는 reviewer 재호출로만** 해소한다(부족분을 명시해 재의뢰, 연속 incomplete면 파일 단위로 범위를 좁혀 재의뢰 — 자기 코드의 품질을 메인이 스스로 판정하는 것은 V-6 "자체 검토 금지"와 모순이라 불허). **단 재호출이 기술적으로 불가한 환경이면**(도구 차단 등) "Reviewer 호출 실패 대응" **B 분기**로 해소한다 — 그 경우에도 임의 자체 판정이 아니라 **정의 파일의 판정 항목을 체크리스트로 대조 + 의무 3종 공시**를 거친다(재호출도 대체도 불가능하면 해소 경로가 0이 되어 루프가 완주할 수 없기 때문이며, 이 예외는 "재호출 가능한데 하기 싫을 때"로 확대되지 않는다). incomplete를 조용히 OK 처리하고 다음 task로 넘어가는 것은 금지. (Phase G의 incomplete 처리 원칙을 per-task V-5/V-6에도 동일 적용 — Type B ESCALATE(→C 격상)의 병렬 리뷰 호출 포함 모든 reviewer 응답에 적용.)
- **지적 이의 절차 (사실 오류 반증 — 무조건 수용 방지).** 리뷰 지적을 코드 수정으로 반영하는 것이 기본이지만, 메인이 그 지적을 **사실 오류로 판단하고 파일:라인 인용으로 반증할 수 있으면**(예: 리뷰어가 "caller 누락"이라 했으나 그 caller가 리플렉션·다른 파일에서 실제로 갱신됨을 grep으로 제시), 코드를 바꾸지 않고 **반증 근거를 첨부해 같은 리뷰어를 재호출**한다. **재호출에도 리뷰어가 같은 지적을 유지하면** 그 지적을 수용해 수정하거나(반증이 틀렸을 수 있음), 반증이 확실하면 Halt해 사용자 판단을 받는다 — 이 종결 규칙이 반박의 끝을 보장한다. **이 반증 재호출은 재시도 한계의 "수정 사이클"에 포함**되므로 상한은 그 카운터(수정 사이클 누적 5회·동일 지적 3회 연속)가 강제한다(별도 횟수 캡을 두지 않는 이유 — 상한이 이미 두 겹이다). 이 절차는 antipatterns.md "Review 묵살 금지"의 예외다 — **묵살(근거 없이 무시)이 아니라 근거 있는 반증**이며, 반증이 기각되면 수용한다. 반증 없이 "내 판단엔 틀렸다"로 넘어가는 것은 여전히 금지.

## auto-debug pass (동일 BLOCKER 2회 — Halt 직전 구제)

같은 지적을 **두 번 연속** 받았다는 것은 그 지적을 두 번 고쳤는데도 문제가 남았다는 뜻이다. 그 상태에서 메인이 세 번째 수정을 시도하면 **이미 두 번 빗나간 가정을 그대로 물려받은 채** 고치게 되고, 그 결과가 동일 BLOCKER 3회 Halt다. 이 절은 그 사이에 **오염되지 않은 컨텍스트의 진단 1회**를 끼워 넣는다 — 사용자에게 넘기기 전에 "수단 자체를 의심"하는 마지막 자리다.

- **발동 조건**: 같은 task에서 **동일 BLOCKER/MAJOR가 2회 연속** 지적됨(V-5/V-6 어느 쪽이든). 3회 Halt 규정의 **직전**이며, 2회 시점 자체는 Halt 지점이 아니다.
- **상한**: **task당 1회.** 소진 후 2회 시점이 또 와도 재호출하지 않는다.
- **호출**: `root-cause-analyzer` subagent를 **동기 호출**(`run_in_background: false`) — 진단을 받아야 Phase I 복귀 내용이 정해진다(「Subagent 호출 규약」).
- **전달물** (5종): task ID + plan.md 해당 섹션 · **리뷰어 지적 원문 2회분** · `## Retry Ledger`의 해당 task 실패 기록 · BASE_SHA/HEAD_SHA · AGENTS.md 경로. **실패 이력을 함께 주는 이유**: fresh란 *"메인의 오염된 추론을 안 물려받는다"*이지 *"정보를 굶긴다"*가 아니다 — 이력이 없으면 진단자가 이미 기각된 가설을 다시 제시한다.
- **수신 후 행동**: 진단서(원인 + 근거 위치 + 기각된 가설)를 **입력으로 삼아 Phase I로 복귀**한다. 진단서는 패치를 담지 않으며 수정은 메인이 한다 — 진단과 수정의 주체를 분리해야 이 호출이 의미를 갖는다.
- **호출 실패 시**: 「Reviewer 호출 실패 대응」의 **A(과부하)·C(거절)·D(빈 응답)는 준용하되 B(도구 불가 → 체크리스트 대체)는 적용하지 않는다** — 구제 경로이므로 생략하고 **기존 경로 그대로 진행**한다(메인이 대체 진단을 흉내내면 그것은 fresh가 아니라 오염된 컨텍스트의 자기 진단이다). **호출 실패는 `1/1` 소진으로 세지 않는다**(진단서를 못 받았으므로 구제를 쓴 것이 아니다). 반면 진단서가 **"미규명"으로 와도 그것은 소진**이다 — 진단을 받았고 결과가 빈손인 것이라, 같은 조사를 다시 시킬 이유가 없다.
- **Retry Ledger 기록 형식**: `auto-debug <task> 1/1 — <확정 원인 요지 또는 "미규명">`. 호출 **직후** 기록한다(압축·재개 생존 — 재개 시 이 줄이 있으면 소진으로 보고 재호출하지 않는다).

### 계수 규칙 (auto-debug는 어떤 Halt 카운터도 증감시키지 않는다)

기존 카운터 사이에 새 단계를 끼우면서 계수를 정의하지 않으면, 같은 배선이 *"2회에서 즉시 Halt"*로도 읽혀 **안전 임계가 사실상 2회로 내려간다**. 세 줄로 못 박는다:

1. **동일 BLOCKER 카운터 무증감.** auto-debug는 리뷰 라운드가 아니므로 세지 않는다. 진단 후 Phase I에서 고치고 **재리뷰에서 같은 지적이 다시 나오면 그것이 3회째**이며 그 시점에 기존 규정대로 Halt한다. auto-debug가 임계를 늦추지도 앞당기지도 않는다.
2. **수정 사이클·그라인딩 카운터에도 포함하지 않는다.** auto-debug 자체는 수정도 빌드도 아니다. **단 진단서를 받아 Phase I에서 수행한 수정은 종전대로 수정 사이클 1회로 센다.** (같은 형태의 삽입인 「지적 이의 절차」의 반증 재호출은 *포함*으로 규정돼 있는데, 그쪽은 **자체 상한이 없어** 카운터가 유일한 제동이기 때문이다. auto-debug는 위 `1/1`이라는 자기 상한을 가져 그 이유가 성립하지 않는다.)
3. **자체 상한은 별도 카운터** `auto-debug <task> 1/1`. 위 둘과 독립이며 Retry Ledger에 영속화한다.

결과적으로 **세 Halt 카운터의 도달 시점은 auto-debug 도입 전과 동일하다** — 이 절이 추가하는 비용은 task당 subagent 호출 1회뿐이고, 지연되는 Halt 경로는 없다.
