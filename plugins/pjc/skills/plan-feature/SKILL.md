# Plan Feature

코드 작성 전에 작업을 분해하고, 모든 결정 분기를 사전 해결하고, 검증 가능한 수용 기준을 정의한다.

## Trivial Bypass — 이 skill을 건너뛰는 경우

다음 케이스는 **plan-feature를 호출하지 않고** Claude가 직접 Write/Edit으로 처리한다:

| 카테고리 | 예시 |
|---|---|
| UI 문구·라벨 | "확인 버튼 라벨을 'OK'로", "메시지 문구 변경" |
| 아이콘·이미지 교체 | "이 아이콘을 SVG 파일로 교체", "PNG 새 파일로 변경" |
| 색상·치수·간격 순수 값 치환 | "Primary 색상을 #336699로", "padding을 16px로", "여러 요소 width/height/font-size 숫자만 조정" (개수 무관, 로직·구조 변화 없으면) |
| 문서·README 오타 | "README 오타 수정", "줄바꿈 추가" |
| 주석 추가 | "이 메서드에 한글 주석 추가" |
| 단일 라인 설정 | ".editorconfig에 한 줄 추가", "gitignore에 폴더 추가" |
| 단일 라인 리소스 | "strings.xml의 키 한 개 값 변경" |
| **작은 코드 수정** | **변수 값·조건·문자열 변경 등 3줄 이내, 새 함수/클래스/시그니처 추가 아님** |

**Trivial 판정 기준** (모두 만족):
1. 변경이 **3줄 이내, 단일 위치**
2. **새 함수/클래스/메서드 추가 없음, 시그니처 변경 없음**
3. 사용자 요청이 **명백하고 단순** (의도 모호함 없음)

**예외 — 순수 값 치환은 개수·줄 수 제한 없이 trivial**: 사이즈·색상·간격·폰트 크기 등 **디자인 토큰/리터럴 값을 다른 값으로 바꾸기만** 하고 로직·조건·구조·시그니처 변화가 전혀 없으면, 값이 3개든 10개든·여러 줄이든 trivial로 보고 직접 수정한다(값만 바뀌므로 개수가 많아도 위험이 낮고, 잘못돼도 화면에서 바로 보인다). 단 다음은 **순수 치환이 아니므로 trivial 아님**(plan 또는 최소한 질문):
- 새 **반응형 분기**(`@media` 블록 신설 등) 추가 — 화면 크기별 동작이 새로 생기는 구조 변화.
- 값 변경이 **레이아웃 구조**(flex/grid 방향·배치)나 **동작 로직·조건**을 함께 바꿈.
- 값을 바꾸면서 **계산식·변수 도입**(하드코딩 → 계산) 등 구조가 변함.

위 기준(1-3 또는 순수 값 치환 예외)을 만족하면 코드 파일(`.cs`, `.xaml`, `.ts`, `.kt`, `.py`, `.css` 등)이라도 직접 수정한다.
`require-plan-for-write` hook이 작은 변경을 자동 통과시키고, cross-file 영향은 `impact-warn` hook이 사후 검출한다.

**트리거 우선순위 — "여러 곳"보다 순수 치환이 먼저.** 요청이 여러 파일·여러 위치에 걸친다는 이유만으로 plan-feature를 발동하지 않는다. 대상이 순수 값 치환(위 예외)이면 파일·개수와 무관하게 이 Trivial Bypass가 "여러 곳/전체" 발동 트리거보다 **우선**한다 — 발동을 애초에 막는 것이 1차이고, 발동 후 실제 확인에서 걸러내는 Step 1.5 off-ramp는 2차 안전망이다.

### 애매한 경우 — plan을 강제하지 말고 질문 (3갈래)

trivial인지 plan이 필요한지 **판단이 애매하면** 임의로 plan-feature를 강제하지 않고 사용자에게 **한 번** 묻는다 — **A) 바로 수정**(빠르게, plan 없이 — `impact-warn` hook이 사후 caller 영향 검출) / **B) 계획부터**(plan-feature 영향분석+검증). 명백히 trivial(위 3기준)이면 묻지 말고 직접 수정, 명백히 큰 작업(다중 파일·시그니처·새 정의)이면 묻지 말고 plan 진행. **즉 3갈래: 명백 trivial=직접 / 명백 대형=plan / 애매=A/B 질문.** (질문은 작업당 1회, 선택대로 진행.)

## 자율성 모드: USER-INTERACTIVE

> **이 skill 안에서는 사용자에게 물어도 된다.** 모호한 요구사항은 명확화 질문 권장.
>
> 그러나 **`implement-task` 단계로 넘어가기 전에 모든 질문이 해결**되어야 한다.
> implement-task는 FULLY AUTONOMOUS이므로 그 안에서는 사용자에게 묻지 않는다.

```
plan-feature (이 skill)         | implement-task
USER-INTERACTIVE                | FULLY AUTONOMOUS
                                |
질문 OK (Open Questions에 모음) | 질문 금지 (Halt만 가능)
사용자 승인 1회 (게이트)         | plan = 전체 위임장
                                |
↓ 모든 질문 해결 후 ──────────→ ↓
```

> **위임장 = plan 승인(1회)이 전체 작업의 위임이며, 여기에는 plan의 `## 사전 승인 항목 (일괄 승인 대상)`이 명시적으로 포함된다.** 단 `## 불가피한 Halt (위임 불가)` 항목(파괴적·외부/비가역·돌발 결정)은 위임에서 제외돼 그 지점에서 별도 승인받는다.

## 절대 규칙 (Hard Rules)

1. **이 Skill은 코드 파일을 작성·수정하지 않는다.** 계획 산출물은 `plan.md`(+ 대규모 작업 시 `PRD`)이며, 그 외에는 **발동된 스킬 규약이 정한 큐 기록**만 남긴다(예: `pjc:llm-wiki` 절차 K의 `[SKILL-IMPROVE]` 큐 1줄). 코드·문서 등 대상 프로젝트 파일은 건드리지 않는다.

2. **팩트 기반 — 예측 금지, 전수 확인.**
   - 모르는 것은 "확인 필요"로 표시. "아마도", "보통은", "일반적으로" 같은 가정은 금지.
   - 모든 주장은 Read 또는 grep으로 직접 확인한 결과여야 한다.
   - 사용처는 grep으로 **전수 조사**. "샘플 몇 개 확인 후 전체가 그럴 것"이라 결론짓지 않는다.
   - **읽기 비례 원칙 (hit 수에 따른 처리).** grep 결과는 양끝이 다 위험하다 — 많으면 세고 끝내게 되고, 0이면 「없다」의 증거로 삼게 된다.
     - **hit 과다(30건 초과)**: 전건 Read 대신 `grep -C <n>`으로 **1차 영향 판정** 후 의심분만 전체 Read하고 **판정 근거를 Investigation Log에 남긴다**(예: "hit 42건 중 호출부 9건만 정독, 나머지는 문자열/주석"). 전수 조사의 포기가 아니라 **단순 카운트로 끝내는 것을 막는** 방법이다(Step 4 Halt 조건과 정합 — 카운트가 아니라 영향 판정이 있어야 한다). 30건 이하면 전건 Read.
     - **hit 0 — 부재 판정**: *"그것이 없다"*를 **결론의 근거로 쓸 때**(신규 작성·미구현 단정)는 검색 1회의 0건으로 단정하지 않는다. ① **검색어 2개 이상**(이름 + 동작 키워드 — 이름만 쓰면 *다른 이름의 같은 구현*은 원리상 안 나온다) ② **스코프는 레포 전체** ③ **각 검색어와 0건을 Log에 기록**. 결론에 쓰이지 않는 존재 확인은 대상이 아니다.
     - **읽기 절단**: 파일 일부만 읽고 **부재를 단정하지 않는다** — 부재 결론은 전체를 훑는 grep 또는 전량 Read로만 낸다. 부분만 읽었으면 **읽은 범위를 Log에 적는다**.
   - 확인 방법은 Investigation Log에 기록.

3. **근본 해결.** 증상 우회는 plan의 해결책이 될 수 없다. **선택지를 낼 때도 같다 — ★은 근본 해결안에 준다**(판정·기록 형식은 Step 8 「추천(★) 기준」).

4. **결정 사전화 — 자율 실행 전제.**
   `implement-task`는 plan.md를 받으면 **사용자 개입 없이 모든 task를 끝까지 실행**한다.
   - **근거로 결정 가능한 항목은 자체 확정 — 질문은 근거로 결정 불가한 것만.** 코드·AGENTS.md·기존 컨벤션으로 답이 정해지는 항목(명명 관례, 기존 패턴 준수, 프로젝트 표준 등)은 사용자에게 묻지 말고 **Decisions에 `Source`(확인한 코드/문서 위치)와 함께 자체 확정**한다. 사용자에게 묻는 것은 **근거만으로 결정할 수 없는 항목**(제품 방향·UX 선택·비가역 데이터 형식 등 갈림길)에 한한다 — 자명한 것까지 묻는 것은 과잉이다.
   - 근거로 결정 불가한 모호한 요구사항은 **빠짐없이 모두** 사용자에게 미리 묻는다 (카테고리별로 묶어서 한 번에 제시, 개수 제한 없음).
   - 각 선택지에 **Claude 추천 ★** 표기로 사용자 결정 부담 ↓.
   - 답변 후 새 모호함 발견 시 **다음 라운드에서 추가 질문 가능** (라운드 통상 3-5회).
   - **답변 시간 < 재작업 시간**. 질문이 많아 보여도 plan 완전성을 우선한다. 추측으로 코드 작성하면 그게 재작업의 원인.
   - **구현 도중 결정 분기 0의 대상은 "외부 관찰 가능 계약"**(공개 API·스키마·UX 동작·의존성)이다 — 이 계약이 갈리는 지점은 plan에서 모두 확정한다. 반면 **순수 내부 세부**(지역 변수명, 국소 구현 방식 등 가역·비노출)는 구현자가 컨벤션에 따라 결정하도록 위임해도 된다(모든 미세 결정을 plan에 못박으라는 뜻이 아니다 — 계약이 흔들리지 않으면 충분).
   - 자기 검증: **"이 plan을 다른 사람에게 넘겨도 (외부 계약에 대한) 추가 질문 없이 끝낼 수 있는가?"**

5. **연관 파일 의무 명시 (Cross-File Awareness).**
   - 변경 대상의 모든 호출자/구현체/직렬화/테스트를 task의 Files 목록에 **모두** 명시.
   - 누락 시 plan-reviewer 또는 spec-compliance-reviewer가 차단한다.

6. **요청 범위 밖 작업 금지 — 단 "동반 변경"은 범위 밖이 아니다.** "참고 김에 정리"는 plan에 새 task로 등록 후 사용자 확인.
   - **경계**: 이 변경 없이는 **요청이 성립·정합하지 않는** 것(그 문서·규약·검증 자산이 어긋난 채 남는 것)은 **범위 밖이 아니라 요청의 일부**다 — Step 4-E로 판정해 task에 편입한다(그 판정의 적용 범위는 Type C/D task가 있는 plan — 4-E 말미). 범위 밖이란 성립과 무관한 "참고 김에"를 말한다.
   - 이 구분이 없으면 규칙 6이 동반 변경 검토를 억제해, **구현이 끝난 뒤에야 "추가로 고칠 곳이 있다"고 보고**하게 된다(실제 관측된 결함 — 알림이 늦은 것이 문제다).

7. **"이번 제외"와 "영구 제외"를 구분해 기록.** 작업을 빼기로 한 경우 둘 중 어디인지 정확히 판단한다 — 잘못 적으면 다음에 할 일이 영영 누락된다:
   - 사용자가 **"이번엔 빼고 다음에 하자"** → plan.md의 `## Deferred / Follow-up`에 기록 (향후 진행 대상).
   - 사용자가 **"이 기능은 안 만든다"** → `## Out of Scope`에 기록 (영구 제외).
   - 애매하면 사용자에게 "이번만 제외인가요, 아예 제외인가요?" 확인. 기본 가정은 **Deferred**(다음에) — 영구 제외는 명시적일 때만.

8. **모든 task에 검증 가능한 acceptance — 항목 간 동시 만족 가능해야 한다.** "잘 동작한다" 같은 모호한 기준 금지. 여러 acceptance 항목을 가진 task는 항목들이 **동시에 만족 가능**한지 확인한다 — 하나를 지키면 다른 하나가 깨지는 조합(예: "프로세스 1개만 기동" + "스크립트 무수정"인데 대상 구조상 양립 불가)은 실현 불가능한 계획이므로 발견 시 설계 자체를 재검토한다(plan-reviewer 항목 4가 BLOCKER로 검출).
   - **수치를 acceptance로 쓸 수 있는 조건 — 결과 지표만, 그것도 전수 + 최종 재측정일 때.** **결과 지표**(대상 **전수**를 재는 값 — 발동률·통과율·잔량 등)의 목표선은 acceptance로 쓸 수 있다. 반면 **작업량 수치**(`"신규 N건 등재"`·`"3개 파일 수정"`처럼 **대상이 늘어도 그 수만 채우면 통과**하는 값)는 쓰지 않는다 — 나중 task가 대상을 늘리고 재적용하지 않아도 그 수치는 그대로 통과해 **누락을 못 잡는다**. 둘의 차이는 *"대상이 늘면 값이 반응하는가"* 다: 전수를 재는 값은 누락이 곧 분모에 들어와 값을 떨어뜨리고, 작업량 수치는 분모가 없다.
     - **결과 지표라도 두 조건을 함께 적어야 한다** — ⓐ **대상 전수를 잴 것** ⓑ **최종 상태에서 재측정할 것**. 고장의 원인은 "수치의 종류"가 아니라 **재적용하지 않음**이므로, `발동률 ≥ 0.90`도 중간 측정값으로 통과시키면 같은 실패를 그대로 물려받는다.
     - 이 구분은 *"숫자를 고정한 acceptance는 누락을 못 잡는다"* 는 종전 지적의 **예외가 아니라 적용 대상 밖**이다(그 지적이 겨냥한 예시가 `"신규 N건 등재"`라는 작업량 수치다). 다만 그 판단은 **예시로부터의 해석**이므로, 대상이 애매하면 안전하게 **판정 축**(그 기준을 채택했는가 · 그 값이 보존됐는가)으로 쓴다.
   - **판정용 명령을 acceptance에 넣을 때는 작성 시점에 1회 실행해 기대 건수를 병기한다.** 대상은 **판정에 쓰이는 명령**(`grep`·검사기·러너 등 — 그 출력으로 충족 여부가 갈리는 것)이며, 설명용 인용 명령이나 구현 중 실행할 명령은 대상이 아니다(「규모 수치 라벨」이 설명용 수치를 제외하는 것과 같은 경계). 형식은 `**작성 시점 N건** → 수정 후 M건`처럼 **현재값과 기대값을 함께** 적는다.
     - **왜**: 그 명령을 한 번도 돌리지 않고 기대 건수를 적으면 **구조적으로 그 값이 될 수 없는 패턴**을 acceptance로 박게 된다 — v1.165.0 계획 리뷰에서 같은 결함이 리터럴만 바꿔 **2라운드 연속** 났고(`typ != "decision-log"`가 무관한 가드에도 존재 / 새 패턴이 `qtyp != "question"`을 부분문자열로 물어 3곳 잔존), 둘 다 *"0건이어야 한다"*고 적었지만 0이 될 수 없는 패턴이었다. 뿌리는 **작성자가 그 grep을 실행해 보지 않은 것**이다.
     - **현재값을 함께 적는 이유**: 기대값만 적으면 *"이미 그 상태였다"* 와 *"이번에 그렇게 만들었다"* 가 구분되지 않는다. 「잔존 0」처럼 기대값이 0인 판정에서 특히 그렇다.
     - **예외 ⓐ 대상 파일이 아직 없는 경우**(신규 생성 task) — 병기 대신 `T<N> 완료 후 최초 실행`을 적는다(추정 라벨과 같은 구조).
     - **예외 ⓑ 실행 비용이 큰 러너** — 골든 스위트처럼 정본 절차로 수 분~십수 분이 걸려 계획 중 실행이 사실상 불가한 것은, **문서화된 기준선 수치를 날짜 라벨과 함께 인용하고 착수 시 재측정**한다(예: `635케이스(2026-08-20 실측 — <문서> 「골든 러너 운용」) → 착수 시 재계수`). 이 예외가 없으면 골든 acceptance를 쓰는 모든 plan이 이 규약의 위반이 된다.

## 실행 단계

### Step 0. 작업 공간 정리 (계획 작성 전 가장 먼저)

**계획을 작성하기 전에, 이전 작업의 잔여 상태부터 정리한다.** 계획을 다 만든 뒤에 정리하면 그 과정에서 방금 만든 plan.md를 백업·복구해야 하는 낭비가 생긴다 — 정리를 먼저 하면 깨끗한 상태에서 계획을 쓸 수 있다.

0. **컨텍스트 여유 확인 (새 세션 권유)**: 이번 세션에 이미 auto-compact가 있었거나 대화가 매우 길게 누적됐으면(작업 중 압축 반복으로 품질 저하 위험) 시작 전에 새 세션 시작을 권한다. 시작 전은 멈춰도 안전한 분기점이므로 **여기서는 질문 형태를 유지한다**(계획 수립은 자율 루프 계약이 아니다 — 작업 *중간*의 압축 통과와 구분). **컨텍스트가 여유로우면 묻지 않고 조용히 통과**(과잉 방지).
   - **출력 형식 (마커 필수)** — 아래 헤더를 달아 출력한다:
     > `## ⏸️ 세션 확인`
     > 컨텍스트가 많이 찼습니다. plan.md로 맥락은 유지됩니다 — 이대로 진행할까요, 새 세션으로 옮길까요?
   - 헤더의 `⏸️`는 **Strong 마커**다. `require-evidence` 검사 4는 **어느 스킬이 말했는지 구분하지 못하고** 세션에 `implement-task` 발동 흔적이 있는지만 보므로, 루프가 Halt·중단으로 끝난 뒤 같은 세션에서 계획을 요청받으면 이 정당한 질문도 판정 대상이 된다 — 마커가 없으면 "세션 전환 제안"(금지 표현 ③)으로 차단될 수 있다. 판정·질문 여부는 그대로이고 **형식만** 갖추는 것이다(정본: `implement-task/SKILL.md` 금지 표현 예외 목록의 마커 규약).

1. **미커밋 변경 확인**: `git status`로 커밋되지 않은 변경이 있는지 본다. **단, 미커밋이 있다고 항상 묻지 않는다** — 다음을 구분한다:
   - **이번 요청과 무관한 이전 작업의 잔재**(다른 기능의 미완성 변경 등)가 섞여 있으면 → 사용자에게 처리를 묻는다(커밋/stash/폐기). 미정리 상태로 새 작업을 쌓으면 변경이 뒤섞여 커밋 단위가 엉키기 때문이다.
   - **이번 요청과 직접 관련된 변경**이거나, **방금 이 세션에서 진행해 곧 이어서 작업할 변경**이면 → 묻지 않고 그대로 진행한다 (개발 중 미커밋은 정상이며, 매번 물으면 과잉이다).
   - 판단이 애매하면(무관한 잔재인지 진행 중인지 불분명) 그때만 한 번 묻는다.
   - **'폐기'는 데이터 손실이므로 Claude가 직접 실행하지 않는다** — `git clean -fd` 같은 untracked 영구 삭제는 `block-destructive` hook이 차단한다. 단 **`git checkout -- <파일>`(추적 파일 되돌리기)은 hook이 막지 않는다**(정당한 파일 복원과 구분 불가하므로) — 그래도 uncommitted 변경 손실이라 Claude가 스스로 실행하지 않는다. 폐기를 원하면 사용자가 직접 실행하도록 안내하고, Claude는 커밋·stash까지만 돕는다.
2. **기존 plan.md 확인** (= Step 0.2 — 외부 문서가 이 라벨로 지칭한다): 이미 `plan.md`가 있으면 다음을 구분한다 (항상 묻지 않는다):
   - **이전 계획이 완료됨**(모든 task가 `[x]` + 미처리 Deferred의 대장 이관 완료)이 명백하면 → 묻지 않고 새 계획으로 교체한다 (완료된 plan.md는 휘발성 잔재이므로 보존 가치 없음 — 회차 서사 커밋과 `docs/plans/deferred.md`가 영구 기록을 이미 담았다). **판정 축 둘 다 관측 가능하다** — 체크박스는 plan.md에서 보고, **이관 여부는 그 plan의 `## Deferred / Follow-up`에 미처리 항목이 남아 있는지로 판정한다**(1차 축). 대장(`docs/plans/deferred.md`)을 텍스트 매칭으로 뒤질 필요는 없다 — 남은 항목이 있으면 아래 규정대로 지금 이관하면 되고, 없으면 이관할 것이 없었거나 이미 끝난 것이다. **단 교체 전에 기존 plan의 `## Deferred / Follow-up`에 미처리 항목이 남았는지 확인한다** — task 체크박스가 전부 `[x]`여도 Deferred는 "다음에 할 일"이라 완료가 아니다. 남아 있으면 이번 작업과 관련된 항목은 새 plan의 `## Deferred / Follow-up`으로 이관하고, 무관한 항목은 `docs/plans/deferred.md` 대장의 `## 대기`로 옮긴 뒤 교체한다(커밋되는 대장이 Deferred 추적 정본이며 **등재처는 `deferred.md` 하나**다 — 형식·중복 억제는 implement-task `references/phase-f-detail.md` F-6.5 규정, 파일 없으면 생성 — 커밋되는 대장이 **유일한 정본**이므로 이관을 빠뜨리면 그 항목은 사라진다 — 이관처는 언제나 `deferred.md`의 `## 대기`다).
     - **PRD 연결 plan은 완료 판정에 Phase G 통과까지 포함한다** — task가 전부 `[x]`여도 `**PRD**:` 줄이 있으면 그것만으로 완료가 아니다. **`## Phase Ledger` 마커 상태별 판정 표는 `references/prd-template.md` 「(plan-feature Step 0.2) PRD 연결 plan의 완료 판정 표」가 정본**이다 — 요지: `Phase G 통과 (Must 100%)`만 완료로 보고, **`Phase F 통과`까지만·재루프 중·마커 없음은 전부 완료 단정 금지**(사용자 확인). 마지막 task 직후 세션이 끊겨 Phase F/G가 실행되지 않은 plan을 완료로 오인해 폐기하는 것을 막는다. (**PRD 없는 plan은 비적용** — Phase F가 최종)
   - **진행 중이거나 미완료 task가 남은 plan.md**이면 → 이번 요청과의 관계를 묻는다 (이어서 할지, 보류하고 새로 시작할지). 미완료 작업이 묻히지 않게 한다.
   - **완료 여부가 불분명**하면(체크박스 상태와 `## Deferred / Follow-up` 내용이 서로 어긋나 판독이 안 되는 등) 그때만 확인한다 — 판정 근거는 여기서도 **plan.md 자체**이며, 위 1차 축과 같다.
3. 정리가 끝난(깨끗한) 상태에서 Step 0.5 이후로 진행한다.

> 미커밋 변경이 없고 기존 plan.md도 없으면 이 단계는 즉시 통과한다 (묻지 않음).
>
> **이 단계의 질문은 Step 8 일괄 질문과 별개다.** 작업 공간 정리는 계획을 시작하기 *전에* 끝나야 하는 선결 조건이므로(미정리 상태로 계획을 쓰면 안 됨), Step 8로 미루지 않고 여기서 즉시 묻고 처리한다.

### Step 0.5. 대규모 작업 판정 — PRD 필요 여부

다음 중 하나라도 해당하면 **대규모 작업**이다. plan.md 작성 전에 PRD를 먼저 만든다:

- 앱/제품을 새로 만드는 요청 ("메모장 앱 만들어줘", "OO 도구 만들어줘")
- 예상 task가 10개 이상인 대형 feature
- 요구사항 자체가 미정의 상태 (사용자가 "필요한 기능을 검토해서" 같은 위임 표현 사용)

**대규모가 아니면 이 단계를 건너뛰고 Step 1로** (일상 기능 추가·수정·버그는 plan.md만으로 충분).

대규모일 때의 **PRD 절차 0~5와 「승인 후 기능 변경 처리」는 `references/prd-template.md` 「(plan-feature Step 0.5) 대규모 작업 PRD 절차」가 정본**이다. 판정선만 옮겨 적으면:
- **기존 PRD 확인이 먼저다** — 신규/기존 갱신/분할 귀속을 판정하지 않으면 중복 등록·오배치가 난다.
- **질문 라운드 1회 이상이 의무다** — 대규모 위임은 그 자체가 모호함의 신호라 "모호하지 않다"는 판단으로 생략할 수 없다.
- **PRD는 승인 후 고정**이며, plan·코드는 그 뒤에 온다. 요구를 바꿔야 하면 **승인 → PRD → plan → 코드** 순서를 지킨다(거꾸로 가면 Phase G 재검증의 기준 자체가 틀린다).
- plan.md 상단에 **`**PRD**: <경로>` 줄이 의무**다 — `implement-task` Phase G 진입의 단일 신호다.

    - **분류는 `personal`로 등록하되 추정임을 남긴다** — frontmatter `confidence: medium` + 허브 본문에 *"분류는 자동 등록 추정값 — 다음 ingest에서 확인"* 1줄. **레포 경로로는 personal/work를 판정할 수 없다**(실측: work 프로젝트도 같은 상위 폴더 아래 있다). 오배치는 위키 세션에서 정정한다.
    - **조용히 통과하는 경우**: vault 미설정·경로 부재 / 게이트 미충족 / `git config user.email` 미설정(판정 불가 — 오등록보다 미등록이 싸다) / 이미 등록됨(절차 A-1 1-1 중복 가드) / 절차 A 실패. **어느 경우에도 계획 흐름을 막지 않는다.**
    - 등록했으면 그 사실을 Investigation Log에 1줄 남긴다(위 「기록 의무」의 형식과 별개 — `위키 자동 등록: <허브 경로> — 게이트 3축 충족`).
  - **vault 판정 — "미설정" 단정 금지**: **위키 vault 자체가 없으면 건너뛴다.** 단 그 판정은 `pjc:llm-wiki` 절차 K 1의 `⚠ 판정 게이트`를 거친 **확인 결과**여야 한다. 확인 없이 "미설정"으로 단정하고 건너뛰지 않는다 — **확인 없는 단정이 실제 사고로 관측됐다**(`references/rationale.md` 「vault 미설정 단정」). 세션 컨텍스트에 vault 상태 라인이 주입돼 있으면 그것을 확인 결과로 인정하되, **라인의 부재는 판정 근거가 아니다**(K 1 정본).
  - **함께 확인·기록할 것**: **대상 프로젝트의 결정 이력(`decisions.md`)** — 과거에 보류·기각된 기획을 모르고 다시 계획하는 것을 방지(`pjc:llm-wiki` 절차 K 2). 계획 중 **pjc 스킬 자체의 결함·마찰**을 발견하면 절차 K 5-1의 `[SKILL-IMPROVE]` 큐에 1줄 기록한다(vault 없으면 그 규약의 폴백).
  - **기록 의무 (면제 없음)**: **참조 결과는 plan.md Investigation Log에 기록한다** — 형식: `위키 참조: <페이지> — <핵심 결론 1줄>`(참조한 페이지별 1줄), 양방향 검색 후 무매칭이면 `위키 참조: 관련 위키 자료 없음 — 코드 1차 출처로 진행` 1줄. **건너뛴 경우에도 생략하지 않는다** — vault 미설정·설정 경로 부재·빈 위키 어느 사유든 **절차 K 1 기록 형식 3종 중 실제 확인 결과에 해당하는 하나**를 1줄 남긴다(형식 리터럴은 K 1이 정본 — 여기에 복제하지 않는다). 이 의무는 **위 전제(llm-wiki를 쓰는 세션)가 성립할 때만** 적용되므로 위키 기능을 쓰지 않는 프로젝트의 plan에 빈 기록이 강제되지는 않는다. 기록의 목적은 plan-reviewer·implement-task 재개 세션이 같은 근거를 재조회 없이 쓰게 하는 것이다.
- **독립 read-only 조사(위치·패턴 찾기)가 2개 이상이면 `explorer` subagent 병렬 위임을 기본으로 한다** (메인 컨텍스트 보호). 단일·소규모라도 메인 컨텍스트를 아껴야 하면 위임 가능.
  - **서로 독립적인 조사 질문이 여러 개면 explorer를 한 turn에 병렬 호출한다** (예: "DI 등록 위치" + "기존 테마 처리 방식" + "테스트 구조" → 3개 동시). read-only라 충돌이 없고 대기 시간만 줄어든다. Step 4(영향 범위 조사)에서도 동일 — 기능별 독립 조사는 병렬로. **단 Step 4 위임은 후보 위치 찾기(grep locating)까지만이다 — 사용처를 전수 Read해 영향을 판단·확정하는 일은 메인이 직접 한다(아래 품질 경계).** 위임은 **수신 확인 호출**이다 — 동시 실행이라 대기 시간이 주는 것이지 결과를 안 기다린다는 뜻이 아니며, 반환된 후보 위치를 받아야 다음 단계가 성립한다. 정본: `implement-task/references/recovery.md` 「Subagent 호출 규약」.
  - **위임 품질 경계**: 위임 대상은 "어디 있나 / 패턴이 무엇인가"(locating)뿐이다. "이 코드가 X를 하는가" 같은 **판단**과 **전체 파일을 읽어야 하는 작업**은 explorer(발췌만 읽음)에 맡기지 말고 메인이 직접 한다. 정확도가 품질에 직결되는 단계를 발췌-읽기에 떠넘기면 오판 위험. (토큰보다 품질·정확도 우선 — 병렬 위임은 latency만 줄이고 토큰은 늘므로, 무분별 위임이 아니라 "독립 locating"에 집중한다.)
  - **explorer 결과 취급 (후보 위치일 뿐)**: explorer가 반환한 위치·패턴은 **후보**다 — Investigation Log에 근거로 등재하기 전에 **메인이 그 파일을 직접 Read해 확인**한다. explorer는 발췌만 읽으므로 그 요약을 검증 없이 "확인된 사실"로 옮기면 환각이 스며들 수 있다. locating은 위임하되, 등재되는 근거는 메인이 직접 본 것이어야 한다(explorer는 조회 보조이지 사실 판정자가 아니다).
  - 단, 앞 결과가 다음 질문을 결정하는 **의존 조사는 순차로** (예: "DI 컨테이너 종류 확인" → 그 결과에 따라 "해당 컨테이너의 등록 패턴 조사").
  - **위임 상한 (과위임 방지)**: 위의 병렬 권장은 "독립 조사가 여러 개일 때"에 한한다. ① **병렬 상한** — 한 turn의 explorer는 서로 독립이고 **답을 각각 쓸 질문**만큼만 띄운다. 같은 질문을 여럿에 나눠 던져 교차 확인하려는 중복 위임은 확신을 주는 게 아니라 서로 다른 요약을 만들어 판단을 흐린다. ② **소작업 다중 위임 금지** — **읽을 대상이 이미 특정된** 조사(파일 한둘·grep 한 번)는 직접 한다. 위임의 이득은 "읽을 양이 커서 메인에 담기 부담스러울 때" 생기므로, 첫 불릿의 "메인 컨텍스트를 아껴야 하면 위임 가능"은 **대상 범위가 아직 넓어 읽을 양 자체가 큰 경우**를 가리킨다 — 대상이 두어 곳으로 좁혀진 뒤에는 직접 읽는 편이 싸고 정확하다. 판정 기준은 "왜 위임하는가"(자기 서술로 언제든 정당화된다)가 아니라 **"읽을 대상이 몇 곳으로 특정돼 있는가"**다. **단 축이 하나 더 있다 — 「읽을 양이 큰가」.** 대상이 **한 파일이어도 그 파일이 대형이면** 위임 이득이 있다(이 레포 실측: Deferred 대장은 분할 전 296KB였고 `README.md`는 57KB다 — 계획 1건마다 열리는데 메인이 통째로 담으면 그 자체가 후반 판단의 품질을 깎는다). 두 축은 **OR**다: 대상이 넓거나 읽을 양이 크면 위임 후보다. **어느 쪽이든 판정을 위임하는 것은 여전히 금지**이며(위 「위임 품질 경계」), 위임 금지 가드가 지목한 세 단계(P-2 Files 정독·P-3 caller 전수 추적·V-7 caller 재검증)는 **이 확장의 대상이 아니다** — 그쪽은 대상 크기와 무관하게 메인이 직접 한다. ③ **검증 목적 위임 금지** — Step 9의 `plan-reviewer`를 **제외한** "이 plan이 괜찮은지 봐 달라"식 위임은 하지 않는다. plan의 근거는 메인이 직접 읽어 확인한 것이어야 한다(위 「explorer 결과 취급」과 같은 이유).

### Step 1.5. Trivial 재판정 — 진입 후 off-ramp (컨텍스트 확인 직후)

plan-feature는 "여러 곳/여러 파일" 트리거로 발동되지만, **파일을 실제로 열기 전엔 그 여러 곳이 순수 값 치환(색상·치수)인지 구조 변경인지 알 수 없다.** Step 1에서 관련 파일을 확인한 결과 이 작업이 **Trivial Bypass 기준(특히 순수 값 치환 예외)에 실제로 부합**하면 — plan 작성을 시작하지 말고 직접 편집으로 되돌린다. 무거운 plan을 만들어 사용자에게 내놓는 순간 사용자는 그것을 정상 작업량으로 보고 승인하므로, **승인 게이트(Step 10)보다 앞에서 걸러야 한다.**

- **명백히 순수 값 치환 / 3기준 부합** → 한 줄 통지("확인해보니 색상 값 N곳 치환뿐이라 plan 없이 직접 수정합니다") 후 plan-feature를 종료하고 직접 Write/Edit으로 처리한다(Trivial Bypass 경로).
- **애매하면**(순수 치환 같지만 일부 구조 변화 의심) → 위 "애매한 경우 — plan을 강제하지 말고 질문" A/B 질문을 1회 하고 선택대로.

재판정은 **1회만**. 여기서 plan 진행으로 정하면 이후 단계에서 다시 되돌리지 않는다(판정 왕복 방지).

### Step 2.5. 시각 디자인 정합 명세 분해 (해당 시에만)

**발동 조건 (①-a 또는 ①-b 중 하나 + ② 를 충족할 때만)**:
- **①-a 시각 충실도 요청** — "디자인과 동일하게/똑같이 맞춰줘" 같이 **보이는 모습**을 기준에 맞추라는 요청.
- **①-b 화면 이식 요청** — "A 프로젝트와 동일하게 설정화면 만들어줘", "저 화면 똑같이", "그대로 옮겨줘", "같은 항목으로" 같이 **기준 UI 구현이 소스로 실재**하는 화면을 복제·이식하라는 요청. 시각 충실도를 명시하지 않아도 **표시 항목·문구·컨트롤이 같아야 한다는 요구**가 담겨 있다.
- **② 대조할 기준이 존재** — 디자인 HTML·이미지·Figma·기존 화면, 또는 **다른 프로젝트/모듈의 화면 소스**.

②가 없거나 ①-a·①-b 어느 쪽도 아니면 이 단계를 건너뛴다 (단순 UI 변경 "버튼 색 바꿔줘", 기준 없는 신규 화면은 발동 안 함 — 과잉 방지). **비UI 이식은 발동 대상이 아니다** — "A와 동일한 로직/API/설정 구조"처럼 화면이 아닌 대상의 복제는 이 단계가 다루지 않는다(인벤토리 표의 컬럼이 화면 요소 전제라 맞지 않는다. 그런 요청은 일반 task로 계획한다).

> **①-b(화면 이식)를 별도로 둔 이유는 `references/visual-decomposition.md` 「①-b(화면 이식)를 별도 발동 조건으로 둔 이유」에 있다** — 요지: 이식 요청은 "디자인을 맞춰달라"는 말이 없어 시각 충실도 요청으로 읽히지 않는데, 이 단계가 발동하지 않으면 `## 시각 요소 분해` 섹션이 없어 **V-9·F-8·spec 항목 I·plan-reviewer 항목 15가 모두 미발동**한다.

**수행 시 `references/visual-decomposition.md`를 읽고 그 절차(분해 전 기준 확보 · `### 시각 속성` 표 · `### 참조 정합 인벤토리` 표의 형식과 작성 규칙)를 그대로 따른다.** 산출 섹션의 표준 제목은 `## 시각 요소 분해`이며, 이식 요청이면 그 서두에 `**원본**: <절대 경로>` 1줄이 의무다(둘 다 상세는 그 파일).

#### 4-A. 심볼/타입 추적

> **먼저 "무엇을 셀지"를 확정한다 (대상 집합 전수 — 아래 grep보다 앞선다).** 이 절의 나머지는 *이름을 아는 심볼*의 사용처를 찾는데, **이름 자체가 빠지면 그 심볼은 원리상 찾을 수 없다**(아는 이름으로 grep하면 모르는 이름은 안 나온다 — 순환 검증). 이동·삭제·재타입이 있는 plan은 이 셋을 먼저 한다:
> - **① 대상 집합을 소스에서 열거**한다 — "옮길 함수 6개"를 기억이나 요약이 아니라 **파일에서 세어** 확정한다.
> - **② grep 스코프를 모듈 디렉터리로 좁히지 않는다** — 소비자는 대개 그 모듈 **밖**에 있다. 좁힐 거면 왜 그 밖에는 없는지를 근거로 적는다.
> - **③ 소유가 옮겨가는 심볼은 「심볼 → 실측 호출부 → 담당 task」 대응을 확정**한다 — 개별 지적을 점수정하면 다음 라운드에 다른 파일이 튀어나온다.
> - 세 축이 각각 어느 실패에서 나왔는지: `references/rationale.md` 「Step 4-A — 대상 집합을 먼저 세는 세 축이 생긴 사고」.
>
> **`plan-reviewer` 항목 3과의 경계**: 항목 3은 *"plan에 적힌 심볼의 호출자가 Files에 있는가"* 를 사후 검사하고, 이 축은 *"셀 대상 자체가 빠지지 않았는가"* 를 사전에 막는다 — 같은 누락을 두 번 지적하지 않는다.

- [ ] 심볼 참조 grep — **결과를 모두 Read로 열어 확인** (요약만으로 끝내기 금지. hit 30건 초과 시 절대 규칙 2의 읽기 비례 원칙 적용 — 판정 근거를 Investigation Log에)
  - **grep 스코프는 변경 대상 분기의 수만큼 세운다.** 변경 지점이 여러 분기·여러 문면이면 **그 각각의 고유 리터럴 전부로** 검색한다 — 일부 리터럴로만 돌리면 나머지 분기의 소비자가 통째로 빠지고, 그 상태에서 「전수 확인했다」는 문장이 산출물에 남는다. **분기를 Impact Analysis 표에 적는 것과 그 분기의 리터럴로 grep하는 것은 별개 행위이며, 앞을 했다고 뒤가 된 것으로 보지 않는다.** (v1.214.0 실측: 어느 hook의 출력 분기가 셋인데 두 리터럴로만 grep해 세 번째 분기의 골든 케이스를 놓쳤고, 계획 리뷰 1R·2R에서 **같은 축의 지적이 연속으로** 났다.)
- [ ] 인터페이스 변경 시 — 모든 **구현체 파일** 식별
- [ ] 메서드 시그니처 변경 시 — 모든 **호출자 파일** 식별
- [ ] 타입/필드 변경 시 — 모든 **참조 위치** 식별
- [ ] DI 등록·이벤트 핸들러·옵저버 — 등록부와 사용처 모두

#### 4-B. 계약·직렬화 변경
- 시그니처, 이벤트 페이로드, 직렬화 형식 변경 → 호환성 확인
- 마이그레이션 필요 시 별도 task

#### 4-C. 영향 받는 테스트
- 변경 대상을 직접 호출하는 테스트
- 변경 대상에 간접 의존하는 통합 테스트
- 테스트가 없으면 추가 필요성 검토 (plan에 task로)

#### 4-D. 재사용·중복 방지 조사
- [ ] plan이 도입하는 **각 신규 함수/클래스/컴포넌트**에 대해, 같은 일을 하는 기존 구현이 레포에 이미 있는지 grep(이름·핵심 동작 키워드)으로 검색한다 — 재사용/확장 가능하면 신규 작성 대신 **재사용을 task에 명시**한다 (모르고 만든 유사 구현이 중복 코드의 주원인).
- [ ] **UI 신규 요소**는 기존 공통 컴포넌트·스타일 자원(공용 스타일/템플릿/컨트롤)을 먼저 검색한다 — **재사용 우선, 없을 때만 신규**(신규 사유 한 줄). 확인 없이 중복 컴포넌트를 만들지 않는다.
- [ ] **최소 의존 원칙 — 신규 외부 패키지 도입 전 "직접 구현으로 되는가"를 먼저 따진다.** 플랫폼·표준 API나 직접 구현으로 합리적 노력 안에 가능하면 패키지 추가보다 우선하고, 신규 라이브러리를 고르면 그 사유(직접 구현 불가·비효율)를 Decisions의 **의존성** 항목에 근거로 남긴다. "이 작업의 표준이 패키지라서"는 근거가 아니다(상세·예는 `references/decision-points.md` 의존성 행 — 직접 구현 vs 신규 vs 재사용).
  - **순차 체크 순서**: ① 정말 필요한가(**필요 없으면 만들지 않는 것이 최선**) → ② 코드베이스에 이미 있는가(위 두 항목) → ③ 언어 **표준 라이브러리**로 되는가 → ④ **플랫폼·프레임워크 기본 기능**으로 되는가 → ⑤ **이미 설치된** 의존성으로 되는가 → ⑥ 그래도 없으면 **최소 구현**. 신규 패키지는 ⑥까지 와서야 후보가 된다. 위 원칙이 "직접 구현 vs 신규"라는 **결론**만 말하는 데 비해 이 순서는 그 사이의 ③④⑤(표준·플랫폼·기설치를 훑는 단계)를 채운다 — 실제 중복 도입은 대개 이 세 칸을 건너뛸 때 생긴다. (판단 상세·예는 위 포인터가 정본 — 여기 복제하지 않는다.)
- 검색 결과는 plan.md의 `### 4-D. 재사용 확인` 표(신규 심볼 | 검색어·스코프 | hit | 유사 기존 구현 검색 결과 | 재사용/신규 사유)에 기록한다 — **`검색어·스코프`·`hit`는 절대 규칙 2 「부재 판정」의 산출물**이라 실제로 돌린 검색어를 전부 적는다(그 열이 없으면 「없음」이라는 결론만 남아 `plan-reviewer` 항목 1이 반증할 대상이 없다). **신규 심볼이 없는 plan(기존 코드 수정만)은 "해당 없음" 한 줄로 충분**하다 (과잉 방지).

#### 4-E. 동반 변경 판정 (요청 밖이지만 함께 손봐야 할 것)

4-A~4-D가 **변경 대상 심볼의 사용처**를 본다면, 이 단계는 **"이 변경 때문에 무엇이 어긋나는가"**를 본다. 아래 **확인 축 5개**를 훑어 발견한 것을 3분류한다:

① 이 변경을 **서술하는 문서**(README·가이드·AGENTS.md) ② 같은 규약을 **복제한 다른 파일**(정본이 둘 이상인 지점) ③ 이 변경이 **입력이 되는 검증 자산**(테스트·eval·골든 픽스처·루브릭) ④ **버전·매니페스트**(릴리즈 규약이 있는 프로젝트) ⑤ 변경으로 **무효화되는 기존 기능·설정**.

> **③과 4-C의 경계** — 4-C는 *"변경 대상을 호출하는 테스트"*(그 코드가 깨지면 함께 깨지는 것)를 세고, ③은 *"이 변경을 입력으로 삼는 검증 자산"*(코드는 그대로여도 **기대값·픽스처가 낡는** 것 — 골든 케이스·루브릭·검사 축)을 센다. 같은 파일이 양쪽에 걸릴 수 있고 그건 정상이다 — **어느 쪽에 적을지 고민되면 4-C**(호출 관계가 더 좁고 확실한 판정이다).

> **이번 변경이 원인이 되어 어긋나는 것은 이 3분류의 대상이 아니다 — 언제나 필수다.** 대상은 `implement-task` **규칙 4-1**이 열거한 전부다 — **어긋난 문서·주석·규약**뿐 아니라 **회귀·깨진 호출부·무효화된 기존 동작**까지이며, 위 확인 축으로는 ③(검증 자산)·⑤(무효화되는 기존 기능)이 이번 변경으로 깨지는 경우가 여기 해당한다(같은 규칙이 이연을 막고, 주석은 **규칙 7-1**이 고치는 방법까지 정한다). *"없어도 성립하지만 불일치가 남는다"*는 **선택**의 정의에 형식상 부합해 보여도 선택지가 될 수 없고, **사용자에게 묻지 않는다** — 물어서 "빼자"는 답이 나오면 그 순간 규칙 4-1을 어긴 plan이 승인된다.
>
> **3분류가 다루는 것은 「자기 유발이 아닌」 동반 변경이다** — 이번 변경 이전부터 어긋나 있던 것, 스코프가 다른 산출물, 품질 자산의 미반영 같은 것들. 원인이 이번 변경인지 아닌지가 갈림선이며, **애매하면 자기 유발로 본다**(규칙 4-1의 같은 판정).
>
> **적용 범위는 이번 diff가 건드린 것에 딸린 서술**이다. 손대지 않은 파일의 낡은 주석·문서까지 필수로 삼으면 범위가 폭발하므로, 그 소급 정리는 종전대로 3분류(대개 **선택**)를 따른다.

| 구분 | 정의 | 처리 |
|---|---|---|
| **필수** | 이 변경 없이는 요청이 **성립·정합하지 않는다**(문서가 실제와 어긋남·규약 정본이 갈림·검증 자산이 깨짐) | **task로 편입**한다. 절대 규칙 6의 "범위 밖"이 아니다 |
| **선택** | 없어도 성립하지만 **불일치·부채가 남는다**(품질 자산 미반영·기존 초과분 심화 등) | **Step 8에서 개별 항목으로 질문**한다(임의 편입도, 조용한 생략도 금지) |
| **무관** | 이 변경과 닿지 않는다 | 건드리지 않되 **판정 근거 1줄**을 남긴다 |

- 결과는 plan.md의 **`## 동반 변경 판정`** 섹션에 표로 기록한다(형식은 `references/plan-template.md`). **판정 대상이 없으면 `- 해당 없음 — <확인한 축 1줄>`** 로 충분하다(과잉 방지).
- **적용 범위: Type C/D task가 있는 plan.** 문서 오타·trivial 수정만으로 이뤄진 plan(Type A/B만)에는 이 판정을 요구하지 않는다 — 통과 체크리스트·`plan-reviewer` 항목 16의 적용 범위도 같다(**셋이 어긋나면 저자 의무와 검사 범위가 갈려 사각이 생긴다**).
- **필수를 발견하고도 task에 넣지 않는 것이 이 단계가 막으려는 결함이다** — 그 경우 구현은 "계획대로" 끝나지만 산출물은 어긋난 채 남고, 사용자는 완료 보고에서야 그 사실을 듣는다.

#### Halt 조건
- 사용처 추적이 단순 grep 카운트만으로 끝남 (실제 파일 Read 안 함)
- "기타 영향 있을 수 있음" 같은 모호한 표현
- 변경 대상이 인터페이스인데 구현체 식별이 누락됨
- plan이 신규 심볼을 도입하는데 유사 기존 구현 검색 기록(4-D)이 없음

### Step 5. 작업 분해

- 각 작업은 **독립 검증 가능 + 주 파일 5개 이내** 규모를 기준으로 나눈다(시간이 아니라 구조로 판단 — LLM 실행은 벽시계 시간이 일정치 않으므로 "몇 시간"보다 "독립 검증되는가·주 파일 몇 개인가"가 실질 기준이다). 주 파일이 5개를 크게 넘거나 독립 검증이 안 되면 task를 쪼갠다.
- **각 task는 `T1`, `T2`, ... 형식으로 번호를 매긴다.** "Phase 1", "단계 1", "Step 1" 등 다른 명칭으로 작업을 나누지 않는다 — implement-task의 자율 루프가 `T<N>` 형식을 전제하며, "Phase"는 pjc 내부 단계(Phase P/I/V/D·F·G)와 혼동된다. 작업을 큰 묶음으로 그룹화하고 싶으면 task 번호는 유지한 채 주석으로만 묶는다 (예: `T1~T3 (데이터 계층)`).
- 각 작업마다 acceptance criterion 1줄 명시
- **의존 관계 표시 — 순서 의존만이 아니라 「전제 의존」까지 적는다.** ⓐ *이 task가 앞 task의 산출물을 전제하는가*(전제 의존) ⓑ *이 task의 변경이 뒤 task의 Files·acceptance를 무효화하는가*(역방향)를 함께 본다. **같은 자원을 여러 task가 갱신하면 그 사슬을 적는다** — 계수 앵커·기준선 표·버전 문자열처럼 **절대값을 기록하는 자리**는 각 task가 「자기 몫만」 반영해야 하는데, 어느 task가 어느 값에서 시작하는지 적지 않으면 이중 가산이나 덮어쓰기가 난다. (짝은 `plan-reviewer` **항목 18**이다 — 그쪽이 사후 검사하고 여기가 사전 기재한다.)
- **각 task에 Type 분류 명시 (의무)** — implement-task가 fast-path 결정에 사용

#### Task Type 분류 (필수)

| Type | 정의 |
|---|---|
| **A** (Doc/Config) | `.md`, `.json`, `.yml`, `.csproj`, `.editorconfig` 등 코드 외 파일만. **단 동작을 바꾸는 Config는 Type A 아님** — DI 배선·기능 플래그 기본값·라우팅·빌드 산출에 영향 주는 설정은 런타임 동작을 바꾸므로 **Type B 이상**으로 본다(순수 문서·주석·비동작 설정만 A). Type A는 적대적 리뷰(V-5/V-6)를 건너뛰므로 동작 변경이 A로 숨으면 무검증 통과된다. |
| **B** (Trivial Code) | 단일 코드 파일, 단일 메서드/필드, **호출자 변경 없음**. 기존 코드의 값·문자열·주석 수정, 자명한 접근자(getter/setter)·상수·순수 위임 수준 (typo, 주석). **단 비자명 로직·알고리즘·제어흐름·상태 변경을 담은 신규 심볼(함수/메서드/클래스) 추가는 파일이 하나여도 Type C 이상** — Type B는 V-5가 prefilter(Haiku)만, V-3·V-6을 생략하므로 검토가 필요한 신규 로직이 B로 새면 무검증 통과된다. |
| **C** (Normal Code) | 단일 또는 2-3개 파일, caller 갱신 있음 |
| **D** (Complex/Cross-cutting) | 다중 파일, 인터페이스 변경, 시그니처 변경, 직렬화 변경, DDD/아키텍처 영향 |

> Type이 결정하는 **적용 Phase V 단계 매핑은 implement-task Fast-Path 표가 정본** — plan은 Type 분류만 명시하고 V-단계 선택은 implement-task 소관이다.

확실하지 않으면 **한 단계 더 무거운 쪽 선택** (안전 우선).

**Type C/D의 V-6(code-quality)는 항상 실행된다** — plan이 별도 표기를 붙일 필요 없다(적용 Phase V 단계는 implement-task Fast-Path 표가 정본. 이 기본값이 된 경위는 `references/rationale.md`).

#### Design 필드 (Type D 필수 · Type C는 신규 심볼 도입 시)

Type D task 전부와 **신규 심볼(함수/클래스/컴포넌트)을 도입하는 Type C task**는 task에 `**Design**:` 필드로 구조 명세를 확정한다(대상 판정은 4-D 재사용 확인과 동일 기준 — 4-D 표에 신규 심볼이 있으면 대상. Type A/B는 비대상 — 과잉 방지). 4요소를 1~4줄로 자유 서술: ① **배치**(어느 파일/레이어에 두는가) ② **신규 심볼과 책임**(이름 — 책임 1줄) ③ **의존 방향**(무엇을 참조하고 무엇이 참조하는가) ④ **비추상화 선언**(이번에 추상화하지 *않을* 것 — YAGNI 앵커). 설계가 계획에 없으면 구현자가 그때그때 편한 구조를 택하고 사후 리뷰(V-6)는 완성된 코드를 뒤집지 못한다 — "계획 단계에서 확정하는 것이 가장 싸다"(decision-points.md와 동일 원리).
- **Decisions '위치' 카테고리와의 역할 구분**: Decisions '위치' = **갈림길일 때의 선택 기록**(Options/Chosen), Design = **task별 구조 명세의 확정 기록**(갈림길이 아니어도 명시). 겹치면 Design이 `(D<N> 참조)`로 중복 서술을 피한다.
- 신규 심볼 없는 Type D는 "해당 없음 — <근거 1줄>"로 적는다(무근거 공백·placeholder는 plan-reviewer 항목 14가 MAJOR로 검출).

**PRD 복귀 게이트**: 분해 결과 task가 **10개 이상**인데 plan에 PRD 연결(`**PRD**:` 줄)이 없으면 — Step 0.5의 판정이 추정(예상 task 수) 기준이라 실분해와 어긋난 경우다 — Step 0.5로 돌아가 PRD를 먼저 작성한 뒤 계속한다(대규모 안전망(Phase G 재검증) 상실 방지).

#### task가 많은 plan — 회차 분리 안내 (컨텍스트 관리)

**plan은 언제나 루트 `plan.md` 하나다 — 파일을 나누지 않는다.** task가 **12개를 초과**하면 선택지를 안내한다. **제시 문안·회차 분리 규약은 `references/plan-template.md` 「(plan-feature Step 5) task가 많은 plan — 회차 분리 안내」가 정본**이다.

- **기본값은 A(그대로 진행)** 다 — 단일 plan은 Progress Log + Phase Ledger + git log로 압축을 통과한다.
- **B(회차 분리)가 유리한 경우는 앞 결과가 뒤 설계를 바꿀 여지가 있을 때**다. 이번 plan은 앞부분만 담고 뒤는 `## Deferred / Follow-up`으로 미룬 뒤, **그 회차를 끝내 커밋하고 나서 다음 plan을 새로 쓴다** — 그래야 다음 계획이 앞 회차의 실제 결과를 반영한다.

### Step 6. Decision Points 발굴

각 task에 대해 결정 분기를 사전 해결.

**Type별 적용 범위 + 카테고리 12개 + 기록 형식은 `references/decision-points.md` 정본 참조** (요지: Type A skip / B 1-2개 / C 5-6개 + 보안·자격증명(해당 시) / D 12개 전체). **보안·자격증명**은 Type C/D가 **인증·자격증명·외부 접근**을 다룰 때 발동한다 — 시드 계정 유무·강제 변경, 자격증명 보관처(문서에 값 금지), 계정 잠금·시도 제한을 계획 단계에서 확정한다.

### Step 6.5. Edge Case & Halt Forecast (자율 실행 대비)

`implement-task`가 사용자 개입 없이 끝까지 가야 하므로, 구현 중 발생 가능한 멈춤 지점을 사전 예측.

**Type별 적용 범위 + 상세 카테고리 + Halt Forecast + 자율 실행 준비도 자문은 `references/edge-cases.md` 정본 참조** (요지: Type A skip / B 빈·null+경계값 / C 5-6개 / D 10개 전체).

**Halt Forecast ↔ Decision 역매핑 (자율 루프 중단 예방).** 예측한 각 Halt Forecast 항목은 **(i) 사전 해소**(Step 6 Decision·Step 8 Open Question) / **(ii-a) 사전 승인 가능**(`## 사전 승인 항목`에 등록 — 비파괴 의존성/구조/스키마·계획된 공개 API 변경, plan 승인 시 일괄 위임 — "우회"가 아닌 명시적 일괄 승인) / **(ii-b) 위임 불가 Halt**(`## 불가피한 Halt (위임 불가)`) / **(ii-c) 완료 후 일괄 승인**(승인은 필요하나 **그 작업 없이 acceptance가 충족**되는 부수 작업 — 루프가 미루고 최종 보고가 모아 승인받는다) 중 하나로 분류한다. **4분류 정의·파괴적 예시 목록은 `references/edge-cases.md` 6.5-B 정본.**

**(ii-c)는 plan에 등재처를 두지 않는다** — (ii-a)는 `## 사전 승인 항목`, (ii-b)는 `## 불가피한 Halt`에 등재되지만 (ii-c)는 **승인을 구현 후에 받으므로 plan 승인 시점에 목록이 필요 없다**(등재처는 구현 중의 `## Progress Log`). Halt Forecast 안에 그 분류로 적는 것으로 끝이며, 사전 승인 항목에 넣으면 받지 않아도 될 승인을 미리 받게 된다.

**파괴적 작업은 (ii-a)·(ii-c) 어느 쪽에도 절대 넣지 않는다 — 항상 (ii-b)(안전 게이트).** 둘 다(i/ii) 아닌 예측 halt는 추측을 유발하므로 plan을 보강해 (i)로 해소한다. (ii-b) 위임 불가 항목을 사전결정으로 우회해 자동 실행으로 바꾸지 않는다 — 회피 가능한 중단(결정 누락)만 제거.

**확인 이연 금지 (성립을 좌우하는 확인).** 예측 halt를 (i)로 해소할 때 "구현 첫 단계에서 확인"은 해소가 아니다 — 그 확인이 **설계·acceptance의 성립 여부를 좌우**하면(부정될 경우 task 자체가 성립 불가) 계획 단계에서 Investigation Log로 확인을 **완료**해야 한다(plan-reviewer 항목 9가 BLOCKER로 검출). 결과가 진행 방식만 바꾸는 확인의 이연은 정상.

### Step 7. plan.md 작성

**위치는 `<repo>/plan.md` 하나다**(덮어쓰기) — 레포 크기·`AGENTS.md` 선언과 무관하며 판정할 것이 없다. `docs/plans/`에는 plan을 두지 않는다(그 디렉터리는 Deferred 대장 3파일 전용이고, hook의 plan 존재 판정도 루트 `plan.md`만 본다).

**`## Investigation Log` 하위의 `### 전제 검증` 표를 채운다** (Type C/D task가 있는 plan은 의무 — 형식은 `references/plan-template.md`). 이 plan의 설계·acceptance가 **참으로 삼는 사실**을 뽑아 확인 근거와 짝짓는다(반증 근거의 한 소스가 Step 1 대장 ② 읽기다). Investigation Log는 "확인한 것"만 적어 **확인하지 않고 전제로 삼은 것이 문서에 아예 나타나지 않는데**, 그 공백이 구현 중 *"계획이 잘못됐다"*며 루프가 서는 주된 원인이다. 확인하지 못한 전제는 지우지 말고 `⚠ 미확인`으로 남기고, **성립을 좌우하는 것**(부정되면 task 자체가 성립 불가)은 `## Open Questions`로 올려 승인 전에 해소한다(Step 6.5 「확인 이연 금지」와 같은 축).

**규모 수치에는 「실측」/「추정」 라벨을 붙인다.** 대상은 **acceptance와 작업 대상 규모에 쓰이는 수치**다(대상 건수·항목 수·파일 수). 설명용 인용 수치에는 요구하지 않는다 — 모든 숫자에 라벨을 달게 하면 과잉이다.
- **「추정」에는 그것을 확정하는 task를 함께 지목한다.** 지목 없는 추정은 라벨이 면죄부가 된다 — `plan-reviewer` 항목 7이 그것을 지적한다.
- **왜 필요한가**: 라벨은 **어느 값이 아직 확정되지 않았는지**를 승인 시점에 드러낸다 — 확정되지 않은 수치를 확정처럼 적으면 구현 중에 *"계획이 잘못됐다"*며 루프가 선다(그렇게 plan이 8회 수정된 회차: `references/rationale.md` 「Step 7 — 규모 수치에 실측/추정 라벨을 붙이는 이유」).
- 라벨은 **값 옆 괄호**로 최소 침습으로 단다 — `38건(실측)` · `약 60건(추정 — T1이 확정)`.

**`## 요구 이해`를 반드시 채운다** (원문 요청 인용 + 이해한 요구 3~5줄 — 형식·작성 규칙은 `references/plan-template.md` 정본). 승인 게이트를 통과한 요구 오해는 이후 어느 리뷰도 잡지 못하므로(구현 후 plan-completion-reviewer 항목 2.5가 요구 이해 ↔ 산출물 **커버**는 사후 대조하지만, 이해 자체의 옳음은 사용자만 판정), 이 섹션이 Step 10 승인 프롬프트 첫 항목으로 노출되어 사용자가 오해를 승인 전에 발견하는 장치다.

> **plan 작성은 이 스킬 경유가 정본이다 — 스킬 없이 손으로 쓰지 않는다** (`require-plan-for-write` hook이 기계 강제). 직접 Write하면 Step 1~9의 자산이 통째로 우회되고, 그렇게 만든 plan이 `require-plan`의 "plan 있음" 판정을 켜서 **이후 모든 코드 변경이 무검증 통과**한다(경위·우회되는 자산 목록은 `references/rationale.md` 「plan 작성 게이트」). hook은 plan 파일 Write와 **체크박스를 새로 도입하는 Edit**을 이 스킬(또는 `implement-task`) 발동 흔적 없이는 차단한다. **기존 plan의 부분 갱신(체크박스 `[ ]`→`[x]`, Progress Log·Retry Ledger·Deferred append)은 게이트 대상이 아니므로** implement-task의 정상 갱신은 그대로 진행된다.

**상세 plan.md 템플릿은 `references/plan-template.md` 참조.**

### Step 7.5. PRD 커버리지 확인 (PRD 있을 때만)

PRD가 있으면 (Step 0.5에서 새로 작성했거나 Step 1에서 기존 PRD를 연결한 경우), plan이 PRD를 빠짐없이 반영하는지 **구현 전에** 확인한다. 여기서 일치시키면 Phase G(구현 후 재검증)에서 누락이 발견돼 재구현하는 비용을 막는다. (소규모 연결 plan도 이 표를 채운다 — Step 1에서 정한 커버 대상·범위 외 구분을 그대로 기록.)


**매핑표 작성·일치 판정 규칙은 `references/prd-template.md` 「(plan-feature Step 7.5) PRD 커버리지 확인 절차」가 정본**이다. 판정선:
- 결과는 plan.md `## PRD Coverage` 표로 남긴다(Phase G가 이 표를 기준으로 재대조).
- **커버 대상으로 선언한 Must FR에 대응 task가 없으면 누락**이다 — task를 추가해 일치시킨 뒤에만 구현에 들어간다.
- **소규모 연결 plan**은 이번에 닿지 않은 active Must FR을 `이번 범위 외 (기구현/후속)`로 명시하고 대조에서 제외한다. **대규모 신규 작업은 이 제외를 쓰지 않고 전수 커버**한다.
- Should/Could를 빼려면 **명시적 제외 사유**를 적는다(암묵 누락과 구분).

### Step 8. Open Questions 해결 — 일괄·완전 모드

질문이 있으면 **여기서** 사용자에게 묶어 질문하고, 답변을 plan.md에 반영한다. (리뷰 게이트(Step 9)보다 먼저 — plan-reviewer는 미해결 Open Questions를 BLOCKER로 보므로, 질문을 먼저 해소한 뒤 리뷰해야 한다.) **답변을 반영한 질문은 `## Open Questions`에서 `[x]`로 바꾸고, 답 요약과 함께 ★이 어느 선택지였는지·그 판정(〔근본〕/〔우회〕)·사용자가 무엇을 골랐는지를 병기한다** — `[ ]`로 남기면 plan-reviewer(항목 6)가 미해결로 오판하고, ★ 기록을 지우면 항목 2가 검사할 대상이 사라진다(미해결 질문만 `[ ]`로 남긴다).

#### 질문 형식 (카테고리별 묶음)

질문이 많아도 영역별로 그룹핑하여 가독성 확보. 개수 제한 없음.

```markdown
## Open Questions

이 plan에 N개 결정이 필요합니다. 카테고리별로 정리했습니다.

### [명명] (3)

Q1. UserService 클래스 이름?
  A) ★ UserService (현재 컨벤션과 일치, src/Application/Services 패턴)
  B) UserManager
  C) AccountService

Q2. ...

### [에러 처리] (4)

Q4. 검증 실패 처리 방식?
  A) ★ Result<T> 패턴 (AGENTS.md 명시, 프로젝트 일관성)
  B) 예외 throw
  C) null 반환

Q5. ...

### [테스트 전략] (2)
...

### [UI 동작] (3)
...
```

#### 원칙

- **각 선택지에 Claude 추천 ★** — 사용자가 그대로 동의하면 빠른 결정, 다른 선택을 원하면 명확한 비교 기준 제공.
- **추천 근거**를 한 줄로 명시 (AGENTS.md / 코드 컨벤션 / 영향 분석 등).
- **추천(★) 기준 — 근본 해결 우선**: ★은 "가장 쉽게·빨리 끝나는 선택지"가 아니라 **문제를 근본적으로 해결하는 선택지**에 준다(절대 규칙 3 "근본 해결"과 정합 — 증상 우회·임시방편은 구현이 간단해도 추천하지 않는다). 구현이 다소 복잡해도 근본 해결안이 있으면 그것을 추천하고, 복잡도·작업량 차이는 추천 근거에 트레이드오프로 함께 명시해 사용자가 비교할 수 있게 한다(예: "★ B — 근본 해결(원인 제거), 단 파일 3개 수정 / A는 1줄이지만 증상 우회라 재발 여지"). 단 **단순함 자체가 근본 해결인 경우**(YAGNI — 불필요한 구조 제거·과설계 회피)는 그 단순안이 곧 근본 해결안이다 — 복잡한 안을 기계적으로 선호하라는 뜻이 아니다.
  - **판정을 선택지마다 라벨로 적는다 (검사 가능하게).** 각 선택지 끝에 〔**근본**〕/〔**우회**〕를 근거 1구와 함께 붙이고 ★은 〔근본〕에 준다. **라벨이 없으면 그 추천이 근본 해결이라 붙은 것인지 간단해서 붙은 것인지 산출물에서 구분되지 않는다** — 이 규약은 정본·README·위키 3곳에 있었는데도 지켜지지 않았고, 빠진 것은 규약이 아니라 **판정을 남기는 자리**였다(`plan-reviewer` 항목 2가 이 라벨을 검사한다). **범위 선택**(D2 자유 조합)은 근본/우회 축이 성립하지 않아 대상이 아니다.
- **질문 유형에 맞는 선택지 형식을 쓴다 (중요)**:
  - **택1 질문**(명명·에러 처리·패턴 선택 등 서로 배타적): A/B/C 중 하나를 고르는 형식.
  - **범위·대상 질문**(여러 항목 중 무엇을 포함할지): 고정 조합(a만/a+b/모두)만 제시하면 원하는 조합(a+c 등)이 없어 막힌다 — **개별 항목을 나열하고 자유 조합·선택**하게 한다(각 항목 영향·근거 한 줄 + 추천 조합 ★). "원하는 것만 지정 가능(예: 'a와 c만')"과 **"하나도 적용 안 함"도 항상 유효**를 명시한다(이번 요청은 별도 진행되므로 확장 전부 거절도 막히지 않음). 기록 형식은 `references/decision-points.md` D2(자유 조합) 정본.
- **선택 동반 변경(4-E)은 개별 항목으로 묻는다** — `references/decision-points.md` D2(자유 조합) 형식으로 항목별 영향·근거 1줄과 함께 나열하고, **"하나도 채택하지 않음"도 항상 유효**임을 명시한다(요청 자체는 별도로 진행되므로 전부 거절해도 막히지 않는다). 묶음 선택지로만 제시해 원하는 조합을 못 고르게 하지 않는다.
- **라운드 반복 가능** (통상 3-5 이내). **5 라운드 초과면 plan 자체가 너무 모호** → 사용자에게 작업 범위 재확인 권고. (라운드·"답변 시간 < 재작업 시간" 원칙은 절대 규칙 4.)

#### 질문 도구 사용 규약 (`AskUserQuestion`)

위 형식은 마크다운 나열을 전제하지만 실제로는 **`AskUserQuestion` 도구**로 묻는 경우가 많고, 그 도구에는 **질문 4개·옵션 4개 상한**이 있다. **네 규약(ⓐ~ⓓ)의 상세는 `references/decision-points.md` 「(plan-feature Step 8) 질문 도구 사용 규약 (`AskUserQuestion`)」이 정본**이다. 요지:
- **ⓐ 요구 원문 선택지 의무 (가장 중요)** — 사용자가 방향을 지정했으면 **그 안을 반드시 첫 선택지로** 넣는다. 대안만 나열하고 원문 안을 빠뜨리는 것은 선택지 제시가 아니라 **요구 변조**다(문제가 있다고 판단되면 빼는 대신 남기고 설명에 트레이드오프를 적는다).
- **ⓑ 옵션 상한에 굴복하지 않는다** — 먼저 성립하는 안을 빠짐없이 발굴하고 그 다음에 형식을 정한다. 5개 이상이면 도구로 자르지 말고 마크다운으로 전량 제시한다.
- **ⓒ 근본 해결안을 첫 옵션에** — 임시방편만으로 선택지를 채우지 않는다(절대 규칙 3).
- **ⓓ 옵션마다 설명 의무** — 무엇이 달라지는가 + 비용/트레이드오프. 라벨만 보고 고르게 하는 것은 선택지를 준 것이 아니다.

### Step 9. 리뷰 게이트 (subagent 필수)

Open Questions가 모두 해소돼 plan이 완성된 뒤 검토한다. **`plan-reviewer` subagent 호출.** 자체 검토 금지 (예외 2종은 아래 — 도구 불가 / Type A·B). **수신 확인 호출**(규약 정본은 `implement-task`의 `references/recovery.md` 「Subagent 호출 규약」) — 검토 결과를 받아 판정한 뒤에만 Step 10으로 간다(아래 재호출·대체 실행도 같다).
- **호출 프롬프트 끝에 판정문 요구를 1줄 붙인다**: *"조사를 마치면 반드시 판정문(Verdict + 지적)을 출력할 것 — 조사 서술만으로 끝내지 말 것."* **이 요구의 근거·수치·리뷰어측 규약의 정본은 `plan-reviewer.md`의 「실행 예산 (검토 전에 먼저 읽는다)」 절**이다(예산 자기인지·조기 골격·사용량 계측 3종). 여기서 한 번 더 주는 이유는 **호출 시점 주입이 정의 파일 하단보다 상기율이 높기** 때문이며, 아래 **D 분기**는 사후 회수라 이 예방과 서로를 대체하지 않는다.
  - **같은 요구가 `implement-task` V-5에도 있다 — 한쪽만 고치지 말 것.** 두 스킬은 서로를 로드하지 않으므로 포인터만 두면 호출 시점에 문구가 손에 없어, 같은 문장을 양쪽에 둔다(리뷰어 4종 각주와 같은 구조 — `docs/harness-conventions.md` 「리뷰어 4종 공통 규약」).
- **호출 프롬프트 끝에 조사 산출물 위치를 1줄 붙인다**: *"조사 산출물(임시 파일·중간 결과)은 레포가 아니라 시스템 임시 폴더에 만들 것."* `plan-reviewer`는 `tools`에 Bash가 없어 위험이 낮지만, **네 호출 지점의 문면을 같게 두는 편이 드리프트를 막는다**(리뷰어 4종 각주와 같은 구조). 근거·실사고는 `implement-task/SKILL.md` V-5의 같은 항목.
- **호출 프롬프트 끝에 러너 직접 실행 금지를 1줄 붙인다**: *"메인이 돌리는 러너·무거운 검증 명령을 직접 실행하지 말 것 — 정적 읽기와 가벼운 grep만 쓸 것."* **금지 대상을 이름으로 적는다**(예: `run-hook-evals.ps1`) — "무거운 것"이라고만 쓰면 리뷰어가 자기 판단으로 돌린다. 바로 위 조사 산출물 항목과 **축이 다르다** — 그쪽은 *레포를 더럽히는* 쓰기를 막고 이쪽은 *메인 실행과 자원을 다투는* 실행을 막는다(리뷰어 2종과 메인이 같은 러너를 겹쳐 돌려 세 실행이 모두 정체한 실사고: `implement-task/SKILL.md` V-5의 같은 항목). **`plan-reviewer`는 `tools`에 Bash가 없어 실효 위험이 낮고 이 1줄은 문면 정합이 목적이다** — V-5·V-6·`spec-prefilter`가 주입하는 네 축(판정문·Bash 쓰기 금지·조사 산출물 위치·러너 금지) 중 이 자리에만 없던 비대칭을 메운다(Bash 쓰기 금지 축은 도구가 없어 대상이 아니다).
- **예외 (도구 사용 불가)**: subagent 호출이 **물리적으로 불가**한 환경이면(도구 미제공·즉시 거부·환경상 실행 불가) `implement-task`의 `references/recovery.md` 「Reviewer 호출 실패 대응 (과부하·도구 불가·거절·빈 응답) — 모든 subagent 호출 공통」 **B 분기**를 따른다 — `plan-reviewer.md`의 판정 항목을 체크리스트로 대조 + 의무 3종. **이 예외는 아래 Type A/B 대체와 축이 다르다** — 아래는 **task 등급**에 따른 면제(Type C/D면 대체 불가)이고 이것은 **도구 가용성**에 따른 것이라 Type C/D에서도 적용된다(그렇게 읽지 않으면 plan이 영원히 통과할 수 없다). 발동 조건이 애매하면 예외를 쓰지 말고 사용자에게 묻는다. **정상 응답으로 검토를 거절한 경우는 이 예외가 아니라 C 분기**다. **세션 정책이 "사용자 요청 없는 에이전트 호출"을 금지하는 상황도 이 예외가 아니다** — 이 스킬 발동이 곧 Step 9 리뷰 호출 요청이므로 묻지도 강등하지도 않고 정상 호출한다.
- **예외 (Type A/B만으로 구성된 plan)**: plan의 모든 task가 Type A(Doc/Config) 또는 B(Trivial Code)뿐이면 — 적대적 plan-reviewer(Opus) 대신 **메인이 자체 체크리스트 검토로 대체**할 수 있다(문서 끝 `## 통과 체크리스트`를 메인이 직접 대조). Type A/B는 cross-file·시그니처 변경이 없어 plan-reviewer의 핵심 항목(3 Impact·9 Autonomous)이 얕게 적용되므로, Opus 호출 비용이 검증 가치를 넘는다. **단 Type C/D가 하나라도 있으면 plan-reviewer 필수**(대체 불가). 자체 검토로 대체한 경우 그 사실을 사용자 승인 프롬프트에 1줄 명시한다.
  - **Type 선언의 근거 대조는 대체 불가다 (순환 차단 — 대체를 택하기 *전에* 한다).** 이 예외는 *"모든 task가 A/B다"* 라는 **plan 자신의 선언**을 발동 조건으로 쓰는데, **그 선언이 맞는지 검사하는 것이 바로 생략되는 `plan-reviewer`**다(A/B라서 리뷰를 빼고 → 그래서 A/B가 맞는지 아무도 안 본다). 그래서 대체를 택하려면 메인이 **선언의 근거를 먼저 대조**한다 — 판정 기준은 `plan-reviewer.md`의 **「Type A 오분류 검출 (declared Type 무관 상시 적용)」**(A 축)과 그 절의 **Type B 오분류 불릿**(B 축) 둘이며, **기준의 정본은 그 파일이므로 대조 시 그 두 자리를 직접 읽는다**(여기 재서술하지 않는다 — 두 곳에 적으면 갈린다. 요약조차 두지 않는 것은 실제로 그 요약이 정본과 어긋난 채 커밋될 뻔했기 때문이다).
  - **하나라도 걸리면 그 task를 재분류하고 `plan-reviewer`를 정상 호출한다**(재분류 결과 C/D가 생기므로 위 "대체 불가"가 그대로 적용된다). 걸리는 것이 없으면 그 **대조 결과를 plan에 1줄 남기고** 자체 검토로 진행한다 — 기록이 없으면 *"대조했더니 없었다"* 와 *"대조하지 않았다"* 가 구분되지 않는다.
  - **이것은 리뷰어 호출이 아니라 근거 확인 1회다** — 예외의 비용 근거(Opus 호출 절감)를 무너뜨리지 않는다.
- 결과가 BLOCKER 또는 MAJOR면 plan 수정 후 재호출 (**최대 2회**). 3회에서 2회로 줄인 근거는 `references/rationale.md` 「재호출 상한」 — 요지는 **그 구간의 수정이 새 결함을 만든다**는 것이다. **재호출 시 이전 라운드 이력을 `| 라운드 | 지적 | 심각도 | 반영 방식 |` 4열 표로 전달한다** — `plan-reviewer`의 「재리뷰 규약」이 이 표를 전제하며, 없으면 리뷰어가 이전 판정을 알 수 없어 **같은 지점이 라운드마다 뒤집히는 진동**이 생긴다. 반환된 `### CONFLICT` 섹션(이전 지적과 상충한다는 보고)은 **Verdict가 OK여도 통과로 보지 않고** 메인이 채택/유지를 판정한 뒤에만 Step 10으로 간다(같은 지점 2회면 사용자 판단을 받는다).
- **plan을 고치기 전에 고칠 자리를 먼저 센다 — 지목된 자리부터 손대지 않는다.** 지목된 자리만 고치면 다음 라운드에 나머지가 그대로 돌아온다. 발동 조건·절차·기록 형식은 `implement-task`의 `references/recovery.md` 「리뷰 결과 처리」 정본이며 **여기 복제하지 않는다**.
- **incomplete·미검증 잔여분은 통과가 아니다.** plan-reviewer 결과에 `incomplete`(turn 소진), "심볼 N개 미검증"(항목 3 grep 상한), "항목 미검토"(항목 우선순위) 표시가 있으면 — **BLOCKER/MAJOR가 0이어도 그 리뷰를 통과(OK)로 보지 않는다.** 메인이 잔여분을 직접 검증하거나(미검증 심볼은 grep으로 호출자를 직접 대조, 미검토 항목은 그 항목의 판정 기준을 체크리스트로 직접 대조해 결과를 남김) plan-reviewer를 재호출해 나머지를 마저 검토한 뒤에만 통과한다. 잔여분을 조용히 흘려보내고 Step 10으로 넘어가는 것은 금지 — reviewer가 정직하게 보고한 미검증분을 소비하지 않으면 보고 의무가 무의미해진다(implement-task V-5의 incomplete 처리와 동일 원칙). 단 위 Type A/B 자체 검토 대체 경로는 메인이 체크리스트 전 항목을 완주하므로 이 규정의 대상이 아니다.
- **2회 후에도 BLOCKER/MAJOR가 잔존하면 → 사용자에게 에스컬레이션**(**2라운드에도 동일 지적이 잔존하는지 메인이 판정**한다. `plan-reviewer`의 RECURRING 임계도 **2회 연속**으로 함께 내렸으므로(`plan-reviewer.md`의 「행동 원칙」 중 *"재호출 인지"* 불릿 — 라인 번호로 가리키지 않는다, 파일이 자라면 조용히 어긋난다) 그 표시가 오면 그대로 인용하되, **표시 유무와 무관하게 2회 잔존이면 에스컬레이션한다** — 판정 주체는 메인이고 리뷰어 표시는 보조 근거다. 임계를 함께 내리지 않았다면 3회 연속 기준의 RECURRING이 **영원히 도달 불가**가 되어 이 경로가 죽었을 것이다): 무엇이 왜 2라운드 연속 잔존했는지 + 선택지(수정 방향 승인 / 범위 축소 / 직접 지침)를 제시하고 지시를 기다린다. **자동 통과·무한 재시도 금지** — plan을 통과시키지 못한 채 implement-task로 넘어가지 않는다(교착 방지: 종결은 **① 통과 / ② 「예산 소진 종결」 / ③ 「반영 미검증 종결」 / ④ 에스컬레이션** 넷 중 하나(②·③ 상세는 다음 항목)이며, 그 밖의 방식으로 Step 10에 가지 않는다).
- **상한을 소진해 끝난 두 종결(②「예산 소진 종결」·③「반영 미검증 종결」)의 정본은 `references/review-gate.md`다** — 갈림선은 *마지막 라운드에 미해결 BLOCKER/MAJOR가 남았는가*(남으면 ②, 0이면 ③), 둘 다 ⓐ 대조 기록 + ⓑ 승인 명시가 **함께** 필요하다.
- 리뷰 중 새 질문이 드러나면 Step 8(Open Questions)로 돌아가 해소한 뒤 다시 리뷰한다.
- 통과 후에만 다음 단계.
- **호출 실패 시**: `plan-reviewer`는 Opus라 과부하가 잦다. `implement-task`의 `references/recovery.md` 「Reviewer 호출 실패 대응 (과부하·도구 불가·거절·빈 응답) — 모든 subagent 호출 공통」을 그대로 따른다 — **A** 과부하(529)는 재시도 후 Sonnet 대체 + 깊이 저하 명시, **B** 도구 불가는 위 예외의 체크리스트 대체, **C** 거절은 범위를 좁혀 1회 재의뢰 후 B로 수렴(사유 "거절 — 미검토 범위"), **D** 빈 응답(도구 호출은 됐는데 판정문이 비어 옴)은 같은 에이전트에 판정문만 1회 재요청 후 B로 수렴.

### Step 10. 사용자 승인 게이트

ExitPlanMode로 plan.md 제시. 승인 시 `implement-task` 호출. **제시 전에 문서 끝 `## 통과 체크리스트`를 먼저 대조한다** — 체크리스트는 승인 후가 아니라 승인 요청 전 게이트다.

**승인 프롬프트에 plan 요약을 반드시 포함한다 — 사용자가 plan.md 파일을 열지 않고도 판단할 수 있게**:
1. **요구 이해** — plan의 `## 요구 이해`(원문 인용 + 이해 3~5줄)를 **최상단에 그대로 노출**. 요구 오해는 사용자만 판정할 수 있으므로 승인 판단의 첫 항목이다 (여기서 어긋나면 아래 task가 전부 맞아도 무의미).
2. Goal 1~2줄
3. **task 요약 표 (전 task)**: `| T# | Type | 내용 한 줄 | 주요 파일·범위 |`
4. **동반 변경 판정 요지** (Step 4-E 결과 — 필수 n건은 어느 task에 편입됐는지, 선택 n건은 사용자가 무엇을 정했는지). 승인 전에 이것이 보여야 *"작업이 끝난 뒤에야 추가 수정을 통보받는"* 경로가 닫힌다.
5. Deferred / Follow-up · Out of Scope 요지 (있으면)
6. 사전 승인 항목·불가피한 Halt (아래 규정)

"상세는 plan.md 참조"로 요약을 대체하지 않는다 — 승인 판단에 파일 열람을 요구하는 것 자체가 승인 마찰이다. plan.md는 실행용 정본, 승인 프롬프트의 요약은 판단용이다.

**plan에 `## 사전 승인 항목 (일괄 승인 대상)`이 비어 있지 않으면, 승인 프롬프트에 그 목록을 그대로 나열하고 "이 plan 승인은 아래 사전 승인 항목의 일괄 위임을 포함합니다 — 자율 루프가 그 지점에서 멈추지 않습니다"를 명시한다.** 사용자가 plan을 승인하면 그 항목들은 일괄 승인된 것으로 본다(implement-task가 Phase 0에서 인정).

이 승인은 **plan 실행(구현) 승인**이다 — `## 불가피한 Halt (위임 불가)`의 항목(push·main 병합·태그·릴리즈·PR·파괴적 작업·인증정보 필요 신규 외부 서비스·돌발 결정)은 이 승인에 **포함하지 않으며**, 각 지점에서 그 행위를 이름으로 적어 따로 승인받는다 (implement-task 절대 규칙 12). push·릴리즈 등은 구현·검증 완료 후 implement-task 최종 보고에서 별도로 받는다.

**승인 직후 결정 큐잉**: plan의 **기능 단위** 채택 결정·`## Deferred / Follow-up`(보류)·`## Out of Scope`(기각)를 `pjc:llm-wiki` 절차 K 5-2의 `[DECISION]` 큐에 항목별 1줄로 기록한다(vault 없으면 그 규약의 폴백, 구현 세부 결정은 제외 — 입도 기준은 K 5-2 정본) — 다음 계획 때 위키 조회로 회수된다. 같은 시점에 계획 중 확인된 **작업 규약·함정 사실**(레포에 안 담는 크로스 세션 지식)은 `[PROJECT-FACT]` 큐에 기록한다(형식·입도는 절차 K 5-3 정본 — 배치 트리거 ① plan 승인).

## 통과 체크리스트

다음을 모두 만족해야 implement-task로 넘어갈 수 있다:

- [ ] **근거 없는 단정 0** (핵심 주장이 모두 Investigation Log의 확인 근거와 매칭됨 — "아마도/보통" 같은 표현은 그 신호일 뿐, 판정 기준은 표현 유무가 아니라 근거 매칭. plan-reviewer 항목 1과 동일 기준)

- [ ] **`## 동반 변경 판정` 섹션 작성됨** (Step 4-E — Type C/D task가 있는 plan만. **필수**는 전건 task에 편입 완료, **선택**은 Step 8 질문 결과가 반영됨, 대상이 없으면 "해당 없음 + 확인한 축" 1줄)
- [ ] **Investigation Log에 위키 참조 기록 1줄 이상** (Step 1 「기록 의무 (면제 없음)」 — 참조했으면 페이지별 `위키 참조: <페이지> — <결론 1줄>`, 양방향 검색 후 무매칭이면 그 1줄, **건너뛰었으면 절차 K 1 기록 형식 3종 중 실제 확인 결과에 해당하는 하나**. 기록이 없으면 *"위키를 참조한 계획"*과 *"한 번도 보지 못한 계획"*이 산출물에서 구분되지 않아, 사용자와 후속 세션이 없는 근거를 있다고 오인한다)
  - **적용 전제**: 이 항목은 **llm-wiki를 쓰는 세션**에만 적용된다(Step 1의 같은 전제) — 위키 기능을 쓰지 않는 프로젝트의 plan에 빈 기록을 강제하지 않는다. **단 "쓰지 않는다"는 판정도 절차 K 1의 `⚠ 판정 게이트`를 거친 확인 결과여야 하며**, 확인 없이 미설정으로 단정해 이 항목을 건너뛰는 것이 바로 이 검사가 막으려는 형태다.
  - **짝은 `plan-reviewer` 항목 17이다** — 여기(메인 자체 게이트)와 그쪽(적대적 게이트) 둘 다 두는 이유는, 한쪽만 두면 그 경로가 생략될 때(Step 9의 Type A/B 자체 검토 대체·도구 불가 대체) 검사가 통째로 사라지기 때문이다. **문면은 서로 복제하지 않는다**(판정 주체가 달라 관점이 다르다).
- [ ] plan-reviewer 이슈 0 (또는 MINOR만 follow-up으로 등록) — **미검증 심볼·미검토 항목 잔여분도 처리 완료** (해소 경로의 정본은 `implement-task`의 `references/recovery.md` 「리뷰 결과 처리」이며 Step 9가 그것을 plan 리뷰에 적용한다 — 직접 검증 또는 재호출, 조용한 통과 금지. Type A/B 자체 검토 대체 경로는 그 체크리스트 완주로 이 항목을 갈음하되, **그 갈음은 Step 9가 요구하는 「Type 선언의 근거 대조」 결과가 plan에 1줄 기록됐을 때만 성립한다** — 그 대조가 없으면 A/B 선언이 검사 없이 자기 자신을 면제한 것이라 갈음의 전제가 무너진다). **도구 불가로 체크리스트 대조로 대체한 경우**(Step 9 예외 B)는 그 사실을 **승인 프롬프트에 1줄 명시**한다 — 사용자가 적대적 검토를 받은 plan으로 오인하지 않게 한다(Type A/B 대체 경로의 명시 의무와 동일 형식). **「예산 소진 종결」·「반영 미검증 종결」(Step 9) 경로로 Step 10에 간 경우는 이 `이슈 0` 조건을 메인의 자체 대조 기록으로 갈음한다**(둘 다 ①「통과」의 하위가 아니라 **별개 종결**이다 — Step 9의 4분기 나열과 같은 구분) — 전자는 정의상 마지막 라운드에 미해결 BLOCKER/MAJOR가 남은 채 종결하고 **후자는 반영을 검증한 라운드가 없어 리뷰어 OK 자체가 존재하지 않으므로**, 예외 없이는 이 항목을 원리상 만족할 수 없다(Type A/B 대체가 *"체크리스트 완주로 갈음"*하는 것과 같은 구조). **갈음의 조건은 ⓐ 지적별 수용·기각 판정이 근거와 함께 plan에 기록됐고 ⓑ 승인 프롬프트에 그 종결 형태가 명시됐을 것** 둘 다이며, 하나라도 빠지면 갈음이 성립하지 않는다.
