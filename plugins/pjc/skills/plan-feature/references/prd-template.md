# PRD Template (대규모 작업 전용)

앱 신규 개발·대형 feature에서만 사용. 일상 기능 추가/수정에는 plan.md만으로 충분하다.

## 위치

- **기본: `docs/prd.md` 단일 파일.** 대부분의 작업은 한 파일에 FR을 누적·관리한다(원칙 5·8 — 폐기는 삭제 않고 표시, 부활은 새 ID). 한 파일이면 "새 요구가 어느 파일에 속하나"라는 귀속 문제가 아예 생기지 않는다.
- **분할은 예외**: 단일 파일이 원칙 7의 임계(40항목/250줄)를 넘는 초대형 프로젝트에서만 기능군별로 나눈다 — `docs/prds/<YYYY-MM-DD>-<기능군>.md` 누적 방식. 분할하면 작성 시 귀속·중복 판정이 필요해지므로(원칙 6 + plan-feature Step 0.5), 임계를 넘기 전엔 단일을 유지한다.
- plan.md와 같은 민감 정보 규칙 적용 (API key·password·개인정보 금지)

## PRD vs plan.md 역할 구분

| 문서 | 질문 | 변경 빈도 |
|---|---|---|
| PRD | **무엇을** 만들어야 하는가 (요구사항) | 거의 불변 — 사용자 승인 후 고정 |
| plan.md | **어떻게** 만들 것인가 (구현 계획) | task 진행에 따라 갱신 |

Phase G(요구 재검증)는 PRD를 기준으로 구현 전체를 재대조한다. plan.md가 빠뜨린 요구도 PRD에 있으면 잡힌다.

## Template

```markdown
# PRD: <제품/기능명>

## 목적
<한 단락 — 누가, 왜 사용하는가>

## 기능 요구사항 (Functional Requirements)

각 항목은 검증 가능한 문장으로 쓴다. "메모를 관리한다" ❌ → "메모를 생성/편집/삭제할 수 있다" ✅

| ID | 요구사항 | 우선순위 | 검증 방법 |
|----|---------|---------|----------|
| FR-1 | 사용자는 새 메모를 생성할 수 있다 | Must | 단위테스트: 생성 → Repository 조회 시 존재 |
| FR-2 | 메모는 자동 저장된다 (편집 중 1초 디바운스) | Must | 단위테스트: 편집 이벤트 → 1초 후 저장 호출 검증 + (UI 체감은 HUMAN-VERIFY) |
| FR-3 | 메모 검색 (제목+본문) | Should | 단위테스트: 키워드 → 매칭 목록 반환 |
| FR-4 | 다크 모드 지원 | Could | 테마 토큰 적용 코드 확인 + 화면 반영은 HUMAN-VERIFY |

우선순위: Must(없으면 미완성) / Should(중요하나 1차 출시 후 가능) / Could(여유 시)
폐기: 구현 후 기능이 제거된 FR은 행을 지우지 말고 요구사항에 `~~취소선~~` + 우선순위 셀을 `REMOVED (YYYY-MM: 사유)`로 (작성 원칙 5 — Phase G/reviewer 검증 제외 대상). 예) `| ~~FR-5~~ | ~~메모 태그 분류~~ | REMOVED (2026-06: 태그 기능 제거, → FR-9로 재도입) | — |`

> **검증 방법 작성 규칙**: 가능한 한 **기계 검증(테스트·CLI·파일 확인)으로 쓰기**. GUI 조작·시각 확인만으로 쓰면 Phase G에서 자동 검증이 불가능해 `HUMAN-VERIFY`(사용자 확인 필요)로 남는다. "단위테스트 X + UI는 HUMAN-VERIFY"처럼 병기하는 것이 최선.

## 비기능 요구사항 (Non-Functional)

| ID | 요구사항 | 검증 방법 |
|----|---------|----------|
| NFR-1 | 시작 시간 2초 이내 | 콜드 스타트 측정 |
| NFR-2 | 한글/영어 다국어 | 언어 전환 → 모든 문구 확인 |

## Out of Scope (명시적 제외)
- <이번에 만들지 않는 것 — 클라우드 동기화, 협업 등>

## 성공 기준
- Must 요구사항 100% 충족 + Should 80% 이상
- <측정 가능한 기준>

## 폐기 이력 (Removed) — 선택
<!-- 위 FR 표의 REMOVED 항목이 쌓여 본문이 커지면 여기로 이동(삭제 금지, 이력 보존).
     active FR 표에는 현재 유효한 FR만 남겨 Phase G 대조를 가볍게 유지한다. -->
| ID | 요구사항 | 폐기 시점·사유 |
|----|---------|---------------|
| ~~FR-9~~ | ~~예: 메모 태그 분류~~ | 2026-06: 태그 기능 제거 (→ FR-14로 재도입) |
```

## 작성 원칙

1. **요구는 검증 가능하게.** "좋은 UX" 같은 모호한 항목 금지 — Phase G에서 검증할 수 없다.
2. **Must를 엄격하게.** Must가 많을수록 Phase G 재루프가 길어진다. 정말 필수만 Must.
3. **Out of Scope 명시.** 자율 루프가 범위를 확장하는 것을 막는 가드.
4. **ID 부여.** plan.md의 task가 `(FR-1, FR-3 충족)` 형식으로 역참조한다.
5. **FR 폐기는 삭제가 아니라 표시.** 구현했던 FR의 기능이 이후 제거되면 표에서 행을 지우지 말고 요구사항을 `~~취소선~~` 처리하고 우선순위 셀을 `REMOVED (YYYY-MM: 사유)`로 바꾼다. PRD는 역사적 기록이라 삭제하면 "그때 무엇을 합의했나"가 사라진다. **Phase G·plan-completion-reviewer·plan-reviewer는 REMOVED FR을 미충족으로 잡지 않는다** — 이미 제거된 기능을 자율 루프가 다시 만들려는 거짓 재구현을 막기 위함이다.
6. **중복 FR 금지.** FR을 추가·갱신하기 전, 같은 요구가 기존 FR(active + REMOVED 모두)에 이미 있는지 확인한다. **PRD가 분할돼 여러 파일이면(`docs/prds/`), 같은 기능군 파일뿐 아니라 분할된 다른 PRD 파일까지 확인 대상이다** — 한 파일만 보면 다른 조각에 같은 요구가 이미 있는 것을 놓친다. 같은 요구를 다른 ID로 중복 등록하면 Phase G가 같은 것을 두 번 대조하고 plan task 역참조가 흩어진다. 중복이면 새로 만들지 말고 기존 FR을 갱신·통합한다(plan-reviewer가 중복 FR을 경고한다).
7. **기본은 단일 파일, 분할은 마지막 수단.** PRD는 가능한 한 `docs/prd.md` 한 파일로 유지한다(위치 규약). 분할은 단일 파일이 너무 커져 Phase G 대조가 얕아질 때만 쓴다 — active FR+NFR이 대략 **40항목 또는 250줄**을 넘으면 ⓐ 먼저 REMOVED 항목을 `## 폐기 이력` 섹션으로 모아 active 표를 줄이고(대개 이걸로 충분) ⓑ 그래도 크면 기능군별로 PRD를 분할한다(`docs/prds/<YYYY-MM-DD>-<기능군>.md` 누적 방식). **분할하면 이후 새 작업마다 "어느 기능군 파일에 속하나"를 판정해야 하므로**(원칙 6 중복 확인 + plan-feature Step 0.5 귀속 판정), 분할은 비용이다 — 임계를 넘기 전엔 단일을 유지한다.
8. **폐기된 FR의 부활은 새 ID로.** REMOVED FR의 기능을 다시 만들기로 하면 그 ID를 되살리지 말고 **새 FR ID(FR-N)로 추가**한다(옛 ID는 REMOVED로 그대로 둠). 옛 REMOVED 행 사유에 `→ FR-N으로 재도입 (YYYY-MM)`을 덧붙인다. 같은 ID를 재사용하면 과거 plan task가 역참조한 FR의 의미가 흔들리고 "언제 죽고 언제 부활했나" 이력이 사라진다. 부활은 PRD 변경이므로 사용자 승인이 필요하다(plan-feature Step 0.5 PRD 갱신 절차).
