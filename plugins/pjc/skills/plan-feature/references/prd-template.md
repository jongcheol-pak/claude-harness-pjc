# PRD Template (대규모 작업 전용)

앱 신규 개발·대형 feature에서만 사용. 일상 기능 추가/수정에는 plan.md만으로 충분하다.

## 위치

- `docs/prd.md` (단일) 또는 `docs/prds/<YYYY-MM-DD>-<slug>.md` (누적)
- plan.md와 같은 민감 정보 규칙 적용 (API key·password·개인정보 금지)

## PRD vs plan.md 역할 구분

| 문서 | 질문 | 변경 빈도 |
|---|---|---|
| PRD | **무엇을** 만들어야 하는가 (요구사항) | 거의 불변 — 사용자 승인 후 고정 |
| plan.md | **어떻게** 만들 것인가 (구현 계획) | task 진행에 따라 갱신 |

Phase G(요구 재검증)는 PRD를 기준으로 구현 전체를 재대조한다. plan.md가 빠뜨린 요구도 PRD에 있으면 잡힌다.

## Template

```markdown
# PRD: <제품/기능명>

## 목적
<한 단락 — 누가, 왜 사용하는가>

## 기능 요구사항 (Functional Requirements)

각 항목은 검증 가능한 문장으로 쓴다. "메모를 관리한다" ❌ → "메모를 생성/편집/삭제할 수 있다" ✅

| ID | 요구사항 | 우선순위 | 검증 방법 |
|----|---------|---------|----------|
| FR-1 | 사용자는 새 메모를 생성할 수 있다 | Must | 단위테스트: 생성 → Repository 조회 시 존재 |
| FR-2 | 메모는 자동 저장된다 (편집 중 1초 디바운스) | Must | 단위테스트: 편집 이벤트 → 1초 후 저장 호출 검증 + (UI 체감은 HUMAN-VERIFY) |
| FR-3 | 메모 검색 (제목+본문) | Should | 단위테스트: 키워드 → 매칭 목록 반환 |
| FR-4 | 다크 모드 지원 | Could | 테마 토큰 적용 코드 확인 + 화면 반영은 HUMAN-VERIFY |

우선순위: Must(없으면 미완성) / Should(중요하나 1차 출시 후 가능) / Could(여유 시)

> **검증 방법 작성 규칙**: 가능한 한 **기계 검증(테스트·CLI·파일 확인)으로 쓰기**. GUI 조작·시각 확인만으로 쓰면 Phase G에서 자동 검증이 불가능해 `HUMAN-VERIFY`(사용자 확인 필요)로 남는다. "단위테스트 X + UI는 HUMAN-VERIFY"처럼 병기하는 것이 최선.

## 비기능 요구사항 (Non-Functional)

| ID | 요구사항 | 검증 방법 |
|----|---------|----------|
| NFR-1 | 시작 시간 2초 이내 | 콜드 스타트 측정 |
| NFR-2 | 한글/영어 다국어 | 언어 전환 → 모든 문구 확인 |

## Out of Scope (명시적 제외)
- <이번에 만들지 않는 것 — 클라우드 동기화, 협업 등>

## 성공 기준
- Must 요구사항 100% 충족 + Should 80% 이상
- <측정 가능한 기준>
```

## 작성 원칙

1. **요구는 검증 가능하게.** "좋은 UX" 같은 모호한 항목 금지 — Phase G에서 검증할 수 없다.
2. **Must를 엄격하게.** Must가 많을수록 Phase G 재루프가 길어진다. 정말 필수만 Must.
3. **Out of Scope 명시.** 자율 루프가 범위를 확장하는 것을 막는 가드.
4. **ID 부여.** plan.md의 task가 `(FR-1, FR-3 충족)` 형식으로 역참조한다.
