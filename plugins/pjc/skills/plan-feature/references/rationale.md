# Rationale — plan-feature 규칙의 배경

> **이 파일은 규칙이 아니다.** 규칙의 정본은 `SKILL.md`이며, 여기 서술과 충돌하면 **`SKILL.md`가 우선한다.**
>
> 여기 담는 것은 "이 규칙이 왜 지금 형태가 됐는가"의 이력·근거뿐이다 — 판정 조건·수치 임계·금지/의무 문장·예외 경계는 담지 않는다(그것을 옮기면 본문만 읽는 실행 경로에서 규칙이 사라진다).
>
> **읽는 시점**: 규칙을 그대로 따를 때는 읽지 않아도 된다. 규칙이 반직관적으로 보여 그대로 적용해도 되는지 판단이 필요할 때, 또는 규칙을 바꾸려 할 때만 참조한다.

## Step 5 — Type C/D의 V-6(품질 리뷰)이 항상 실행되는 경위

종전에는 Type C가 opt-in 플래그(`(quality-review)`)를 붙여야 V-6을 받았다. 그 기본값이 **가장 흔한 Type C 코드를 spec 검증만 받고 품질 검토 0회로 커밋**시키는 공백이라 반전했다(v1.122.0). 그래서 지금은 plan이 별도 표기를 붙일 필요가 없고, 기존 plan에 남은 플래그는 no-op으로 취급한다.

V-5와 병렬 호출이라 소요 시간은 늘지 않는다. (출처: v1.122.0 — 2026-07-15 사용자 확정) 여기서 병렬은 동시에 실행돼 시간이 안 는다는 뜻이지, 결과를 안 기다린다는 뜻이 아니다.

## plan 작성 게이트 — 손으로 쓴 plan이 위험한 이유 (Step 7)

`require-plan-for-write` hook이 v1.118.0부터 기계 강제한다. plan을 이 스킬 없이 직접 Write하면
Step 1~9의 자산이 통째로 우회된다 — **영향 범위 전수 조사 · Deferred 대장 확인 · 적대적
plan-reviewer 검토 · Type 분류 · 사전 승인 항목 · Halt Forecast**. 더 나쁜 것은 그렇게 만든
plan이 `require-plan`의 "plan 있음" 판정을 켠다는 점이다: 검증을 하나도 거치지 않은 문서가
**이후 모든 코드 변경의 통과증**이 된다. AGENTS.md를 `bootstrap-agents-md` 없이 직접 쓰는 것을
막는 이유와 같은 구조다.

## 재호출 상한 — 3회에서 2회로 줄인 근거 (Step 9)

**3라운드 이후 지적은 대체로 MINOR·표현**인데, 그 구간에서 **수정이 새 결함을 만든 사례가
3회 연속 관측**됐다. 라운드를 늘릴수록 배출물이 늘고 그것이 그대로 Deferred 대장으로 흘러
순증한다 — 리뷰를 더 도는 것이 품질을 올리지 않고 부채를 옮기기만 한 구간이다.

## vault 미설정 단정 — 확인 없이 건너뛴 사고 (Step 1)

설정돼 있고 실재하는 vault를 "미설정"으로 보고해 건너뛴 적이 있다. 그 결과 허브의 작업
규약과 `decisions.md`의 기각 이력이 통째로 계획에서 빠졌다 — 이미 기각된 안을 모르고 다시
계획하는 것이 정확히 그 조회가 막으려던 실패다. 그래서 "미설정"은 추측이 아니라 절차 K 1의
판정 게이트를 거친 **확인 결과**여야 한다.
