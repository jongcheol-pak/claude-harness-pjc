# 시각 요소 분해 — 상세 절차

> `pjc:plan-feature` **Step 2.5**의 상세본이다. 발동 조건(①-a 시각 충실도 · ①-b 화면 이식 + ② 기준 존재)은 SKILL.md 본문에 남아 있고, 그 조건을 충족해 분해를 수행할 때 이 파일을 읽고 아래 절차를 그대로 따른다.

**분해 전 — 기준 확보 (필요 시 사용자에게 요청)**: 분해는 기준을 **실제로 본 상태**에서만 정확하다. 아래에 해당하면 Step 8 일괄 질문으로 미루지 말고 **이 자리에서 즉시 요청**한다 — 기준은 분해의 **입력**이라, 없으면 표 자체를 만들 수 없다(질문 분산 방지 규칙의 예외).

- **시각 충실도 요청인데 기준 디자인 소스가 없다** → 시안 파일 경로 또는 렌더된 화면 이미지를 요청한다. 받기 전에는 분해를 시작하지 않는다.
- **화면 이식 요청인데 원본 소스 위치를 모른다** → **원본의 로컬 절대 경로**(다른 폴더에 있는 프로젝트면 그 루트 또는 화면 파일 경로)를 요청한다. **받기 전에는 분해를 시작하지 않는다.** clone·복사 없이 그 경로를 직접 Read/grep해 항목을 추출한다. 경로 없이 "설정화면이면 보통 이런 항목이겠지"로 표를 채우는 것은 **추측이며 금지** — 그것이 문구가 달라지는 직접 원인이다.
- **시안이 HTML·CSS 코드로만 주어졌다** → 에이전트는 그것을 **렌더된 그림이 아니라 텍스트로 읽는다.** 마크업·스타일에서 최종 레이아웃을 역산하면 간격·정렬·시각 위계가 어긋나기 쉬우므로, **시안을 브라우저로 열어 캡처한 화면 이미지를 함께 요청**한다(렌더 캡처 도구를 쓸 수 있으면 요청 대신 직접 캡처해 사용). 이미지를 끝내 얻지 못하면 진행하되, 표의 "확인 방법"에 `HTML 소스만(렌더 미확인)`으로 적어 근거 강도를 남긴다.
- **대상이 데스크톱 UI(WinUI 3/WPF/MAUI)인데 시안이 웹(HTML/CSS)** → CSS 속성은 XAML로 1:1 대응하지 않는다. 분해 표에 **디자인 값과 XAML 대응 수단을 함께** 적는다(예: `flex:1` → `ColumnDefinition="*"`, `gap:12px` → `Spacing="12"`, `border-radius` → `CornerRadius`). 대응이 모호한 항목만 Step 8 일괄 질문으로 넘긴다.

발동 시, 분해 결과를 plan의 **`## 시각 요소 분해` 섹션**에 만든다(이 표준 제목이 있어야 implement-task V-9가 인식한다 — task 본문에 묻으면 V-9가 미발동으로 오판할 수 있다). 섹션은 **두 하위 표**로 구성되며, **각각 조건부다 — 둘 다 요구하지 않는다**:

| 하위 표 | 담는 것 | 필요한 경우 |
|---|---|---|
| `### 시각 속성` | 폰트·간격·정렬·색·레이아웃 | ①-a 시각 충실도 요청 |
| `### 참조 정합 인벤토리` | 표시 항목·문구·컨트롤 타입·선택지·기본값 | ①-b 화면 이식 요청 |

시각 정합만인 작업(디자인 시안 기준)은 인벤토리 표를 생략하고, 항목 이식만인 작업은 시각 속성 표를 생략한다. 둘 다 해당하면 둘 다 만든다. **하위 제목 없이 표 하나만 있는 기존 plan은 종전대로 `### 시각 속성` 표로 취급한다**(무회귀 — 하위 제목 부재를 부실로 보지 않는다).

**이식 요청이면 섹션 서두에 원본 경로를 1줄로 남긴다 (의무)**:

```markdown
## 시각 요소 분해

**원본**: D:\Projects\ProjectA\src\Views\SettingsPage.xaml
```

implement-task는 plan.md만 보고 실행하므로, 계획 세션에서만 알던 경로가 이 줄로 남지 않으면 **V-9의 원본 대조도 reviewer 전달도 참조할 값이 없다.** 인벤토리 표의 `원본 근거` 열은 이 경로 기준의 상대 표기로 적는다. (경로에 사용자명 등 개인정보가 들어가고 plan이 커밋·공유되는 경우의 처리는 `references/plan-template.md`의 민감 정보 절 참조.)

#### `### 시각 속성` 표

**변경 대상 화면의 시각 요소를 요소 단위로 분해**한다. "placeholder만 일치" 같은 부분 추출은 금지 — 한 요소를 속성별로 쪼갠다. **표는 "디자인 값 + 확인 방법"까지만 적는다 — "현재 값"과 "일치" 판정 열은 두지 않는다**(현재 값 대조는 구현 후 implement-task V-9의 몫이다. 계획 단계에서 현재 값을 적으면 구현 시점에 stale해지고, plan-feature는 코드를 안 고치므로 "일치" 판정이 무의미하다):

```markdown
| 요소 | 속성 | 디자인 값 | 확인 방법 |
|------|------|----------|-----------|
| 헤더 | font-size | 14px | 디자인 HTML `.header` 컴퓨티드 |
| 검색박스 | layout | flex:1, max 340px | 디자인 CSS |
| 검색박스 | 아이콘 | ⌕ 있음 | 디자인 스크린샷 |
| 필터 칩 | 정렬 | 세로 중앙 | 디자인 CSS `align-items` |
```

규칙:
- **공유·재사용 컴포넌트도 분해 대상**에 포함한다. "리스트 행만 보고 헤더·검색·칩은 기존 공용 클래스라 맞겠지"라고 가정하지 않는다 (실제로 어긋나는 경우가 많다 — cross-file caller 원리의 시각 버전).
- 디자인 소스의 **모든 시각 속성**(폰트 크기·굵기, 간격, 정렬, 아이콘 유무, 색, 레이아웃 방식)을 요소별로 항목화한다. 체크리스트에 없으면 구현·검증에서 통째로 누락된다.
- 이 표가 Step 5 작업 분해와 Phase V 시각 대조의 기준이 된다.
- 디자인 요소가 애매한 경우(예: 정확한 색·간격 미확정)는 여기서 즉시 묻지 말고, Step 8 일괄 질문에 모아서 처리한다 (질문 분산 방지).

#### `### 참조 정합 인벤토리` 표

**원본 화면에 표시되는 항목을 원본 순서대로 전수 추출**한다. 이 표의 축은 시각 속성이 아니라 **"무엇이 어떤 컨트롤로 어떤 문구로 표시되는가"** 이며, **렌더 없이 소스 대조만으로 판정 가능한 것들**이다(그래서 implement-task V-9가 이 축에 `⏳ 미확인`을 금지한다):

```markdown
| # | 항목(원본 순서) | 라벨 문구(원문) | 컨트롤 타입 | 선택지·범위 | 기본값 | 활성·비활성 조건 | 원본 근거 |
|---|----------------|----------------|------------|------------|--------|----------------|----------|
| 1 | 테마 | 앱 테마 | ComboBox | 시스템 설정 / 라이트 / 다크 | 시스템 설정 | 항상 활성 | SettingsPage.xaml:42 |
| 2 | 시작 시 실행 | Windows 시작 시 자동 실행 | ToggleSwitch | — | 꺼짐 | 항상 활성 | SettingsPage.xaml:58 |
| 3 | 백업 주기 | 자동 백업 주기(일) | NumberBox | 1~30 | 7 | 자동 백업 켜짐일 때만 | SettingsPage.xaml:71 |
```

작성 규칙:
- **ⓐ 문구는 원문 그대로 복사한다.** 의역·축약·재작성·번역 금지. "앱 테마"를 "테마 설정"으로 바꾸지 않는다. 문구를 바꿔야 할 이유가 있으면 임의 판단하지 말고 Step 8 일괄 질문으로 확인받는다.
- **ⓑ 컨트롤 타입은 원본 타입명 그대로 적는다.** `ComboBox`를 "선택 입력"으로 일반화하지 않는다 — 일반화하면 구현 단계에서 TextBox로 대체돼도 표와 어긋나 보이지 않는다.
- **ⓒ 원본 항목을 순서대로 전수 기재한다.** "주요 항목만"·"대표적인 것 몇 개"는 금지 — 체크리스트에 없는 항목은 구현·검증에서 통째로 누락된다. 그룹·섹션 구분이 있으면 그 구조도 순서에 반영한다.
- **ⓓ 모든 행에 `원본 근거`(파일:라인)를 적는다.** 근거를 적을 수 없는 행은 원본을 읽지 않았다는 뜻이므로 **표에 넣지 않는다**(추측 행을 만드는 것보다 없는 편이 낫다 — 있으면 검증을 통과한 것처럼 보인다).
