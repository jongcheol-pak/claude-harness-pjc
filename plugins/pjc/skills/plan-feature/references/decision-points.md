# Decision Points — plan-feature Step 6 상세

## Type별 검토 범위

| Task Type | 검토 카테고리 |
|---|---|
| **A** (Doc/Config) | **skip** — Decision Points 적용 안 함 |
| **B** (Trivial Code) | 명명, 공개 범위, 에러 처리 (해당하는 1-2개만) |
| **C** (Normal Code) | 명명, 위치, 공개 범위, 에러 처리, 상태 관리, 테스트 전략 (5-6개) + **보안·자격증명**(아래 발동 조건에 해당할 때) |
| **D** (Complex/Cross-cutting) | **12개 전체 검토** |

> **보안·자격증명 카테고리의 발동 조건**: Type C/D task가 **인증·자격증명·외부 접근**을 다룰 때만 검토한다(로그인·계정·시크릿·API 키·DB 접속·외부 서비스 연동). 무관한 task에서 발동시키지 않는다 — 모든 task에 보안 결정을 요구하면 과잉이다.

## 카테고리 12개

| 카테고리 | 결정 예시 |
|---|---|
| **명명** | 클래스/메서드/파일/네임스페이스 이름 |
| **위치** | 어느 레이어/프로젝트에 둘 것인가 |
| **공개 범위** | public/internal/private, 인터페이스 분리 |
| **에러 처리** | 예외 vs Result, 로깅 레벨, 재시도 |
| **상태 관리** | 보관 위치, 라이프사이클, 스레드 안전성 |
| **외부 계약** | API 시그니처, 이벤트 페이로드, 설정 키 |
| **마이그레이션** | 기존 데이터·설정 호환성 |
| **UI 동작** | 빈 상태, 로딩, 에러 표시, 단축키, **문구 톤**(개발 용어 대신 일반 사용자가 이해하는 일상 언어 — implement-task 규칙 7-2) |
| **성능 트레이드오프** | 메모리 vs 속도, 동기 vs 비동기 |
| **테스트 전략** | 단위 vs 통합, 모킹 범위 |
| **의존성** | **직접 구현(무의존)** vs 신규 라이브러리 vs 기존 재사용 |
| **보안·자격증명** | ① **시드/기본 계정을 둘 것인가** — 둔다면 운영에도 생성되는가, **최초 로그인 시 변경을 강제**하는가 ② **자격증명을 어디에 둘 것인가** — 환경변수·시크릿 파일(gitignore). **문서(README·docs)에 실제 값을 적지 않는다** — 공개 저장소에 한 번 올라가면 이력에서 회수할 수 없다 ③ **인증 실패 정책** — 계정 잠금(lockout), 시도 횟수·속도 제한 |

> **의존성 항목의 기본 선택지는 "직접 구현"이다**: 새 패키지는 유지보수·보안·라이선스·빌드 비용을 영구히 지운다. 플랫폼·표준 API 또는 이미 있는 의존성으로 합리적 노력 안에 구현 가능하면 그것을 우선하고, **신규 라이브러리를 고르면 "직접 구현이 왜 불가·비효율인지"를 Rationale에 남긴다.** "이 작업의 표준이 패키지라서"는 근거가 아니다 — 잘 닦인 패키지 경로가 유일 경로는 아니다(예: WinUI 3 트레이 아이콘은 `Shell_NotifyIcon` P/Invoke로 직접 구현 가능한데도 관성적으로 트레이 패키지부터 설치하는 편향이 실제로 관측된다). 이 세 선택지를 모두 올려 비교하지 않으면 "직접 구현" 안이 계획 단계에서 아예 검토되지 않는다.

> **왜 이 카테고리가 필요한가**: 이 결정들이 계획에 없으면 구현자가 그때그때 편한 쪽으로 정한다 — 그렇게 README에 기본 관리자 계정이 적히고, 강제 변경도 계정 잠금도 없는 채로 공개 저장소에 push된 사고가 실제로 있었다. 코드 리뷰·커밋 게이트가 사후에 잡아도 이미 늦다(git 이력에 남는다). **계획 단계에서 확정하는 것이 가장 싸다.**

## 기록 형식

각 결정은 Options/Chosen/Rationale/Source 형식:

```markdown
### D1. <결정 항목>
- **Options**: A) <대안1> / B) <대안2> / C) <대안3>
- **Chosen**: A
- **Rationale**: <왜 선택했는가>
- **Source**: AGENTS.md 또는 사용자 확인 또는 코드 확인 (파일:라인)
```

**범위·대상 결정**(여러 항목 중 무엇을 포함할지 — 예: "동일 패턴 a/b/c에도 적용할까")은 배타적 A/B/C가 아니라 **항목 단위 자유 조합**으로 사용자에게 묻는다. 고정 묶음(a만 / a+b / 모두)만 제시하면 사용자가 원하는 조합(a+c 등)이 없어 답을 못 하고 막힌다:

```markdown
### D2. <범위 결정 — 예: 동일 패턴 적용 대상>
- **항목**: a(필수) / b / c — 각 항목에 영향·근거 한 줄
- **Options(자유 조합)**: 원하는 항목을 자유롭게 선택 (예: "a+c", "a만", "모두")
- **추천 ★**: a+b+c (일관성) — 단 사용자가 일부만 골라도 됨
- **Chosen**: <사용자가 고른 조합>
- **Rationale / Source**: ...
```

정보 부족으로 결정 불가능한 항목은 Open Questions로 모은다.

> **`AskUserQuestion` 도구로 물을 때의 규약**(옵션 4개 상한 대응·요구 원문 선택지 의무·근본 해결안 배치)은 **이 파일의 「(plan-feature Step 8) 질문 도구 사용 규약 (`AskUserQuestion`)」**이 정본이다(2026-08-05 `SKILL.md` Step 8에서 이관) — 위 D2 형식이 선택지 구성의 정본이고, 그 규약은 도구 경로에서 이 형식을 어떻게 지킬지를 다룬다.

## (plan-feature Step 8) 질문 도구 사용 규약 (`AskUserQuestion`)

위 형식은 마크다운 나열을 전제로 쓰였지만, 실제로는 **`AskUserQuestion` 도구**로 묻는 경우가 많다. 그 도구에는 **질문 4개·옵션 4개 상한**이 있고 "Other"(자유 입력)가 자동 추가된다 — 이 제약을 모른 채 쓰면 위 원칙이 조용히 무너진다. 아래를 지킨다.

- **ⓐ 요구 원문 선택지 의무 (가장 중요).** 사용자가 요청에서 **이미 방향을 지정했으면** 그 안을 **반드시 첫 선택지로 넣는다.** 예: "A 프로젝트 기능을 확인해서 **동일하게** 구현해줘" → 선택지에 **"A와 동일하게 구현(코드까지)"** 이 있어야 한다. 대안(다른 라이브러리로 비슷하게 등)만 나열하고 원문 안을 빠뜨리는 것은 **선택지 제시가 아니라 요구 변조**다 — 사용자는 자기가 말한 것을 고를 수 없게 되고, 무엇을 골라도 요청과 다른 결과가 된다.
  - 원문 안에 문제가 있다고 판단되면 **빼는 대신 남기고** 그 옵션 설명에 트레이드오프를 적는다(예: "원문대로 — 단 라이선스가 GPL이라 …"). 판단은 사용자 몫이다.
  - 명백히 불가능한 경우(존재하지 않는 API 등)에도 선택지에 남기고 설명에 불가 사유를 적는다. 조용히 없애면 사용자는 그 안이 검토됐는지조차 알 수 없다.
  - 이 의무는 **사용자가 방향을 지정했을 때만** 발동한다. 원문이 모호해 선택지로 만들 수 없으면 해당 없음.
- **ⓑ 옵션 상한에 굴복하지 않는다.** **먼저 실제로 성립하는 안을 빠짐없이 발굴하고, 그 다음에 형식을 정한다** — 도구의 옵션 칸이 4개라고 해서 **선택지를 관행적으로 3~4개에 맞추지 말 것**(사용자가 지적한 *"보통 3개정도만 표시해서 너무 제한적"* 이 이 습관이다. 칸 수가 사고의 상한이 되면 존재하는 대안이 조용히 사라진다). 발굴 결과가 **5개 이상이면 도구로 자르지 말고** 위 마크다운 형식으로 전량 제시한다("개수 제한 없음"은 도구 제약보다 우선하는 원칙이다). 도구를 쓸 때는 **"원하는 조합이나 다른 안은 Other로 자유 입력 가능"** 을 질문 본문에 명시한다. 범위·대상 질문은 `multiSelect`를 쓰되, 항목이 4개를 넘으면 마크다운으로 간다(형식 정본은 `references/decision-points.md` D2).
- **ⓒ 근본 해결안을 첫 옵션에.** 위 「추천(★) 기준 — 근본 해결 우선」을 도구 경로에서도 그대로 지킨다: 근본 해결안을 **첫 옵션**에 두고 라벨 끝에 `★`(또는 "(권장)")와 근거를 적는다. **임시방편만으로 선택지를 채우지 않는다** — 증상 우회안을 넣을 때는 **근본 해결안을 같은 질문에 반드시 병기**한다. "빨리 끝나는 것"이 아니라 "문제가 사라지는 것"이 추천 기준이다(절대 규칙 3).
- **ⓓ 옵션마다 설명 의무.** 각 옵션 `description`에 **무엇이 달라지는가 + 비용/트레이드오프**를 적는다. 라벨만 보고 고르게 하면 사용자는 이름만으로 판단하게 되고, 그건 선택지를 준 것이 아니다.
