# plan 산출물 품질 루브릭

`plan-feature`가 만든 `plan.md`의 품질을 고정 기준으로 채점한다. `rubric_eval.py`가 이 파일 전문을 judge 프롬프트에 실어 보내므로, **여기 적힌 항목·척도가 곧 계약**이다 — 항목을 더하거나 빼면 과거 run과의 비교가 깨진다(그럴 땐 `run_id`를 새 세대로 구분할 것).

## 채점 규칙 (judge가 반드시 지킬 것)

1. **근거 없는 점수는 금지한다.** 각 항목 점수에는 그 판단의 근거가 된 **`파일:라인`** 을 하나 이상 붙인다. plan에서 근거를 지목할 수 없으면 점수 대신 `"N/A"`를 쓴다 — 억지로 중간 점수를 주지 않는다.
2. **있는 것만 본다.** "이런 게 있었으면 좋았다"는 감상이 아니라, plan에 실제로 쓰인 문장을 근거로 판정한다.
3. **길이를 품질로 착각하지 않는다.** 긴 plan이 자동으로 높은 점수를 받지 않으며, 항목 8은 오히려 장황함을 감점한다.
4. **8개 항목을 전부 채운다.** 판단이 서지 않는 항목도 생략하지 말고 `"N/A"`로 남긴다.

## 항목

### 1. 요구 명확성 (goal_clarity)
목표와 범위가 한 가지로 읽히는가. 무엇을 하고 무엇을 하지 않는지가 분리돼 있는가.
- **1**: 목표가 한 문장도 없거나 여러 해석이 가능하다.
- **5**: 목표는 있으나 범위 경계(하지 않을 것)가 없다.
- **10**: Goal이 단일 해석으로 읽히고 `Out of Scope`가 실제 후보를 명시적으로 배제한다.

### 2. task 분해 적정성 (task_decomposition)
각 task가 독립적으로 착수·검증 가능한 단위인가. 의존이 명시돼 있는가.
- **1**: task가 1개거나, 하나의 task가 서로 무관한 여러 변경을 뭉쳤다.
- **5**: 분해는 됐으나 의존 관계가 없거나 단위 크기가 들쭉날쭉하다.
- **10**: 각 task가 단일 관심사이고 `Depends on`으로 순서가 강제된다.

### 3. Acceptance 검증가능성 (acceptance_verifiability)
완료 조건이 **관측 가능한 사실**로 쓰였는가. 실행·grep·diff로 참/거짓을 가릴 수 있는가.
- **1**: "잘 동작한다", "개선된다" 같은 주관적 서술뿐이다.
- **5**: 구체적이나 판정 주체가 사람의 감에 맡겨진다.
- **10**: Given/When/Then 또는 "diff 0줄", "N건 전부 잔존" 같은 기계 판정 가능한 조건이다.

### 4. 결정 사전해결 (decisions_resolved)
구현 중 갈릴 선택이 계획 단계에서 닫혔는가. 선택지·채택·근거·출처가 함께 있는가.
- **1**: `Decisions`가 없거나 결론만 있고 근거가 없다.
- **5**: 결정은 있으나 대안이나 출처 중 하나가 빠졌다.
- **10**: Options/Chosen/Rationale/Source가 갖춰져 구현자가 되물을 것이 없다.
- **가산 관점 (규칙 도입 이후 plan에만 적용)**: `### 전제 검증` 표가 있고 각 행에 확인 근거(파일:라인·명령)가 붙었는가 — 확인하지 않고 전제로 삼은 것이 `⚠ 미확인`으로 드러나 있는가. **그 표가 없는 구 plan은 이 관점을 적용하지 않는다**(도입 이전 plan과 이후 누락을 산출물로 구분할 수 없어, 적용하면 A/B 비교가 왜곡된다).

### 5. 영향 분석 완전성 (impact_analysis)
변경이 닿는 심볼·호출부·계약·테스트가 추적됐는가. 추적 방법(grep 등)이 재현 가능하게 적혔는가.
- **1**: 영향 분석이 없다.
- **5**: 파일 목록은 있으나 심볼 단위 추적이나 건수 실측이 없다.
- **10**: 심볼별 영향 파일·건수가 표로 있고 `Verified by`처럼 추적 명령이 남아 있다.
- **가산 관점 (규칙 도입 이후 plan에만 적용)**: `## 동반 변경 판정` 섹션에서 요청 밖이지만 함께 손봐야 할 것이 **필수/선택/무관**으로 분류되고, **필수분이 실제 task에 편입**됐는가(분류만 하고 편입하지 않은 것은 감점). **그 섹션이 없는 구 plan은 이 관점을 적용하지 않는다**(위 항목 4와 같은 사유).

### 6. Edge Case 구체성 (edge_cases)
실패 경로가 "무엇이 일어나면 어떻게 한다"까지 적혔는가.
- **1**: Edge Case가 없다.
- **5**: 나열은 있으나 대응이 없다("~할 수 있음"에서 끝난다).
- **10**: 각 케이스에 트리거 조건과 처리 방침이 함께 있다.

### 7. 검증 전략 실행가능성 (verification_strategy)
task 단위·전체 단위 검증 방법이 **명령 수준**으로 특정되는가. 검증 불가 항목이 구분됐는가.
- **1**: 검증 방법이 없다.
- **5**: "빌드·테스트한다" 수준으로만 적혔다.
- **10**: 변경 유형별 검증 명령이 지정되고, 기계 검증이 불가한 항목이 따로 표시된다.

### 8. 간결성 (conciseness)
같은 내용을 반복하지 않는가. 결정과 무관한 서술로 부풀지 않았는가. **길수록 감점이 아니라, 중복·군더더기가 감점이다.**
- **1**: 같은 규정이 여러 절에 중복돼 어느 것이 정본인지 알 수 없다.
- **5**: 부분적 중복이 있으나 정본이 식별 가능하다.
- **10**: 각 사실이 한 곳에만 있고 다른 곳은 그곳을 가리킨다.

## 출력 형식

아래 JSON **한 덩어리만** 출력한다. 코드펜스·설명·인사말을 붙이지 않는다.

```
{
  "scores": {
    "goal_clarity":            {"score": 8,     "evidence": "plan.md:15", "note": "한 줄 사유"},
    "task_decomposition":      {"score": 7,     "evidence": "plan.md:220", "note": "..."},
    "acceptance_verifiability":{"score": "N/A", "evidence": null,          "note": "근거를 지목할 수 없음"},
    "decisions_resolved":      {"score": 9,     "evidence": "plan.md:138", "note": "..."},
    "impact_analysis":         {"score": 6,     "evidence": "plan.md:91",  "note": "..."},
    "edge_cases":              {"score": 8,     "evidence": "plan.md:234", "note": "..."},
    "verification_strategy":   {"score": 7,     "evidence": "plan.md:430", "note": "..."},
    "conciseness":             {"score": 5,     "evidence": "plan.md:46",  "note": "..."}
  }
}
```
