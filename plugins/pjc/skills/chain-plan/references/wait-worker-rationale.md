# 워커 대기 스크립트 근거 (`scripts/wait-worker.py` · `scripts/pr_stage.py`)

> 코디네이터는 이 파일을 읽지 않는다 — `../SKILL.md` 「워커 루프」 는 대기를 띄우고 출력 첫 줄 `RESULT: <갈래> — <지시>` 를 따를 뿐이다. 이 파일은 두 스크립트를 고칠 때 연다. 출력 갈래와 인자는 `wait-worker.py` 모듈 docstring 이 정본이고, 여기는 판정이 왜 그런 모양인지를 담는다.

## 왜 따로 두는가

코디네이터가 `check --wait` 를 9분마다 직접 돌리면 그때마다 큰 컨텍스트를 다시 읽는다(2026-10-04 실측 — 체인 1회 폴링에 53~68턴 · 21~32M 토큰). 이 스크립트가 그 반복과 멈춤 판정을 맡고, 코디네이터는 출력 첫 줄의 지시만 따른다.

## 진행 줄

워커가 끝낸 task 마다 `<label>: T<N>/T<M> 완료 — <무엇을> · T<다음> 시작` 한 줄을 따로 깨우지 않고 message·stall·error 원문 앞에 싣는다 — task 마다 깨우면 코디네이터가 그때마다 큰 컨텍스트를 다시 읽어, 이 스크립트가 없애려던 폴링 턴이 task 수만큼 되살아난다(2026-10-12 감사).

## 자리 대기

`worker-start` 가 `duplicate_worker` 로 다른 세션 워커를 이름 댔을 때 띄운다. 주기(`--poll-ms`, 기본 1분)마다 `check --wait` 로 쉬고 `worker-list --json`(전 Run)에서 그 dispatch 행을 본다. 행이 없거나 Karina `holds_place_at` 기준으로 놓았으면 freed 다. 시한·멈춤 판정은 없다 — 사람이 탭을 놓아야 풀리는 상태도 있어서다. 이 모드의 message·freed 지시문은 `--place` 재기동을 말하고 error 는 두 모드가 같다.

## 병렬 대기

배치는 코디네이터 터미널에 오므로 `check` 는 주기마다 한 번이고, 화면 비교·멈춤 연속 수·진행 감지만 dispatch 마다 따로 둔다. 멈추면 그 dispatch 하나를 지목하고 지시문은 `parallel.md`「멈춤」 을 가리킨다. 잠금은 dispatch 마다 하나씩이고 전부 쥐었을 때만 소유다(AllLocks) — 끝난 워커를 뺀 나머지로 다시 띄운 대기가 집합이 겹치는 앞 대기를 물린다.

## 멈춤 판정

`check` 가 시한 만료(count 0)로 돌아올 때마다 `worker-read`(커서 없음 — 커서는 출처에 묶여 다른 출처로 넘기면 `source_changed` 다)로 화면을 읽고, 앞 체크포인트와 `lines` 가 같으면 연속 수(일치한 비교 횟수 — 같은 화면 장 수보다 하나 적다)를 올린다.

일하는 워커는 대개 스피너 경과 시간이 바뀌어 화면이 같지 않다. 그러나 워커가 커밋을 쌓는 동안 `worker-read` 가 고정된 화면을 돌려준 사례가 있어(2026-10-15), 진행 감지(`--repo`)가 켜져 있으면 앞 비교 뒤 그 dispatch 레포의 HEAD 가 움직였을 때 화면이 같아도 연속 수를 0 으로 되돌린다. 즉 멈춤은 같은 화면이면서 HEAD 가 움직이지 않은 것이다. HEAD 를 처음 본 비교와 git 이 실패한 주기는 움직임으로 세지 않는다. 병렬 대기는 dispatch 마다 자기 레포만 본다.

화면 비교까지 남은 대기를 시계가 아니라 차감으로 센다 — `check` 시한은 min(`--poll-ms`, 남은 대기)이고 남은 대기가 0 이 된 주기에만 화면을 읽는다(비교 간격을 9분으로 지킨다).

## 진행 감지

주기마다 `git -C <repo> log <본 sha>..HEAD` 에서 제목이 `<유형>: T<N> — <무엇을>`(implement 「커밋」 형식)인 커밋을 고른다. 분모는 `<repo>/plan.md` 의 `### T<N>.` 번호 최댓값(implement 의 `T<N>/T<M>` 과 같은 정의)이고 다음 시작은 N 보다 큰 최소 번호다 — N 이 최댓값보다 크면 분모·다음 시작 없이 낸다.

본 sha 와 표시한 번호는 dispatch 별 상태 파일에 두어 재기동해도 같은 커밋·같은 task 의 후속 커밋(「수정: T2」)을 다시 표시하지 않는다. 진행 줄이 있는 갱신은 그 줄을 결과에 실어 낼 때만 저장하고, 그때까지는 주기마다 같은 기준에서 다시 계산한다. 진행 감지는 잠금 확인보다 먼저 돌고, 잠금을 잃은 대기는 상태를 쓰지 않는다. 시작할 때 임시 폴더의 7일 지난 `pjc-chain-wait-*` 를 지운다(sweep_stale).

git 실패는 대기를 끊지 않고, 본 sha 가 무효하면 HEAD 로 다시 채운다. 상태 파일이 없으면(시작 때 HEAD 를 못 잡음) 주기마다 다시 잡고, 있는데 읽지 못하면 덮어쓰지 않는다. 상태 파일은 임시 파일을 바꿔 넣어 쓰고, 저장 실패는 대기를 끊지 않는다.

## PR 단계

`--pr <base>` 는 계획 체인 PR 모드(`pr-mode.md`)에서만 준다. 워커는 PR 을 연 뒤 `gh pr checks --watch` 를 백그라운드로 걸고 turn 을 끝내므로(`../../pr/SKILL.md`「전제」), CI 를 기다리는 동안 화면도 HEAD 도 움직이지 않는다. 그대로 두면 멈춤 판정이 정상 대기를 멈춤으로 센다.

- **브랜치는 dispatch 레포의 현재 브랜치가 base 가 아닐 때 기억한다** — 워커는 ship 이 merge 한 뒤 base 로 돌아오므로, 그 뒤에는 현재 브랜치로 PR 을 찾지 못한다. 기억은 메모리와 상태 파일 둘이고, 상태 파일은 진행 줄과 같은 규칙으로 저장된다(실어 낼 때만). 메모리가 그 사이를 잇는다.
- **단계는 열림 → CI green → 화면 확인 대기 → merged 이고, 관측한 단계까지 아직 내지 않은 단계를 차례로 낸다** — 1분 주기라 PR 이 열린 뒤 merge 까지가 한 주기 안에 끝날 수 있다. merged 를 처음 본 주기에 열림·CI green·merged 를 다 낸다.
- **화면 확인 대기는 OPEN 이고 CI green 이며 본문에 `## 화면` 줄(줄 끝 공백·CR 허용)이 있을 때다 — merged 를 본 주기에는 내지 않는다** — 그 표지가 있는 PR 은 ship 이 사용자 확인 전까지 merge 하지 않는다(`../../pr/references/ship.md` 7번). merge 됐으면 이미 확인을 받은 뒤라 대기 줄이 거짓이 된다. 본문은 같은 `gh pr list` 호출의 `body` 필드로 받아 호출 수가 늘지 않는다. 같은 브랜치에 새 PR 이 열리면(이어받기) 번호가 바뀌어 단계를 처음부터 센다.
- **CI green 은 `gh pr checks --json bucket` 의 bucket 이 하나 이상이고 전부 `pass`·`skipping` 일 때다. `pending` 이 하나라도 있으면 바쁨이다** — bucket 은 gh 가 체크 상태를 다섯(pass·fail·pending·skipping·cancel)으로 묶은 필드다(gh 2.86.0 `gh pr checks --help`). `gh pr checks` 는 pending 이면 exit 8 이라 종료 코드가 아니라 출력으로 가른다.
- **바쁨이면 같은 화면이어도 그 비교를 움직임으로 센다 — 단 바쁨인 채 같은 화면이 연속 6비교(약 54분)를 넘으면 다시 멈춤으로 센다** — 러너를 못 받은 CI 처럼 끝나지 않는 대기로 체인이 경보 없이 서지 않게 한다.
- **gh 가 실패하거나 JSON 이 아니면 정보 없음이다** — 진행 줄을 내지 않고 바쁨도 아니라, 멈춤 판정은 PR 모드가 아닐 때와 같다. gh 는 레포 폴더에서 돌리고 stdin·stderr 를 잇지 않으며 30초 시한을 둔다(아래 「외부 호출 시한」).
- **`--pr` 이 없으면 gh 를 부르지 않는다** — PR 모드가 꺼진 체인의 대기는 그대로다.

## 고아 감시

시작할 때 자기 조상 사슬에서 앞쪽 python(WindowsApps 스텁)을 건너뛰고 셸들과 첫 비셸(claude.exe 등)을 고르고(pick_watch_targets), Windows 는 그 프로세스마다 SYNCHRONIZE 핸들을 연다. `check` 가 돌아올 때마다 하나라도 끝났으면 orphaned 로 끝난다 — 잔존 상한은 한 주기(`--repo` 경로 60초)다. TaskStop 은 셸 트리째 죽이지만(실측) claude.exe 자체가 죽을 때 백그라운드 트리가 함께 죽는지는 재지 못해 둔 감시다. 사슬 조회나 핸들 열기가 전부 실패하면 감시 없이 종전대로 기다리고, 일부만 열리면 연 것만 본다. POSIX 는 직계 부모 변경만 본다(실험적 지원).

## 외부 호출 시한

`check --wait --timeout-ms X` 는 X 에 60초를 더한 시각, 그 밖 CLI 호출은 60초, git·gh 는 30초다. CLI 시한 초과는 error(「CLI 실행 실패」), git·gh 시한 초과는 다른 실패와 같이 대기를 끊지 않는다.

## stdout 인코딩

stdout 을 utf-8 로 바꾸는 것은 필수다 — 백그라운드 stdout 은 cp949 라 첫 줄의 「—」에서 죽는다(실측).
