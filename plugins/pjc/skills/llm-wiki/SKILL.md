# LLM WIKI 운영 스킬

이 스킬은 위키 작업의 **실행 절차(A~K) + 규칙**을 **자기완결적으로** 담는다. **vault에 아무 파일이 없어도(빈 폴더) 동작**한다.
규칙·타입·예산의 진실원천은 **이 스킬 번들** `<skill>/references/wiki-schema.md` 다. vault에는 SCHEMA.md 사본을 두지 않는다(번들만 사용).

> **`<skill>` 경로**: 이 SKILL.md가 위치한 폴더. pjc plugin으로 설치된 경우 `${CLAUDE_PLUGIN_ROOT}/skills/llm-wiki`, 독립 설치된 경우 `~/.claude/skills/llm-wiki`. 본문의 `<skill>/...` 참조는 모두 이 폴더 기준이며, 실제로는 이 SKILL.md와 같은 디렉터리의 `references/`·`scripts/`·`config.json`을 가리킨다.

## 절차 목차

- **0. 시작 절차** — vault 경로 결정 · 빈 위키 초기화 검사 · 규칙 로드 (모든 작업 전 1회)
- **A. 프로젝트 추가** / **B. 정보 갱신(Ingest)** / **C. 삭제** / **D. 상태 변경**
- **E. 지식 페이지 관리** / **F. Lint(건강 검진)** / **G. Query(질문)**
- **H. 지침 자동 갱신** / **I. 가이드·레시피 작성** / **J. 빈 위키 부트스트랩** / **K. 작업 참조(read-only)**

## 0. 시작 절차 (모든 작업 전 1회 실행)

### 0-1. vault 경로 결정 (`<vault>`)

vault 경로는 **사용자 설정 파일** `~/.claude/llm-wiki-config.json`에 저장한다. 이 파일은 plugin 번들 **밖**(사용자 홈)에 있어 plugin 업데이트로 덮어써지지 않는다 — 한 번 설정하면 PC마다 1회로 영속된다.

다음 우선순위로 정한다:
1. 사용자가 이번 요청에 vault 경로를 명시 → 그 경로 (그리고 `~/.claude/llm-wiki-config.json`에 저장).
2. `~/.claude/llm-wiki-config.json`의 `vault_path`가 있고 **그 폴더가 실제 존재** → 그 경로.
   - **경로는 있으나 폴더가 없는 경우** (vault를 이동·삭제·이름변경): 그 경로를 그대로 쓰지 않는다 (빈 위키로 오인해 잘못 부트스트랩하거나 파일 작업이 실패함). 사용자에게 알리고 재확인한다: *"저장된 위키 경로 `<경로>`를 찾을 수 없습니다. 위키를 옮기셨나요? 새 경로를 알려주세요."* → 새 경로를 받으면 폴더 존재를 확인하고 `~/.claude/llm-wiki-config.json`을 갱신한다.
3. (사용자 config 없음) plugin 번들의 `<skill>/config.json`에 `vault_path`가 비어있지 않고 그 폴더가 존재하면 → 그 경로 (마이그레이션: `~/.claude/llm-wiki-config.json`에 복사 저장).
4. 모두 실패 → **사용자에게 "LLM WIKI 폴더 경로를 알려주세요"라고 물어본다.** 답을 받으면 폴더를 만들고(없으면) **`~/.claude/llm-wiki-config.json`** 의 `vault_path`에 저장한다 (plugin 번들 config가 아니라 사용자 홈에 저장 — 업데이트 시 유지).
- 사용자가 "위키 폴더 변경/지정/설정" 등을 요청하면 `~/.claude/llm-wiki-config.json`의 `vault_path`를 갱신한다.

> **저장된 경로는 매번 실재를 확인한다.** 폴더가 없으면(이동·삭제) 빈 위키로 오인하지 말고 사용자에게 재확인한다. 단, 경로가 정상 존재하면 묻지 않는다 — PC마다 최초 1회 + 경로가 사라진 경우에만 묻고, 그 외 업데이트·재사용에는 묻지 않는다.

### 0-2. 빈 위키 초기화 검사
- (0-1에서 `<vault>` 폴더 존재는 이미 확인됨. 폴더가 아예 없는 경우는 0-1에서 재확인 처리.)
- `<vault>` 폴더는 있으나 `<vault>/index.md` 또는 `<vault>/log.md`가 없으면 = 빈/신규 위키 → **J. 부트스트랩**을 먼저 실행한 뒤 본 작업을 진행한다.

### 0-3. 규칙 로드
- 규칙·타입·예산·네이밍·통제 어휘는 스킬 번들 `<skill>/references/wiki-schema.md`를 따른다. (vault에는 SCHEMA.md 사본을 두지 않는다.)

## 사전 준수 사항 (모든 작업 공통)

- 본문의 모든 상대경로(`10_sources/...` 등)는 §0에서 결정한 `<vault>` 기준이다.
- **모든 위키 작업 전 §0(경로 결정 + 초기화 검사 + 규칙 로드)을 먼저 수행한다.**
- 위키는 **자기완결적 상세 지식베이스**다. 레포 문서를 출처로 삼되, 기능·구현·UI/UX·동작·신규 생성법의 핵심 상세를 검색·재사용 가능하게 정제해 담는다(단순 복붙 금지). 프로젝트 간 관계와 크로스-커팅 지식도 함께 축적한다. (상세는 규칙 번들 `wiki-schema.md` §1)
- **출처 우선순위(고정)**: 실제 코드 > 레포 문서(README/notes/CLAUDE.md) > 모델 추론(금지). 문서↔코드 충돌 시 **코드를 따르고** 충돌 사실을 `30_knowledge/questions/`에 기록한다. 모델 기억만으로 사실을 단정 서술하지 않는다.
- 모든 위키 콘텐츠는 한글로 작성한다(사람도 읽는 human-readable 유지). 파일명과 frontmatter 키는 영문.
- **민감 정보 금지.** 실제 비밀번호·API 키·토큰·시크릿·DB 연결 문자열·내부 IP/호스트·개인정보를 위키 어느 페이지에도 적지 않는다. 위키는 영구 축적·공유되므로 한 번 유입되면 회수가 어렵다. 구현 설명에 자격증명이 필요하면 **환경변수 이름·설정 키 이름만** 기록하고 실제 값은 적지 않는다. 레포에서 정제할 때 우연히 시크릿 값이 보이면 위키에 옮기지 말고 생략한다.
- **시간민감 사실**(버전·수치·"현재 …" 등)은 본문에 `(as of YYYY-MM)`를 붙여 신선도를 추적 가능하게 한다.
- **question 페이지는 삭제하지 않는다** — 해결되면 결론을 관련 페이지에 흡수하고 `status: resolved`로 닫아 **보존**한다(해결 이력도 지식 — 같은 질문 재조사 방지, schema §2.7). `index.md`의 `## 미해결 질문`에서만 행을 제거한다(lint §7-23이 open 미등록·resolved 잔존을 기계 검사). 삭제는 사용자가 명시적으로 지시한 경우에만 한다.
- 작업 완료 후 반드시 `<vault>/log.md`에 1줄 기록을 추가한다. **항목은 2~3문장 이내 요지만** — 갱신 파일 목록·세부 근거는 해당 페이지에 두고 log에는 무엇을 했는지만 적는다. 단 절차 K(read-only 참조)는 위키 무변경이므로 기록하지 않는다.
- **log 월별 롤오버(공통)**: log 기록 추가 후 `log.md` 문자 수가 **6000자**를 넘으면, 가장 오래된 항목부터 그 항목의 `[YYYY-MM-DD]` 월의 `90_archive/log/{YYYY-MM}.md`로 이동(**3000자 이하까지, 항목 단위**)하고 `log.md` 하단 `## 아카이브 인덱스`(`- {YYYY-MM}.md: {키워드}`)를 갱신한다. 보존 이동이므로 **승인 불필요**. 이동된 항목 검색은 `## 아카이브 인덱스` → 해당 월 파일(상세 wiki-schema §8).
- **병렬 다중 에이전트 분업 규칙** (한 위키 세션 내부에서 다중 에이전트 병렬 실행 시): ① 쓰기 파일 소유권을 겹침 없이 분할(각 에이전트는 자기 담당 페이지만) ② 공유 파일(`index.md`·`log.md`·`plan.md`·`dashboard.md`·허브)은 에이전트 쓰기 금지 — 호스트가 완료 후 일괄 갱신 ③ 발견사항·등록 데이터는 파일 생성 대신 **반환값으로만** 보고 ④ 여러 프로젝트가 걸린 공유 페이지(concept 등)는 단일 에이전트 전담 ⑤ **위임 프롬프트에 형식 규칙을 반드시 포함** — 경로 표기(백틱 필수·물리 경로·brace 축약 금지·`obj/`/`bin/` 제외), 작성 전제(소스 실제 Read), 섹션 순서·예산, 반환값 형식(파일 생성 금지). 소유권만 지정하고 형식을 생략하면 에이전트 산출물의 형식 편차가 lint WARN으로 되돌아온다. (상세: 규칙 번들 §9)
- **지침 자동 갱신**: 실제 위키 구조·형식·규칙이 이 스킬 또는 규칙 번들 `wiki-schema.md`와 달라진 경우, 사용자 요청 없이도 현행화한다. 상세는 아래 "H. 지침 자동 갱신".

## 작업별 실행 절차

### A. 프로젝트 추가

사용자가 "프로젝트 추가해줘" / "{프로젝트} 위키에 등록"이라고 요청하면 다음을 순서대로 실행한다.

#### A-1. 정보 수집
1. 사용자에게 확인할 것:
   - 프로젝트 경로 (예: `D:/Source/ProjectName`)
   - 분류: `personal` 또는 `work`
2. 해당 경로에서 다음 파일을 읽어 프로젝트 정보를 파악한다:
   - `CLAUDE.md`, `AGENTS.md` (있으면)
   - `README.md` (있으면)
   - `notes.md` 또는 `NOTES.md` (있으면, 처음 50줄만)
   - `*.sln`, `*.csproj`, `Cargo.toml`, `package.json` 등 프로젝트 설정 파일
   - 서브 디렉토리 목록 (`ls`)
3. **기능 망라용 소스 스캔 (문서 미기재 기능 포착)**: 문서만으로는 기능이 누락될 수 있으므로, UI/기능 진입점을 표적 스캔해 화면·명령·기능을 열거한다(전체 정독이 아니라 enumeration 목적, Grep/Glob 사용).
   - WinUI/WPF/.NET: `Views/`·`Pages/`·`Presentation/`, `*ViewModel*`·`*Page.xaml`·`*Dialog*`, `[RelayCommand]`/`*Command`
   - Unity: `Assets/Scripts/`·`Scenes/`, 주요 `MonoBehaviour`
   - Web: 라우트/페이지(`pages/`·`routes/`·`app/`)·주요 컴포넌트
   - 공통: 메뉴/네비 정의, 설정 화면, 명령/액션 핸들러
   - 문서(README/notes)에 없는 기능도 이 목록에 포함한다.
4. 파악할 정보:
   - 프로젝트 한 줄 요약 / 기술 스택 / 서브프로젝트 유무
   - **전체 기능 목록(문서 + 소스 스캔 종합)** — A-2 feature 망라의 기준
   - 최근 변경 내역 3~5개
   - 기존 위키 프로젝트와 공유하는 기술/패턴

#### A-2. 파일 생성

> 모든 타입의 frontmatter/본문 템플릿은 `<skill>/references/templates.md` 참조.

1. **소스 스텁** → `10_sources/{personal|work}/src-{프로젝트명소문자}.md` (예산 ~30줄). 서브프로젝트 있으면 `- **서브프로젝트**:` 추가. **"기술 스택" 줄에는 프레임워크/라이브러리 이름만**(SDK/패키지 major.minor 버전 숫자 제외 — 스텁은 불변이라 버전이 영구 stale이 됨, 버전 진실원천은 코드/csproj).
2. **프로젝트 허브** → `20_projects/{personal|work}/{프로젝트명소문자하이픈}.md` (예산 ~120줄)
   - "기능 목록": 파일 3 feature를 표로 인덱싱.
   - "관련 위키 지식": `30_knowledge/`·`40_guides/`에 **이미 존재하는** 페이지만 링크.
   - "프로젝트 간 공유 패턴": 겹치는 기술/패턴을 `20_projects/`의 다른 프로젝트에 wikilink.
   - 서브프로젝트 있으면 "## 서브프로젝트" 테이블 추가.
   - **온보딩/아키텍처 가이드(선택)**: 큰 프로젝트면 "## 온보딩 / 아키텍처 가이드"(아키텍처 레이어·주요 흐름·복잡도 핫스팟)를 선택 포함한다 — 실제 코드/구조를 읽고 작성(추측 금지), 예산 ~120줄 유지(schema §2.2).
3. **feature 상세 페이지(들)** → `20_projects/{personal|work}/{프로젝트명}/feat-{기능명}.md` (feature당 ~180줄)
   - **작성 전제(필수)**: 구현/동작/UI·UX 서술 전에 해당 기능의 **핵심 소스 파일을 Read로 정독**한다 — A-1 enumeration 스캔(파일명·클래스명 열거)으로 대체 불가. 파일명만 보고 내부 동작을 추론해 쓰지 않는다.
   - 섹션: 개요 / **관련 파일** / 동작(사용법) / 구현 방법 / UI·UX / 관련 지식·레시피. **`## 관련 파일`은 이 기능을 구성하는 파일의 한눈 지도** — `- \`레포 상대경로\` — 역할 한 줄` 목록으로 작성한다(각주는 근거, 이 섹션은 지도 — lint §7-21이 경로 실존 검사). 구현 상세 주장은 레포 근거 각주 `[^src-...]` 필수 + **각주에 근거 소스 파일 경로(레포 상대경로) 병기**. **경로 표기(각주·관련 파일 공통)는 schema §2.3 규칙(정본)을 따른다** — 요지: 물리 경로·brace 축약 금지(전체 규정·예외는 §2.3 한 곳에서만 관리, 여기 재열거하지 않음). 동작·UI·UX도 코드·문서로 확인된 내용만 단정 — 실행해야만 확인 가능한 서술은 `(미검증)` 표기. 시간민감 사실은 `(as of YYYY-MM)` 표기.
   - **최초 등록 시 주요 기능/화면을 빠짐없이 망라**(핵심 일부만 만들고 미루지 않음). 과도한 분할은 피해 기능 단위로 그룹화, 예산 초과 시 하위 분리. 레포 README/notes의 화면별 상세를 근거로 정제.
   - 각 feature는 허브 "기능 목록" + `index.md` "기능별 인덱스"에 모두 등록(분할 시 그 프로젝트 category의 sub-index 기능별 인덱스에 등록 — §4; 상세는 A-3).
4. **(조건부) 새 지식 페이지** → `30_knowledge/tech/{기술}.md`(entity ~100줄) 또는 `patterns/{패턴}.md`(concept ~80줄)
   - 조건: 새 기술/패턴이 기존 페이지 없고 이미 등록된 다른 프로젝트 1개 이상과 공유 시에만. 1개 전용은 생성 금지.

#### A-3. 기존 파일 갱신 (반드시 모두 수행)

1. **`index.md`**:
   - 해당 카테고리(개인/업무) 프로젝트 테이블에 행 추가
   - **"기능별 인덱스" 테이블에 새 feature 행 추가**(기능 → feature/레시피/가이드 링크, 행 형식은 schema §3 — 첫 컬럼은 평문·상세 컬럼 alias는 `feature`/`recipe` 권장). 행 첫 컬럼(기능명)에 **한글 키워드와 영문 키워드를 양방향으로 모두 병기**한다 — 한글로 등록하든(예: "로그인 (login)") 영문 기술용어로 등록하든(예: "OG image (OG 이미지)") **한쪽만 적지 않는다**. 영문은 feature 파일명·코드 식별자에서, 한글은 기능 설명에서 가져온다. 이로써 한글로 검색하든 영문으로 검색하든 인덱스 한 줄에서 잡힌다(lint이 한/영 병기 누락을 검사 — F-1 16). **동의어 명명 일관성(schema §3)**: 등록 전 기존 기능별 인덱스를 한/영으로 검색해 **다른 프로젝트에 같은 기능이 이미 있으면 그 행의 한/영 키워드를 재사용**한다(같은 기능 = 같은 검색어 — 교차 프로젝트 검색 정합). 새 이름이 더 적절하면 기존 키워드도 괄호 병기. **인덱스가 sub-index 파일(`index-{카테고리}.md`)로 분할된 상태면**, `index.md`가 아니라 그 프로젝트의 category(personal/work)에 해당하는 sub-index(`index-personal.md`/`index-work.md`)에 행을 추가하고 `index.md` 상단의 sub-index 목록이 최신인지 확인한다.
   - 기술 스택 지식 테이블에 해당 프로젝트를 "사용 프로젝트"에 추가
   - 범용 패턴 테이블에 관련 있으면 추가
   - 가이드를 생성했으면 "가이드 / 레시피" 섹션에 링크 추가
2. **`30_knowledge/tech/*.md`·`patterns/*.md`**: 사용 기술/패턴의 기존 지식 페이지 `used_by`/`related_projects`에 프로젝트 추가 + 본문 목록/카운트 갱신.
3. **관련 프로젝트 페이지**: 밀접한 기존 프로젝트의 "프로젝트 간 공유 패턴"에 새 프로젝트 연결 추가.
4. **`log.md`**: `- [YYYY-MM-DD] [INGEST] {프로젝트명} {카테고리} 프로젝트 추가. ...`

#### A-3a. recipe 승격 확인 (필수 사용자 게이트)

> feature 망라 후, 코드 스니펫 recipe 승격 여부를 **항상 사용자에게 묻는다**(에이전트 단독 자동 승격 금지). feature는 기본적으로 산문 + 각주만 담으므로, 코드 수준 재사용은 사용자 선택으로 recipe에 적재한다.

1. **후보 식별**: A-1 소스 스캔/feature 작성 중 발견한 **재사용 가능한 비자명한 함정**(구현 트랩·플랫폼 제약·성능/안정성 트릭)을 후보로 모은다. 선별 기준 — ① 단일 화면 고유 로직이 아니라 다른 프로젝트에서도 재현 가능, ② 코드 없이는 재현이 어려운 함정/트릭.
2. **질문(필수)**: 후보를 1줄씩 나열하고 "코드 스니펫 recipe로 승격할까요? (전체 / 일부 선택 / 안 함)"을 **반드시 묻는다**. 후보가 0개면 "승격할 함정 후보 없음"을 보고하고 질문은 생략한다.
3. **승인 시**: 선택 항목을 **절차 I(가이드/레시피 작성)**로 진행 — 해당 스택 폴더에 recipe 생성, 실제 소스 코드로 스니펫 검증(`[^src-...]` 각주), `index.md` 가이드+기능별 인덱스 등록, 관련 feature "관련 지식·레시피"에 상호 링크.
4. **거절 시**: feature 산문 + 각주만 유지(현행 동작). 함정 정보는 feature에 남으므로 손실 없음.

#### A-4. 검증
1. `python <skill>/scripts/lint.py "<vault>"` 실행 — 예산·wikilink·통제어휘·인덱스/허브 동기화를 기계 검증(오류·경고 0 확인).
2. **전체 망라 검증 (기능 누락 차단)**: A-1의 "전체 기능 목록(문서 + 소스 스캔)" 각 항목이 feature 페이지 또는 의도적 묶음에 매핑되는지 대조. 미커버는 feature로 생성, 묶은 경우 사유를 해당 feature에 명시. 누락 0이어야 완료.

### B. 프로젝트 정보 갱신 (Ingest)

"위키 업데이트", "{프로젝트명} 변경분 반영" 요청 시.

#### B-1. 변경분 파악
0. **pending.md 확인 (drift 큐 소비)**: vault 루트 `pending.md`가 있으면 먼저 읽어, 이번 프로젝트 관련 `[K-DRIFT]` 항목을 갱신 범위에 반영한다. 처리한 항목은 pending.md에서 제거한다(소비 완료 — 남기면 다음 세션이 중복 처리). 다른 프로젝트의 항목은 그대로 둔다.
1. 레포 경로는 프로젝트 위키 페이지(`20_projects/`)의 "레포 정보 > 경로"에서 확인.
2. 레포 `notes.md`(또는 `NOTES.md`)로 마지막 위키 갱신(`updated`) 이후 변경분 파악.
3. 레포가 git 저장소면 `git log --oneline --since=<updated 날짜>`를 보조 신호로 사용해 notes.md에 누락된 변경분을 보완한다.
4. `README.md`, `CLAUDE.md` 변경이 있으면 함께 확인.
5. **델타 신뢰도 점검**: 위키 허브 `updated`가 **30일 초과**면 notes.md(1개월 보존 규칙)에서 그 사이 변경분이 이미 삭제됐을 수 있다 — git이면 git log로 보완하고, git이 아니면 notes 델타를 신뢰하지 말고 갱신 대상 feature의 **소스 직접 대조**로 강도를 올린다.

#### B-1a. 망라 재대조 (경량 드리프트 점검 — 필수)

> 델타(notes 변경분)만으로는 코드에서 **조용히 제거·이름변경**된 기능을 놓친다. A-1식 진입점 enumeration으로 가볍게 대조한다(전체 deep read 아님). 무거운 정합은 Lint의 **코드 정합 샘플링**(F-1 10)에 위임.

1. **현재 기능 열거**: A-1의 "기능 망라용 소스 스캔"(Views/Pages/ViewModels·라우트·`[RelayCommand]` 등, Grep/Glob)으로 현재 기능 목록을 도출한다(정독이 아니라 enumeration 목적).
2. **위키와 대조**: 이 목록을 허브 "기능 목록" + `index.md` "기능별 인덱스"의 기존 feature와 대조한다.
3. **드리프트 처리**:
   - **추가**(코드엔 있는데 위키에 없음) → feature 신규 생성(B-2 1-1, A-3a recipe 게이트 포함).
   - **제거/이름변경 후보**(위키엔 있는데 코드에 없음) → **자동 삭제 금지**. 후보 목록을 사용자에게 **명확한 선택지로** 제시하고 확인한다 (각 후보마다 삭제/이름변경/유지):
     ```
     코드에서 사라진 기능이 위키에 남아 있습니다. 각각 어떻게 할까요?
     - feat-old-login (위키엔 있으나 코드에 없음)
       · 삭제 — 위키에서 제거 (참조·인덱스·링크 정리)
       · 이름변경 — 실제로는 이름만 바뀐 경우 (새 이름 알려주세요)
       · 유지(폐기 표시) — 의도적으로 남기되 "더 이상 사용 안 함"으로 표시
     ```
   - **삭제 승인 시**: 절차 C-3(참조·`index.md`·크로스링크 정리)에 준해 처리하고, lint로 깨진 wikilink가 0인지 확인한다.
   - **'유지(폐기 표시)' 선택 시**: 파일을 남기되 frontmatter에 `deprecated: {날짜}` (또는 `status: deprecated`)를 적고 페이지 상단에 "⚠️ 이 기능은 코드에서 제거됨 — 이력 보존용"을 명시한다. **표시 없이 그냥 두면 절차 K 참조 시 현재 기능으로 오인**되므로, 유지는 반드시 폐기 표시와 함께 한다. 폐기된 feature는 허브 "기능 목록"의 **현재 기능 표에서 빼되, 허브에 "## 폐기된 기능" 구역을 두어 링크는 유지**한다 — 허브에서 링크를 완전히 제거하면 lint의 허브↔feature 동기화 검사가 "허브 기능 목록 누락"으로 오인한다. `index.md` 기능별 인덱스에도 폐기로 표기한다(분할 상태면 그 프로젝트 category의 sub-index 기능별 인덱스에 표기 — project feature이므로 sub-index, §4).
   - 확실치 않으면(제거인지 이름변경인지 불명확 등) 삭제·폐기 대신 `30_knowledge/questions/q-{날짜}-{설명}.md`에 기록(정보를 버리지 않음).

#### B-2. 갱신 (rewrite-on-ingest 원칙: 새로 추가가 아니라 기존 페이지를 갱신)
0. **교차 sweep (stale 드리프트 차단)**: 변경된 사실이 **여러 페이지에 중복 기재**됐을 수 있으니, 갱신 전 그 사실을 위키 전체에서 검색(`grep`)해 **나온 곳을 모두 일괄 갱신**한다. 같은 주제 기존 페이지가 있으면 신규 생성 대신 갱신(중복 방지). **단 `10_sources/` 소스 스텁은 불변이라 sweep 대상에서 제외** — 그러므로 휘발성 사실(SDK/패키지 버전 등)을 애초에 스텁에 두지 않는다(이름만, 버전 진실원천은 코드).
1. `20_projects/` 허브: `updated` 오늘로, "최근 주요 변경" 갱신(최신 위, 3~5개), tech_stack 변경 반영, 예산(~120줄) 초과 시 오래된 내역 압축.
   - **온보딩/아키텍처 가이드(선택)**: 허브에 "## 온보딩 / 아키텍처 가이드"(아키텍처 레이어·주요 흐름·복잡도 핫스팟)가 있으면 이번 변경에 맞게 갱신하고, 큰 프로젝트인데 없으면 선택적으로 추가한다 — 코드 기반·추측 금지, 예산 ~120줄 유지(schema §2.2).
   - **허브 개요·서술 stale 점검**: 허브 페이지의 "개요" 본문(프로젝트가 무엇인지 설명하는 산문)이 현재 프로젝트와 일치하는지 확인한다. 이번 변경으로 개요 서술이 **틀려졌으면** 갱신한다 — 예: 개요에 적힌 런타임·프레임워크 라인(`.NET 5` → `.NET 10` 같은 제품 라인 major 식별자), 아키텍처, 프로젝트 성격·범위(단일 도구 → 다기능 플랫폼)가 바뀐 경우. **개요 내용이 여전히 맞으면 건드리지 않는다**(단순 기능 추가로 성격이 그대로면 그대로 — 불필요한 재작성 방지). 판단 기준은 "개요 서술이 지금도 사실인가"이다(코드 주석 stale 방지와 동일 원리). tech_stack 필드만 바꾸고 개요 산문의 같은 내용을 stale로 남기지 않는다.
     - **버전 표기 정책 준수**: 개요에도 `.NET 10`·`WinUI 3` 같은 **제품 라인 major 식별자만** 쓰고, `8.0.4` 같은 major.minor 이상 정밀 버전은 적지 않는다(버전 진실원천은 코드 — §2.1 휘발성 버전 금지와 동일). 즉 ".NET 5 → .NET 10" 라인 변경은 갱신하되, 패치 수준 숫자는 애초에 개요에 두지 않는다.
1-1. `20_projects/{프로젝트}/` feature: 변경분이 특정 기능이면 해당 feature "동작/구현/UI·UX" 갱신 + `updated`. **`## 관련 파일` 목록도 이번 변경과 동기한다** — 파일 추가·이동·이름변경·삭제가 있으면 지도를 갱신(stale 경로는 §7-21 lint이 WARN). **갱신·신규 작성 모두 해당 기능의 소스 파일을 실제로 읽은 뒤 서술한다**(A-2 3 작성 전제 동일 적용). 새 기능은 feature 신규 생성 + 허브 "기능 목록" + `index.md` "기능별 인덱스" 동기화(분할 상태면 그 프로젝트 category의 sub-index `index-personal.md`/`index-work.md` 기능별 인덱스에 동기화 — project feature이므로 sub-index 대상, §4). 인덱스 행 명명은 **동의어 일관성(schema §3·A-3 1)** 준수 — 다른 프로젝트에 같은 기능이 있으면 그 한/영 키워드를 재사용. **새 기능 feature를 신규 생성한 경우 A-3a(recipe 승격 확인) 게이트를 동일 적용**한다(재사용 함정 후보를 사용자에게 묻는다).
   - **feature "관련 지식·레시피" stale 점검**: feature를 갱신할 때, 그 안의 "관련 지식·레시피"(함정·해결한 문제·주의점)가 **현재 구현에서도 여전히 유효한지** 함께 확인한다. 이번 변경으로 그 함정이 사라졌거나 해결책이 달라졌으면 갱신·삭제한다(틀린 지식은 없는 것보다 나쁨 — 주석 stale 방지와 동일 원리). 여전히 유효하면 그대로 둔다.
1-1a. **recipe 연동 갱신 (stale 방지)**: 갱신한 feature를 기반으로 만든 recipe(`40_guides/`의 재사용 레시피)가 있으면, 그 recipe가 **현재 구현과 맞는지** 확인하고 어긋나면 갱신한다. feature 구현이 바뀌었는데 recipe가 옛 구현 기준이면, 다른 프로젝트가 그 stale recipe를 절차 K로 참조해 잘못된 코드를 재사용하게 된다(추측·재작업 유발). 해당 recipe가 없으면 이 단계는 건너뛴다.
2. `30_knowledge/`: 크로스 프로젝트 패턴이면 지식 페이지에 사례 추가. 2개 이상 프로젝트 해당 시 새 지식 페이지.
2-1. **개선 교훈 기록·승격 (재사용 가능한 경우)**: 이번 변경이 단순 기능 추가가 아니라 **"문제를 이렇게 개선·해결했다"**는 내용이고 다른 프로젝트에도 적용될 범용성이 보이면, 그 교훈을 **"문제 → 원인 → 해결 → 사례 프로젝트"** 형태로 기록한다. 단 기록 위치는 기존 지식 페이지 규칙(2개 이상 프로젝트 실증 시에만 `30_knowledge/patterns/` 생성)을 따른다:
   - **첫 발견(이 교훈이 처음, 1개 프로젝트)**: 새 patterns 페이지를 만들지 않는다(검증 안 된 "범용일 것 같은" 패턴 양산 금지 — "불확실하면 제외"). 대신 해당 feature 페이지의 "관련 지식·레시피"나 프로젝트 허브 "주요 변경"에 교훈을 남긴다.
   - **이미 같은 patterns 페이지가 있으면**: 신규 생성 대신 `related_projects`에 이번 사례를 추가한다.
   - **두 번째 프로젝트에서 같은 교훈 발견 시**: 이제 2개 실증이므로 `30_knowledge/patterns/{패턴}.md`로 승격(concept). 잠재 연결 발굴(절차 F 13번)이 이 승격을 자동 후보로 제안할 수도 있다.
   - 예: "대량 리스트 렉 → 가상화", "비동기 취소 누락 → CancellationToken", "XAML 레이아웃 깨짐 → 회피법". 다음에 다른 프로젝트가 같은 문제를 만나면 절차 K로 찾아 시행착오를 줄인다.
   - **프로젝트 고유 일회성 수정(범용성 없음)은 기록만, 승격 안 함** — feature·log에만 둔다(패턴 남발 방지).
3. **모순 처리**: 새 정보가 기존 서술과 충돌하면 가능한 한 reconcile(최신·출처 우선). 깔끔히 정리 안 되면 정보를 버리지 말고 `30_knowledge/questions/q-{날짜}-{설명}.md`에 모순을 기록한다.
3-1. **해결된 questions 닫기 (stale 방지)**: 이번 변경으로 기존 `30_knowledge/questions/`의 미해결 질문이 **해결됐으면**, 그 질문 페이지에 해결 내용·근거(코드 확인 등)를 기록하고 `status: resolved`로 표시(또는 frontmatter에 `resolved: {날짜}`) + `index.md`의 "미해결 질문"에서 제거한다. 해결된 질문이 계속 "미해결"로 남으면 인덱스가 부정확해지고, 같은 질문을 또 조사하게 된다. (질문 페이지 자체는 삭제하지 않고 보존 — 해결 이력도 지식이다.)
4. `log.md`: `- [YYYY-MM-DD] [INGEST] {프로젝트명} 갱신. {요약}.`

#### B-3. 검증
- `python <skill>/scripts/lint.py "<vault>"` 실행으로 예산·wikilink·동기화 기계 검증(오류·경고 0 확인).

### F. Lint (건강 검진)

"위키 점검", "lint" 요청 시. 코드 작업 세션과 혼합하지 않는다.

#### F-0. 보조 스크립트 (먼저 실행)
- **pending.md 잔량 확인**: vault 루트 `pending.md`에 미처리 `[K-DRIFT]` 항목이 있으면 이번 점검 보고에 포함하고, 관련 프로젝트의 정합 확인에 반영한다(처리한 항목은 제거 — B-1 0과 동일 소비 규칙).
- `python <skill>/scripts/lint.py "<vault>"` 로 **아래 F-1 중 "lint.py가 기계 검사"로 표시된 전 항목**을 기계적으로 1차 점검(읽기 전용 — 항목 정본은 F-1·schema §7, 여기 재열거하지 않음). 그 결과를 아래 항목과 합쳐 보고한다.
- **폴백 (python 부재·실행 실패)**: `python`이 없거나 lint 실행이 실패하면 lint 단계를 **하드 실패로 막지 말고 건너뛰고** §7-10 에이전트 수동 점검으로 진행하되, "기계 lint 미실행(python 부재/실패)"을 보고에 명시한다. (`python3`만 있는 환경이면 그것으로 시도.) 이 폴백은 A-4·B-3·C-4의 lint.py 호출에도 동일 적용된다.

#### F-1. 실행 순서
1. **깨진 wikilink**: 모든 `[[...]]`가 실제 파일을 가리키는지.
2. **예산 초과**: 모든 파일 줄 수를 규칙 번들 예산과 대조.
3. **신선도**(`updated` 기준):
   - 60일+ 미편집(`status: paused` 제외): 목록 + confidence 하락 제안
   - 90일+ 미편집(`status: paused`, `type: feature`, `type: guide` 제외): `90_archive/` 이동 후보
   - feature/guide는 검색형 핵심이라 시간기반 이동 제외(confidence 하락만).
4. **모순 탐색**: 동일 주제를 다루는 페이지 간 상충 서술 → `30_knowledge/questions/`에 기록.
5. **크로스참조 누락**: 프로젝트 허브 tech_stack ↔ `30_knowledge/` `used_by` 일치.
6. **기능별 인덱스 동기화**: `index.md` "기능별 인덱스" ↔ 실제 `feat-*.md` 일치. vault 루트에 `index.md` 자체가 없으면 ERR 1건 보고 후 인덱스 기반 검사(6·14·15·16·23번)를 건너뜀(침묵 통과 방지, schema §7-6).
7. **통제 어휘 위반**: 모든 `platform` 값이 고정 어휘를 따르는지.
8. **고아 페이지**: 어디서도 링크 안 되는 페이지, 타입 미지정 파일.
9. **미래/이상 날짜**: `updated`·본문 날짜가 오늘보다 미래거나 비정상인지(데이터 위생).
10. **코드 정합 샘플링**: 프로젝트당 feature 1~2개 표본 — **핵심 서술(구현/동작)이 실제 코드와 일치하는지** 대조(에이전트 수행, lint.py 범위 아님). **표본 선정(로테이션)**: 직전 lint 이후 변경된 feature 우선 + `log.md`(+ 롤오버 아카이브)의 이전 `[LINT]` 표본은 후순위 — 같은 feature 반복 표본을 피해 세션에 걸쳐 커버리지 누적(이번 표본을 `[LINT]` log에 명시 — F-2, schema §7-10). 각주 경로의 레포 실재는 20번(§7-20)이 전수 기계 검사하므로 표본은 서술 정합에 집중하되, **lint이 레포 접근 불가로 건너뛴 프로젝트(20번 INFO)에서는 경로 실재 확인도 에이전트가 폴백 수행**. 불일치는 `30_knowledge/questions/`에 기록. **보수 판정**: 사실 오류만 flag(문서 누락·스타일 무시), 최근 `log.md`(+ `90_archive/log/` 롤오버 아카이브) 이력 대조로 이미 수정된 이슈 재-flag 금지.
11. **tech_stack 휘발성 버전**: 소스 스텁 "기술 스택" 줄 + project 허브 `tech_stack` frontmatter에 major.minor 이상 버전(`\d+\.\d+`)이 있으면 경고(이름만 기재 — 버전 진실원천은 코드). lint.py가 기계 검사.
12. **(미검증)·미해결 question 집계**: `20_/30_/40_` 본문(frontmatter·아카이브 제외)의 `(미검증)` 표기 수와 미해결 question 수를 INFO로 집계(0건 생략, lint.py). 닫힘 판정은 `status: resolved`·`resolved:` 필드(B-2 3-1) 모두 인정, `lint-*` 리포트는 제외 — 23번 등록 요구와 동일 기준(schema §7-12). 1건 이상이면 보고 시 **사용자 검증 후보로 명시**한다(§11 회수 장치).
13. **잠재 연결 발견 (크로스-프로젝트 미연결 공통점)**: 전 프로젝트 허브의 `tech_stack`·기능 목록·"프로젝트 간 공유 패턴"을 가로질러, **아직 `30_knowledge/` 지식 페이지나 허브 "공유 패턴" 링크로 안 묶인 2개 이상 프로젝트의 공통점**(공유 기술/패턴/접근/함정)을 발굴해 후보로 제안한다. 5번(크로스참조 누락)이 *기존* 지식 페이지의 정합성 점검이라면, 이 항목은 *신규* 연결의 발굴이다. **보수 정책**: tech_stack 일치·동일 명명 패턴 등 구체적 근거가 있는 공통점만 제안(추측 링크 금지), 기존 지식 페이지·기존 공유 패턴 링크와 중복은 제외, `log.md`(+ `90_archive/log/` 롤오버 아카이브) 이력으로 이미 처리된 후보는 재-제안 금지. **자동 생성 금지** — 후보만 🔵정보로 제시하고, 사용자 승인 시에만 절차 E(지식 페이지 — 2개 실증 충족 시 concept, 단일 기술이면 entity) 또는 허브 "프로젝트 간 공유 패턴" 상호링크로 반영. (**에이전트 수행 — lint.py 범위 아님**)
14. **index.md·sub-index 분할 신호**: index.md 본문(frontmatter 포함 전체) 줄 수 또는 기능별 인덱스 표 행 수, **그리고 각 sub-index(`index-*.md`) 자체의 본문 줄 수·기능별 인덱스 행 수**가 임계(400줄/200행) 초과면 INFO 제안(index.md는 2단계 파일 분할, sub-index는 추가 파일 분할 대신 `### ` 하위 소제목 구역화 — `wiki-schema.md` §4 — `INDEX_BODY_LINES`/`INDEX_FEAT_ROWS`). 행 판정은 형상+대상 기반(schema §3 행 형식 — alias 무관). lint.py가 기계 검사.
15. **sub-index 목록 정합**: vault에 실재하는 sub-index 파일(`index-*.md`)이 `index.md`에 언급(목록 등록)됐는지 — 미등록이면 WARN(절차 K·검색이 분할 인덱스를 빠뜨리지 않게). 역방향(목록엔 있으나 파일 없음)은 깨진 wikilink 검사(1번)가 커버. lint.py가 기계 검사.
16. **기능별 인덱스 한/영 병기**: 기능별 인덱스 유형 행(feature/recipe)의 첫 컬럼(기능명)에 한글(`[가-힣]`)·영문(`[A-Za-z]`)이 모두 있는지 — 한쪽만 있으면 WARN(한글 등록이든 영문 등록이든 양방향 검색 보장, §3·A-3 1). 행 인식은 14번과 공용인 형상+대상 기반(schema §3 — alias 무관, 첫 컬럼이 wikilink인 표는 제외), 스캔은 index+sub-index 전체 텍스트(`## ` 소분할 뒤 행도 커버). lint.py가 기계 검사.
17. **deprecated 표기 정합·집계**: 폐기 표시(`status: deprecated`/`deprecated:` 필드) 페이지를 INFO 집계(이력 가시성) + "코드에서 제거" 안내 누락 시 WARN + 신선도 후보 제외(`paused`처럼). "표기 누락"은 코드 미열람이라 탐지 불가(표기된 것의 정합만). lint.py가 기계 검사(§2.3·§8).
18. **feature 구현 근거 각주**: `type: feature`이고 `## 구현 방법`이 있으나 `[^src-...]` 각주가 0개면 WARN(얕은 feature 의심). 이 항목은 각주 존재를, 경로 실존은 20번(§7-20 — 레포 접근 가능 시)이, 서술↔코드 정합은 §7-10(에이전트)이 담당. lint.py가 기계 검사(§2.3).
19. **log 아카이브 인덱스 정합**: `log.md`의 `## 아카이브 인덱스`에 등록된 `{YYYY-MM}.md` ↔ 실재 `90_archive/log/*.md`를 양방향 대조 — 파일이 있으나 미등록(검색 누락) 또는 인덱스에 있으나 파일 없음(깨진 참조)이면 WARN(롤오버 항목이 검색에서 빠지지 않게, §8). lint.py가 기계 검사.
20. **feature 각주 경로 레포 실존**: feature의 `[^src-...]` 각주 정의 줄에 백틱 병기된 레포 상대경로(구분자 `/`·`\` 포함 토큰만)가 프로젝트 허브 `## 레포 정보 > 경로`의 레포에 실재하는지 전수 확인 — 부재·글롭 매치 0이면 WARN. 파일 실존만 보고 코드 내용은 해석 안 함(내용 정합은 §7-10). 허브 레포 경로 미기재·디렉터리 부재(다른 PC)면 프로젝트 단위 INFO 후 건너뜀(§7-10 폴백). deprecated·아카이브 제외. lint.py가 기계 검사(§7-20).
21. **feature `## 관련 파일` 섹션**: `type: feature`(deprecated·아카이브 제외)에 `## 관련 파일` 섹션이 없거나 경로 항목이 0개면 WARN — 문구로 원인 구분: "섹션 누락"(다음 ingest 시 채움) / "경로 항목 0개"(섹션은 있으나 백틱 경로 없음 — 형식 안내, §2.3). 섹션 내 백틱 경로 토큰(구분자 포함)은 20번과 동일 로직으로 레포 실존을 검사(레포 접근 불가 시 동일 INFO 폴백). lint.py가 기계 검사(§7-21).
22. **시크릿 의심 스캔**: 전 페이지 본문에서 password/API key·token/Bearer/DB 연결문자열/개인키/URI 자격증명 패턴 발견 시 WARN — 실값 형태만 매칭(보수 정규식), 플레이스홀더·"환경변수" 안내 줄은 제외. "민감 정보 금지"(사전 준수 사항)의 기계 강제. lint.py가 기계 검사(§7-22).
23. **미해결 질문 인덱스 동기**: open question(`lint-*` 리포트 제외)이 `index.md` `## 미해결 질문`에 미등록이면 WARN(유실 위험), resolved question이 잔존하면 WARN(stale — index에서만 제거, 페이지 보존). 닫힘 판정은 `status: resolved`·`resolved:` 필드(B-2 3-1) 모두 인정(12번 집계와 동일 기준), 등록 판정은 `.md` 포함·파일명만 링크도 인정(형식 위반은 1번 링크 검사가 별도 보고). "question 삭제 금지"(사전 준수 사항·§2.7)의 인덱스 측 기계 보조. lint.py가 기계 검사(§7-23).

#### F-2. 결과 보고
- 결과를 **심각도 등급**(🔴 오류 / 🟡 경고 / 🔵 정보)으로 분류해 보고.
- 이슈가 있으면 `30_knowledge/questions/lint-{YYYYMMDD}.md`에 리포트 페이지 작성(상세 보존), 요약은 사용자에게.
- 사용자 승인 후 수정.
- `log.md`: `- [YYYY-MM-DD] [LINT] 위키 점검. {발견}건 발견, {수정}건 수정. 표본: {코드 정합 샘플링 feature 목록}.` — 표본 명시는 다음 lint의 로테이션 근거다(F-1 10, schema §7-10).

### G. Query (위키 질문)

사용자가 위키 내용을 질문하면.
1. **위키가 진실원천 — 안다고 생각해도 모델 기억으로 답하지 않는다.** 반드시 `index.md`(기능별 인덱스 포함)로 관련 페이지를 식별하고 실제로 읽는다. **`index.md` 상단에 sub-index 파일 목록(`index-{카테고리}.md` 등)이 있으면**(인덱스가 비대해 파일 분할된 경우), 관련 카테고리의 sub-index도 함께 읽어 거기서 식별한다 — `index.md`만 보고 분할된 인덱스를 빠뜨리지 않는다(K-2·schema §6-2와 동일).
2. 관련 feature/guide/지식 페이지를 읽고 답변을 합성한다.
3. 출처를 각주로 명시(페이지 wikilink + 원 각주). 위키에 근거가 없으면 "위키에 없음"을 밝히고 추정은 `(미검증)` 표기.
4. **파일백**: 답이 위키에 없던 유용한 종합이면 → 사용자에게 "이 답을 위키에 페이지로 저장할까요?" 제안(2개 실증 시 `30_knowledge/patterns/` concept, 아니면 관련 feature/guide 보강).
5. 모순 발견 시 `30_knowledge/questions/q-{날짜}-{설명}.md` 생성.

### H. 지침 자동 갱신

위키 작업(A~J) 중 아래에 해당하면 **사용자 요청 없이** 이 스킬(`SKILL.md`) 또는 규칙 번들(`references/wiki-schema.md`)을 즉시 갱신한다.

#### H-1. 대상 조건
1. 형식 불일치(frontmatter/본문 섹션/경로가 템플릿과 다름)
2. 새 페이지 타입/섹션/필드 도입
3. 네이밍 규칙 변경
4. 디렉토리 구조 변경
5. 워크플로우 절차 변경
6. 예산 규칙 변경
7. 태그/링크 규칙 변경

#### H-2. 실행 방법
1. 작업 완료 직전 이 스킬과 규칙 번들 `references/wiki-schema.md`를 다시 읽는다.
2. 위키 실제 상태와 대조한다.
3. 불일치를 실제 상태에 맞게 수정한다.
4. 규칙 번들 수정 시 frontmatter `version`을 올린다.
5. 예산·통제어휘 변경 시 세 곳을 동시 갱신한다 — `SKILL.md` 예산표, `wiki-schema.md` §3~§4, `scripts/lint.py` 상수(BUDGET/GUIDE_BUDGET/SPECIAL_BUDGET/PLATFORM_VOCAB/ORIGIN_VOCAB/CONFIDENCE_VOCAB/ORIGIN_REQUIRED_TYPES/INDEX_BODY_LINES/INDEX_FEAT_ROWS). lint에 신규 검사(상수 아님)를 추가할 때도 `wiki-schema.md` §7 검사항목 + `SKILL.md` F-1에 동일 항목을 문서화한다.
6. `log.md`: `- [YYYY-MM-DD] [SCHEMA] {요약}. (자동 갱신)`

#### H-3. 범위 제한
- **내용을 실제 위키 상태에 맞추는 것**만 허용. 설계 방향/의도 변경은 사용자 요청 필요.
- 예: 실제 파일에 `status` 필드 추가 → 템플릿 반영(O). 아카이브 60일→30일 변경(X).

### I. 가이드/레시피 작성 (선행형 + 특정 기능 추가)

두 경우에 실행:
- **선행형 가이드**: "WinUI3 신규 프로젝트 가이드 작성" 등 신규 프로젝트용 가이드.
- **특정 기능 추가(프로젝트 추가 아님)**: "{기능} 구현 방법 위키에 추가" 등. 프로젝트 전체 등록(A) 없이 그 기능을 **해당 스택의 recipe로** 적재.

#### I-1. 특징
- **선행형**: 기존 프로젝트에서 추출하지 않아도 선제 작성 가능.
- **실증 면제**: concept의 "2개 프로젝트 실증" 조건 미적용.
- **출처**: 공식 문서/지침 파일(각주) + 실제 프로젝트 사례. 미등록 프로젝트는 wikilink 대신 이름 + 출처 각주. 미확인 내용 단정 금지, 불확실하면 `(미검증)`.
- **코드 스니펫 출처 규칙**: 스니펫은 ① 실제 프로젝트 소스에서 추출(각주에 소스 파일 경로 병기) 또는 ② 공식 문서 예제 인용(출처 링크 각주)만 허용. **모델 기억만으로 스니펫 작성 금지** — 불가피하면 `(미검증)` 표기 + `confidence: low`.

#### I-2. 종류 / 위치 / 본문

> frontmatter/본문 템플릿은 `references/templates.md`의 guide 템플릿 참조.

- **platform-bootstrap** (`40_guides/platforms/`): 기본 프로젝트 생성·구조. 예산 ~200줄.
  본문: `## 대상 플랫폼`/`## 기본 프로젝트 생성`/`## 권장 구조`/`## 필수 의존성`/`## UI/UX 기본`/`## 체크리스트`.
- **ui-ux** (`40_guides/ui-ux/`): UI/UX 가이드라인. 예산 ~150줄.
- **recipe** (`40_guides/recipes/{스택}/`): 특정 기능 구현 절차. 예산 ~120줄.
  본문: `## 목적`/`## 적용 플랫폼`/`## 단계`/`## 코드 스니펫`/`## 사용 프로젝트 사례`/`## 주의점 / 함정`(선택). 함정형 recipe는 재사용 함정·플랫폼 제약·성능/안정성 주의점을 `## 주의점 / 함정` 별도 섹션에 둔다(단계 산문에 묻지 않음 — 디버깅 회수, §2.6).

#### I-2a. 특정 기능 추가 시 스택 결정 (라우팅)
1. 기능이 속한 **스택 폴더** 결정(개방 목록): `winui`/`wpf`/`csharp`/`dotnet`/`unity`/`rust`/`web`/`tauri` …
   - 프레임워크 전용이면 그 프레임워크(예: WinUI 자동 실행 → `winui`), 언어 일반이면 언어(예: `csharp`). 폴더 없으면 생성.
2. `40_guides/recipes/{스택}/{기능}.md` 생성. frontmatter `platform`은 OS 통제 어휘로 별도 지정.
3. 같은 스택에 동일 기능 recipe가 있으면 신규 대신 **갱신**(중복 방지).

#### I-3. 등록 (반드시)
1. `index.md` "가이드 / 레시피" 섹션에 링크. recipe(특정 기능)는 "기능별 인덱스"에도 등록. **recipe는 category가 없어(cross-stack) sub-index로 분할되지 않는다 — 분할 상태에서도 `index.md` 본체의 "가이드 / 레시피" 섹션·기능별 인덱스에 등록한다(§4).**
2. 관련 가이드/허브/feature "관련" 섹션에 상호 링크.
3. `log.md`: `- [YYYY-MM-DD] [GUIDE] {가이드명} 작성.`

#### I-4. 검증
- 예산·wikilink·`platform` 통제 어휘·recipe 스택 폴더 배치 확인.

`<vault>`가 비었거나 골격이 없으면 생성한다(이미 있으면 건너뜀). §0-2에서 트리거.

1. **디렉터리**: `10_sources/{personal,work}`, `20_projects/{personal,work}`, `30_knowledge/{tech,patterns,questions}`, `40_guides/{platforms,ui-ux,recipes}`, `90_archive`
2. **`index.md`**: 빈 카탈로그 골격 — 섹션: `## 개인 프로젝트` / `## 업무 프로젝트` / `## 기능별 인덱스` / `## 가이드 / 레시피` / `## 기술 스택 지식 (tech/)` / `## 범용 패턴 (patterns/)` / `## 미해결 질문` / `## 참조`. 표는 헤더만, 내용은 "아직 없음" 주석. 참조 섹션은 **실제 존재하는 파일만** 링크(log/dashboard).
3. **`log.md`**: `## 최근 변경` + `- [YYYY-MM-DD] [INIT] 위키 초기 골격 생성 (llm-wiki 스킬).` + `## 아카이브 인덱스`(빈 목록 — 6000자 초과 시 월별 롤오버 항목을 `- {YYYY-MM}.md: {키워드}`로 등록, wiki-schema §8). `90_archive/log/`는 첫 롤오버 시 생성(미리 만들지 않음).
4. **`dashboard.md`** (선택): Dataview 쿼리(프로젝트/feature/guide/신선도/질문).
5. **규칙은 vault에 복사하지 않는다** — 진실원천은 스킬 번들 `references/wiki-schema.md` 뿐. index `## 참조`에는 번들 경로를 텍스트로 안내한다(vault에 SCHEMA.md를 만들지 말 것).
6. 부트스트랩 완료 후 본래 요청(A~I)을 이어서 진행한다.

### K. 작업 참조 (코드 작업 세션 read-only 조회)

코드 프로젝트 세션에서 **기능 구현·버그 수정·리팩토링 전에** 위키를 참고할 때 사용한다. **읽기 전용** — §9 "코드 작업 세션 wiki 갱신 금지"는 그대로 유지되며, 이 절차는 조회만 허용한다.

> **pjc 하네스 연동**: pjc plugin과 함께 설치된 경우, `pjc:plan-feature`가 컨텍스트 수집 단계(Step 1)에서 이 절차 K를 호출해 관련 feature/recipe를 참조한다. **`pjc:implement-task`도 재개 진입(plan-feature를 거치지 않는 새 세션 "T<N>부터 계속")에서 첫 Phase P 전에 이 절차 K를 세션당 1회 경량 호출한다** — plan-feature 우회 경로에서 위키 지식이 빠지는 공백을 메운다(동일 세션에서 Step 1을 이미 거쳤으면 생략). 또한 `pjc:implement-task` 완료 후 위키 갱신이 필요하면 절차 B(ingest)가 별도 세션에서 제안된다. 즉 코드 작업 전 참조(K)는 자동 연계, 작업 후 반영(B)은 사용자 확인 후 별도 세션.

1. vault 경로는 §0-1로 결정한다. **단 절차 K(코드 작업 중 read-only 참조)에서는 §0-1의 경로 재확인 질문을 띄우지 않는다** — 저장된 vault 경로가 없거나(미설정) 경로는 있으나 폴더가 사라졌으면(이동·삭제) "참조할 위키 없음"으로 보고 **조용히 건너뛴다**(코드 작업 흐름을 위키 경로 관리 질문으로 막지 않는다 — read-only 참조는 "있으면 참조, 없으면 통과"가 원칙). 경로 정정은 사용자가 위키 작업(A~J)을 명시적으로 요청할 때 처리한다. 빈 위키(index.md 없음)면 참조할 것이 없으므로 부트스트랩하지 말고 종료한다.
2. `index.md`의 "기능별 인덱스"·프로젝트 테이블·"범용 패턴" 섹션에서 작업 대상과 관련된 feature·recipe·guide·**개선 패턴(`30_knowledge/patterns/`)**을 식별한다(필요 시 vault 전체 Grep 보조). **`index.md` 상단에 sub-index 파일 목록(`index-{카테고리}.md` 등)이 있으면**(인덱스가 비대해 파일 분할된 경우), 관련 카테고리의 sub-index도 함께 읽어 거기서 식별한다 — `index.md`만 보고 분할된 인덱스를 빠뜨리지 않는다. 특히 **버그 수정·성능 개선·문제 해결 작업이면 patterns에 같은 문제의 과거 해결책이 있는지 우선 확인**한다 — 다른 프로젝트의 시행착오를 재사용해 재조사를 줄인다. patterns로 아직 승격 안 된 1개 프로젝트 교훈은 관련 feature 페이지의 "관련 지식·레시피"에 있을 수 있으니 함께 본다.
3. **식별된 페이지만 Read** — 위키 전체 정독 금지. feature의 **`## 관련 파일` 섹션으로 기능 구성 파일 지도를 먼저 파악**하고, 각주에 병기된 소스 파일 경로로 근거 코드에 점프한다.
   - **폐기 표시 확인**: 참조한 feature에 `deprecated`/`status: deprecated` 표시나 "코드에서 제거됨" 안내가 있으면, 그것은 **현재 기능이 아니라 이력**이다. 현재 구현의 근거로 삼지 말고(이미 제거된 기능), 필요하면 "과거에 이런 게 있었다"는 맥락으로만 참고한다.
   - **검색어 한/영 양방향 시도**: 위키 콘텐츠는 한글이지만 **파일명·frontmatter 키·코드 식별자는 영문**이다(예: `feat-install.md`, `feat-login.md`). 한글 개념어로 grep해 못 찾으면 영문도 시도한다 — 설치↔install, 로그인↔login, 설정↔settings, 결제↔payment, 검색↔search 등. 한 방향만 시도하고 "없다"고 단정하지 않는다. index.md 기능별 인덱스의 한글 설명은 한글이 잘 매칭되지만, 파일명·식별자까지 닿으려면 영문 검색이 필요하다. (등록 시 A-3 규칙대로 인덱스 행에 한/영이 양방향 병기돼 있으면 어느 쪽으로 검색하든 인덱스 한 줄에서 잡힌다.)
   - **무매칭 = 사실대로 보고(합성 금지)**: 양방향 검색 후에도 관련 feature/recipe/guide가 없으면 "관련 위키 자료 없음"을 그대로 밝히고 **코드를 1차 출처로 진행**한다. 위키에 자료가 있는 것처럼 지어내지 않는다 (WRONG: 무매칭인데 "위키에 ~가 있다"고 합성 → RIGHT: "관련 위키 자료 없음 — 코드로 진행").
4. `origin`/`confidence`/`(미검증)` 표기를 신뢰도 판단에 반영한다 — `(미검증)`·`confidence: low` 서술은 코드로 재확인 후 사용한다.
5. **쓰기 금지 + drift 큐잉**: 모순·드리프트(위키↔코드 불일치)를 발견해도 위키 본문 페이지·인덱스를 수정하지 않는다. 발견 사실을 사용자에게 보고하고, **동시에 vault 루트 `pending.md`에 1줄 append**한다 — 형식: `- [YYYY-MM-DD] [K-DRIFT] {프로젝트}: {요약 1줄}` (파일이 없으면 생성). 보고만 하고 끝내면 세션이 닫힐 때 발견이 유실되므로, pending.md가 다음 위키 세션(B/F)의 소비 큐 역할을 한다. **같은 프로젝트+같은 요지가 이미 pending.md에 있으면 append를 생략**한다(중복 방지). append가 실패하면(쓰기 불가 등) 보고로만 폴백한다. 본격 반영은 여전히 별도 위키 세션(B/F)에서 처리한다.
6. `log.md` 기록도 하지 않는다(위키 상태 무변경 원칙). **유일한 쓰기 예외는 위 5의 `pending.md` 1줄 append뿐**이다 — 루트 단일 파일 append로 예외를 최소화하며, 본문 페이지·인덱스·log는 계속 무변경.
