## 7. Lint 워크플로우

> 주기적 건강 검진. 별도 세션에서 월 1회(로컬 스케줄 자동 실행 권장) 또는 수동 트리거.

> **`--fix` 모드 (opt-in 자동 수정)**: `python lint.py "<vault>" --fix`는 **판단이 필요 없는 참조 무결성 동기 3종만** 자동 수정한다(`--dry-run`을 함께 주면 **무엇을 고칠지만 `[WOULD-FIX]`로 내고 한 바이트도 쓰지 않는다** — 백업·30일 정리도 건너뛴다: 정리는 폴더를 지우는 동작이라 미리보기에 섞이면 안 된다) — §7-23 미해결 질문 인덱스(양방향 — 등록 행은 섹션에 표가 있으면 **컬럼 수를 맞춘 표 행**·없으면 불릿으로 추가: 부트스트랩 골격 "표는 헤더만"과 정합·불릿형 vault 하위호환), §7-24 decisions 아카이브 포인터(양방향 — 깨진 포인터 **제거는 `## 아카이브` 섹션 안 행만**: 결정 항목 본문이 그 경로를 인용해도 지우지 않는다, §2.8 항목 불변. 섹션 밖 깨진 포인터는 제거 0건으로 남고 §7-24 WARN이 계속 가리킨다 — 검출 광역·수정 보수), §7-19 log 아카이브 인덱스 **stale 행 제거만**(누락 행 추가는 그 달 키워드 요약이 필요해 수동). 그 외 검사(기능별 인덱스 행 생성·한/영 병기·updated 기입 등)는 내용 판단이 필요해 영구 제외. 안전장치: 비 git vault 만 수정 전 원본을 `90_archive/backup/{오늘}/`에 백업(§8 미덮어쓰기 규약 — 복구는 절차 L. git vault 는 백업하지 않고 직전 체크포인트 커밋이 보호한다 — §8), 수정 내역을 `[FIXED]` 줄로 출력, 위반 0이면 무변경. **플래그 없는 기본 실행은 완전 read-only**(불변). 실행 시점은 F-2 사용자 승인 후(절차 F — 무승인 자동 수정 금지).
 **단 생성 마커가 있는 vault에서는 §7-23 삽입/제거를 건너뛴다**(그 섹션은 `--build-index`의 생성 구역이라 생성기가 정합을 보장한다. §7-24·§7-19는 마커 유무와 무관하게 그대로 동작하며, 마커 없는 vault는 3종 전부 종전대로다). 
> **각 항목은 `N. **이름** [주체] — 심각도` + 근거 포인터다.** 번호 1~36 중 폐지 2(§7-3·27)를 뺀 **34개 검사가 [기계] 30, [에이전트] 4**이고 **수행 주체는 각 항목 이름 뒤 태그(`[기계]`=lint.py 자동 · `[에이전트]`=세션이 직접 대조)가 정본이다** — 폐지 항목은 실행 주체가 없어 태그를 달지 않고, 검사는 번호 순으로 돈다. [기계] 항목의 판정은 `scripts/lint.py` 가 수행한다 — 세션은 그것을 호출해 출력을 읽을 뿐이라 **판정 기준·오탐 사례·경계 조건은 원칙적으로 여기 두지 않고** `references/lint-rationale.md` 로 내렸다(그 파일은 `lint.py` 를 고칠 때 읽는다). **단 §7-9·14·19·28·29·32 는 본문이 아직 여기 남아 있다**(rationale 에 대응 절이 없다). **[에이전트] 4건(§7-4·5·10·13)은 본문이 여기 남아 있다** — 모델이 직접 판정한다. §7-2 는 예산 트리거 조건의 정본이라 다른 문면이 그 조건을 재서술하지 못하게 하는 자리이고, 그 본문은 `schema-budget.md` 의 「7-2. 예산 준수」 절에 있다(아래 2번은 번호를 지키는 포인터).

### 검사 항목
1. **참조 무결성** `[기계]` — ERR. 판정 기준·오탐 사례·경계 조건은 `references/lint-rationale.md` 「§7-1」.
2. **예산 준수** `[기계]` — 본문은 `schema-budget.md` 「7-2. 예산 준수」.
3. **~~신선도~~ — 폐지 (v1.238.0)** — 실행하지 않는다. 번호는 재사용하지 않고 비워 둔다(폐지 경위는 `references/lint-rationale.md` 「§7-3」).
4. **모순 탐색** `[에이전트]`: 동일 주제 상충 기술 → question 페이지 생성. **보수 정책**: `A는 X` vs `A는 not-X`처럼 **실제로 상충하는 서술을 구체적으로 지목할 수 있을 때만** question을 만든다. 상충이 없으면 아무것도 생성하지 않는다(§7-10 코드 정합·§7-13 잠재 연결과 동일 — "모순 탐색을 했다"는 산출을 위해 억지 question을 지어내지 않는다). 최근 `log.md`(+ 롤오버 아카이브) 이력으로 이미 처리된 모순은 재-제기 금지. (에이전트 수행 — lint.py 범위 아님)
5. **크로스참조 품질** `[에이전트]`: 누락된 연결 제안, 프로젝트 tech_stack ↔ entity `used_by` 일치 확인. **보수 정책**: tech_stack↔`used_by` 불일치 등 **구체적 근거가 있는 누락만** 제안한다(발굴형 신규 연결은 §7-13이 담당). 근거 없으면 제안하지 않는다.
6. **기능별 인덱스 동기화** `[기계]` — ERR. 판정 기준·오탐 사례·경계 조건은 `references/lint-rationale.md` 「§7-6」.
7. **통제 어휘 위반** `[기계]` — ERR·WARN. 판정 기준·오탐 사례·경계 조건은 `references/lint-rationale.md` 「§7-7」.
8. **고아/비표준 파일** `[기계]` — WARN. 판정 기준·오탐 사례·경계 조건은 `references/lint-rationale.md` 「§7-8」.
9. **미래/이상 날짜·updated 누락** `[기계]`: `updated`·본문 날짜가 오늘보다 미래거나 비정상인지 검사 (데이터 위생). **이 항목은 두 판정을 포함한다**: ⓐ 값 이상(미래 날짜 ERR·형식 이상 WARN — **미래 날짜 ERR은 `90_archive` 제외**, 동결 백업이 exit 1을 유발하지 않게) ⓑ **필드 부재 WARN**(`UPDATED_REQUIRED_TYPES` = origin 필수 타입 + question + decision-log + convention, `90_archive` 제외) — 필드가 없으면 미래날짜 검사가 조용히 건너뛰어지고 절차 B의 델타 신뢰도 점검(§5-2b)도 기준을 잃는다(source-stub은 불변 스텁이라 `ingested`를 쓰므로 제외). (lint.py 검사)
10. **코드 정합 샘플링** `[에이전트]`: 프로젝트당 feature 1~2개를 표본으로 골라 **핵심 서술(구현/동작)이 실제 코드와 일치하는지** 대조. **표본 선정(로테이션)**: ⓐ 직전 lint 이후 변경된(updated 최신) feature 우선 ⓑ `log.md`(+ `90_archive/log/` 롤오버 아카이브)의 이전 `[LINT]` 기록에 표본으로 남은 feature는 후순위 — 매 lint마다 같은 feature만 재검증하지 않고 세션에 걸쳐 커버리지를 누적한다(**위키가 변한 lint에 한해** 이번 표본 목록을 `[LINT]` log 항목에 명시 — 절차 F-2(`references/procedures-ops.md`)). **`origin` 승격이 일어나는 지점이 이 표본 대조다** — 승격 규칙은 §11 이 정본이고, 승격·미승격 건수는 F-2 보고에 적는다.
    - **무변경 lint(발견 0건·수정 미승인)는 log를 쓰지 않으므로 그 세션의 표본이 남지 않는다** — F-2의 log 기록 조건(위키 파일이 실제로 변했을 때만) 때문이다. 그 경우 ⓑ는 참조할 이력이 없으므로 **vault 상태로 선정한다**: `updated`가 **오래된** feature 우선 + `(미검증)` 표기 보유 feature 우선(§7-12 집계가 후보를 공급). **이때 ⓐ는 적용하지 않는다** — ⓐ(updated 최신 우선)와 이 폴백(오래된 우선)은 정렬이 정반대이므로, 무변경 lint에서는 **폴백이 ⓐ를 대체한다**(ⓐ의 목적인 "직전 변경분 우선 검증"은 애초에 변경이 없었으니 대상이 없다). **ⓐ만 남기면 로테이션이 퇴화한다** — `updated`는 lint로 바뀌지 않아 매 세션 같은 순서·같은 표본이 뽑히고, 위키가 건강할수록(발견 0건이 잦을수록) 커버리지가 한 곳에 정체된다. 이 조항이 그 퇴화를 막는다. 각주 경로의 레포 실재(①)는 §7-20 lint이 전수 기계 검사하므로 표본 대조는 서술↔코드 정합(②)에 집중하되, **lint이 레포 접근 불가로 건너뛴 프로젝트(§7-20 INFO)에서는 ① 경로 실재 확인도 에이전트가 폴백 수행**한다. 불일치는 question 페이지에 기록. **보수 판정 정책**: 사실 오류만 flag(문서 누락·스타일은 무시), 최근 `log.md`(+ 롤오버 아카이브) 이력을 대조해 이미 수정된 이슈는 재-flag하지 않는다. (**에이전트 수행 — lint.py 범위 아님**)

13. **잠재 연결 발견 (크로스-프로젝트 미연결 공통점)** `[에이전트]`: 전 프로젝트 허브의 `tech_stack`·기능 목록·"프로젝트 간 공유 패턴"을 가로질러, 아직 `30_knowledge/` 지식 페이지나 허브 "공유 패턴" 링크로 묶이지 않은 **2개 이상 프로젝트의 공통점**(공유 기술/패턴/접근/함정)을 발굴해 후보로 제안한다. 5번(크로스참조 품질)이 *기존* 지식 페이지의 정합성(tech_stack↔used_by) 점검이라면, 이 항목은 *신규* 연결의 발굴이다. 위키의 명시 목적(크로스-커팅 지식 축적)을 ingest 시점에만 의존하지 않고 주기적으로 회수하는 장치. **보수 정책**: tech_stack 일치·동일 명명 패턴 등 구체적 근거가 있는 공통점만 제안(추측 링크 금지), 기존 지식 페이지·공유 패턴 링크와 중복 제외, `log.md`(+ `90_archive/log/` 롤오버 아카이브) 이력으로 이미 처리된 후보는 재-제안 금지. **자동 생성 금지** — 후보만 정보(INFO) 등급으로 제시하고, 사용자 승인 시에만 §2.5 concept(생성 조건 충족) 또는 §2.4 entity 생성, 혹은 허브 "프로젝트 간 공유 패턴" 상호링크로 반영. (에이전트 수행 — lint.py 범위 아님) **「언급됐으나 자기 페이지가 없는 개념」 검사는 두지 않는다** — 원 설계(karpathy, LLM Wiki)의 lint 항목 중 하나지만 *무엇이 페이지를 가질 만한 개념인가*는 판단이라 기계화하면 판정 불가능한 INFO가 쌓인다(v1.238.0이 없앤 「집행 주체 없는 축」과 같은 종류). 그 판단은 이 13번(에이전트 검사)과 §2.5 concept 생성 조건이 함께 맡는다.
14. **index.md·sub-index 분할 신호** `[기계]` *(생성 마커가 있으면 축소 — 아래)*: index.md 본문(frontmatter 포함 전체) 줄 수 또는 기능별 인덱스 표 행 수, **그리고 각 sub-index(`index-*.md`)의 본문 줄 수·기능별 인덱스 행 수**가 임계(`INDEX_BODY_LINES` 400 / `INDEX_FEAT_ROWS` 200) 초과면 INFO를 낸다. **index.md 초과는 B/F 세션이 §4 2단계 파일 분할로 자동 수행**한다(승인 불요 — §4 분할 수행 절차 1번). **sub-index 초과도 B/F 세션이 자동 분할한다**(승인 불요 — 순번 분할 방식은 schema-budget §4 「분할 수행 절차」 2번 「3단계(순번)」). 행 판정은 alias 표기가 아니라 **형상+대상 기반**(§3 행 형식 — 첫 컬럼 평문 ∧ wikilink 대상 `feat-*`/`40_guides/`)이라 비표준 alias 행도 정확히 센다. **⚠ 생성 마커가 있는 vault에서는 이 INFO를 「수기 분할 지시」로 읽지 않는다** — 분할은 `--build-index`가 매 실행 수행하므로(§6 「인덱스 생성」), 이 신호는 *"생성기를 한 번 돌려라"* 로만 해석한다. **못 잡게 되는 것**: 없다 — 임계 계측 자체는 그대로 돌고 INFO도 그대로 나온다. 달라지는 것은 **처방**뿐이다(수기 분할 → 생성기 실행). (lint.py 검사)

### 결과 처리
- **lint은 제안(ERR/WARN/INFO)만 하고 위키를 자동 수정하지 않는다(read-only 원칙).** 아카이브 이동·드리프트 교정 등 **적용은 사용자 승인 또는 B/F 세션**에서 수행한다(자동 변경은 의도적으로 안 한다 — 예외는 §7 서두의 `--fix` 3종과 §4 `--auto-split`뿐이다).
  - **예외는 넷이다** — ① **`§4 index 분할`**(2단계 category sub-index + 3단계 순번 파일): 라우팅이 category·등록 순서로 결정론적이고 결과를 §7-15·§7-1·§7-6이 기계 검증한다. ② **§7-2 발동으로 소비 지점(F-2·A-4·B-3)이 착수한 산문 타입 하위 분리 및 그 판정 결과인 `budget_split` 3필드 부착**: 신호(§7-2 발동)·주체(그 세 절차)·대상(산문 타입 하위 분리 + 나눌 하위가 없다는 판정의 기록)이 모두 열거로 특정된다. 판정 부착을 함께 넣는 이유는 **그것이 처방의 한 결과**이기 때문이다 — 「나눌 하위가 없다」로 닫는 것도 소비의 완결이라, 분리만 승인 불요로 두면 그 경로가 매 lint 반복된다. ③ **§7-2 발동으로 소비 지점(F-2·A-4·B-3)이 착수한 롤오버**(project 허브 `## 최근 주요 변경` → `changes.md` · decision-log → `90_archive/` 원경로 재현 파일 · `log.md` → `90_archive/log/{YYYY-MM}.md`): 보존 이동이라 원문 손실이 없고(§2.2·§2.8·§8이 append·미덮어쓰기를 규정), 주체·대상이 열거로 특정된다. **⚠ project 허브만 트리거가 다르다** — `## 최근 주요 변경` 롤오버의 트리거는 schema-types §2.2 「6번째 항목」이다(§7-2 WARN 과의 관계는 schema-budget §7-2 「별개 트리거」ⓑ). **여기 열거한 것은 「무엇을 승인 없이 해도 되는가」이지 「언제 하는가」가 아니며, 시점은 각 절(§2.2·§2.8·§8)이 정한다.** ④ **§7-2 발동으로 소비 지점이 착수한 처방 없는 타입의 상세 이관**(같은 곳 ⓕ — `source-stub`의 상세를 feature/entity로 옮기고 포인터를 남기기 · `question`을 관련 페이지에 흡수하고 `status: resolved`): **이동이라 원문 손실이 없다**(§2.1·§2.7). **이 넷만** B/F 세션이 승인 없이 수행하고 **성공은 보고하지 않는다**(넷 다 §4 분할 수행 절차를 따르며, 보고 억제는 그 6번이다 — 실패·보류만 1줄). **④를 더한 것은 술어를 넓힌 것이 아니다** — 「사람 판단이라 코드가 못 한다」와 「승인이 필요하다」는 다른 축인데 종전 문면이 그 둘을 겹쳐 두어, 스크립트가 못 하는 처방이 그대로 사용자 승인 대상으로 남아 있었다. **`--fix`는 이 예외가 아니다** — 참조 무결성 3종도 실행은 종전대로 **F-2 사용자 승인 후**다(§7 서두). confidence 강등·아카이브 이동·드리프트 교정도 모두 승인 대상으로 남는다. 예외를 "판단이 없으면 승인 불요"라는 **술어로 넓히지 않는다** — 그렇게 읽으면 `--fix`가 그 술어에 들어맞아 승인 게이트가 무력해진다. 위키 내용↔코드 사실 정합도 기계 검사(§7의 `[기계]` 항목 — `[에이전트]` 4종 §7-4·§7-5·§7-10·§7-13을 뺀 나머지. 주체 구분의 정본은 각 항목 이름 뒤 태그)로는 일부(§7-20의 파일 실존, §7-26의 커밋 수 등)만 잡히고, 본질은 §7-4(모순)·§7-10(코드 정합) **에이전트 표본 검토**가 담당한다(lint의 레포 접근 범위는 §7-20·§7-21의 파일 **실존 확인** + §7-21 진입점 심볼의 **문자열 포함 여부** + §7-26의 **git 이력 조회**(커밋 수 계산)까지다 — **코드 내용은 해석하지 않는다**. 파일이 있는지·그 안에 그 이름이 나오는지·커밋이 몇 개 쌓였는지는 보지만, **그것이 무엇을 하는 코드인지는 보지 않는다**. 심볼 검사를 포함 여부로 한정하는 이유가 그것이다 — 정의인지 호출인지 주석인지 가르려면 파싱이 필요하고, 그것은 이 도구의 일이 아니다).
- **위키 파일이 실제로 변했을 때만** `log.md`에 Lint 결과 요약 1줄 추가 — 수정 적용·큐 소비·리포트 페이지 생성 중 하나라도 있었을 때. 발견 0건이거나 수정 미승인이라 **아무 파일도 안 변한 lint는 log를 쓰지 않는다**(log 기록 자체가 vault 쓰기가 되어 비 git vault 사전 백업까지 연쇄 발동 — 무변경 점검이 부작용을 낳지 않게. 기록 조건 정본은 `references/wiki-ops-rules.md`, 절차는 procedures-ops.md F-2)
