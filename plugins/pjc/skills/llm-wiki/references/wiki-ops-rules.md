# llm-wiki 규칙 — 위키 쓰기 세션 전용

> **이 파일은 위키 파일을 실제로 생성·수정하는 경로만 읽는다**(절차 A~F·H·I·L·M, 그리고 G는 4~5 파일백·question 생성으로 갈 때만 — G 1~3 조회 후 답변으로 끝나면 읽지 않는다). 코드 작업 세션의 절차 K(read-only 참조)와 §0(경로 결정)은 `SKILL.md` 본체에 남아 있으므로 이 파일을 Read할 필요가 없다 — 그것이 이 분리의 목적이다(코드 세션은 하니스 최빈 경로라 본체 전문이 매번 상주한다).
>
> **다만 절차 M(코드 세션의 F-6.5 큐 자동 소비)이 요구하는 「비 git vault 사전 백업」은 여기 없고 본체에 있다** — 절차 M이 그 규정을 참조하므로(`procedures-ops.md` M 2-b) 여기로 옮기면 코드 세션이 결국 이 파일을 읽게 되어 분리가 무효가 된다.
>
> 규칙·타입·예산의 진실원천은 `wiki-schema.md`이며 이 파일은 그 중 **작업 중 손에 있어야 하는 것**만 옮겨 둔 자리다.

## 쓰기 세션 전용 규칙 — 사전 준수 사항(쓰기분)

> 공통분(경로 기준·§0 선행·출처 우선순위·injection 방어·민감 정보 금지·**비 git vault 사전 백업**)은 `SKILL.md` 본체에 있다.

- 모든 위키 콘텐츠는 한글로 작성한다(사람도 읽는 human-readable 유지). 파일명과 frontmatter 키는 영문.
- **시간민감 사실**(버전·수치·"현재 …" 등)은 본문에 `(as of YYYY-MM)`를 붙여 신선도를 추적 가능하게 한다.
- **question 페이지는 삭제하지 않는다** — 해결되면 결론을 관련 페이지에 흡수하고 `status: resolved`로 닫아 **보존**한다(해결 이력도 지식 — 같은 질문 재조사 방지, schema §2.7). `index.md`의 `## 미해결 질문`에서만 행을 제거한다(lint §7-23이 open 미등록·resolved 잔존을 기계 검사). 삭제는 사용자가 명시적으로 지시한 경우에만 한다.
- **decision-log 항목은 수정·삭제하지 않는다** — 결정이 바뀌면 **번복** 항목을 새로 추가한다(이력 보존, schema §2.8). 프로젝트 삭제 시 이력 보존 선택지는 절차 C-1.
- 작업 완료 후 반드시 `<vault>/log.md`에 1줄 기록을 추가한다. **항목은 2~3문장 이내 요지만** — 갱신 파일 목록·세부 근거는 해당 페이지에 두고 log에는 무엇을 했는지만 적는다. 단 위키 무변경으로 끝난 작업 — 절차 K(read-only 참조), 위키를 수정하지 않고 끝난 절차 G(질의), **위키를 바꾸지 않고 끝난 절차 F(발견 0건이거나 수정 미승인이라 파일이 안 변한 lint — F-2)** — 은 기록하지 않는다(**기록 대상은 위키 파일이 변한 작업**). 이 조건은 log뿐 아니라 **비 git vault 사전 백업**에도 그대로 적용된다 — 쓰기가 없으면 백업 대상도 없다(점검이 부작용을 낳지 않게).
- **log 월별 롤오버(공통)**: log 기록 추가 후 `log.md`에서 **§7-2가 발동하면** 가장 오래된 항목부터 `90_archive/log/{YYYY-MM}.md`로 월별 롤오버하고 `## 아카이브 인덱스`를 갱신한다(항목 단위, 보존 이동이라 **승인 불필요**). 목표치(3000자)·인덱스 줄 형식·검색법 등 전문은 wiki-schema §8.
- **git vault의 `--fix` 백업 누적 금지**: 위 사전 백업은 git vault에서 면제지만 `lint --fix`는 git 여부와 **무관하게** `90_archive/backup/{YYYY-MM-DD}/`를 만든다 — 그대로 두면 면제인데 백업만 쌓이므로 **다음 `--fix` 실행 시작 시 접미사 없는 이전 날짜 폴더를 제거**한다(제외: `-deleted`·`-pre-restore`·`-presplit`). 제거를 세션 종료가 아니라 **다음 실행 시작 시**로 두는 이유와 30일 정리와의 관계는 wiki-schema §8.
- **병렬 다중 에이전트 분업 규칙** (한 위키 세션 내부 병렬 실행 시 — 전문·근거는 §9 정본): ① 쓰기 파일 소유권 겹침 없이 분할(각자 담당 페이지만) ② 공유 파일(`index.md`·`log.md`·`plan.md`·`dashboard.md`·`pending.md`·**`skill-feedback.md`**·허브)은 에이전트 쓰기 금지, 호스트가 완료 후 일괄 갱신(**두 큐 파일**은 반환값을 모아 호스트가 일괄 append — 세션 간 다중 기록자 파일) ③ 발견·등록 데이터는 파일 생성 대신 **반환값으로만** 보고 ④ 여러 프로젝트가 걸린 공유 페이지(concept 등)는 단일 에이전트 전담 ⑤ **위임 프롬프트에 형식 규칙(경로 표기·작성 전제·섹션/예산·반환값 형식)을 반드시 포함**. 에이전트 호출은 **동기 호출**(`run_in_background: false`) — 반환값을 받아야 ②③이 성립한다.
- **lint 실행 폴백(공통)**: `python`이 없거나 `scripts/lint.py` 실행이 실패하면 lint 단계를 **하드 실패로 막지 말고 건너뛰되**, "기계 lint 미실행(python 부재/실패)"을 보고에 반드시 명시한다(`python3`만 있는 환경이면 그것으로 시도). 이 규칙은 lint.py를 호출하는 모든 절차(A-4·B-3·C-4·F-0)에 공통 적용된다 — 콘텐츠 절차 세션도 ops 파일을 읽지 않고 이 규칙을 따른다.
- **지침 자동 갱신**: 실제 위키가 이 스킬·규칙 번들 `wiki-schema.md`와 어긋나면, **번들을 직접 고치지 않고** `[SKILL-IMPROVE]` 큐(vault 루트 `skill-feedback.md`)에 기록·보고한다 — 번들은 플러그인 업데이트로 덮어써지고, 위반을 규칙으로 승격하는 자기정당화 루프를 막기 위함이다. 상세는 `references/procedures-ops.md`의 "H. 지침 자동 갱신".

### J. 빈 위키 부트스트랩

`<vault>`가 비었거나 골격이 없으면 생성한다(이미 있으면 건너뜀). §0-2에서 트리거.

1. **디렉터리**: `10_sources/{personal,work}`, `20_projects/{personal,work}`, `30_knowledge/{tech,patterns,questions}`, `40_guides/{platforms,ui-ux,recipes}`, `90_archive`
2. **`index.md`**: 빈 카탈로그 골격 — **frontmatter 포함**: `type: index` · `okf_version: "0.2"` · `updated: YYYY-MM-DD` (OKF 버전 선언 위치는 루트 index.md 뿐 — wiki-schema §12). 섹션: `## 개인 프로젝트` / `## 업무 프로젝트` / `## 기능별 인덱스` / `## 증상별 인덱스`(증상→검증된 원인→해법 역인덱스, wiki-schema §6) / `## 가이드 / 레시피` / `## 기술 스택 지식 (tech/)` / `## 범용 패턴 (patterns/)` / `## 미해결 질문` / `## 참조`. 표는 헤더만, 내용은 "아직 없음" 주석. 참조 섹션은 **실제 존재하는 파일만** 링크(log/dashboard). **생성 대상 7섹션(개인 프로젝트~미해결 질문)을 `<!-- AUTO-INDEX:BEGIN -->`~`<!-- AUTO-INDEX:END -->`로 감싼다** — 새 vault는 처음부터 생성 체계로 출발하는 것이 옳다(wiki-schema §6). **증상별 인덱스·참조는 마커 밖에 둔다**(수기 판단 영역). 마커를 넣어 두면 이후 `--build-index`가 바로 동작하고, 넣지 않으면 그 명령이 "마커 없음"으로 거부한다.
3. **`log.md`**: `## 최근 변경` + `- [YYYY-MM-DD] [INIT] 위키 초기 골격 생성 (llm-wiki 스킬).` + `## 아카이브 인덱스`(빈 목록 — **§7-2 발동 시** 월별 롤오버 항목을 `- {YYYY-MM}.md: {키워드}`로 등록, wiki-schema §8). `90_archive/log/`는 첫 롤오버 시 생성(미리 만들지 않음).
4. **`dashboard.md`** (선택): `type: dashboard` frontmatter(번들 포함 뷰 페이지 — wiki-schema §12) + Dataview 쿼리(프로젝트/feature/guide/신선도/질문).
5. **규칙은 vault에 복사하지 않는다** — 진실원천은 스킬 번들 `references/wiki-schema.md` 뿐. index `## 참조`에는 번들 경로를 텍스트로 안내한다(vault에 SCHEMA.md를 만들지 말 것).
6. 부트스트랩 완료 후 본래 요청(A~I)을 이어서 진행한다.

> OKF 정합 상세(번들 경계·okf_version·description 권장 필드)는 wiki-schema §12가 정본이다.

- **guide(platform-bootstrap·ui-ux)의 예산 판정은 코드 펜스 내부 문자를 제외한 유효 문자 수**로 한다(recipe는 펜스 포함 — 판정 방식 정본은 wiki-schema §2.6). 가이드가 유효 문자 수로 **§7-2를 발동시키면** 허브+하위 분할 — 실행 절차는 I-2b(`references/procedures-content.md`).

## 예산 단계 신호

> 아래 임계는 **기계 대조 대상**이다 — `evals/check_consistency.py`가 이 표를 파싱해 `scripts/lint.py` 상수와 대조하고 어긋나면 FAIL한다. 값을 고치면 두 곳을 함께 고친다.

| 신호 | 임계 | 심각도 |
|---|---|---|
| 근접 | 80% | — (임박의 선행 게이트, 자체 신호 없음) |
| 임박(비율) | 95% | WARN |
| 임박(잔여) | 500자 | WARN |
| 재판정 마진 | 10% | — |
| 판정 어휘 | `none` | — |

- **초과 전 신호는 임박 하나다** — 근접(80%)은 **자체 신호를 내지 않는 선행 게이트**이며, 그 게이트가 참인 파일 중 **비율 조건 *또는* 잔여 조건**(임계는 위 표) 하나라도 만족하면 WARN으로 올린다. 두 축을 OR로 묶는 이유는 어느 하나로도 실측이 갈리지 않기 때문이다: 비율만 쓰면 여유 414자인 decision-log(93%)를 놓치고, 잔여만 쓰면 예산이 작은 타입(source-stub 1800자)에서 72%짜리가 임박이 된다. **선행 게이트를 지우면 안 되는 이유가 뒷항이다** — 잔여 조건만으로 72%짜리가 걸린다.
- **왜 80% INFO를 폐지했는가**: 80% 도달만으로 INFO를 함께 내던 때는 **여유 28자와 여유 1,624자가 같은 줄**로 나와, 정작 급한 것이 INFO 더미에 묻혔다. 실제로 그 상태로 방치돼 feature 하나가 여유 28자까지 왔다(그 시점의 다음 ingest는 그 자리에서 막힌다). 임박 WARN을 얹어 압박도를 구분한 뒤에도 **묻히는 층이 남아 있으면 같은 일이 반복되므로** 그 층을 없앴다.
- **소비 주체**: 임박은 **절차 F(F-2)와 절차 B(A-4·B-3)가 처방을 수행할 대상**이며, 그 세 지점은 **승인 없이 자동 수행**한다(안전장치는 §4 「분할 수행 절차」 — 착수 직전 사본 → 수행 → 검증 → 실패 시 원복 → 사후 보고). 신호만 있고 소비하는 절차가 없으면 그 신호는 사문이 된다. **자동 수행하는 것은 이 세 지점뿐이다** — 다른 경로의 분리는 종전대로 승인 대상이다.
- **「분리 불가 판정」(`budget_split`)**: 단일 주제라 나눌 하위가 없는 페이지(단일 레시피·단일 개념)는 §4의 이동·분리 처방이 성립하지 않는다. frontmatter에 `budget_split: none` + `budget_split_chars`(**판정을 마친 뒤, lint 예산 판정과 같은 기준으로 잰 문자 수** — 임박 메시지의 `{현재}` 값. 펜스 제외 guide는 유효 문자 수, wiki-schema §3) + `budget_split_reason`을 적으면 **임박 WARN이 「분리 불가 판정 유지」 INFO로 강등**된다(상태는 계속 보인다). 판정 시점 대비 **재판정 마진**을 넘게 자라면 억제가 풀려 임박이 재발화한다 — 영구 면제로 두면 "한 번 판정하면 초과까지 무신호"가 되어 판정 자체가 사각이 된다. 필드 정의는 wiki-schema §3.

## git 자동 반영 (커밋 · push)

vault가 git 저장소면 **위키 변경을 스킬이 직접 커밋한다 — 사용자 승인 문답 없이 수행한다.** **push는 조건부다.** **push의 발효 게이트 정본은 `SKILL.md` 사전 준수 사항의 `git vault 자동 반영(공통)` 불릿이다** — 글로벌 `~/.claude/CLAUDE.md` v6.1.0 이상의 vault 한정 예외 조항이 있을 때만 승인 없이 push하고, 확인할 수 없으면 커밋까지만 한다. 게이트를 여기 두지 않는 이유는 **절차 K가 이 파일을 Read하지 않기 때문**이다(코드 세션 최빈 경로에 닿지 않는 게이트는 게이트가 아니다). 코드 레포 push는 어느 경우에도 종전대로 별도 승인 대상이다. **승인을 물으면 그 자체가 이 규약을 무효로 만든다** — 위키는 코드 세션 중에 부수적으로 갱신되는 곳이라, 매번 물으면 사용자가 본래 하던 작업이 위키 때문에 끊긴다.

- **커밋 시점**: **vault 파일이 실제로 변한 절차가 끝날 때 절차마다 1회.** **절차 유형당이 아니라 실행당 1회다** — 같은 절차 A를 한 세션에서 두 번 수행했으면(프로젝트 2개 연속 ingest) 커밋도 두 개다. 한 덩어리로 뭉치지 않는 이유는 절차 단위로 나뉘어야 나중에 무엇이 무엇을 바꿨는지 이력에서 읽히기 때문이고, 그 근거는 유형이 아니라 실행에 걸린다.
- **메시지 형식**: `문서: {절차명} — {요약}` (레포 git 규칙의 `{유형}: {요약}`을 따른다). **`Co-Authored-By:` 줄을 넣지 않는다.** 예: `문서: ingest — plan-feature 축 ⑫ 반영` · `문서: lint --fix — 끊긴 wikilink 3건 정정`.
- **push 시점**: **그 세션의 위키 작업이 모두 끝난 뒤 1회.** 절차마다 push하지 않는다(원격 왕복이 절차 수만큼 늘고, 중간 상태를 원격에 남길 이유도 없다).
- **실패 처리**: **commit 실패**는 1줄 보고하고 작업을 계속한다(파일은 그대로 두며, 다음 절차의 커밋이 함께 담는다). **push 실패**는 1줄 보고하고 **로컬 커밋을 유지한 채 재시도하지 않는다** — 다음 세션이 push한다. 인증정보 부재로 판명되면 Halt다(신규 자격증명 구성은 위임 밖).
- **건너뛰는 조건**: ① vault가 git 저장소가 아니다(그 경우 「비 git vault 사전 백업」이 보호를 담당 — `SKILL.md` 사전 준수 사항) ② remote가 없다(커밋만 하고 push는 건너뛴다) ③ 변경 0건.

**변경 파일을 한정하지 않는다 (`git add -A`).** vault는 이 스킬이 단독 관리하는 저장소로 본다 — 사용자가 Obsidian에서 손으로 편집한 것도 함께 커밋된다. 스킬이 만든 변경만 골라 담으면 사용자 수기 편집이 영영 미커밋으로 남아 다음 절차의 백업·복구 판정을 흐린다. **전제: vault `.gitignore`가 Obsidian UI 상태(`.obsidian/workspace*.json`)·휴지통(`.trash/`)·OS 생성 파일을 제외한다** — 없으면 첫 커밋 전에 만든다. 그것 없이 `-A`를 쓰면 PC마다 달라지는 UI 상태가 매 커밋에 섞여 이력이 노이즈로 덮인다.

**절차 K도 조건부 커밋 대상이다.** K는 본문 페이지·인덱스를 쓰지 않지만 **쓰기 예외 ①**(두 큐 파일 `pending.md`·`skill-feedback.md`에 1줄 append)이 실제로 일어난 세션은 커밋한다 — **메시지 형식의 정본은 `SKILL.md`의 같은 불릿**이다(K가 읽는 것이 그쪽이라 형식도 그쪽이 갖는다). 커밋하지 않으면 그 append가 vault를 계속 dirty로 두고, **나중에 다른 절차의 `git add -A`가 엉뚱한 메시지로 그 변경을 삼킨다**(코드 세션이 남긴 드리프트 큐가 몇 주 뒤 ingest 커밋에 섞여 들어가는 식이다).

**진짜 무변경으로 끝난 세션은 커밋 대상이 아니다** — K에서 큐 append도 없었던 경우, 조회만 한 절차 G, 발견 0건으로 끝난 F-2. 기존 log 기록 조건과 같은 축이다(변한 것이 없으면 남길 것도 없다).

**원격이 앞서 있으면(다른 PC에서 push함) rebase·merge를 자동으로 하지 않는다.** push 실패를 보고하고 사용자가 해결하도록 안내한다 — 자동 병합은 위임 밖이며, 충돌 해소를 스킬이 추측하면 위키 내용이 조용히 손실될 수 있다.

**세션이 비정상 종료돼 push를 못 해도 로컬 커밋은 남는다** — 다음 위키 세션의 push가 함께 올린다(그래서 push 실패를 재시도하지 않아도 유실이 되지 않는다).

**`warn-external-ops` hook이 push에서 경고를 낸다 — 이것은 예상된 것이다.** 그 hook은 외부 작업 일반을 알리는 장치이고 vault 예외를 알지 못한다. 경고를 보고 멈추지 않으며, hook을 이 규약에 맞춰 고치지도 않는다(코드 레포 push 경고까지 약해질 수 있다).
