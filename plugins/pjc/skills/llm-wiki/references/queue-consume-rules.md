# llm-wiki 큐 태그별 소비 규칙 — 위키 쓰기 세션 전용

> **이 파일을 읽는 절차는 셋이다** — 절차 **B-1 0**(ingest 진입) · **F-2**(lint 수정 승인 시 큐 소비) · **M**(경량 큐 소비). 셋 다 *소비* 시점에 이 파일을 Read 한다.
> **코드 세션의 *기록* 규약은 여기가 아니라 `queue-rules.md`(절차 K 5~6)다** — 기록과 소비는 읽는 주체가 다르다(코드 세션 ↔ 위키 세션). 합쳐 두면 코드 세션이 소비 규칙까지 로드한다.
> 회차 65 에서 절차 B 의 진입 단계로부터 갈라져 나왔다 — 그 한 단계가 절차 B 의 38% 를 차지해, B 를 여는 Read 가 매번 상한에 걸렸다.

## 게이트는 묶어 묻는다

**아래 규칙들이 요구하는 사용자 확인 중 서로 독립인 것은 한 번에 묶어 묻는다.** 이 단계에서 독립으로 발동하는 것은 다섯이다 — `[DECISION]`·`[PROJECT-FACT]`·`[K-MISS]`·`[SYMPTOM]`의 **타 프로젝트 동의**와 **미등록 프로젝트 등록 여부**. 하나씩 물으면 왕복이 다섯 번이고, 묶으면 한두 번이다.

- **게이트 수를 줄이는 것이 아니다** — 판정 항목은 그대로이고 **왕복만** 묶는다. 확인받아야 할 것을 생략하는 근거로 이 규칙을 쓰지 않는다.
- **묶을 수 없는 게이트가 셋 있다** — **A-3a**(recipe 승격)·**B-1a**(삭제 후보)·**F-2**(lint 수정 승인). 셋 다 **작업 결과에 의존**하므로(무엇이 나왔는지 봐야 물을 것이 정해진다) 그 자리에서 따로 묻는다.

## 큐 태그별 소비 규칙

0. **큐 확인 (drift 큐 소비)**: vault 루트 **두 큐 파일을 먼저 읽는다** — `pending.md`(다섯 태그)와 **`skill-feedback.md`(`[SKILL-IMPROVE]` 전용)**. 각각 없으면 그 파일은 건너뛴다. `pending.md`에서 이번 프로젝트 관련 `[K-DRIFT]` 항목을 갱신 범위에 반영한다. **항목 제거는 위키 반영을 실제로 완료한 뒤에 한다**(반영 전 제거 후 세션이 중단되면 그 drift 발견이 큐에서도 위키에서도 사라져 영구 유실 — [DECISION] 재큐잉 대비와 동형). 제거 시점에는 pending.md를 다시 읽어(그 사이 다른 세션의 append 보존, schema §9) 해당 항목만 지우고 재작성한다(소비 완료 — 남기면 다음 세션이 중복 처리). 다른 프로젝트의 항목은 그대로 둔다.
   - **`[SKILL-IMPROVE]` 항목 (플러그인 개선 후보 — 위키 반영 금지, 저장처는 `skill-feedback.md`)**: 이 태그는 위키 콘텐츠가 아니라 pjc 스킬 자체의 개선 후보이며 **`pending.md`가 아니라 vault 루트 `skill-feedback.md`에서 읽는다**(절차 K 5-1). **위키에 반영하지 않고** 사용자에게 "플러그인 개선 후보"로 보고하고 처리를 묻는다 — 개선 진행이면 하네스(플러그인) 레포 세션에서 작업하도록 안내하고 항목은 유지, 기각·이미 처리됨이면 제거, 보류면 유지. K-DRIFT와 달리 위키 세션이 스스로 소비(반영 후 제거)할 수 없으므로 **제거는 사용자 지시가 있을 때만** 한다. **단 예외가 하나 있다 — 하네스(플러그인) 레포 세션**이 *그 회차가 실제로 고친* 항목을 근거(커밋·파일 지목)와 함께 제거한다(정본은 `plugins/pjc/skills/WIKI.md`의 「하네스 레포 자신에서 작업할 때」). 이 규정이 막는 것은 **판정할 자격이 없는 세션의 제거**이지 고친 당사자 세션까지 막는 것이 아니다 — 그 예외가 없으면 큐는 유입만 되고 영영 비워지지 않는다.
   - **재보고 억제**: 보고한 `[SKILL-IMPROVE]` 항목에는 줄 끝에 `(보고됨 YYYY-MM-DD)` 표식을 붙인다(위키 세션의 `skill-feedback.md` 소비 쓰기 권한 내). 이후 세션은 **표식 있는 항목을 개별 재보고하지 않고** "플러그인 개선 후보 n건 대기 중(skill-feedback.md)" 요약 1줄로만 알린다 — 매 세션 같은 목록 반복 나열 방지. 사용자가 처리를 지시하면(기각/완료) 그때 제거한다.
   - **`[DECISION]` 항목 (결정 이력 — 대상 프로젝트 즉시 소비 / 타 프로젝트 동의 소비)**: 해당 프로젝트의 `decisions.md`(schema §2.8)에 항목을 추가하고(최신 위, 파일 없으면 templates.md의 decision-log 템플릿으로 생성 + **프로젝트 허브 "관련 위키 지식"에 링크 1회 추가** — 고아 방지) pending.md에서 제거한다. **이번 ingest 대상 프로젝트의 [DECISION] 항목은 이 세션에서 바로 소비**한다(코드 대조 불필요). **다른 프로젝트의 [DECISION] 항목은 자동 소비하지 않는다** — 잔량을 "다른 프로젝트 결정 n건 대기 중(pending.md): {프로젝트 목록}"으로 **보고하고, 사용자가 소비에 동의할 때만** 그 프로젝트들의 항목을 decisions.md에 반영한다(동의 없으면 큐에 유지). 이번 세션이 대상하지 않은 프로젝트의 결정까지 말없이 소비하면 사용자가 인지하지 못한 채 다른 프로젝트 위키가 바뀌므로, 동의 게이트를 둔다(등록 보류 항목은 종전대로 큐에 남긴다).
     - **프로젝트 매칭**: 큐의 프로젝트명이 위키 등록명과 다를 수 있다(레포 폴더명 등) — "미등록" 판정 전에 **앵커 대조를 먼저 한다**(이름이 통째로 바뀐 개명은 아래 이름 변형 검색으로 잡히지 않는다 — 실제로 한 프로젝트가 개명된 뒤 큐 67건이 고아가 된 적이 있다). 순서는 **① `[repo_url: …]` ↔ 허브 frontmatter `repo_url`**(1순위 — PC가 달라도 일치한다) **② `[repo_path: …]` ↔ 허브 "레포 정보 > 경로"**(구형 큐 항목의 폴백. **다른 PC에서 기록된 값이면 일치하지 않는데 그것은 판정 실패이지 「다른 프로젝트」의 근거가 아니다**) **③ 허브 frontmatter `project`·이름 변형(한/영·하이픈)**. 유사 허브가 있으면 사용자에게 매칭을 확인한다(미등록 오인 → 중복 등록 방지).
     - **소비 전 중복 검사**: 대상 decisions.md(+아카이브)에 같은 주제·같은 결정 항목이 이미 있으면 **추가를 생략하고 큐에서 제거만** 한다 — 재개 세션 재큐잉 등으로 이중 큐잉돼도 이중 기재되지 않게(항목 불변 규칙 때문에 중복은 영구 고착된다).
     - **번복·기각 전파 점검**: 번복·기각 항목을 소비할 때 기능별 인덱스에서 같은 기능의 feature/recipe 존재를 확인하고, 본문 서술과 모순될 수 있으면 사용자에게 해당 프로젝트 ingest(절차 B) 필요를 보고한다(즉시 처리가 어려우면 question 기록 — 결정과 본문이 어긋난 채 침묵 방치 금지).
     - **롤오버**: 추가 후 **§7-2가 발동하면** §2.8 롤오버를 즉시 수행 — 오래된 항목부터 90_archive 원경로 파일로 이동(**기존 파일이 있으면 덮어쓰지 않고 append**) + decisions.md 하단 `## 아카이브` 포인터 갱신(포인터 정합은 lint §7-24가 기계 검사).
     - **미등록 프로젝트**: 위 매칭으로도 허브가 없으면 사용자에게 "이 프로젝트를 위키에 등록할까요?"를 확인한다 — 등록 승인 시 절차 A 수행 후 소비, 보류 시 항목 끝에 `(등록보류 YYYY-MM-DD)` 표식을 붙이고 큐에 유지한다. **이 확인은 위키 세션의 경로다** — 코드 세션은 미등록 프로젝트를 큐에 `(등록보류 …)` 표식으로 남길 뿐 스스로 등록하지 않으므로, 여기 오는 항목이 있는 것이 정상이다. 사용자가 등록을 원하지 않으면(참고용 clone 등) **등록을 강요하지 않는다**. **표식 있는 항목은 이후 세션에서 개별 재질문하지 않고** "등록 대기 결정 n건(pending.md)" 요약 1줄로만 알린다(SKILL-IMPROVE 재보고 억제와 동형) — 사용자가 등록을 지시하면 그때 소비한다.
   - **`[PROJECT-FACT]` 항목 (프로젝트 작업 사실 — 대상 프로젝트 즉시 소비 / 타 프로젝트 동의 소비)**: 해당 프로젝트의 `conventions.md`(`20_projects/{카테고리}/{프로젝트}/conventions.md`, schema §2.9)에 항목을 추가하고(최신 위, **파일 없으면 templates.md의 convention 템플릿으로 생성 + 프로젝트 허브 "관련 위키 지식"에 링크 1회 추가** — 고아 방지, [DECISION] 동형) pending.md에서 제거한다. 예산 ~12000자. **§7-2 발동 시**: **①** 무효가 된 항목을 제거하고, **② ①로도 §7-2가 해소되지 않으면** 주제별 하위 파일(`conventions-{주제}.md`)로 분리 — **①보다 먼저 ⓪ 구역화가 필요할 수 있다(조건은 §2.9)** + `## 하위 문서` 목록 갱신(목록 정합은 lint §7-30ⓑ). **압축하지 않는다** — 절차 K가 매 작업 전에 읽는 파일이라 아카이브 롤오버도 하지 않는다(이동이 곧 유실, §2.9).
     - **미마이그레이션 허브 폴백**: 허브에 옛 `## 작업 규약·주의사항` 섹션이 남아 있으면 **거기에 추가하지 말고** `conventions.md`를 만들어 그리로 넣는다 — 그리고 그 기회에 허브 섹션의 기존 항목도 함께 옮기고 섹션을 제거한다(lint §7-31 INFO가 가리키던 이전 대상. `[PROJECT-FACT]` 유입이 마이그레이션을 유발하는 자연 경로다). 소비·게이트 규칙은 위 [DECISION]과 동형 — 이번 ingest 대상 프로젝트 항목은 즉시 소비, **다른 프로젝트 항목은 사용자 동의 시에만**, 프로젝트 매칭·미등록 확인(`(등록보류 YYYY-MM-DD)` 표식·재보고 억제)·제거 시점 재읽기-병합도 동일하게 따른다. **소비 전 중복 검사**: `conventions.md`(+하위 문서)에 같은 요지 항목이 이미 있으면 추가를 생략하고 큐에서 제거만 한다. **낡은 항목 갱신**: 새 사실이 기존 항목을 무효화하면 그 항목을 고치거나 지운다(§2.9 — decision-log와 달리 항목 불변이 아니다). 레포 귀속 실행 사실(빌드/테스트 명령 등)이 잘못 큐잉돼 있으면 허브에 넣지 말고 AGENTS.md 기록(`pjc:record-project-fact`) 제안으로 사용자에게 보고한다(라우팅 정본은 `references/queue-rules.md`의 K 5-3).
     - **스택 공통 지식 라우팅 (프로젝트 미매칭 — `conventions.md` 대상이 아니다)**: 항목의 `{프로젝트}` 자리가 **프로젝트가 아니라 기술·라이브러리·도구**를 가리키면(예: `gpui 공통`·`Rust/serde 공통`·`windows-rs 0.62 공통`·`도구 공통`·`Windows GUI 검증 함정`) 이 분기로 처리한다. **판정은 표기 형태가 아니라 실질로 한다** — *"`공통`으로 끝나는가"* 로 거르면 형태가 다른 항목을 놓치므로, **그 이름의 프로젝트 허브가 vault에 없고 기술·도구 이름인가**를 본다.
       - **위 「미등록 프로젝트」(`[DECISION]` 절)와의 경계**: 그쪽은 *프로젝트인데 위키에 아직 없는* 경우라 등록 여부를 묻고, 이 분기는 *애초에 프로젝트가 아닌* 경우다. 섞으면 *"gpui를 프로젝트로 등록할까요?"* 같은 잘못된 질문이 나간다.
       - **처리**: ⓐ `conventions.md`에 **넣지 않는다**(그 파일은 프로젝트 단위 규약이다) ⓑ 목적지 후보를 **판정 기준과 함께 사용자에게 보고**한다 — **entity**(`30_knowledge/tech/`, 특정 기술·라이브러리 지식. **§2.4 개수 게이트: 2개 이상 프로젝트에서 실증된 것만** — 1개 프로젝트 관측을 entity로 자동 승격하지 않는다) / **concept**(`30_knowledge/patterns/`, 프로젝트·스택을 넘는 일반 패턴) / **recipe**(`40_guides/recipes/{스택}/`, 특정 기능 구현법). 한 항목이 여러 후보에 걸치면 **복수로 제시**한다(단일 목적지를 강요하지 않는다) ⓒ 사용자가 동의하면 절차 E(지식 페이지)·절차 I(가이드/레시피)로 넘긴다 — **큐가 곧 자동 페이지 생성은 아니다**(생성·승격 게이트는 A-3a·절차 I 규약 그대로) ⓓ 동의 전에는 항목 끝에 `(스택보류 YYYY-MM-DD)` 표식을 붙여 **큐에 유지**한다.
       - **이 분기는 기각 경로가 아니다.** 목적지가 없다는 이유로 지우면 실측으로 얻은 스택 지식이 소리 없이 사라진다 — 판정은 "어디로 보낼까"이지 "버릴까"가 아니다.
       - **표식 있는 항목은 이후 세션에서 개별 재질문하지 않고** "스택 지식 대기 n건(pending.md)" 요약 1줄로만 알린다(위 `(등록보류 …)`·`(보류 …)` 억제와 동형) — 매 세션 같은 항목을 다시 판정하게 두면 그 자체가 이 분기가 없앤 문제의 재발이다.
   - **`[K-MISS]` 항목 (참조 미스 = 수요 신호 — 대상 프로젝트 즉시 소비 / 타 프로젝트 동의 소비)**: 코드 세션의 절차 K가 찾았으나 위키에 없던 지식이다(`references/queue-rules.md`의 K 5-4). 이번 ingest 대상 프로젝트의 항목은 **레포 근거를 대조해 그 지식이 실재하면 feature/recipe 생성·보강으로 반영**하고(생성·승격 게이트는 기존 A-3a·절차 I 규약 그대로 — 큐가 곧 자동 페이지 생성은 아니다) pending.md에서 제거한다. 레포에 근거가 없거나 페이지화 가치가 없으면(1회성 조회 등) **기각 사유를 보고하고 제거**한다. 같은 요지의 feature/recipe가 이미 있으면(등록 후 미스가 해소된 경우) 필요 시 보강만 하고 제거한다. 타 프로젝트 동의 게이트·프로젝트 매칭·미등록 확인·제거 시점 재읽기-병합은 위 [DECISION]과 동형.
   - **`[SYMPTOM]` 항목 (증상→검증된 원인→해법 매핑 — 대상 프로젝트 즉시 소비 / 타 프로젝트 동의 소비)**: 디버깅 세션이 규명한 증상↔원인↔해법 페이지다(`references/queue-rules.md`의 K 5-5). 이번 ingest 대상 프로젝트의 항목은 **증상별 인덱스(schema §6)의 등재 게이트 3종을 검증한 뒤 `index.md ## 증상별 인덱스`에 행을 추가**하고(섹션이 없으면 **`<!-- AUTO-INDEX:END -->` 뒤에 생성**한다 — 마커 안에 만들면 다음 `--build-index`가 통째로 치환하며 지운다. 마커가 없는 vault면 `## 참조` 앞) pending.md에서 제거한다 — ① 증상 칸이 관찰 표현인지 ② 원인이 대응 해법 페이지의 `[^src-...]` 각주로 뒷받침되는 검증된 인과인지 ③ 해법 페이지(recipe/feature)가 실존하는지. **게이트 미충족이면 반영을 보류**한다: 해법 페이지가 없으면(게이트 ③) recipe 선행(A-3a·절차 I) 또는 question을 남기고 큐 항목은 `(보류 YYYY-MM-DD)` 표식으로 유지, 원인이 미검증이면(게이트 ②) 기각 사유 보고 후 제거. **실패한 접근·잠정 진단은 등재하지 않는다**(schema §6 실패 미등재). **중복 판정은 증상+원인 기준**: 같은 증상+같은 원인 행이 이미 있으면 추가 생략·큐 제거만 하되, **같은 증상이라도 검증된 원인이 다르면 별도 행으로 추가**한다(한 증상 다원인 병렬, schema §6 — 첫 원인만 남기면 인덱스가 "유일 원인"으로 오도). 타 프로젝트 동의 게이트·프로젝트 매칭·미등록 확인·제거 시점 재읽기-병합은 위 [DECISION]과 동형.
