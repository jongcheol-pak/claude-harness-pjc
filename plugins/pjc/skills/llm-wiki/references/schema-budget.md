## 4. 파일 예산

> **[자동]** = `--auto-split`이 수행하고 세션은 호출·검증한다 / **[세션]** = 처방이 판단이라 코드가 대신할 수 없다 — **세션이 승인 없이 자동 수행하고 성공은 보고하지 않는다**(lint은 WARN을 내고 그것을 받는 것이 세션이다. `wiki-ops-rules.md` 「신호 층위」 표의 '소비 주체' 열이 갈래별 정본). **유효 문자 수 = 전체 − 비계(정본 포인터 줄·`## 하위 문서`) − (guide) 펜스 내부**이며 판정 방식의 정본은 §2.6이다. **`[사람]`이라는 세 번째 어휘를 쓰지 않는다** — 이 표가 정의하는 것은 둘뿐이고, 세션이 수행하는 것을 사람 몫으로 적으면 그 자리가 영영 소비되지 않는다.

(이 recipe·프로젝트 테이블 귀속은 절차 규칙이며 lint 기계 검사 대상이 아니다 — recipe는 category가 없어 자동 식별이 어렵고 분할은 드문 경로다.) `index.md` 본체는 sub-index 목록 + 이런 비분할 섹션(미해결 질문·증상별 인덱스(§6)·recipe 기능별 인덱스·프로젝트 테이블)만 최신으로 유지한다. **sub-index 비대 시(3단계 자동 분할)**: 분할된 `index-*.md` 자체가 임계(본문 400줄/기능별 인덱스 200행)를 넘으면 lint이 INFO로 알리고 **B/F 세션이 순번 파일(`index-{cat}-{n}.md`)로 자동 분할한다**(승인 불요 — 등록 순서 기준 결정론이라 2단계와 동일하게 판단 개입이 없다, 아래 분할 수행 절차 3단계). personal/work 종착 분류는 유지하고(새 분류를 만들지 않는다), category 내부만 등록 순서 순번 청크로 나눈다 — 무순번 `index-{cat}.md`가 초과하면 `index-{cat}-1.md`로 개명 + 초과분을 `index-{cat}-2.md`에 append, 이미 순번 체계면 마지막 순번 파일이 차면 `index-{cat}-{N+1}.md` 신설(append-only 증분 — 기존 순번 파일 재배치 없음, 신설 번호 `max+1`). ingest 신규 feature 행은 항상 해당 category의 **최종 순번 파일**에 등록하고, 순번 파일이 또 초과하면 같은 규칙으로 무제한 분할한다. `index.md` 상단 sub-index 목록에 순번 파일 전부를 나열해 조회 홉 1(index→sub-index)을 유지한다. 분할된 sub-index는 `## 기능별 인덱스` 섹션을 그대로 보유한다 — lint의 행수 측정·동기화 검사가 이 헤딩을 기준으로 한다.) | - |

- **§7-2 발동 시 위 표의 해당 타입 처방을 수행한다**(발동·종료·재발동·승급 네 조건의 정본은 §7-2 — 여기에 조건을 다시 적지 않는다) — 전 타입이 **이동·분리 처방**을 가지므로(롤오버·하위 분리·재분할·흡수 보존) 내용을 요약으로 줄이는 압축은 어느 타입에도 적용하지 않는다. 압축은 그때마다 근거·경위를 소실시키고, 내용이 계속 쌓이는 이상 무한 반복된다.
- **처방 전에 「나눌 하위 주제가 있는가」를 먼저 판정한다 — 없으면 「분리 불가 판정」으로 닫는다.** 위 표의 처방은 전부 이동·분리인데, **단일 주제 페이지에는 옮길 곳이 없다**(하나의 레시피, 하나의 개념). 그런 페이지를 억지로 허브+하위로 쪼개면 조회 홉만 늘고 2,000자짜리 조각이 남는다. 판정 절차는 셋이다 — ① 주제 축으로 나뉘는지 본다(나뉘면 표의 처방을 수행) ② 나뉘지 않으면 `budget_split` 3필드(§3)를 부착해 **판정 근거를 페이지에 남긴다** ③ 그 판정은 영구가 아니라 **판정 시점 문자 수 기준**이며, `BUDGET_REJUDGE_MARGIN`만큼 자라면 억제가 풀려 §7-2가 재판정한다. **이 경로가 없으면 처방 불가 페이지는 매 lint마다 같은 신호를 내고 아무도 처리하지 못한 채 신호만 쌓인다** — 실측에서 당시 80% INFO 기준 근접 10건 중 5건(recipe 4 + concept 1)이 이 상태였다.
- **내용을 줄이는 것이 아니라 옮기는 것이 원칙이다.** 날짜·결론·핵심 코드 스니펫, 소스 스텁과 설계 결정의 핵심은 **절대 삭제 금지**. (가이드 분할의 허브+하위 구성·펜스 제외 예산 판정은 §2.6 정본, 실행 절차는 I-2b — `references/procedures-content.md`)
- **log.md 항목은 2~3문장 이내 요지만 기록**(갱신 파일 목록·세부 근거는 해당 페이지에 — log는 무엇을 했는지만). 토큰 비대 방지: log는 모든 위키 작업에서 읽히는 파일이다

### 재분할 일반 규칙 (타입 무관 — 분할한 파일에서 §7-2가 다시 발동할 때)

> 분할은 2단계에서 멈추지 않는다. **하위 파일에서 §7-2가 다시 발동하면 같은 규칙으로 재분할하며 횟수 제한이 없다**(재발동 조건은 §7-2 정본) — 2단계까지만 규정하면 하위가 찼을 때 갈 곳이 없어 다시 압축으로 돌아가기 때문이다. 이 규칙은 `index.md`가 이미 쓰고 있는 3단계 순번 분할(위 표 index.md 행)을 타입 무관으로 일반화한 것이다.

- **적용 대상**: 하위 페이지 분리 처방을 가진 전 타입 — feature(§2.3) · entity(§2.4) · concept(§2.5) · guide(§2.6) · index(위 표). **convention(§2.9)은 v1.303.0부터 대상이 아니다** — 분리 처방 자체가 없어졌다. 그때까지 만들어진 하위는 그대로 남고 ② 목록·복귀 링크 규정이 계속 적용된다.
- **① 재분할**: §7-2가 발동한 하위 파일을 같은 기준(주제·기능 단위, 또는 index처럼 등록 순서 순번)으로 다시 나눈다. 기존 파일을 재배치하지 않고 **새 파일을 추가**한다(append-only — 순번 체계면 `max+1`).
  - **순번은 루트 family 기준이고 접미를 중첩하지 않는다** — 이미 `{stem}-{n}`인 파일을 다시 나눌 때 그 이름에 순번을 또 이으면 `{stem}-{n}-{m}`이 되고 실제로 3단까지 자란 것이 vault 에 3건 있었다. 신설 이름은 **루트 stem 의 다음 형제 순번**이다(`{stem}-2`를 나누면 `{stem}-4`). 구현은 `lint.py`의 `_root_stem` 이고 순번 계산·이름 조립·형제 탐색 세 자리가 그것을 공유한다. **조회 계층은 파일명이 아니라 ②의 목록·복귀 링크가 유지하므로** 하위가 루트와 형제 이름을 가져도 정합이 깨지지 않는다(§7-30 ⓔ가 복귀 링크로 상위를 확정한다).
- **② 진입 파일의 `## 하위 문서` 목록에 전 파일을 나열한다 (조회 홉 1 — 전 타입 공통)**: 분할한 파일들의 **진입 파일**(원본 페이지·허브·`conventions.md` 등)에 하위 파일 전부를 목록으로 둔다 — 진입 파일 하나만 열면 나머지 위치를 전부 알 수 있어야 한다. **목록 없이 쪼개면 분할이 곧 유실**이다(읽는 경로가 없는 보존은 없는 것과 같다).
  - **형식(전 타입 동일)**: 진입 파일 하단 `## 하위 문서`에 `- [[{하위 경로}|{표시 이름}]] — {담당 범위 1줄}`. 담당 범위는 *"언제 이 파일을 읽어야 하는가"*를 적는다(§2.9의 규정을 전 타입으로 넓힌 것 — 그 한 줄이 절차 K의 「어느 하위를 열지」 판정에 쓰인다).
  - **하위 상단에는 복귀 링크**: `> 상위 문서: [[{진입 파일}|{표시 이름}]]`. 이 줄이 「분리해 나온 하위」의 판정 신호이고(lint §7-30ⓔ), 하위만 열고 들어온 세션이 전체 맥락으로 돌아가는 경로다.
  - **`index.md`만 예외**다 — sub-index 목록은 상단에 두고 형식도 다르다(§7-15가 그쪽을 본다). 산문 타입은 전부 위 형식을 쓴다.
  - **정합은 기계가 본다**: §7-30 ⓑ(convention)·ⓓ(guide)·**ⓔ(그 밖의 산문 타입)**가 목록↔실파일 양방향을 검사한다.
- **③ 허브 개념이 없는 타입**(feature·entity·concept — 별도 허브가 없다): 자동 분할은 원본을 `{stem}-{n}.md`로 나누므로 **원본 자신이 진입 파일**이고 위 ②의 `## 하위 문서` 목록이 그 자리를 담당한다. 더해 그 기능·기술·패턴을 가리키는 상위 참조(허브 `## 기능 목록`·`index.md` 기능별 인덱스·관련 지식 링크)에도 **분할된 전 페이지를 등록**한다 — 인덱스 쪽 도달 경로는 §7-30ⓒ가 별도로 본다.
- **③-1 본문을 옮긴 자리에는 정본 포인터를 남긴다**: 산문 하위 분리는 헤딩을 원본에 남기고 본문만 옮기므로(§7-2 처방), 그 자리에 `**정본은 [[{하위}|{표시 이름}]]의 「{절 이름}」이다** — {한 줄}`을 둔다. **포인터가 가리키는 파일과 절 이름이 실재해야 한다** — lint §7-30이 파일뿐 아니라 **절 이름까지** 대조한다(§7-1 링크 검사는 파일까지만 보므로, 절이 사라진 「옮겼는데 못 찾는」 상태는 그 검사만이 잡는다).
- **④ 내용은 무손실**: 원본의 장·절 번호를 유지하고 삭제·축약하지 않는다. 재분할은 이동이며 압축이 아니다.

### 분할 수행 절차 (index.md 2단계 category + sub-index 3단계 순번 파일 분할, 산문 타입 하위 분리, 그리고 롤오버 — 실행 스텝)

> lint §7-14 INFO(본문 400줄/기능별 인덱스 200행 초과)를 받았을 때, **그리고 §7-2 발동으로 소비 지점(F-2·A-4·B-3)이 착수한 산문 타입 하위 분리 또는 롤오버(project 허브 `## 최근 주요 변경`·decision-log·log.md — **project 허브는 §2.2의 「6번째 항목」이 트리거이고 문자 예산과 무관하다**)를 수행할 때** 아래 순서대로 수행한다. 위 표의 분할 **상태 규정**(무엇이 어디에 있어야 하는가)을 실행 순서로 옮긴 것 — 두 규정은 항상 일치해야 한다.
>
> **두 경로 모두 「무엇을 어디로 나눌지」가 결정론이다** — 그래서 코드가 수행할 수 있다(근거는 `references/lint-rationale.md` 「§4 분할 수행 절차 2·4번」).

1. **자동 수행 (사용자 승인 불요)**: 세션이 `--auto-split`을 **호출**하고, 그 결과를 5번으로 **검증**한 뒤 6번의 **「보고 억제」를 적용한다**(성공은 알리지 않고 실패·보류만 1줄) — 승인을 묻지 않는다. **옮기는 일 자체는 스크립트가 한다**(§7-2 번복 — 경계를 스키마가 정한 `## ` 섹션·항목 단위로 고정하면 「무엇을 옮길지」가 크기·시간 순서로 결정돼 판단이 사라진다). **아래 근거는 index 경로 한정이다** — 산문 분리와 롤오버의 승인 불요 근거는 §7 결과 처리의 **예외 ②·③**이다(위 서두 참조). 특히 **롤오버는 「보존 이동이라 원문 손실이 없다」**가 근거이지 결정론이 아니다. index 분할은 **판단이 개입하지 않는 결정론적 구조 정리**다: 어느 행이 어느 파일로 가는지는 위 표대로 **프로젝트 category로 자동 결정**되고, 결과는 §7-15(sub-index 목록 정합)·§7-1(깨진 링크)·§7-6(기능별 인덱스 동기)이 기계 검증하며, 실패하면 **이 항목에서 만든 사본**으로 되돌린다(복원 절차는 5번). "승인할지 말지"에 사용자가 보탤 판단이 없으므로 게이트는 마찰만 남긴다.
   - **범위는 2단계 category 분할과 3단계 순번 파일 분할이다** — 둘 다 라우팅이 결정론적(2단계는 category로, 3단계는 category 내부 등록 순서 순번으로)이라 자동 수행한다. 3단계는 무순번 `index-{cat}.md` 초과 시 `index-{cat}-1.md` 개명 + `index-{cat}-2.md` append, 순번 체계면 최종 순번 파일이 차면 `index-{cat}-{N+1}.md` 신설(append-only, `max+1`) — 위 표의 sub-index 규정을 실행 순서로 옮긴 것. **1단계(본체 비분할 섹션 분리)도 자동 수행한다** — `--build-index`가 본체가 임계를 넘으면 **고정 4파일**로 덜어낸다: `index-projects.md`(프로젝트 카탈로그) · `index-tech.md`(기술 스택 지식) · `index-patterns.md`(범용 패턴) · `index-questions.md`(미해결 질문). **어느 섹션이 어느 파일로 가는지가 고정 목록이라 판단이 없다**(`AUX_INDEX_GROUPS`) — 종전에 이 자리를 「제안」으로 둔 이유는 *"어떤 구역으로 나눌지"*가 판단이라는 것이었는데, 구역을 목록으로 못박으면서 그 전제가 사라졌다. **남는 「제안」은 `## 기능별 인덱스` 아래를 `### ` 소제목으로 나누는 것뿐**이며 그것은 행수 신호(§7-14) 정확도를 위한 편의라 자동화 대상이 아니다. **이 문단은 index 경로의 자동화 근거를 말하는 것이고, §7-2 발동으로 소비 지점(F-2·A-4·B-3)이 착수한 산문 타입 하위 분리는 여기가 아니라 §7 결과 처리의 예외 ②가 근거다**(그쪽은 결정론이 아니라 열거로 범위를 특정한다). 이 제안 한정은 그대로 유지한다(자동화 근거가 결정론이므로 그 근거가 없는 곳으로 넓히지 않는다).
   - **수행 시점은 그 세션의 주 작업 완료 후**다(ingest는 feature 행을 더하므로 작업 중 분할하면 직후 다시 임계를 넘는다).
   - **트리거는 "그 시점 임계 초과"** — 이번 세션이 만든 초과인지 이전부터 넘어 있었는지 가리지 않는다. B-3의 "델타 기준"은 *lint 경고 해소 책임의 범위* 규정이라 분할 트리거와 무관하다(`index.md`는 전 프로젝트 공용 단일 파일이라 "남의 잔여"라는 개념이 없고, 기존 초과를 넘기면 아무도 수행하지 않아 영구 누적된다).
   - **착수 직전 상태를 잡아 둔다 — git vault면 체크포인트 커밋 1회**(`references/wiki-ops-rules.md` 「git 자동 반영」의 「체크포인트 커밋」 · `pass` 당 1회 · 실패하면 착수하지 않는다), **비 git vault면 사본을 `90_archive/backup/{날짜}-{시각}/`에 만든다**(index 분할·산문 분리·롤오버 공통 — 5번 원복의 기준). **대상은 이번 분할·분리로 수정될 파일 전부**이고 **그 집합이 곧 5번이 되돌릴 목록이다** — 구현에서는 `SplitSession.current_claims`가 이 집합이고 신설물은 `created`가 따로 갖는다(둘이 갈리면 그 차이가 그대로 복원 누락이다). 목록 자체는 아래와 같다 — index는 `index.md`+대상 sub-index, 산문은 **원본 파일 + 목록·참조를 갱신할 파일 전부**(convention은 `conventions.md`, guide는 허브 **+ `index.md`**(§2.6 등록 대상), feature·entity·concept은 **§4 「재분할 일반 규칙」 ③의 상위 참조 중 실제로 이 페이지를 등록한 곳 전부** — 허브 `## 기능 목록`·`index.md` 기능별 인덱스·관련 지식 링크 중 해당하는 것 **여럿일 수 있다**). **롤오버 처방**(project 허브·decision-log·log.md)도 같은 절차를 쓴다 — 사본 대상은 **원본 + 옮겨 담을 아카이브 파일**(project는 허브 + `90_archive/…/changes.md`, decision-log는 원본 + 아카이브 재현 파일, log.md는 원본 + `90_archive/log/{YYYY-MM}.md`)이다. 원본만 복사하면 4번에서 갱신한 등록처가 원복되지 않는다. 세션 사전 백업 폴더 `{YYYY-MM-DD}/`를 쓰면 §8 미덮어쓰기 규정에 걸려 사본이 생성되지 않는다).
2. **신설 파일 생성 · 4. 등록(도달 경로 확보)** — **내부 동작은 `--auto-split`이 수행한다.** 경로별 파일 이름·형태·등록처의 정본은 위 예산 표와 §2.3~§2.9 타입 규정이고, 그 결정론적 라우팅의 근거·경계는 `references/lint-rationale.md` 「§4 분할 수행 절차 2·4번」에 있다. **세션이 이 두 스텝에서 하는 일은 없다** — 호출(1번)과 검증(5번) 사이의 구간이다. `[세션]` 처방(source-stub·question의 상세 이관)만 예외이며 그 행동은 예산 표가 규정한다.
     - **3단계(순번)**: 초과한 sub-index가 무순번(`index-{cat}.md`)이면 `index-{cat}-1.md`로 개명 + `index-{cat}-2.md` 신설, 이미 순번(`index-{cat}-N.md`)이면 `index-{cat}-{N+1}.md` 신설(`max+1`). 새 파일도 `type: index`·`## 기능별 인덱스` 헤딩 보유.
3. **내용 이동(잘라내기)** — **산문 타입**은 가장 큰 `## ` 섹션의 **본문만** 하위 파일로 옮기고(요약·압축하지 않는다) 원본에는 **헤딩 + 정본 포인터 1줄**을 남긴다(③-1). **절을 통째로 들어내지 않는다** — 필수 섹션 게이트(§7-18ⓐ·§7-21)가 깨지고, 제목까지 사라지면 목차에서도 그 주제가 보이지 않아 「어디로 갔는지 물을 실마리」조차 없다. **각주 정의는 원본에 남기고 하위에도 복제한다**(§7-18ⓑ는 문서 전체의 `[^src-` 개수를 보므로 정의를 통째로 옮기면 자동 분할이 스스로 위반을 만든다). **index 분할**은 project feature 행만 해당 category의 sub-index로 옮긴다(3단계면 초과분을 신설/개명 순번 파일로 — append-only, 기존 순번 파일은 재배치하지 않는다). **롤오버**는 오래된 항목부터 아카이브 파일로 **append 이동**한다(덮어쓰지 않는다 — 목적지에 파일이 이미 있으면 시간순 append. 항목 단위로만 자르고 쪼개지 않는다 — §2.2·§2.8·§8). 본체에 남는 비분할 섹션의 목록·귀속은 위 표 규정을 따른다(여기 재열거하지 않음).
5. **검증**: lint 재실행 — 경로별로 볼 항목이 다르다.
   - **index 분할**: 깨진 wikilink 0, 기능별 인덱스 동기(§7-6, 본체+sub 합산 검사) 통과, sub-index 등록(§7-15) 통과, 한/영 병기(§7-16) 유지 확인.
   - **산문 타입 하위 분리 (전 타입 공통)**: 깨진 wikilink 0(§7-1), **분리한 원본과 신설 하위 모두에서 §7-2가 발동하지 않는 상태**(종료 조건은 §7-2 정본 — 정지 가드 예외 포함. 하위가 여전히 발동하면 압축하지 말고 §4 「재분할 일반 규칙」), 고아 페이지 0(§7-8 — 신설 하위가 어디서도 링크되지 않으면 조회 경로 밖이다), 타입별 필수 섹션 유지.
   - **롤오버**(project 허브·decision-log·log.md): 옮긴 내용이 아카이브에 **append로 보존**됐는지(덮어쓰기 0) + 원본이 목표치 이내인지(**단 §2.8·§8의 「항목 단위 정지 가드」가 발동한 경우 — 한 항목이 커서 목표치 밑으로 못 내려간 경우 — 는 예외이며 실패로 판정하지 않는다**) + **포인터·인덱스 정합** — project는 §7-30ⓐ(허브 `## 아카이브` ↔ `changes.md` 양방향), decision-log는 §7-24, log.md는 §7-19(`## 아카이브 인덱스` ↔ 월별 파일). 롤오버는 **분리가 아니라 이동**이라 위 두 갈래의 「신설 하위 등록」 대신 이 포인터 정합이 도달 경로를 담당한다.
   - **도달 경로(4번 등록)의 기계 검증은 §7-30 이 맡는다** — ⓑ `convention`(`conventions.md` 의 `## 하위 문서` ↔ 하위 파일) · ⓓ `guide` 허브의 `## 하위 문서` ↔ 하위 · ⓔ 그 밖의 산문 타입(feature·entity·concept)의 `## 하위 문서` ↔ 하위를 양방향으로, ⓒ guide·entity·concept 의 인덱스 등록을 검사한다. **남는 수기 확인은 생성 표 하나다**(guide 인덱스는 `--build-index`가 `index-guides.md`로 파생하므로 수기 등록 대상이 아니지만, **생성기를 돌리지 않으면 새 하위가 그 표에 오르지 않는다**. §7-16은 **이미 있는 행의 병기만** 보고 행 누락은 보지 않으므로, 분리 후 생성기를 한 번 돌려 신설 페이지가 표에 실제로 오른 것을 눈으로 확인한다. ui-ux 가이드는 그 표가 유일 검색 경로라 누락이 곧 유실이다) — 여기서 "lint 통과"만 보고 넘기면 등록 누락이 조용히 통과해 신설 페이지가 조회 경로 밖에 남는다(§7-8 고아 검사는 **어디서든** 링크되면 통과하므로 "올바른 등록처"까지는 보지 못한다).
   - **실패 시 원복 후 보고(자동 재시도 금지)**: 원복은 **1번이 잡아 둔 상태로 되돌리기 + 그 회차가 만들거나 늘린 것 되돌리기**로 한다 — git vault면 **`git checkout -- <1번의 대상 목록>`**(구현은 `current_claims`), 비 git vault면 **사본 복원**이다. 이어서 index는 신설 `index-*.md` 제거, 산문은 그 회차에 만든 하위 파일 제거, **롤오버는 원본과 아카이브 파일 둘 다 되돌리기**(아카이브가 그 회차에 신설된 것이면 파일째 제거) — 「방금 append한 블록만 골라 지우기」를 쓰지 않는다. 한 회차에 여러 항목이 옮겨지거나 하위 불릿 포함 블록이면 경계를 되짚는 것이 통째 복원보다 실패하기 쉽고, **1번이 아카이브 파일까지 대상으로 잡는 이유가 바로 이것**이다.
     - **⚠ 되돌림은 1번의 목록으로 한정한다 — `git reset --hard`·`git clean -fd` 같은 워킹트리 전역 명령을 쓰지 않는다.** 근거는 둘이다. ① **세션 중 사용자 편집이 설계 전제다** — `references/wiki-ops-rules.md`가 *"사용자가 Obsidian에서 손으로 편집한 것도 함께 커밋된다"*로 그것을 전제하는데, lock은 **스킬 세션 간** 배타 장치라 Obsidian은 그 파일을 알지 못하고 잠금 구간에도 쓴다. 체크포인트와 원복 사이에 사용자가 만든 새 파일은 미추적 상태라 `clean -fd`에 **영구 삭제**된다. ② **lint ERR의 원인은 예상 밖 구조**(수기 편집된 비표준 행 등)이므로 자동 교정의 반경이 넓을수록 훼손을 키운다. **①은 체크포인트 커밋이 생겨도 사라지지 않는다** — 커밋이 없애는 것은 *"미커밋 주 작업이 함께 지워진다"*는 종전의 세 번째 근거뿐이고, 나머지 둘은 그대로다.
6. **보고 억제**: **성공한 분할·분리·롤오버는 사용자에게 알리지 않는다**(index 분할·산문 분리·롤오버 공통) — 진행 보고에도, 완료 보고의 파일별 1줄에도 담지 않는다(이 항목이 정본이고 `SKILL.md` 「진행 보고 분량」은 여기를 가리킨다). **사용자가 그 정보로 내리는 결정이 없기 때문**이다: 승인 게이트가 없으니 승낙할 것이 없고, 되돌릴 판단은 무엇을 옮겼는지가 아니라 **결과가 틀렸는지**로 하는데 그것은 5번이 이미 기계로 검증한다. **가시성은 사라지지 않고 자리를 옮긴다** — 무엇이 만들어졌는지는 7번의 `log.md` `[SCHEMA]` 기록이, 되돌리는 수단은 1번이 잡아 둔 착수 직전 상태가 담는다(git vault면 체크포인트 커밋 — git 이력에, 비 git vault면 `{날짜}-{시각}/` 사본 — vault에 남아 나중에 언제든 조회된다). **예외는 실패·보류다** — 5번이 원복했거나 처방을 못 돌린 경우는 **사유 1줄**을 낸다(그 페이지는 예산에 막힌 채 남아 다음 세션이 그 자리에서 멈춘다). **그 1줄에도 예산 수치(`{현재}/{예산}자`·여유 문자 수·백분율)를 적지 않는다** — 사용자가 그 숫자로 내리는 결정이 없고(처방은 세션 몫이다), 숫자를 옮기는 순간 그 페이지가 **「사용자가 나눠야 할 것」으로 읽힌다.** 적는 것은 *무엇을 못 했고 왜인가*뿐이다.
7. **기록**: `log.md`에 `- [YYYY-MM-DD] [SCHEMA] {index 분할|산문 분리|롤오버} — {대상}: {신설 파일}. (사유: 임계 초과)` 1줄을 **`--auto-split`이 남긴다**(세션이 손으로 적지 않는다). **그 기록이 `log.md`를 다시 임계로 밀 수 있으므로 기록 직후 롤오버 트리거를 1회 재점검하고, 그 재점검이 수행한 처방도 같은 형식으로 기록한다** — 연쇄를 끊는 것은 **「1회」라는 횟수 고정**이지 기록의 부재가 아니다(재점검 뒤에는 점검이 없으므로 그 기록이 다음 회를 부르지 않는다). 종전에는 그 회차의 기록을 생략했는데, 연쇄 차단이라는 목적은 횟수 고정만으로 이미 달성되고 생략의 대가는 **파일은 만들어졌는데 기록이 없는 상태**였다 — **6번이 성공을 보고하지 않으므로 이 기록이 「무엇이 만들어졌는가」의 유일한 자리**이고 5번의 원복도 그것에 기대므로, 기록에서 빠진 파일은 되돌릴 대상에서도 빠진다. 예) index는 `index 분할 — index.md: index-work·index-work-1/index-work-2`, 산문은 `산문 분리 — conventions.md: conventions-release.md`.

## 7-2. 예산 준수 (Lint 검사 항목 2)

2. **예산 준수**: 모든 파일 문자 수 확인(산문 타입 — index는 행/줄 수, log는 문자 수 별도) 후 §4 표의 해당 타입 처방(롤오버·분리·재분할)을 수행한다. **이 항목이 예산 처방 트리거의 정본이다** — **발동·종료·재발동·승급** 네 조건을 아래 소불릿에서만 정의하고, §2.x 타입 절·§4 표·§8·절차 문서(F-2·A-4·B-3·I-2b)·`lint.py`의 **처방·소비 주석**은 조건을 **다시 쓰지 않고** `§7-2 발동 시`로 가리킨다. **예외는 `lint.py`의 임계 상수 근거 주석 하나다** — 그 자리는 *"이 상수를 지우면 안 되는 이유"*를 적는 곳이라 **조건의 형태(선행 게이트 AND (비율 OR 잔여))를 말하지 않으면 근거가 성립하지 않는다.** 그 주석은 조건을 **정의**하는 것이 아니라 조건을 **근거로 인용**하며, 임계 값 자체는 `references/wiki-ops-rules.md` 「예산 단계 신호」 표가 정본이고 `check_consistency.py`가 상수와 기계 대조한다. 같은 조건이 여러 자리에 살면 한 자리만 고쳐져 *"헤딩은 임박인데 본문은 초과"* 같은 반쪽 상태가 생기는데, **그 드리프트는 개별 지점을 고치는 방식으로 6라운드를 돌아도 수렴하지 않았다**(v1.177 실측 — 매 라운드가 다른 형태의 같은 규정을 찾아냈다). 정본이 하나면 그 상태를 만들 수 없다. **guide는 `guide_kind`(§2.6)가 예산을 선택하므로 값이 부재하거나 통제어휘 밖이면 WARN** — 침묵하면 기본 9000자가 적용돼 recipe 8500자 예산이 조용히 우회된다(WARN 문구에 "기본 9000자 적용됨"을 병기해 가시화). **platform-bootstrap·ui-ux guide의 판정은 백틱 펜스 내부 문자를 제외한 유효 문자 수**(미종결 펜스는 전체 판정, recipe·타 타입은 펜스 포함 — §2.6 예산 판정 방식 정본)이며 초과 WARN 문구에 "코드 펜스 N자 제외"를 병기한다. **층을 하나로 줄인 이유는 압박도가 구분되지 않으면 신호가 묻히기 때문이다** — 80% INFO 하나뿐일 때 여유 28자와 여유 1,624자가 같은 줄로 나왔고, 실제로 INFO 99건 속에서 소비되지 않은 채 feature 하나가 여유 28자까지 왔다. 임박 WARN을 얹은 뒤에도 그 INFO 층이 남아 있으면 같은 일이 반복되므로 층 자체를 없앴다. **임박은 절차 F(F-2)·절차 B(A-4·B-3)가 처방을 수행할 대상**이며, 그 세 지점은 **승인 없이 자동 수행**한다(안전장치는 §4 「분할 수행 절차」 — 착수 직전 상태 고정(git vault 면 체크포인트 커밋 · 아니면 사본) → 수행 → 검증 → 실패 시 원복 → 보고 억제(성공은 무보고·실패만 1줄)). **나눌 하위 주제가 없는 페이지는 `budget_split` 판정(§3)으로 임박 WARN이 「분리 불가 판정 유지」 INFO로 강등된다** — 억제는 판정 시점(`budget_split_chars`) 대비 `BUDGET_REJUDGE_MARGIN` 이내에서만 유효하고, 그만큼 자라면 풀려 재판정을 강제한다. §4의 *"예산 임박 도달 시 해당 타입 처방을 수행"* 규정에 기계 신호를 붙인 것이다 — 신호가 없으면 그 문장은 사문이고, **초과 시점에야 발견하면 그 세션이 하려던 작업이 막힌다**(project 허브에서 여유 35자를 만나 압축을 7차례 반복한 관측 — 그 반복을 없애려고 §4·§8의 전 타입 처방을 이동·분리로 바꿨다). **처방을 수행하는 것은 `--auto-split`이고, 세션은 그것을 호출·검증한다.** 종전에는 *"자동 수리는 하지 않는다 — 무엇을 옮길지는 판단이라 index 자동 분할의 결정론 근거가 성립하지 않는다"*고 규정했는데, **그 전제는 옮길 단위를 임의로 잡을 때만 참이다.** 경계를 **스키마가 이미 정한 `## ` 섹션**과 **항목 단위**로 고정하면 「무엇을 옮길지」가 크기·시간 순서로 결정돼 판단이 사라진다 — 롤오버 3종(§2.2·§2.8·§8)은 이미 그렇게 규정돼 있었으므로 이 번복은 **새 자동화가 아니라 미구현 코드화**다. 세션이 하는 일은 셋이다: **호출**(`python "<skill>/scripts/lint.py" "<vault>" --auto-split`) · **결과 검증**(§4 분할 수행 절차 5번) · **보고 억제**(6번 — 성공은 알리지 않고 실패·보류만 1줄). `--fix`는 여전히 참조 무결성 3종 한정이고 승인 게이트도 그대로다 — 이 번복은 **§4 처방**에만 적용된다. **수리 경로가 정해진 타입은 **초과 WARN**에 그 처방을 병기한다** — `project`(최근 변경 롤오버 §2.2·§8 + 작업 규약 `conventions.md` 분리 §2.9) · `decision-log`(롤오버 §2.8) · `convention`(무효 항목 제거 §2.9 — 분리·재분할은 v1.303.0에 폐지했다). 초과 시점에 침묵하면 정작 고쳐야 할 때 방법을 못 받는다. **임박 구간의 신호 유무와 문구는 아래 「발동」 ⓐ~ⓒ가 정본이다** — 처방을 기계가 수행할 수 있으면 임박에 아무 신호도 내지 않으므로(ⓐ) 「양쪽에 병기」는 더 이상 성립하지 않는다. **`BUDGET_OVER_ONLY_TYPES`(convention)는 임박 구간에 아예 들지 않아** 위 병기가 초과 한 곳에서만 일어난다
   - **발동**: 유효 문자 수가 예산의 `BUDGET_NEAR_RATIO` 이상**이면서**(선행 게이트 — 자체 신호는 내지 않는다) `BUDGET_CRITICAL_RATIO` 이상이거나 여유가 `BUDGET_CRITICAL_SLACK` 미만이면 처방이 발동한다. **신호는 「그 처방을 기계가 수행할 수 있는가」로 갈린다** — ⓐ **수행 가능하면 신호를 내지 않는다**(`--auto-split`이 F-2·A-4·B-3에서 처리하므로 사람이 알 필요가 없다. 임박 구간에 한하며 **초과 WARN은 그대로 난다**) ⓑ′ **수행 불가하면 WARN**을 낸다 — **처방이 없으면** 종전 `예산 임박` WARN을 발동 조건 그대로(즉 선행 게이트가 아니라 발동선에서) 낸다 — `source-stub`처럼 **어느 처방도 없는 타입**이 여기 해당하며, 이 갈래를 빼면 그 타입이 초과 직전까지 조용해진다. **침묵은 「기계가 맡았다」는 뜻이지 「무시해도 된다」가 아니므로**, 맡을 주체가 없는 파일은 반드시 신호를 받는다 ⓒ **「분리 불가 판정」(`budget_split`)이 유효하면 INFO로 강등**한다(상태는 보이되 수리 의무 없음). 예산을 넘긴 뒤에는 초과 WARN이 별도로 난다 — **초과 WARN은 처방 가능 여부와 무관하게 항상 난다**(ⓐ의 침묵이 임박 구간에 한정되는 이유이자, 자동 처방이 한동안 돌지 않아도 결국 드러나게 하는 안전장치다). 임계 값의 정본은 `references/wiki-ops-rules.md` 「예산 단계 신호」 표이며 **여기 산문에 수치를 복제하지 않는다**(그 표만 `check_consistency.py`가 lint 상수와 기계 대조하므로, 산문에 값을 적으면 그 자리가 무가드로 남는다).
   - **종료**: 처방은 **이 조건이 풀릴 때까지** 반복한다 — 종료 기준은 「예산 이내」가 **아니다.** 한 항목·한 절만 옮겨 문턱 바로 아래로 내려오면 다음 추가로 곧 재발화하므로, 발동이 해소될 때까지 오래된 것부터 반복한다. **정지 가드**: 항목·절 단위로만 자르므로 하나가 커서 해소되지 않으면 **그것까지만 옮기고 멈춘다**(쪼개느니 약간 큰 게 낫다) — 그 경우 §4 5번 검증은 실패로 판정하지 않는다. 타입이 **더 낮은 목표치**를 따로 정하면(log.md의 3000자 이하 — §8) 그쪽이 우선한다.
   - **재발동**: 분할·분리한 **하위 파일도 같은 조건으로 재판정**된다. 하위가 다시 발동하면 압축으로 돌아가지 말고 §4 「재분할 일반 규칙」에 따라 같은 방식으로 재분할한다(무제한). **재분할의 기준은 별도 임계가 아니라 이 조건이다** — 진입만 임박으로 두고 재분할을 초과 기준으로 남기면 같은 파일에 두 트리거가 공존한다.
   - **승급**: 다단 처방(예: project 허브의 `## 최근 주요 변경` 롤오버 → 그래도 해소되지 않으면 작업 규약 분리)에서 **다음 단계의 진입 조건도 이 조건이다** — *"앞 단계로도 §7-2가 해소되지 않으면"* 다음 단계로 간다. 앞 단계만으로 문턱 아래로 내려왔으면 거기서 닫는다. 승급 조건을 「그래도 초과면」으로 두면 ①로 문턱 아래·초과 위에 머문 파일이 ②에 못 가 **WARN이 영구 잔존**한다.
   - **별개 트리거 — 이 조건의 대상이 아니다**: ⓐ **`index.md`·sub-index**는 문자 예산이 아니라 **본문 줄 수·기능별 인덱스 행 수**가 트리거다(§7-14). ⓑ **project 허브 `## 최근 주요 변경` 롤오버**는 §2.2상 **6번째 항목이 생기면**이고 허브 전체 문자 예산과 **무관**하다 — 이 조건이 발동해도 항목이 5개 이하면 그 롤오버는 대상이 아니고, 반대로 발동 없이도 6개가 되면 수행한다(허브의 **문자** 예산 처방은 `conventions.md` 분리 §2.9 쪽이다). ⓒ **feature 섹션 구역화 신호**(§7-32)는 **한 `## ` 섹션의 문자 수 + `### ` 유무**가 트리거다 — 파일이 이 조건의 예산 안이어도 발화하고, 처방도 분리가 아니라 **소제목 추가**다(옮기지 않는다). **이 셋을 여기로 끌어오지 않는다** — 포인터 치환이 「모든 초과·임박 서술은 §7-2」로 미끄러지면 이 축들이 조용히 흡수된다.

## 8. 롤오버 / 아카이브 규칙

### 롤오버·분리 (log 외 타입) — 압축하지 않는다
- **§7-2 발동 시 §4 표의 해당 타입 처방을 수행한다**(조건의 정본은 §7-2 — 여기에 다시 적지 않는다) — 내용을 요약으로 줄이는 압축은 어느 타입에도 적용하지 않는다(압축은 매번 근거·경위를 소실시키고 무한 반복된다).
- **날짜와 핵심 결론은 반드시 보존** — 처방은 전부 **이동·분리**이므로 옮긴 자리에 원문이 그대로 남아야 한다.
- **아카이브 항목 순서 — 오래된 것이 위다(append 순)**: 세 롤오버 공통이다(project 허브 `changes.md` §2.2 · decision-log §2.8 · log 월별 아래 절). 옮길 항목을 **파일 끝에 append**하므로 원본 본문의 「최신이 위」와 **반대 방향**이 된다. **손으로 뒤집지 않는다** — 수행 주체가 `--auto-split`이라 다음 실행이 다시 끝에 붙여 재배치가 유실되고, 골든이 그 동작을 고정하고 있다(2026-09-10 실 vault에서 재배치가 관측돼 이 줄을 명시했다). **금지 대상은 「최신이 위」로 되돌리는 것 하나다** — append 순으로 맞추는 정렬은 해당 없다(2026-09-11 이 구분이 없어 정렬 작업이 판정에서 멈췄다).
- **project 허브 `## 최근 주요 변경`**: 3~5개를 유지하고 초과분을 `90_archive/20_projects/{카테고리}/{프로젝트}/changes.md`로 롤오버(append) + 허브 하단 `## 아카이브` 포인터 1줄 갱신(§2.2 — 포인터 정합은 lint §7-30ⓐ). 아카이브 파일은 frontmatter 없이 `# {프로젝트} 변경 이력 아카이브` 헤딩 + 항목 목록(`90_archive/` 하위라 lint 검사 자동 제외), 목적지에 파일이 있으면 덮어쓰지 않고 append.
- **project 허브 작업 규약**: 허브 섹션이 아니라 `conventions.md`(§2.9)가 정본이다 — 미마이그레이션 허브의 `## 작업 규약·주의사항`은 다음 ingest에서 그 파일로 옮긴다(lint §7-31 INFO).
- **하위 페이지 분리 처방을 가진 타입**(feature·entity·concept·guide): 압축·삭제 대신 분리하고, **하위에서 §7-2가 다시 발동하면 §4 「재분할 일반 규칙」으로 재분할**한다(무제한 — 진입 파일의 목록으로 조회 홉 1 유지).
- **검색(롤오버한 변경 이력 찾기)**: "언제 바뀌었나 / 그동안 무슨 변화가 있었나"를 확인할 때 현행 허브만 보지 말고 하단 `## 아카이브` 포인터를 따라 `changes.md`를 읽는다(절차 K 2·G 2b — 현행 파일만 보고 "기록 없음" 단정 금지).

### log 월별 롤오버 아카이브
- log.md는 줄 단위 압축이 아니라 **월별 묶음 이동**으로 관리한다 — 항목이 이미 한 줄(`- [YYYY-MM-DD] …`)이라 "한 줄 압축"은 줄 수를 못 줄여 무의미하다. 측정 단위도 줄 수가 아닌 **문자 수**다(한 항목이 길면 줄 수가 실제 분량을 못 담음).
- **트리거 / 목표**: log.md에서 **§7-2가 발동하면**, `## 최근 변경`의 **가장 오래된 항목부터** 그 항목의 `[YYYY-MM-DD]`가 가리키는 월(`YYYY-MM`)의 `90_archive/log/{YYYY-MM}.md`로 이동(append, 시간순)해 **3000자 이하**가 될 때까지 반복한다. **실제로 멈추는 선은 2,700자다** — 처방 직후 §4 7번 기록 1줄이 이 파일에 append되므로, 3000에 딱 맞춰 멈추면 그 한 줄이 다시 발동을 만들어 **매 실행 조금씩 도는 상태**가 된다(실측 3,081/3,000). 그 여유분(`LOG_ROLLOVER_SLACK`)은 기록 몫이지 새 임계가 아니다.
- **항목 단위로만 자른다**: 한 항목(`- [YYYY-MM-DD] …` 완결 블록, 하위 불릿 포함)은 절대 쪼개지 않는다. 한 항목이 커서 목표치 밑으로 못 내려가면 그 항목까지만 옮기고 멈춘다(쪼개느니 약간 큰 게 낫다) — **§2.8과 동형의 정지 가드이며, 이 경우 §4 5번 검증의 「목표치 이내」는 실패로 판정하지 않는다**.
- **아카이브 인덱스(검색 진입점)**: 이동 시 log.md 하단 `## 아카이브 인덱스`에 해당 월 한 줄 요약을 추가/갱신한다 — `- {YYYY-MM}.md: {N}건 ({최古}~{최新})`. **키워드 요약은 자동 경로가 쓸 수 없다**(무엇이 주요 작업인지가 판단이다) — 그래서 **건수·기간이라는 결정론 형식**을 쓴다. 사람이 나중에 키워드를 덧붙이는 것은 언제나 허용되며, 그것은 이 줄의 부재를 대신하는 것이 아니라 **추가**다(진입점이 아예 없는 것보다 건수·기간이라도 있는 편이 검색에 쓰인다). 이 인덱스가 §6·§7-10·§7-13 검색의 진입점이며, §7-19 lint이 실파일과의 정합을 강제한다.
- **자동 수행(승인 불필요)**: 위키 작업(§5 ingest·§7 lint 등)에서 log 기록을 추가한 직후 트리거를 점검해 롤오버한다 — **수행 주체는 `--auto-split`이고 세션은 호출·검증한다**(§7-2). 이동은 정보 손실이 아니라 보존이므로 사용자 승인 없이 수행한다 — 되돌릴 수 있고 원문이 그대로 보존되기 때문이다. `90_archive/log/`가 없으면 생성하고, 아카이브 파일은 frontmatter 없이 `# {YYYY-MM} log` + 항목들로 둔다(`90_archive/` 하위라 lint 검사에서 자동 제외).
- **부활 없음**: 아래 페이지 아카이브와 달리 log 롤오버는 시간순 보존이라 원위치 복귀 개념이 없다.
- **검색(아카이브 이동 항목 찾기)**: "이미 처리한 작업/이슈/후보인지" 확인할 때 현행 log.md만 보지 말고 — ① `## 아카이브 인덱스`로 관련 월을 특정해 해당 `90_archive/log/{월}.md`만 읽거나, ② 인덱스로 못 좁히면 `90_archive/log/`를 Grep으로 키워드 검색해 파일을 특정한다(아카이브 전체 정독 금지 — 인덱스로 좁히고 특정된 파일만 읽는다).

### 비 git vault 사전 백업
- **취지**: vault가 git 저장소가 아니면 모든 덮어쓰기·삭제가 되돌릴 수 없다. 글로벌 지침은 이 경우 "사전 백업 또는 사용자 확인"을 요구하므로, 승인 문답 없이 자율 동작을 유지하려면 **사전 백업**으로 요건을 충족한다.
- **git 여부 확인**: 세션의 첫 쓰기 절차 시작 전 1회, `<vault>/.git` 존재로 판단한다. git 관리 vault면 이 절 전체가 해당 없음(git이 이력 보존을 담당). **단 이 면제는 git 이력이 실제 보호를 제공할 때만 유효하다** — vault에 커밋이 하나도 없으면(`git log -1` 실패 — `git init`만 한 상태) `git checkout` 복구가 무력해 보호가 0이므로 **면제를 적용하지 않고 비 git vault로 취급해 사전 백업을 그대로 수행한다**(사후 커밋 권유만으로는 이미 덮어쓴 파일을 복구할 수 없다). 커밋은 있으나 워킹트리가 dirty하면 직전 커밋까지의 보호는 있으며, 미커밋 누적은 「git 자동 반영」이 커밋으로 해소한다. **§4 분할 직전 상태 잡기도 git vault에서는 사본이 아니라 체크포인트 커밋이다** — 종전에는 그 사본(`-presplit`)만 git vault에 예외로 남았는데, 근거가 *"분할 직전은 주 작업이 아직 미커밋인 시점이라 git 이력이 보호한다는 전제가 성립하지 않는다"*였다. **`--auto-split`·`--fix`·복구 직전에 커밋 1회를 두는 것으로 그 전제를 성립시켰으므로**(`references/wiki-ops-rules.md` 「체크포인트 커밋」) 예외가 필요 없어졌다. 비 git vault에서는 종전대로 사본을 뜬다. **그리고 이 면제가 말하는 "git이 담당한다"를 실제로 집행하는 것은 「git 자동 반영」**(`references/wiki-ops-rules.md` — 변경이 생긴 절차마다 커밋, 세션 끝에 push 1회)**이다** — 그 규약이 없던 때는 커밋을 사용자에게 권하기만 해서 면제의 전제가 자주 거짓이었다.
- **백업 대상·시점**: 비 git vault에서 수정·삭제할 **기존 파일**을, 각 파일의 그 세션 **최초 수정·삭제 직전**에 `90_archive/backup/{YYYY-MM-DD}/` 하위로 vault 상대 경로를 유지해 복사한다(예: `20_projects/personal/proj-a.md` → `90_archive/backup/2026-07-02/20_projects/personal/proj-a.md`). 같은 파일의 같은 세션 2회째 수정은 재복사하지 않는다(세션 시작 시점 상태 1부만 보존). **신규 파일 생성은 백업 불필요**(덮어쓰기가 아님).
- **복사 시 목적지에 파일이 이미 있으면 덮어쓰지 않는다**(decisions 롤오버 §2.8과 동일 규정) — 같은 날짜에 **다른 세션**이 먼저 떠 둔 원백업(그날 최초 상태, 가장 가치 있는 복구 지점)을 그 세션의 현재본으로 덮어써 유실하는 것을 막는다.
- **삭제(절차 C) 백업은 분리**: 프로젝트/파일 삭제 백업은 `90_archive/backup/{YYYY-MM-DD}-deleted/` 하위에 둔다 — 삭제는 원본이 vault에서 사라져 그 백업이 **유일 사본**이므로, 아래 정리·복구 규칙이 수정 백업과 달라야 한다.
- **§4 분할 착수 직전 상태(index 2·3단계 + 산문 타입 하위 분리 + 롤오버)도 분리**: **git vault면 체크포인트 커밋**이 그 상태를 잡는다(`references/wiki-ops-rules.md` 「체크포인트 커밋」 · `pass` 당 1회 · 실패하면 착수하지 않는다). **비 git vault면 사본을 `90_archive/backup/{날짜}-{시각}/` 하위에 둔다**(§4 분할 수행 절차 1번·5번의 원복 기준 — 구현은 `lint.py`의 `_presession_dir`). 세션 사전 백업 폴더 `{YYYY-MM-DD}/`를 그대로 쓰면 위 미덮어쓰기 규정에 걸려 사본이 만들어지지 않고, 남아 있는 것은 그 세션 *최초 변경 직전*(=주 작업 이전) 상태라 그것으로 되돌리면 **주 작업까지 유실**된다 — 그래서 시각을 붙여 갈라 둔다. **시각까지 붙이는 두 번째 이유는 pass 격리다** — 한 번의 `--auto-split`이 본 pass와 재점검 pass를 돌리므로 둘이 같은 폴더를 쓰면 1회째 결과가 「원본」으로 보존된다(git vault에서 이 격리를 담당하는 것이 「`pass` 당 1회」 커밋이다). **아래 누적 금지 규칙이 이 폴더도 회수한다**(`-deleted`·`-pre-restore` 같은 보존 특례를 두지 않는다).
- **백업 누적 금지(집행 지점 포함)**: **git vault는 `--fix` 백업도 만들지 않는다** — 사전 백업이 면제인 것과 같은 이유이고, 보호는 직전 체크포인트 커밋이 담당한다(`lint.py`의 `apply_fixes`가 그 분기를 갖는다). **비 git vault는 `90_archive/backup/{YYYY-MM-DD}/`를 만들고**, 그대로 두면 쌓이므로 **다음 `--fix` 실행 시작 시 접미사 없는 이전 날짜 폴더**(`{YYYY-MM-DD}/`)**와 위 분할 사본**(`{날짜}-{시각}/`)**을 제거**한다(**집행 주체는 `scripts/lint.py`의 `cleanup_backups`** — `--fix`가 새 백업을 만들기 **전에** 1회 호출한다. 나중에 하면 방금 만든 오늘 백업을 지울 판정을 다시 하게 된다). **제거 시점을 그 세션 종료 시가 아니라 다음 실행 시작 시로 두는 이유**: `--fix` 변경이 미커밋인 채 세션이 끝나면 git 복구(`checkout`은 미커밋을 되돌리지 못한다)와 백업이 동시에 없어져 복구 수단이 0이 된다 — 한 세션분을 남기면 복구 창이 유지되면서 누적은 1개로 상한된다. **「git 자동 반영」이 도입된 뒤에도 이 규칙은 유지된다** — 커밋 실패 시 보고 후 계속하므로 미커밋 상태가 여전히 가능하고, 그 한 경우를 위해 복구 창이 필요하다. **문자 접미사 폴더(`-deleted`·`-pre-restore`)만 이 규칙의 대상이 아니다** — 유일 사본·복구 재백업이라 지우면 복구가 영구 불가해진다. **시각 접미사(`{날짜}-{시각}/`)는 대상이다** — 분할 사본은 원본이 vault에 그대로 있는 수정 백업 성격이라 보존 특례가 없다. **옛 이름 `-presplit` 폴더는 코드가 보존한다** — 더 이상 생성되지 않으므로 남은 것은 과거 잔여물이고, 그 삭제는 사용자 판단이라 검사기가 자동으로 걷지 않는다.
- **정리(자동, 승인 불필요)**: 위 누적 금지 규칙 하나가 정리를 전담한다(집행 주체는 `cleanup_backups`) — **접미사 없는 `{YYYY-MM-DD}/`와 시각 접미사 `{날짜}-{시각}/`을 다음 `--fix` 시작 시 회수**한다. 방치하면 vault가 비대해진다. 단 **`-deleted`(삭제 백업)·`-pre-restore`(복구 재백업) 문자 접미사 폴더는 정리에서 제외**한다. "삭제해도 정보 손실 없음"이라는 전제는 **수정 백업에만** 성립한다(원본이 vault에 최신으로 존재하므로). **삭제 백업은 원본이 vault에 없어 그 백업이 유일 사본이므로 자동 삭제하면 복구가 영구 불가**해진다(31일 뒤 "그 프로젝트 복구" 요청 시 수단이 이미 없음). 날짜는 추정하지 말고 확인 후 사용한다(확인 불가면 정리는 건너뛴다 — 백업 자체는 날짜 무관하게 수행).
- **lint 관계**: `90_archive/` 하위는 lint 검사에서 자동 제외되므로 백업 파일이 WARN을 만들지 않는다(§7).
- **복구(백업 소비)**: 백업본으로 되돌리는 절차는 절차 L(`references/procedures-ops.md`) — 날짜 폴더에서 사본 확인(없으면 복구 불가 사실대로 보고) → 현재본과 차이 제시 → 사용자 확인 → **복구 직전 상태를 별도 폴더 `90_archive/backup/{YYYY-MM-DD}-pre-restore/`로 재백업**(당일 원백업 `{YYYY-MM-DD}/`을 **덮어쓰지 않는다** — 덮어쓰면 복원하려던 좋은 버전이 사라져 복구가 무효가 된다) → 원위치 복사 → lint 권고 + log 기록. 백업은 이 절차의 존재로 "만들기만 하는 사본"이 아니라 발견 가능한 복구 수단이 된다.

### 아카이브
- 아카이브 구조: 원래 경로를 `90_archive/` 하위에 재현
- **아카이브로 가는 경로는 둘뿐이다** — 롤오버(§2.2 project 허브 · §2.8 decision-log · log.md, 전부 §7-2 또는 항목 수 임계가 발동), 삭제(절차 C). 절차 D 의 상태 전환은 frontmatter `status` 만 바꾸고 파일을 옮기지 않는다. **시간 기반 이동은 없다** — 60일 confidence 하락과 90일 이동은 v1.238.0에 폐지됐다(§7-3). 오래된 페이지를 옮기지 않는 이유는 검색형 지식베이스에서 아카이브가 곧 검색 밖이기 때문이다 — 시간이 지나도 낡지 않는 패턴·개념이 그 대상의 대부분이었다
- 부활: 아카이브 페이지가 다시 참조되면 원래 위치로 복귀
