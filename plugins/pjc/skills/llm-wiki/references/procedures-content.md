# llm-wiki 절차 — 콘텐츠 (A~E·I)

> 이 파일은 `llm-wiki` SKILL.md의 절차 본문이다(컨텍스트 예산 지연 로드 분할 — 본체의 절차 목차 라우팅 표에서 연결).
> **본체 SKILL.md의 §0 시작 절차·사전 준수 사항을 먼저 적용한 뒤** 이 파일의 절차를 수행한다.
> 수록: A. 프로젝트 추가 / B. 정보 갱신(Ingest) / C. 삭제 / D. 상태 변경 / E. 지식 페이지 관리 / I. 가이드·레시피 작성 / 체크리스트(작업 완료 전).

### A. 프로젝트 추가

사용자가 "프로젝트 추가해줘" / "{프로젝트} 위키에 등록"이라고 요청하면 다음을 순서대로 실행한다.

#### A-1. 정보 수집
1. 사용자에게 확인할 것:
   - 프로젝트 경로 (예: `D:/Source/ProjectName`)
   - 분류: `personal` 또는 `work`
1-1. **중복 등록 가드**: 등록 전에 같은 레포 경로의 허브가 이미 있는지 확인한다 — `20_projects/` 허브들의 "레포 정보 > 경로" 대조 + 프로젝트명 한/영·하이픈 변형 검색. 이미 있으면 신규 등록을 중단하고 기존 허브를 안내한다(중복 허브는 결정 이력·기능 인덱스를 두 갈래로 가른다). **단 그 허브의 프로젝트가 미완성이면**(이전 등록 세션 중단 — 소스 대비 feature 페이지가 일부만 존재) 신규 등록 대신 **절차 B(ingest)로 이어 완성**하도록 안내한다(부분 실패 재개 경로).
2. 해당 경로에서 다음 파일을 읽어 프로젝트 정보를 파악한다:
   - `CLAUDE.md`, `AGENTS.md` (있으면)
   - `README.md` (있으면)
   - `notes.md` 또는 `NOTES.md` (있으면, 처음 50줄만)
   - `*.sln`, `*.csproj`, `Cargo.toml`, `package.json` 등 프로젝트 설정 파일
   - 서브 디렉토리 목록 (`ls`)
3. **기능 망라용 소스 스캔 (문서 미기재 기능 포착)**: 문서만으로는 기능이 누락될 수 있으므로, UI/기능 진입점을 표적 스캔해 화면·명령·기능을 열거한다(전체 정독이 아니라 enumeration 목적, Grep/Glob 사용).
   - WinUI/WPF/.NET: `Views/`·`Pages/`·`Presentation/`, `*ViewModel*`·`*Page.xaml`·`*Dialog*`, `[RelayCommand]`/`*Command`
   - Unity: `Assets/Scripts/`·`Scenes/`, 주요 `MonoBehaviour`
   - Web: 라우트/페이지(`pages/`·`routes/`·`app/`)·주요 컴포넌트
   - 공통: 메뉴/네비 정의, 설정 화면, 명령/액션 핸들러
   - 문서(README/notes)에 없는 기능도 이 목록에 포함한다.
4. 파악할 정보:
   - 프로젝트 한 줄 요약 / 기술 스택 / 서브프로젝트 유무
   - **전체 기능 목록(문서 + 소스 스캔 종합)** — A-2 feature 망라의 기준
   - 최근 변경 내역 3~5개
   - 기존 위키 프로젝트와 공유하는 기술/패턴

#### A-2. 파일 생성

> 모든 타입의 frontmatter/본문 템플릿은 `<skill>/references/templates.md` 참조.

1. **소스 스텁** → `10_sources/{personal|work}/src-{프로젝트명소문자}.md` (예산 ~30줄). 서브프로젝트 있으면 `- **서브프로젝트**:` 추가. **"기술 스택" 줄에는 프레임워크/라이브러리 이름만**(SDK/패키지 버전 숫자 제외 — 정본 §2.1 휘발성 버전 금지: 스텁 불변이라 버전이 영구 stale, 진실원천은 코드).
2. **프로젝트 허브** → `20_projects/{personal|work}/{프로젝트명소문자하이픈}.md` (예산 ~120줄)
   - "기능 목록": 파일 3 feature를 표로 인덱싱.
   - "관련 위키 지식": `30_knowledge/`·`40_guides/`에 **이미 존재하는** 페이지만 링크.
   - "프로젝트 간 공유 패턴": 겹치는 기술/패턴을 `20_projects/`의 다른 프로젝트에 wikilink.
   - 서브프로젝트 있으면 "## 서브프로젝트" 테이블 추가.
   - **온보딩/아키텍처 가이드(선택)**: 큰 프로젝트면 "## 온보딩 / 아키텍처 가이드"(아키텍처 레이어·주요 흐름·복잡도 핫스팟)를 선택 포함한다 — 실제 코드/구조를 읽고 작성(추측 금지), 예산 ~120줄 유지(schema §2.2).
3. **feature 상세 페이지(들)** → `20_projects/{personal|work}/{프로젝트명}/feat-{기능명}.md` (feature당 ~180줄)
   - **작성 전제(필수 — 정본 §2.3)**: 구현/동작/UI·UX 서술 전에 해당 기능의 **핵심 소스 파일을 Read로 정독**한다 — A-1 enumeration 스캔(파일명·클래스명 열거)으로 대체 불가(파일명만 보고 추론 금지).
   - 섹션: 개요 / **관련 파일** / 동작(사용법) / 구현 방법 / UI·UX / 관련 지식·레시피. **지도는 두껍게, 산문은 얇게(정본 §2.3)**: **`## 관련 파일`은 이 기능을 구성하는 파일을 빠짐없이 담는 완전한 지도** — `- \`레포 상대경로\` — 역할 한 줄` 목록으로 작성한다(각주는 근거, 이 섹션은 지도 — lint §7-21이 경로 실존 검사). 반대로 **`## 구현 방법` 산문은 얇게** — 코드를 문장으로 재서술하지 말고 방향만 쓰고 세부는 각주로 코드를 가리킨다(코드가 진실원천). 아낀 지면은 코드로 재현 안 되는 함정을 `## 관련 지식·레시피`에. 구현 상세 주장은 레포 근거 각주 `[^src-...]` 필수 + **각주에 근거 소스 파일 경로(레포 상대경로) 병기**. **경로 표기(각주·관련 파일 공통)는 schema §2.3 규칙(정본)을 따른다** — 요지: 물리 경로·brace 축약 금지(전체 규정·예외는 §2.3 한 곳에서만 관리, 여기 재열거하지 않음). 동작·UI·UX도 코드·문서로 확인된 내용만 단정 — 실행해야만 확인 가능한 서술은 `(미검증)` 표기. 시간민감 사실은 `(as of YYYY-MM)` 표기.
   - **최초 등록 시 주요 기능/화면을 빠짐없이 망라**(핵심 일부만 만들고 미루지 않음) — 이 "망라"는 **지도 망라**(모든 기능에 feature+관련파일+기능별 인덱스, schema §5)를 뜻하며 각 feature의 구현 방법 산문은 얇게 쓴다(커버리지는 낮추지 않고 산문 깊이만). 과도한 분할은 피해 기능 단위로 그룹화, 예산 초과 시 하위 분리. 레포 README/notes의 화면별 상세를 근거로 정제.
   - 각 feature는 허브 "기능 목록" + `index.md` "기능별 인덱스"에 모두 등록(분할 시 그 프로젝트 category의 sub-index 기능별 인덱스에 등록 — §4; 상세는 A-3).
4. **(조건부) 새 지식 페이지** → `30_knowledge/tech/{기술}.md`(entity ~100줄) 또는 `patterns/{패턴}.md`(concept ~80줄)
   - 조건: 새 기술/패턴이 기존 페이지 없고 이미 등록된 다른 프로젝트 1개 이상과 공유 시에만. 1개 전용은 생성 금지.

#### A-3. 기존 파일 갱신 (반드시 모두 수행)

1. **`index.md`**:
   - 해당 카테고리(개인/업무) 프로젝트 테이블에 행 추가
   - **"기능별 인덱스" 테이블에 새 feature 행 추가**(기능 → feature/레시피/가이드 링크, 행 형식은 schema §3 — 첫 컬럼은 평문·상세 컬럼 alias는 `feature`/`recipe` 권장). 행 첫 컬럼(기능명)에 **한글 키워드와 영문 키워드를 양방향으로 모두 병기**한다 — 한글로 등록하든(예: "로그인 (login)") 영문 기술용어로 등록하든(예: "OG image (OG 이미지)") **한쪽만 적지 않는다**. 영문은 feature 파일명·코드 식별자에서, 한글은 기능 설명에서 가져온다. 이로써 한글로 검색하든 영문으로 검색하든 인덱스 한 줄에서 잡힌다(lint이 한/영 병기 누락을 검사 — F-1 16). **동의어 명명 일관성(schema §3)**: 등록 전 기존 기능별 인덱스를 한/영으로 검색해 **다른 프로젝트에 같은 기능이 이미 있으면 그 행의 한/영 키워드를 재사용**한다(같은 기능 = 같은 검색어 — 교차 프로젝트 검색 정합). 새 이름이 더 적절하면 기존 키워드도 괄호 병기. **인덱스가 sub-index 파일(`index-{카테고리}.md`)로 분할된 상태면**, `index.md`가 아니라 그 프로젝트의 category(personal/work)에 해당하는 sub-index(`index-personal.md`/`index-work.md`)에 행을 추가하고 `index.md` 상단의 sub-index 목록이 최신인지 확인한다.
   - 기술 스택 지식 테이블에 해당 프로젝트를 "사용 프로젝트"에 추가
   - 범용 패턴 테이블에 관련 있으면 추가
   - 가이드를 생성했으면 "가이드 / 레시피" 섹션에 링크 추가
2. **`30_knowledge/tech/*.md`·`patterns/*.md`**: 사용 기술/패턴의 기존 지식 페이지 `used_by`/`related_projects`에 프로젝트 추가 + 본문 목록/카운트 갱신.
3. **관련 프로젝트 페이지**: 밀접한 기존 프로젝트의 "프로젝트 간 공유 패턴"에 새 프로젝트 연결 추가.
4. **`log.md`**: `- [YYYY-MM-DD] [INGEST] {프로젝트명} {카테고리} 프로젝트 추가. ...`

#### A-3a. recipe 승격 확인 (필수 사용자 게이트)

> feature 망라 후, 코드 스니펫 recipe 승격 여부를 **항상 사용자에게 묻는다**(에이전트 단독 자동 승격 금지). feature는 기본적으로 관련 파일 지도 + (얇은) 산문 + 각주를 담고 코드 스니펫은 담지 않으므로, 코드 수준 재사용은 사용자 선택으로 recipe에 적재한다.

1. **후보 식별**: A-1 소스 스캔/feature 작성 중 발견한 **재사용 가능한 비자명한 함정**(구현 트랩·플랫폼 제약·성능/안정성 트릭)을 후보로 모은다. 선별 기준 — ① 단일 화면 고유 로직이 아니라 다른 프로젝트에서도 재현 가능, ② 코드 없이는 재현이 어려운 함정/트릭.
2. **질문(필수)**: 후보를 1줄씩 나열하고 "코드 스니펫 recipe로 승격할까요? (전체 / 일부 선택 / 안 함)"을 **반드시 묻는다**. 후보가 0개면 "승격할 함정 후보 없음"을 보고하고 질문은 생략한다.
3. **승인 시**: 선택 항목을 **절차 I(가이드/레시피 작성)**로 진행 — 해당 스택 폴더에 recipe 생성, 실제 소스 코드로 스니펫 검증(`[^src-...]` 각주), `index.md` 가이드+기능별 인덱스 등록, 관련 feature "관련 지식·레시피"에 상호 링크.
4. **거절 시**: feature 산문 + 각주만 유지(현행 동작). 함정 정보는 feature에 남으므로 손실 없음.

#### A-4. 검증
1. `python "<skill>/scripts/lint.py" "<vault>"` 실행 — 예산·wikilink·통제어휘·인덱스/허브 동기화를 기계 검증. **판정은 델타 기준**: 이번 작업이 **신규로 만든** 오류·경고 0이 목표다. lint는 vault 전역을 검사하므로 다른 프로젝트의 기존 경고가 섞여 있을 수 있는데, 그것까지 0으로 만들 책임은 이번 작업에 없다(요청 범위 밖 무단 수정 금지). 이번 변경과 무관한 기존 경고는 보고에 "기존 잔여"로 분리해 남기고, **이번 변경 파일 관련 신규 경고만** 해소한다.
2. **전체 망라 검증 (기능 누락 차단)**: A-1의 "전체 기능 목록(문서 + 소스 스캔)" 각 항목이 feature 페이지 또는 의도적 묶음에 매핑되는지 대조. 미커버는 feature로 생성, 묶은 경우 사유를 해당 feature에 명시. 누락 0이어야 완료.

### B. 프로젝트 정보 갱신 (Ingest)

"위키 업데이트", "{프로젝트명} 변경분 반영" 요청 시.

#### B-1. 변경분 파악
0. **pending.md 확인 (drift 큐 소비)**: vault 루트 `pending.md`가 있으면 먼저 읽어, 이번 프로젝트 관련 `[K-DRIFT]` 항목을 갱신 범위에 반영한다. **항목 제거는 위키 반영을 실제로 완료한 뒤에 한다**(반영 전 제거 후 세션이 중단되면 그 drift 발견이 큐에서도 위키에서도 사라져 영구 유실 — [DECISION] 재큐잉 대비와 동형). 제거 시점에는 pending.md를 다시 읽어(그 사이 다른 세션의 append 보존, schema §9) 해당 항목만 지우고 재작성한다(소비 완료 — 남기면 다음 세션이 중복 처리). 다른 프로젝트의 항목은 그대로 둔다.
   - **`[SKILL-IMPROVE]` 항목 (플러그인 개선 후보 — 위키 반영 금지)**: 이 태그는 위키 콘텐츠가 아니라 pjc 스킬 자체의 개선 후보다(절차 K 5-1). **위키에 반영하지 않고** 사용자에게 "플러그인 개선 후보"로 보고하고 처리를 묻는다 — 개선 진행이면 하네스(플러그인) 레포 세션에서 작업하도록 안내하고 항목은 유지, 기각·이미 처리됨이면 제거, 보류면 유지. K-DRIFT와 달리 위키 세션이 스스로 소비(반영 후 제거)할 수 없으므로 **제거는 사용자 지시가 있을 때만** 한다.
   - **재보고 억제**: 보고한 `[SKILL-IMPROVE]` 항목에는 줄 끝에 `(보고됨 YYYY-MM-DD)` 표식을 붙인다(위키 세션의 pending.md 소비 쓰기 권한 내). 이후 세션은 **표식 있는 항목을 개별 재보고하지 않고** "플러그인 개선 후보 n건 대기 중(pending.md)" 요약 1줄로만 알린다 — 매 세션 같은 목록 반복 나열 방지. 사용자가 처리를 지시하면(기각/완료) 그때 제거한다.
   - **`[DECISION]` 항목 (결정 이력 — 대상 프로젝트 즉시 소비 / 타 프로젝트 동의 소비)**: 해당 프로젝트의 `decisions.md`(schema §2.8)에 항목을 추가하고(최신 위, 파일 없으면 templates.md의 decision-log 템플릿으로 생성 + **프로젝트 허브 "관련 위키 지식"에 링크 1회 추가** — 고아 방지) pending.md에서 제거한다. **이번 ingest 대상 프로젝트의 [DECISION] 항목은 이 세션에서 바로 소비**한다(코드 대조 불필요). **다른 프로젝트의 [DECISION] 항목은 자동 소비하지 않는다** — 잔량을 "다른 프로젝트 결정 n건 대기 중(pending.md): {프로젝트 목록}"으로 **보고하고, 사용자가 소비에 동의할 때만** 그 프로젝트들의 항목을 decisions.md에 반영한다(동의 없으면 큐에 유지). 이번 세션이 대상하지 않은 프로젝트의 결정까지 말없이 소비하면 사용자가 인지하지 못한 채 다른 프로젝트 위키가 바뀌므로, 동의 게이트를 둔다(등록 보류 항목은 종전대로 큐에 남긴다).
     - **프로젝트 매칭**: 큐의 프로젝트명이 위키 등록명과 다를 수 있다(레포 폴더명 등) — "미등록" 판정 전에 허브 frontmatter `project`·"레포 정보 > 경로"·이름 변형(한/영·하이픈)으로 기존 허브를 검색하고, 유사 허브가 있으면 사용자에게 매칭을 확인한다(미등록 오인 → 중복 등록 방지).
     - **소비 전 중복 검사**: 대상 decisions.md(+아카이브)에 같은 주제·같은 결정 항목이 이미 있으면 **추가를 생략하고 큐에서 제거만** 한다 — 재개 세션 재큐잉 등으로 이중 큐잉돼도 이중 기재되지 않게(항목 불변 규칙 때문에 중복은 영구 고착된다).
     - **번복·기각 전파 점검**: 번복·기각 항목을 소비할 때 기능별 인덱스에서 같은 기능의 feature/recipe 존재를 확인하고, 본문 서술과 모순될 수 있으면 사용자에게 해당 프로젝트 ingest(절차 B) 필요를 보고한다(즉시 처리가 어려우면 question 기록 — 결정과 본문이 어긋난 채 침묵 방치 금지).
     - **롤오버**: 추가 후 150줄 초과면 §2.8 롤오버를 즉시 수행 — 오래된 항목부터 90_archive 원경로 파일로 이동(**기존 파일이 있으면 덮어쓰지 않고 append**) + decisions.md 하단 `## 아카이브` 포인터 갱신(포인터 정합은 lint §7-24가 기계 검사).
     - **미등록 프로젝트**: 위 매칭으로도 허브가 없으면 사용자에게 "이 프로젝트를 위키에 등록할까요?"를 확인한다 — 등록 승인 시 절차 A 수행 후 소비, 보류 시 항목 끝에 `(등록보류 YYYY-MM-DD)` 표식을 붙이고 큐에 유지한다. **표식 있는 항목은 이후 세션에서 개별 재질문하지 않고** "등록 대기 결정 n건(pending.md)" 요약 1줄로만 알린다(SKILL-IMPROVE 재보고 억제와 동형) — 사용자가 등록을 지시하면 그때 소비한다.
   - **`[PROJECT-FACT]` 항목 (프로젝트 작업 사실 — 대상 프로젝트 즉시 소비 / 타 프로젝트 동의 소비)**: 해당 프로젝트 허브(`20_projects/`)의 `## 작업 규약·주의사항` 섹션(schema §2.2)에 항목을 추가하고(섹션 없으면 `## 최근 주요 변경` 앞에 생성, project 예산 ~120줄 유지 — 초과분은 recipe/patterns 분리) pending.md에서 제거한다. 소비·게이트 규칙은 위 [DECISION]과 동형 — 이번 ingest 대상 프로젝트 항목은 즉시 소비, **다른 프로젝트 항목은 사용자 동의 시에만**, 프로젝트 매칭·미등록 확인(`(등록보류 YYYY-MM-DD)` 표식·재보고 억제)·제거 시점 재읽기-병합도 동일하게 따른다. **소비 전 중복 검사**: 허브 해당 섹션에 같은 요지 항목이 이미 있으면 추가를 생략하고 큐에서 제거만 한다. 레포 귀속 실행 사실(빌드/테스트 명령 등)이 잘못 큐잉돼 있으면 허브에 넣지 말고 AGENTS.md 기록(`pjc:record-project-fact`) 제안으로 사용자에게 보고한다(라우팅 정본은 SKILL.md K 5-3).
   - **`[K-MISS]` 항목 (참조 미스 = 수요 신호 — 대상 프로젝트 즉시 소비 / 타 프로젝트 동의 소비)**: 코드 세션의 절차 K가 찾았으나 위키에 없던 지식이다(SKILL.md K 5-4). 이번 ingest 대상 프로젝트의 항목은 **레포 근거를 대조해 그 지식이 실재하면 feature/recipe 생성·보강으로 반영**하고(생성·승격 게이트는 기존 A-3a·절차 I 규약 그대로 — 큐가 곧 자동 페이지 생성은 아니다) pending.md에서 제거한다. 레포에 근거가 없거나 페이지화 가치가 없으면(1회성 조회 등) **기각 사유를 보고하고 제거**한다. 같은 요지의 feature/recipe가 이미 있으면(등록 후 미스가 해소된 경우) 필요 시 보강만 하고 제거한다. 타 프로젝트 동의 게이트·프로젝트 매칭·미등록 확인·제거 시점 재읽기-병합은 위 [DECISION]과 동형.
   - **`[SYMPTOM]` 항목 (증상→검증된 원인→해법 매핑 — 대상 프로젝트 즉시 소비 / 타 프로젝트 동의 소비)**: 디버깅 세션이 규명한 증상↔원인↔해법 페이지다(SKILL.md K 5-5). 이번 ingest 대상 프로젝트의 항목은 **증상별 인덱스(schema §6)의 등재 게이트 3종을 검증한 뒤 `index.md ## 증상별 인덱스`에 행을 추가**하고 pending.md에서 제거한다 — ① 증상 칸이 관찰 표현인지 ② 원인이 대응 해법 페이지의 `[^src-...]` 각주로 뒷받침되는 검증된 인과인지 ③ 해법 페이지(recipe/feature)가 실존하는지. **게이트 미충족이면 반영을 보류**한다: 해법 페이지가 없으면(게이트 ③) recipe 선행(A-3a·절차 I) 또는 question을 남기고 큐 항목은 `(보류 YYYY-MM-DD)` 표식으로 유지, 원인이 미검증이면(게이트 ②) 기각 사유 보고 후 제거. **실패한 접근·잠정 진단은 등재하지 않는다**(schema §6 실패 미등재). 같은 증상 행이 이미 있으면 추가 생략·큐 제거만. 타 프로젝트 동의 게이트·프로젝트 매칭·미등록 확인·제거 시점 재읽기-병합은 위 [DECISION]과 동형.
1. 레포 경로는 프로젝트 위키 페이지(`20_projects/`)의 "레포 정보 > 경로"에서 확인.
2. 레포 `notes.md`(또는 `NOTES.md`)로 마지막 위키 갱신(`updated`) 이후 변경분 파악.
3. 레포가 git 저장소면 `git log --oneline --since=<updated 날짜>`를 보조 신호로 사용해 notes.md에 누락된 변경분을 보완한다.
4. `README.md`, `CLAUDE.md` 변경이 있으면 함께 확인.
5. **델타 신뢰도 점검**: 위키 허브 `updated`가 **30일 초과**면 notes.md(1개월 보존 규칙)에서 그 사이 변경분이 이미 삭제됐을 수 있다 — git이면 git log로 보완하고, git이 아니면 notes 델타를 신뢰하지 말고 갱신 대상 feature의 **소스 직접 대조**로 강도를 올린다.

#### B-1a. 망라 재대조 (경량 드리프트 점검 — 필수, 소규모 갱신은 축소 가능)

> 델타(notes 변경분)만으로는 코드에서 **조용히 제거·이름변경**된 기능을 놓친다. A-1식 진입점 enumeration으로 가볍게 대조한다(전체 deep read 아님). 무거운 정합은 Lint의 **코드 정합 샘플링**(F-1 10)에 위임.
>
> **축소 조건 (소규모 갱신)**: 프로젝트 허브 `updated`가 **14일 이내**이고 이번 변경 파일이 **5개 이하**이면 — 전체 기능 망라 enumeration 대신 **이번에 갱신하는 기능만** 위키와 대조한다(전량 재열거 생략). 최근에 이미 망라 점검을 했고 변경 폭도 작으면 전체 재열거는 중복이기 때문이다. 단 `updated`가 14일을 넘거나 변경 파일이 5개를 초과하면(그동안 조용한 제거가 쌓였을 수 있음) 아래 전체 망라를 수행한다. (이 축소는 F-1 10 코드 정합 샘플링과 무관 — 그건 lint가 별도로 돈다.)

1. **현재 기능 열거**: A-1의 "기능 망라용 소스 스캔"(Views/Pages/ViewModels·라우트·`[RelayCommand]` 등, Grep/Glob)으로 현재 기능 목록을 도출한다(정독이 아니라 enumeration 목적).
2. **위키와 대조**: 이 목록을 허브 "기능 목록" + `index.md` "기능별 인덱스"의 기존 feature와 대조한다.
3. **드리프트 처리**:
   - **추가**(코드엔 있는데 위키에 없음) → feature 신규 생성(B-2 1-1, A-3a recipe 게이트 포함).
   - **제거/이름변경 후보**(위키엔 있는데 코드에 없음) → **자동 삭제 금지**. 후보 목록을 사용자에게 **명확한 선택지로** 제시하고 확인한다 (각 후보마다 삭제/이름변경/유지):
     ```
     코드에서 사라진 기능이 위키에 남아 있습니다. 각각 어떻게 할까요?
     - feat-old-login (위키엔 있으나 코드에 없음)
       · 삭제 — 위키에서 제거 (참조·인덱스·링크 정리)
       · 이름변경 — 실제로는 이름만 바뀐 경우 (새 이름 알려주세요)
       · 유지(폐기 표시) — 의도적으로 남기되 "더 이상 사용 안 함"으로 표시
     ```
   - **삭제 승인 시**: 절차 C-3(참조·`index.md`·크로스링크 정리)에 준해 처리하고, lint로 깨진 wikilink가 0인지 확인한다.
   - **'이름변경' 선택 시**: 사용자가 준 새 이름으로 ⓐ 파일 rename(`feat-<old>.md`→`feat-<new>.md`, `feat-*` 네이밍 규칙 유지) ⓑ 파일 내 각주·`## 관련 파일` 소스 지도 갱신 ⓒ 프로젝트 허브 "기능 목록"의 항목명·wikilink 갱신 ⓓ `index.md` 기능별 인덱스(분할이면 해당 프로젝트 category의 sub-index) 갱신 ⓔ 그 feature를 가리키던 크로스링크(`[[...feat-<old>...]]`)를 전부 새 이름으로 갱신한다. 완료 후 lint(절차 F)로 깨진 wikilink가 0인지 확인한다(C-3 링크 정리와 동일 요령 — 이름만 바뀌고 내용은 유지되므로 삭제가 아니라 rename+참조 갱신이다).
   - **'유지(폐기 표시)' 선택 시**: 파일을 남기되 frontmatter에 `deprecated: {날짜}` (또는 `status: deprecated`)를 적고 페이지 상단에 "⚠️ 이 기능은 코드에서 제거됨 — 이력 보존용"을 명시한다. **표시 없이 그냥 두면 절차 K 참조 시 현재 기능으로 오인**되므로, 유지는 반드시 폐기 표시와 함께 한다. 폐기된 feature는 허브 "기능 목록"의 **현재 기능 표에서 빼되, 허브에 "## 폐기된 기능" 구역을 두어 링크는 유지**한다 — 허브에서 링크를 완전히 제거하면 lint의 허브↔feature 동기화 검사가 "허브 기능 목록 누락"으로 오인한다. `index.md` 기능별 인덱스에도 폐기로 표기한다(분할 상태면 그 프로젝트 category의 sub-index 기능별 인덱스에 표기 — project feature이므로 sub-index, §4).
   - 확실치 않으면(제거인지 이름변경인지 불명확 등) 삭제·폐기 대신 `30_knowledge/questions/q-{날짜}-{설명}.md`에 기록(정보를 버리지 않음). 생성 시 `index.md` 미해결 질문에 등록(schema §2.7·§7-23).

#### B-2. 갱신 (rewrite-on-ingest 원칙: 새로 추가가 아니라 기존 페이지를 갱신)
0. **교차 sweep (stale 드리프트 차단)**: 변경된 사실이 **여러 페이지에 중복 기재**됐을 수 있으니, 갱신 전 그 사실을 위키 전체에서 검색(`grep`)해 **나온 곳을 모두 일괄 갱신**한다. 같은 주제 기존 페이지가 있으면 신규 생성 대신 갱신(중복 방지). **단 `10_sources/` 소스 스텁은 불변이라 sweep 대상에서 제외** — 그러므로 휘발성 사실(SDK/패키지 버전 등)을 애초에 스텁에 두지 않는다(이름만, 버전 진실원천은 코드).
0-1. **description 점진 보강 (OKF 정합)**: 이번에 갱신하는 페이지(project/feature/entity/concept/guide 5타입)에 `description` frontmatter가 없으면 한 줄 요약을 채운다(schema §12 — 신규 페이지는 템플릿이 포함하므로 해당 없음, 기존 페이지는 이 점진 보강이 백필 경로다. 일괄 백필 세션을 열지 않는다).

1-1b. **recipe 역방향 동기 (공용 recipe 개선을 되돌림)**: 이번 변경 기능이 다른 프로젝트발 공용 recipe로 이미 존재하면(판정: `index.md` 기능별 인덱스 한/영 동의어 검색 — §3), ① recipe 본문(단계·스니펫·주의점)이 이번 개선과 어긋나면 갱신 ② recipe `## 사용 프로젝트 사례`에 이번 프로젝트 추가 + `related_projects` 동기 ③ 이번 feature "관련 지식·레시피"에 상호 링크. ### I. 가이드/레시피 작성 (선행형 + 특정 기능 추가)

두 경우에 실행:
- **선행형 가이드**: "WinUI3 신규 프로젝트 가이드 작성" 등 신규 프로젝트용 가이드.

#### I-1. 특징

- **실증 면제**: concept의 "2개 프로젝트 실증" 조건 미적용.
- **출처**: 공식 문서/지침 파일(각주) + 실제 프로젝트 사례. 미등록 프로젝트는 wikilink 대신 이름 + 출처 각주. 미확인 내용 단정 금지, 불확실하면 `(미검증)`.
- **코드 스니펫 출처 규칙**: 스니펫은 ① 실제 프로젝트 소스에서 추출(각주에 소스 파일 경로 병기) 또는 ② 공식 문서 예제 인용(출처 링크 각주)만 허용. **모델 기억만으로 스니펫 작성 금지** — 불가피하면 `(미검증)` 표기 + `confidence: low`.

#### I-2. 종류 / 위치 / 본문

> frontmatter/본문 템플릿은 `references/templates.md`의 guide 템플릿 참조.

- **platform-bootstrap** (`40_guides/platforms/`): 기본 프로젝트 생성·구조. 예산 ~200줄.
  본문: `## 대상 플랫폼`/`## 기본 프로젝트 생성`/`## 권장 구조`/`## 필수 의존성`/`## UI/UX 기본`/`## 체크리스트`.
- **ui-ux** (`40_guides/ui-ux/`): UI/UX 가이드라인. 예산 ~150줄.
- **recipe** (`40_guides/recipes/{스택}/`): 특정 기능 구현 절차. 예산 ~120줄.
  본문: `## 목적`/`## 적용 플랫폼`/`## 단계`/`## 코드 스니펫`/`## 사용 프로젝트 사례`/`## 주의점 / 함정`(선택). 함정형 recipe는 재사용 함정·플랫폼 제약·성능/안정성 주의점을 `## 주의점 / 함정` 별도 섹션에 둔다(단계 산문에 묻지 않음 — 디버깅 회수, §2.6).

#### I-2a. 특정 기능 추가 시 스택 결정 (라우팅)
1. 기능이 속한 **스택 폴더** 결정(개방 목록): `winui`/`wpf`/`csharp`/`dotnet`/`unity`/`rust`/`web`/`tauri` …
   - 프레임워크 전용이면 그 프레임워크(예: WinUI 자동 실행 → `winui`), 언어 일반이면 언어(예: `csharp`). 폴더 없으면 생성.
2. `40_guides/recipes/{스택}/{기능}.md` 생성. frontmatter `platform`은 OS 통제 어휘로 별도 지정.
3. 같은 스택에 동일 기능 recipe가 있으면 신규 대신 **갱신**(중복 방지).

#### I-3. 등록 (반드시)
1. `index.md` "가이드 / 레시피" 섹션에 링크. recipe(특정 기능)는 "기능별 인덱스"에도 등록. **recipe는 category가 없어(cross-stack) sub-index로 분할되지 않는다 — 분할 상태에서도 `index.md` 본체의 "가이드 / 레시피" 섹션·기능별 인덱스에 등록한다(§4).**
2. 관련 가이드/허브/feature "관련" 섹션에 상호 링크.
3. `log.md`: `- [YYYY-MM-DD] [GUIDE] {가이드명} 작성.`

#### I-4. 검증
- 예산·wikilink·`platform` 통제 어휘·recipe 스택 폴더 배치 확인.
