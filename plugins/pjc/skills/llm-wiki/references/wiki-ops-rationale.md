# llm-wiki 규칙 — 근거 (`wiki-ops-rules.md` 개정용)

> **이 파일은 `wiki-ops-rules.md` 의 규칙을 고칠 때만 읽는다 — 절차 수행에는 필요 없다.**
> 절 이름은 `wiki-ops-rules.md` 와 **같게** 쓴다. 머리말의 근거는 아래 「머리말」 절이 받는다.
> 규칙 본문에서 이리로 옮긴 것은 **왜 그렇게 정했는가 · 어떤 실해가 있었는가 · 무엇을 왜 기각했는가**이고, 규칙 자체는 저쪽에 남아 있다.

## 머리말

- **이 파일을 코드 작업 세션이 읽지 않는 것이 분리의 목적이다** — 절차 K(read-only 참조)는 `references/lookup-rules.md` 에, §0(경로 결정)은 `SKILL.md` 본체에 있어 이 파일을 Read 할 필요가 없다. 코드 세션은 하니스 최빈 경로라 본체 전문이 매번 상주한다(v1.180.0 T8 분리).
- **절차 조건을 이 파일 산문에 다시 쓰지 않는다** — `SKILL.md` 「쓰기 규칙 절 라우팅」 표가 정본이고, 두 곳에 살면 한쪽만 고쳐져 갈린다(v1.304.0).

## 쓰기 세션 전용 규칙 — 사전 준수 사항(쓰기분)

- **`question` 을 지우지 않고 보존하는 이유** — 해결 이력도 지식이라 같은 질문의 재조사를 막는다(schema §2.7).
- **병렬 분업에서 에이전트 호출이 「수신 확인 호출」인 이유** — 반환값을 받아야 ②(공유 파일 일괄 갱신)·③(반환값으로만 보고)이 성립한다. 전문·근거는 wiki-schema §9 가 정본이다.
- **lint 폴백이 콘텐츠 절차에도 걸리는 이유** — 그 세션은 `procedures-ops.md` 를 읽지 않으므로, 규칙이 이 파일에 없으면 폴백 없이 하드 실패한다.

- **log 기록 조건이 사전 백업에도 걸리는 이유** — log 를 쓰는 것 자체가 vault 쓰기라 비 git vault 에서 사전 백업까지 연쇄 발동한다. 쓰기가 없으면 백업 대상도 없고, **점검이 부작용을 낳지 않게** 하려는 것이다.
- **git vault 가 `--fix` 백업에서 면제인 근거는 사전 백업 면제와 같다** — git 이력이 보호를 담당한다. 비 git vault 의 백업 폴더를 세션 종료가 아니라 **다음 실행 시작 시** 회수하는 이유는 wiki-schema §8 이 정본이다.

## 셸 경유 편집 규약

- **`PYTHONIOENCODING=utf-8` 을 붙이는 이유** — 명령 자체는 맞는데 **출력에서 실패**하므로 원인을 찾는 데 시간이 든다.
- **앵커를 짧게 잡는 이유** — `\|` 이스케이프·각주·wikilink 가 든 문장은 어디가 다른지 나오지 않는다. 짧은 앵커는 유일성만 확보되면 충분하다.
- **줄 수로 크기를 재면 안 되는 이유** — 줄 수로 "작다"고 판정하면 출력 상한에 걸려 본문이 오지 않는다(288줄짜리가 66KB 인 파일이 있다).
- **CRLF 복원이 규칙인 이유** — 레포 정합 검사가 LF 전환을 「줄바꿈 전면 LF」로 잡는다.

## git 자동 반영 (커밋 · push)

- **커밋·push 면제 규정을 `SKILL.md` 에 둔 이유** — 절차 K 가 이 파일을 Read 하지 않아, 최빈 경로에 닿아야 하는 규정을 그쪽에 두었다.
- **메시지 형식 예시** — `문서: ingest — 계획 축 ⑫ 반영 [12840]` · `문서: lint --fix — 끊긴 wikilink 3건 정정 [12840]`.

- **「커밋 시점」 ① 이 없으면 「체크포인트 커밋」이 절차의 미커밋 편집을 통째로 삼킨다** — 그 커밋은 `git add -A` 라 그 시점의 모든 미커밋 변경을 담고, 그러면 ingest 편집 6파일이 `문서: auto-split 직전 체크포인트` 라는 이름으로 남고 절차 본 커밋에는 그 뒤 손댄 것만 들어간다(2026-09-16 두 번 관측 — 체크포인트 `8e87b13` 대 본 커밋 `fb85314`). **② 만 두면 ① 의 자리가 비고, 그 자리가 곧 결함이다.**
- **① 을 「호출마다」로 둔 이유** — 첫 호출의 처방 결과가 미커밋으로 남는지는 재점검 pass 가 도는가로 갈리므로(돌면 그 진입 체크포인트가 앞 pass 결과를 담는다 — 2026-09-16 실측), 절차가 그것을 매번 재지 않게 했다.
- **커밋이 늘어도 규정 목적은 더 잘 달성된다** — 「무엇이 무엇을 바꿨는지 이력에서 읽히게」가 목적이고, 처방 결과가 절차 편집과 갈려 각자 이름을 갖는 쪽이 그에 부합한다. 그래서 ① 에 새 메시지 형식을 만들지 않았다.
- **체크포인트의 `pass` 당 1회 격리는 새로 만든 것이 아니라 옮긴 것이다** — 종전에 `-presplit` 폴더가 pass 마다 고유 타임스탬프를 쓴 것이 정확히 이 격리이고, 그 고유성은 *"날짜만 쓰면 재점검 pass 가 본 pass 의 사본을 재사용해 되돌려도 1회째가 반영된 지점으로 돌아간다"* 는 실제 버그를 고친 결과다. **호출당 1회로 합치면 그 수정을 되돌리게 된다.**
- **dirty 거부를 기계가 재는 이유** — 「커밋 시점」 ① 을 빠뜨렸는지를 문면만으로 두었을 때 **같은 결함이 2회 재발했다**. **검사를 진입 시 1회로 둔 이유**는 pass 별로 재면 pass 1 의 처방 결과(스크립트 자신이 만든 dirty)가 pass 2 를 막아 정상 흐름이 서지 않기 때문이고, **탈출 플래그를 두지 않은 이유**는 두면 그것이 기본 경로가 되기 때문이다.
- **HEAD 대조가 lock 을 대체하지 못하는 이유** — ⓐ 는 상대가 이미 커밋한 경우만 보고 **미커밋 워킹트리는 못 본다**(2026-09-10 사고가 정확히 그 형태였다).
- **`git add -A` 를 유지하는 이유** — 스킬이 만든 변경만 골라 담으면 사용자 수기 편집이 영영 미커밋으로 남아 다음 절차의 백업·복구 판정을 흐린다. `.gitignore` 전제 없이 `-A` 를 쓰면 PC 마다 달라지는 UI 상태가 매 커밋에 섞여 이력이 노이즈로 덮인다.

## 동시 실행 — 두 세션이 같은 vault 를 만질 때

- **실해**: 2026-09-10 Maid ingest 의 커밋 `f77126e` 가 같은 시각 진행 중이던 claude-harness-pjc ingest 의 편집 13파일을 함께 담았다. **내용 손실은 없고 이력이 틀린다** — 그 커밋만 보면 Maid 반영이 하니스 위키 13파일을 고친 것으로 읽힌다.
- **그래도 `-A` 를 유지한 이유** — 그 근거(사용자 수기 편집이 영영 미커밋으로 남는 것)는 동시 실행과 무관하게 살아 있고, 경로를 한정하면 그 편집이 다시 떠돈다. **문제는 `-A` 가 아니라 「남의 진행 중 편집이 워킹트리에 있다」는 것**이라 그 자리를 막았다.
- **lock 을 vault 전역이 아니라 `--auto-split`·`--fix` 구간으로 좁힌 이유** — 전역을 잠그면 두 번째 세션이 절차 내내 대기한다. 그 둘만 `glob(vault/**/*.md)`·`_project_hub_paths`·`_decision_log_paths`·`_prose_page_paths` 로 vault 전역을 훑는다.
- **stale lock 을 대기가 아니라 탈취로 처리하는 이유** — 죽은 세션 때문에 다음 세션이 영영 멈추는 것이 더 나쁘다. PID 실존과 경과 시간을 둘 다 보는 것은 프로세스가 죽으면 PID 로, 죽지 않고 멈추면 시간으로 걸리게 하려는 것이다.
- **push 실패를 재시도하지 않아도 유실이 되지 않는 이유** — 세션이 비정상 종료돼 push 를 못 해도 로컬 커밋은 남고, 다음 위키 세션의 push 가 함께 올린다.

## 파일 예산

- **`index.md` 를 행/줄 수로 재는 이유** — index 는 등록 항목 개수가 본질이라 문자 수가 압박을 대변하지 못한다(산문 타입만 문자 수 — v1.138.0).
- **생성 마커가 있는 vault 에서 수기 분할 지시를 남겨 둔 이유** — 그 지시는 마커 없는 vault 용이고, 지우면 그런 vault 에서 분할 경로가 사라진다.

- **압축을 처방으로 쓰지 않는 이유** — 압축은 매번 근거·경위를 소실시키고 무한 반복된다(wiki-schema §4·§8). 전 타입이 이동·분리 처방을 갖는 것이 그 대안이다.
- **비계를 빼고 재는 이유** — 정본 포인터 줄과 `## 하위 문서` 목록은 `--auto-split` 자신의 산출물이라 사람이 줄일 수 없고 나눌수록 늘어난다. 이 둘을 세면 **본문이 전부 포인터 스텁인 허브**가 처방 없이 신호만 내는 상태가 된다.

## 예산 단계 신호

- (임계 표는 `check_consistency.py` 가 `lint.py` 상수와 기계 대조하는 자리라 값도 표도 규칙 쪽에 남는다.)

### 신호 층위

- **ⓐ 가 침묵하는 이유** — `--auto-split` 이 다음 lint·ingest 에서 그 파일을 나눈다. 사람이 할 일이 없는데 「초과까지 몇 % 남았다」를 반복하면 그것은 소음이고, 정작 손이 필요한 ⓑ′ 가 그 더미에 묻힌다.
- **침묵은 「auto-split 이 맡았다」는 뜻이지 「무시해도 된다」가 아니다** — 그래서 맡을 주체가 없는 파일은 ⓑ′ 로 반드시 신호가 난다. 이 구분이 없으면 *조용한데 처리도 안 되는* 파일이 생긴다.
- **「처방 넷」을 넷 다 보고 판정하는 이유** — 산문 분리 하나만 보면 롤오버가 맡은 파일이 「처방 없음」으로 몰리고, 반대로 산문 술어만 참으로 두면 `source-stub` 처럼 **어느 처방도 없는 타입이 초과 직전까지 조용해진다**.
- **`BUDGET_OVER_ONLY_TYPES` 의 값을 `BUDGET` 에서 지우지 않는 이유** — 그렇게 하면 초과 WARN 까지 함께 죽는다. 근접 분기만 막으면 임박인 파일이 ⓒ 로 흘러 같은 신호가 이름만 바꿔 되살아난다(v1.303.0 실측). **그 타입에 크기 신호를 남기는 근거**는 절차 K 가 `conventions.md` 본문을 매 작업 전에 읽는다는 것이다.
- **비율과 잔여를 OR 로 묶은 이유** — 어느 하나로도 실측이 갈리지 않는다: 비율만 쓰면 여유 414자인 decision-log(93%)를 놓치고, 잔여만 쓰면 예산이 작은 타입(`source-stub` 1800자)에서 72%짜리가 임박이 된다. **선행 게이트를 지우면 안 되는 이유가 뒷항이다.**
- **소비 지점을 못 박은 이유** — 신호만 있고 소비하는 절차가 없으면 그 신호는 사문이 된다.
- **「분리 불가 판정」을 영구 면제로 두지 않은 이유** — 그러면 「한 번 판정하면 초과까지 무신호」가 되어 판정 자체가 사각이 된다. 그래서 재판정 마진을 넘게 자라면 억제가 풀린다.

### 세션 처방

- **「처방 넷」과 수가 다른 이유는 수행 주체다.** 넷은 **`--auto-split` 이 실제로 옮길 수 있는 것**이라 표 ⓐ 조건(침묵)을 결정하고, ⓕ 는 **세션이 손으로 하는 것**이라 ⓑ′ 로 신호가 난다. **그것을 넷에 합치면 ⓐ 조건이 참이 되어 스크립트가 못 하는 일에 침묵이 걸린다.** (v1.303.0 전에는 convention 구역화 ⓔ 가 함께 있었으나 그 타입이 분할 처방에서 빠지며 폐지됐다.)
