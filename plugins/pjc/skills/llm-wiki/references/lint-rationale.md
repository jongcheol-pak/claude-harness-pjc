# lint 검사 판정 근거 (§7 상세)

> `wiki-schema.md` §7 의 각 검사가 **무엇을 어떻게 판정하는가**와 그 근거·오탐 사례·경계 조건을 담는다.
> **이 파일은 `scripts/lint.py` 를 고칠 때 읽는다** — 그 판정을 수행하는 것은 코드이고 세션이 아니다.
> 세션이 절차 F(lint)에서 필요한 것은 §7 의 **이름·심각도·호출법**이며 그것은 그 절에 남아 있다.
> 번호는 §7-N 과 1:1 이고 F-1 실행 순서 인덱스와도 같다.

## §7-1. 참조 무결성

**참조 무결성**: 깨진 wikilink 탐색 및 수정/제거 (`20_projects/{proj}/`, `40_guides/`, `index.md`의 `## 증상별 인덱스` 행(§6) 포함 — 해법 페이지가 삭제되면 그 증상 행의 링크가 깨지므로 여기서 제거/수정). **루트 큐 파일(`pending.md`·`skill-feedback.md`, 소비 대기 큐 §6)은 제외** — 큐 항목은 지식 페이지가 아니라 링크 규약(§3)의 대상이 아니며, 큐에 적힌 대상이 이후 삭제·이름변경돼도 lint를 ERR(exit 1)로 실패시키지 않는다(시크릿 §7-22·잔량 집계 §7-25·고아 판정용 링크 수집은 유지)

## §7-3. ~~신선도~~ — 폐지 (v1.238.0)

**~~신선도~~ — 폐지 (v1.238.0)**: `updated` 기준 60일 미편집 → confidence 하락, 90일 → 아카이브 후보 제시를 검사하던 자리다. **집행 주체가 없어 실측 0건이었다** — 실 vault에서 매 실행 121건을 INFO로 내면서 `confidence: low`는 한 건도 만들어지지 않았고(작성 시점 high 342 / medium 25 / low 0), 그 더미가 뒤처짐(§7-26)·큐 잔량(§7-25) 같은 실행 가능한 신호를 덮었다. 면제 목록이 계속 늘어난 것(feature·guide 아카이브 제외 + decision-log·convention·question·paused·archived·deprecated 전체 면제)이 규칙 자체가 이 위키에 맞지 않는다는 신호였다 — 안정된 지식베이스에서 "오래됨 = 신뢰도 낮음"은 성립하지 않는다. 콘텐츠가 레포를 못 따라온 상태는 §7-26이 커밋 수로 더 정확하게 잰다. **번호는 재사용하지 않는다**(§7-27과 같은 이유 — F-1 인덱스와의 1:1 대조가 어긋난다). (lint.py 검사 없음)

## §7-6. 기능별 인덱스 동기화

**기능별 인덱스 동기화**: `index.md` 기능별 인덱스 ↔ 실제 feature 페이지 일치 확인. vault 루트의 `index.md`를 쓸 수 없으면 **ERR 1건** 보고 후 인덱스 기반 검사(§7-6·14·15·16·23)를 건너뛴다(침묵 통과 방지). **불능 사유는 둘이며 처방이 정반대라 각각 다른 ERR을 낸다** — ⓐ **부재**(파일이 없음) → 카탈로그 골격 생성(§4) ⓑ **읽기 실패**(파일은 실재하나 비 UTF-8 등으로 디코딩 불가) → 인코딩 복구. 둘을 한 ERR로 합치면 실재하는 인덱스에 "골격을 생성하라"는 처방을 내리게 된다. (lint.py 검사)

## §7-7. 통제 어휘 위반

**통제 어휘 위반**: `platform`·`origin`·`confidence`·`category` 값이 고정 어휘(§3)를 벗어나면 ERR — category 오타(`Personal` 등)는 sub-index 분할 라우팅·경로 규약을 어긋나게 한다. **이 항목은 두 판정을 포함한다**: ⓐ 값 위반(ERR — 네 필드 공통, category는 값이 있을 때만 검사·부재는 경로 규약과 이중 방지 위해 미검사) ⓑ 필수 필드 누락(WARN — `origin`/`confidence`, `ORIGIN_REQUIRED_TYPES` 대상). **`platform`·`category` 값 위반과 허브 `tech_stack` 휘발성 버전(§7-11) 검사는 `90_archive/`를 제외**한다 — 통제어휘 축소·정책 변경 시 동결 백업이 영구 ERR/WARN(특히 ERR은 exit 1)을 내지 않게(§2.8·§8 자동 제외). (lint.py 검사)

## §7-8. 고아/비표준 파일

**고아/비표준 파일**: 어디서도 링크되지 않는 페이지, 타입 미지정 파일 탐색. **링크 인정 범위는 vault 전체다(90_archive 포함)** — 아카이브 페이지가 걸어놓은 링크도 '링크됨'으로 인정하므로, 아카이브에서만 링크된 현행 페이지는 고아로 잡히지 않는다(보수 판정 — lint은 제안만 하는 read-only이므로 오탐 억제를 우선). **`lint-*` 리포트 페이지는 어디서도 링크되지 않는 게 정상이라 제외**한다 — §7-12 집계·§7-23 등록과 동일 기준(그렇지 않으면 매 lint 리포트가 자기 자신을 고아로 오탐).

## §7-11. tech_stack 휘발성 버전

**tech_stack 휘발성 버전**: 소스 스텁 "기술 스택" 줄 + project 허브 `tech_stack` frontmatter에 major.minor 이상 버전(`\d+\.\d+`)이 있으면 경고(§2.1·§2.2 — 이름만 기재, 버전 진실원천은 코드). entity/feature 본문 산문은 오탐 위험으로 기계 검사 제외(규칙으로 보완). (lint.py 검사)

## §7-12. (미검증)·미해결 question 집계

**(미검증)·미해결 question 집계**: ⓐ `20_/30_/40_` 콘텐츠 페이지 본문(frontmatter 제외, `90_archive`·`lint-*` 리포트 제외 — 리포트는 발견 내역을 원문 인용으로 보존하므로 표기가 본문에 남아 자기참조 오집계가 된다)의 `(미검증)` 표기 발생 수·파일 수 ⓑ `type: question` ∧ 미해결 파일 수를 **정보(INFO) 등급**으로 집계 리포트(0건이면 생략). 닫힘 판정은 `status: resolved` 또는 `resolved:` 필드(B-2 3-1) 어느 쪽이든 인정하고, `lint-*` 리포트 페이지는 질문이 아니라 집계에서 제외한다 — **§7-23 등록 요구와 동일 기준**(집계↔등록 모순 방지), ⓐ·ⓑ 모두 적용. `10_sources`는 불변 스텁이라 검증 루프 대상이 아니므로 제외. (lint.py 검사 — §11 사용자 검증 후보 공급)

## §7-15. sub-index 목록 정합

**sub-index 목록 정합**: vault에 실재하는 sub-index 파일(`index-*.md`)이 `index.md`에 언급(목록 등록)됐는지 — 미등록이면 WARN(절차 K·검색이 분할 인덱스를 빠뜨리지 않게). 역방향(목록엔 있으나 파일 없음)은 깨진 wikilink 검사(1번)가 커버한다. **생성 마커가 있으면 이 정합은 생성기가 보장한다** — sub-index 파일과 본체 목록을 같은 실행에서 함께 쓰기 때문에 어긋날 수 없다. **검사는 그대로 남긴다**(D8) — 생성기가 잘못 만들었을 때 잡는 회귀 안전망이고, 그것이 이 번호를 지우지 않는 이유다. **못 잡게 되는 것**: 없다(검사 불변 — 어긋남의 *원인*이 줄어드는 것이지 검사가 좁아지는 것이 아니다). (lint.py 검사)

## §7-16. 기능별 인덱스 한/영 병기

**기능별 인덱스 한/영 병기** *(생성 마커가 있으면 수정처가 다르다 — 아래)*: 기능별 인덱스 유형 행(feature/recipe)의 첫 컬럼(기능명)에 한글(`[가-힣]`)과 영문(`[A-Za-z]`)이 모두 있는지 — 한쪽만이면 WARN. 한글로 등록하든 영문 기술용어로 등록하든 양방향 검색이 한 줄에서 되도록(§3 기능별 인덱스 한/영 병기). 행 인식은 §7-14와 공용인 **형상+대상 기반**(§3 행 형식 — alias 무관, 첫 컬럼이 wikilink인 프로젝트/기술 표 행은 제외 — 가이드·레시피는 통합 표에서 첫 컬럼이 평문이라 이 검사 대상이고, **옛 `## 가이드 / 레시피` 형상(첫 컬럼 `40_guides/` wikilink, 이름은 alias)도 대상이다 — recipe 제외·full path 한정은 §3 「하위호환 형상」**), 스캔은 index.md+sub-index **전체 텍스트**(§4 — `## ` 소분할 뒤 행도 누락 없음). (lint.py 검사) **⚠ 생성 마커가 있는 vault에서 이 WARN의 수정처는 index 행이 아니라 그 페이지의 `index_label`(§3)이다** — 인덱스가 생성물이 되면 행을 손으로 고쳐도 다음 `--build-index`가 덮는다. 역이관(`scripts/migrate-index-labels.py --apply`) 전에는 폴백 라벨이 쓰여 이 WARN이 다수 뜨는 것이 정상이며, 역이관 후 `index_label`을 고치면 닫힌다. **(§7-27은 폐지돼 이 검사에 흡수됐다 — 그 항목 참조.)** **못 잡게 되는 것**: 없다 — 검사는 그대로 돌고 대상 문자열도 같다(고칠 자리만 페이지 쪽으로 옮겨졌다).

## §7-17. deprecated 표기 정합·집계

**deprecated 표기 정합·집계**: 폐기 표시(`status: deprecated` 또는 `deprecated:` 필드, §2.3) 페이지를 ⓐ INFO로 집계(이력 가시성 — 현행 vault 한정, `90_archive/` 제외) + ⓑ 본문에 "코드에서 제거"류 안내가 없으면 WARN(절차 K 참조 시 현재 기능 오인 방지) (ⓒ 자리는 v1.238.0의 §7-3 폐지로 소멸했다 — 시간 기반 후보에서 제외할 검사가 없다). **단 "deprecated여야 하는데 표기 누락"은 lint이 코드를 못 읽어 탐지 불가** — 표기된 페이지의 정합만 검사. (lint.py 검사)

## §7-18. feature 구현 근거 각주

**feature 구현 근거 각주**: `type: feature`에서 ⓐ **`## 구현 방법` 섹션 자체가 없으면 WARN** — 필수 섹션(§2.3)을 통째로 빼서 각주 게이트를 우회하는 구멍을 막는다(섹션 판정은 줄 시작 헤딩 기준 — 산문 인용은 존재로 안 침) ⓑ 섹션이 있으나 `[^src-...]` 각주가 0개면 WARN(근거 없는 얕은 feature 의심, §2.3 각주 필수 규칙의 기계 강제). 이 항목은 **섹션·각주 존재 여부**를, 각주 경로의 레포 실존은 §7-20이 기계 검사하고(레포 접근 가능 시 — 불가 시 §7-10 폴백), 서술↔코드 사실 정합은 §7-10(에이전트 표본)이 담당한다(역할 경계). deprecated·아카이브 페이지는 제외. (lint.py 검사)

## §7-20. feature 각주 경로 레포 실존

**feature 각주 경로 레포 실존**: feature의 `[^src-...]` 각주 정의 줄에 백틱으로 병기된 **레포 상대경로**(디렉터리 구분자 `/`·`\` 포함 토큰만 — 무구분자 토큰은 클래스·멤버명일 수 있어 제외)가, 프로젝트 허브 `## 레포 정보 > 경로`의 레포에 **실재하는지 전수 기계 검사** — 부재면 WARN(이동·삭제·오기 가능), 글롭(`*`) 토큰은 매치 0건이면 WARN. **brace 축약(`{a,b}.md`)은 확장하지 않는다** — 규약 위반(§3 경로 표기 규칙: 파일마다 개별 병기)이며 그대로 경로 부재 WARN이 된다. lint은 파일 **실존만** 보고 코드 내용은 해석하지 않는다(내용 정합은 §7-10). 허브에 레포 경로가 없거나 그 디렉터리가 실재하지 않으면(다른 PC 등) **프로젝트 단위 INFO 1건** 후 건너뛰고, 그 프로젝트의 경로 실재 확인은 §7-10 에이전트가 폴백 수행한다. deprecated·아카이브 feature 제외("검증 안 된 컨텍스트는 없는 것보다 위험" — 각주 경로가 리팩토링으로 어긋난 채 남으면 절차 K 참조를 오도). (lint.py 검사)

## §7-21. feature `## 관련 파일` 섹션 게이트 + 경로 실존 + 진입점 심볼 실존

**feature `## 관련 파일` 섹션 게이트 + 경로 실존 + 진입점 심볼 실존**: `type: feature`(deprecated·`90_archive/` 제외)에 `## 관련 파일` 섹션이 없거나 백틱 경로 항목이 0개면 WARN — 기능 구성 파일의 한눈 지도(§2.3)가 없으면 "기능 → 관련 파일" 검색이 각주 산개에 의존하게 된다. **WARN 문구는 원인을 구분한다**: "섹션 누락"(섹션 자체 없음 — "다음 ingest 시 채움" 안내로 점진 정비 유도)과 "경로 항목 0개"(섹션은 있으나 백틱 경로 없음 — `- \`경로\` — 역할` 형식 안내)는 수리 방법이 달라 문구를 나눈다. 섹션 내 백틱 경로 토큰(구분자 `/`·`\` 포함만)은 §7-20과 동일 로직·동일 레포 루트 캐시로 실존을 검사(부재·글롭 매치 0 WARN, 레포 접근 불가 시 프로젝트 단위 INFO 폴백 공유). **진입점 심볼이 병기된 행**(`(진입점: `심볼`)` — 선택 필드, 형식 정본은 §2.3)은 **그 행의 첫 경로가 가리키는 파일 본문에 그 문자열이 있는지** 확인하고 없으면 WARN — **정의인지 호출인지 주석인지 가르지 않는다**(파싱은 이 도구의 일이 아니다 — 아래 결과 처리의 레포 접근 범위). **미기재는 검사하지 않는다** — 필수로 하면 기존 페이지가 전부 WARN이 되고, INFO로 두면 그 층에 묻힌다. 파일 자체가 없으면 위 경로 WARN이 이미 알렸으므로 중복 신고하지 않는다. (lint.py 검사)

## §7-22. 시크릿 의심 스캔

**시크릿 의심 스캔**: 전 페이지 본문(frontmatter 제외, 아카이브·코드펜스 포함 — 시크릿은 어디 있든 위험)에서 password/API key·token/Bearer/DB 연결문자열/개인키 블록/URI 자격증명 패턴을 검사 — 발견 시 WARN("실제 값이면 즉시 제거, 환경변수 이름만 기재"). **키워드+구분자+실값 형태만 매칭**하는 보수 정규식이며, 플레이스홀더 표식(`YOUR_`·`<...>`·`{...}`·`$env:`·`예:`·"환경변수"·localhost 등)이 있는 줄은 제외해 규약 안내문 오탐을 막는다. IP 주소는 산문·버전 오탐 위험으로 검사하지 않는다(민감 정보 금지 규칙 자체는 유지 — 사전 준수 사항). (lint.py 검사)

## §7-23. 미해결 질문 인덱스 동기

**미해결 질문 인덱스 동기**: `type: question`(`90_archive/` 제외) ↔ `index.md` 본체 `## 미해결 질문` 표(비분할 섹션 — §4)를 양방향 대조. ⓐ open question이 표에 **미등록**이면 WARN(등록 누락 = 잊힘·유실 위험 — 단 `lint-*` 리포트 페이지는 질문이 아니라 제외) ⓑ resolved question이 표에 **잔존**하면 WARN(stale — index에서만 제거하고 **페이지는 보존**, B-2 3-1·§2.7). 닫힘 판정은 §7-12와 동일 — `status: resolved` 또는 `resolved:` 필드(B-2 3-1) 어느 쪽이든 인정. 등록 판정은 표의 wikilink 대상 기준으로, 규약(§3)은 무확장자 경로 링크가 원칙이나 `.md` 포함·파일명만 링크도 등록으로 인정한다(그 형식 위반은 §7-1 링크 검사가 별도 보고 — 이중 오탐 방지). 섹션 탐색은 코드펜스 제외 사본에서 수행(예시 헤딩 오매칭 방지). resolved 페이지의 '삭제' 행위 자체는 스냅샷 검사로 탐지 불가 — 삭제 금지는 절차 규칙(§2.7·SKILL 사전 준수 사항)이 담당한다. (lint.py 검사) **⚠ 생성 마커가 있는 vault에서는 `--fix`가 이 항목을 건너뛴다 (D11)** — 그 섹션이 `--build-index`의 생성 구역이라 **같은 자리에 writer가 둘이 되면 어느 쪽이 근거인지 사라진다.** 생성기가 매 실행 같은 정합을 보장하므로 자동수정이 할 일이 없다. **검사는 그대로 남는다** — 뒤처짐은 종전대로 WARN으로 보고되고, 닫는 방법만 `--build-index` 1회로 바뀐다. **마커 없는 vault는 무회귀**(안전 3종 전부 동작). 건너뛴 사실은 `[SKIP]` 줄로 출력된다. 

## §7-24. decision-log 정합

**decision-log 정합**: ⓐ 현행 decisions.md(`type: decision-log`) `## 아카이브` 포인터의 경로 실재 + 롤오버 아카이브(`90_archive/**/decisions.md`)가 실재하는데 대응 현행 파일에 포인터가 없으면 WARN — **양방향**. 포인터는 wikilink가 아닌 평문 경로라 §7-1 깨진 링크 검사에 잡히지 않고, 누락·오기 시 조회(K 2·G 2b)가 현행 파일만 읽고 "기록 없음"으로 침묵 오답한다(§2.8). 대응 현행 파일 자체가 없는 아카이브는 절차 C 보존-삭제 이력이므로 건너뛴다. ⓑ 항목 줄(`- [YYYY-MM-DD] …`)의 결정 어휘가 고정 어휘(`채택|보류|기각|번복`)를 벗어나면 WARN — 어긋난 어휘는 G 타임라인 합성·번복 추적에서 누락된다(§2.8·§3). (lint.py 검사)

## §7-25. 큐 잔량 집계 (두 파일)

**큐 잔량 집계 (두 파일)**: `pending.md`의 `[K-DRIFT]`/`[DECISION]`/`[PROJECT-FACT]`/`[K-MISS]`/`[SYMPTOM]`과 **`skill-feedback.md`의 `[SKILL-IMPROVE]`** 태그별 미처리 건수를 INFO로 집계(0건·파일 없음이면 생략. **파일별로 나눠 표기**해 어느 큐가 밀렸는지 보이게 한다) — 소비를 유도한다(ingest는 B-1 0, lint는 F-0 보고 후 F-2 승인 시, 절차 M은 사용자 요청 시; §6 큐 규약). **한 번의 소비가 닿는 것은 그 요청이 지목한 범위뿐이라, 집계에는 나머지 태그·보류분이 계속 남는다** — 이 INFO가 0이 되지 않는 것은 정상이다. **더불어 태그는 있으나 `- [YYYY-MM-DD] [TAG]` 선두 형식이 아닌 줄은 이 집계에서 누락되므로 별도 WARN으로 보고**한다(불릿 ∧ 태그 존재 ∧ 선두 형식 미매치) — 형식 위반 줄은 어느 태그에도 안 잡혀 큐가 쌓여 있어도 잔량 0으로 보고되고, 그러면 **"0건"과 "형식이 틀려 못 셈"이 구분되지 않아** 침묵이 안전 신호로 오독된다(집계 숫자의 신뢰성 문제라 INFO가 아니라 WARN). 형식 규약 정본은 `references/queue-rules.md` 절차 K 5~5-5. (lint.py 검사)

## §7-26. 위키 뒤처짐 (레포 대비)

**위키 뒤처짐 (레포 대비)**: project 허브의 `synced_commit`(§2.2)이 있고 `## 레포 정보`의 경로가 **git 레포로 접근 가능**하면, 그 sha 이후 HEAD까지 쌓인 커밋 수를 세어 **INFO**로 보고한다(`위키 뒤처짐: {프로젝트} — {n}커밋 미반영 (synced: {sha7})`). 0커밋이면 출력하지 않는다(노이즈 방지). **`synced_commit` 미설정이면 INFO 1줄**로 기준점 부재를 알린다(다음 ingest에서 채워짐). **임계값 없이 INFO 고정** — 커밋 수 임계는 프로젝트 커밋 빈도에 따라 의미가 달라 근거 없는 상수가 되므로 "후보 제시"에 머문다(exit code 불변). **fail-open**: 레포 경로 부재·`.git` 없음·git 미설치·sha가 이력에 없음(rebase·force push)·서브프로세스 예외는 조용히 건너뛴다(단 sha가 이력에 없는 경우만 INFO 1줄 — 기준점이 무효화돼 사용자 조치가 필요). 레포 루트는 §7-20·§7-21과 **동일한 출처**(허브 `## 레포 정보 > 경로`)에서 얻는다(같은 `repo_root_for_hub()` 로직 — 다만 §7-20/21의 feature 단위 캐시와 자료구조를 공유하지는 않는다. 허브 수만큼만 호출되므로 캐시가 불필요). (lint.py 검사)

## §7-27. ~~가이드/레시피 섹션 가이드 행 한/영 병기~~ — 폐지 (§7-16에 흡수)

**~~가이드/레시피 섹션 가이드 행 한/영 병기~~ — 폐지 (§7-16에 흡수)**: `index.md`의 `## 가이드 / 레시피` 섹션 행은 첫 컬럼이 wikilink라 §7-16(첫 컬럼 **평문** 형상)이 형상 자체로 놓쳤고, 이 검사가 그 사각을 메웠다. **그 섹션이 통합 표(`index-guides.md`, 첫 컬럼 평문)로 대체되고 §7-16의 대상 조건이 `40_guides/` 전체로 넓어졌으며, §7-16이 옛 섹션 형상(첫 컬럼 `40_guides/` wikilink)까지 함께 받으면서 §7-16 하나가 신·구 양쪽 전 행을 본다**(옛 형상의 recipe만 §3 ①으로 제외되며 그쪽은 평문 행이 대상이다)(하위호환 수용의 범위·제외는 §3 「하위호환 형상」 — 폐지 직후에는 그 수용이 없어 마커 없는 vault에 무신호 구간이 있었고, 그것을 닫은 것이 이 수용이다) — 같은 것을 두 번 검사하게 되므로 폐지했다. **번호는 재사용하지 않는다**(폐지 이력을 지우면 이 자리에 무엇이 있었는지 알 수 없고, `procedures-ops.md` F-1 인덱스와의 1:1 대조도 어긋난다). 승계 실증은 골든 `no-hanyeong-guide` — §7-16의 대상 조건을 되돌리면 그 케이스만 FAIL한다. (lint.py 검사 없음)

## §7-30. 이동·분리 도달 경로 정합

**이동·분리 도달 경로 정합**: 압축을 없앤 대가로 §2.2 롤오버·§2.9 하위 분리는 **옮긴 자리를 읽는 경로**에 의존하므로, 그 경로가 깨지면 이동이 곧 유실이 된다 — 두 판정을 포함한다. **ⓐ 허브 `## 아카이브` 포인터 ↔ `changes.md` 양방향**: 현행 허브(`type: project`, `90_archive/` 제외)의 포인터가 가리키는 아카이브가 실재하는지, 그리고 `90_archive/**/changes.md`가 실재하는데 대응 현행 허브에 포인터가 없으면 WARN. **경로 도출이 §7-24와 다르다** — decisions는 아카이브·현행이 같은 파일명이라 접두만 떼면 되지만, changes는 `90_archive/20_projects/{cat}/{proj}/changes.md` → 현행 허브 `20_projects/{cat}/{proj}.md`로 **폴더가 파일이 된다**. 대응 현행 허브가 없는 아카이브는 절차 C 보존-삭제 이력이므로 건너뛴다(§7-24 동형 — 없으면 삭제된 프로젝트의 아카이브가 영구 WARN이 된다). **ⓑ `conventions.md` `## 하위 문서` 목록 ↔ 하위 파일 양방향**: 목록이 가리키는 `conventions-*.md`가 실재하는지, 그리고 실재하는 하위 파일이 목록에 등재됐는지(미등재면 **조회 홉 1 위반** — 분리한 규약이 절차 K의 조회 경로 밖으로 나간다). 목록 표기는 wikilink(무확장자)·평문 경로 둘 다 인정한다(§7-24 포인터가 평문·§7-15 목록이 파일명 언급 기준인 두 선례 수용 — 형식 위반 자체는 §7-1이 별도로 본다). `## 아카이브`·`## 하위 문서` 섹션이 없으면 롤오버·분리 전이므로 skip. **`--fix` 대상이 아니다**(위 서두가 참조 무결성 3종으로 한정). (lint.py 검사) **ⓒ 인덱스 등록 (guide·entity·concept)**: 이 세 타입이 `index.md`+sub-index 어디에도 링크되지 않으면 WARN — §7-6이 feature에 하는 일을 나머지 타입으로 넓힌 것이다. 종전에는 대응 검사가 없어 **분할·신설한 페이지가 등록에서 빠져도 기계가 침묵**했다(§7-8 고아 검사는 위키 **어디서든** 링크되면 통과하므로 "다른 페이지는 링크하지만 인덱스에는 없는" 상태를 못 잡는다). **어느 인덱스에 실렸는지까지는 보지 않는다** — 그 배치는 `--build-index`가 결정론으로 하므로, 여기서 막는 것은 "조회 경로 밖에 남는 것" 하나다. convention은 ⓑ가, question은 §7-23이 각자 도달성을 보므로 대상이 아니다. 증상별 인덱스는 §7-6과 같은 이유로 제외본에서 센다. **ⓓ guide 허브 ↔ 하위 양방향**: 허브(`## 하위 문서` 섹션 보유 guide)의 목록이 실재하지 않는 파일을 가리키거나, **허브 복귀 링크를 가진 같은 폴더 guide가 그 목록에 없으면** WARN. ⓑ(convention)와 판정 방식이 다른 이유는 guide에 `conventions-{주제}.md` 같은 **파일명 접두 규약이 없기** 때문이다 — 폴더·`guide_kind`만으로 하위를 특정하면 **무관한 독립 가이드가 오탐된다**(실측: `40_guides/ui-ux/`에 분할 하위 2개와 독립 가이드 1개가 공존). 그래서 §2.6이 요구하는 **하위→허브 복귀 링크**를 하위 판정의 신호로 쓴다. **판정은 링크의 위치를 가리지 않는다** — §2.6은 "상단"을 규정하지만 상단의 경계를 정의하지 않아 그 선을 검사가 지어내면 규정에 없는 기준으로 미탐이 생기기 때문이다. 대가로 **같은 폴더의 독립 가이드가 허브를 단순 참조하면 후보로 잡힐 수 있고**(실 vault 399파일에서는 신규 WARN 0), 그때의 처방은 목록에 올리거나 참조를 떼는 것이다 — 어느 쪽도 파괴적이지 않으므로 미탐보다 낫다. **ⓔ 그 밖의 산문 타입 `## 하위 문서` 양방향 + 정본 포인터 도달성**: ⓑ·ⓓ는 타입이 정해진 두 경로만 보는데 §7-2 처방은 feature·project·entity·concept에도 하위를 만든다 — 그 산출물이 목록 밖에 남으면 조회가 닿지 못한다. **판정 신호는 복귀 링크(§4 ②) 하나이고, 상위도 그 링크에서 도출한다.** 종전에는 파일명 순번 접두(`{원본 stem}-{n}.md`)를 함께 요구했는데, 그러면 **순번이 없는 수기 하위가 통째로 미탐**이었다. 복귀 링크는 그 파일이 **스스로 「나는 X의 하위다」라고 선언한 것**이라 접두보다 강한 신호이고, 상위를 이름 규칙으로 추측하지 않고 링크가 가리키는 문서로 확정하므로 «무관한 페이지» 오탐도 그대로 막힌다(그런 페이지에는 복귀 링크가 없다). **`--fix`의 형제 하위 수집도 같은 신호를 쓴다** — 두 자리가 갈리면 「경고는 나는데 자동 수정은 못 하는」 구간이 생기고, 수기 하위가 정확히 그 자리였다. **ⓑ·ⓓ가 이미 보는 타입(convention·guide)은 제외**해 같은 쌍을 두 번 지적하지 않는다. 함께 **정본 포인터(§4 ③-1)의 도달성**을 본다 — 가리키는 파일이 실재하는지, **그리고 그 안에 같은 절 이름이 있는지**. 절 대조가 이 검사의 핵심이다: §7-1은 파일까지만 보므로 절이 사라진 「옮겼는데 못 찾는」 상태를 통과시킨다.

## §7-31. 작업 규약 미마이그레이션

**작업 규약 미마이그레이션**: 프로젝트 허브(`type: project`, `90_archive/` 제외)에 `## 작업 규약·주의사항` 섹션이 남아 있으면 **INFO** — 그 내용은 `conventions.md`(§2.9)가 정본이므로 다음 ingest에서 이전할 대상이라는 신호다. **WARN이 아닌 이유**: 기존 허브의 마이그레이션은 각 프로젝트 ingest 때 점진 적용하는 것이 사용자 결정이고, WARN이면 미마이그레이션 허브 전부가 매 lint마다 경고를 내 실제 결함이 묻힌다(§7-26 INFO 고정과 동일 계열 — 후보 제시에 머문다, exit code 불변). (lint.py 검사)

## §7-33. decision-log 방향 미기재

**decision-log 방향 미기재**: `type: decision-log`(90_archive 제외) 항목의 **첫 판정**이 `**기각**`·`**보류**`인데 그 직후가 `:`가 아니면 **WARN** — 주제 자리에 행위·부정문이 오면 판정만으로 방향이 뒤집혀 읽히고, 조회는 grep으로 행을 특정해 하위 불릿을 못 본다(§2.8 항목 형식). **첫 판정만 보는 것이 이 검사의 핵심이다** — 채택 항목의 본문이 대안을 「기각」으로 언급하는 형태가 실 vault에 흔해(신설 시점 21건 중 6건), 줄 어디든 매치로 세면 그것들이 전부 오탐된다. **괄호 부기는 통과시키지 않는다**: `**기각**(재사용하지 않는다)`처럼 방향인 것과 `**보류**(사용자 결정, 그 뒤 소진)`처럼 메타 정보인 것이 같은 형태라 기계가 가를 수 없어, 인정하면 후자가 그대로 통과한다. 채택·번복은 주제와 방향이 같아 대상이 아니다. **§7-29·§7-28과 달리 decision-log를 제외하지 않는다** — 그 둘은 「항목 불변이라 고칠 수 없는 WARN이 남는다」가 제외 근거였는데, §2.8이 **판정 명료화 예외**(내용 불변 조건)를 열어 이 WARN은 실제로 고칠 수 있다. `--fix` 비대상. ## §7-34. conventions 근거 표기 집계

**conventions 근거 표기 집계**: `type: convention`(90_archive 제외) 항목 중 **줄 끝 `({근거} …)` 앵커**(§3 「근거 통제 어휘」로 시작)가 없는 건수를 `{미보유}건 / 전체 {전체}건` 형태의 **INFO 1줄**로 집계한다(0이면 생략). **WARN이 아니라 INFO인 이유**: 소급 부여는 항목마다 근거를 되짚는 판단이라 코드가 대신할 수 없고, WARN이면 점진 적용 대상 전부가 매 lint마다 경고를 내 실제 결함이 묻힌다(§7-31·§7-32와 같은 계열 — exit code 불변). **파일별이 아니라 vault 집계 1줄인 이유**: 신설 시점 실측이 291/293이라 파일별로 내면 그 자체가 소음이 된다. **분모를 함께 내는 것이 이 집계의 요점이다** — 291/293은 「축이 고장났다」가 아니라 「§2.9가 정한 형식이 아직 안 쓰인다」는 뜻이고, 두 수를 함께 보여야 그것이 한 줄에서 읽힌다. **항목 판정에서 날짜의 닫는 `]`를 요구하지 않는다** — 실 vault에 `- [2026-07-15 갱신]` 같은 **날짜 부기** 형태가 있어, 요구하면 그 항목이 분모에서도 조용히 빠져 「표기 없음」과 「형식이 달라 못 셈」이 구분되지 않는다(§7-25가 큐 형식 위반을 별도 WARN으로 내는 것과 같은 취지). **보유 판정을 줄 끝 앵커로 좁힌 이유**: 어휘가 줄 어디든 있으면 보유로 세는 느슨한 판정은 「형식을 지켰는가」가 아니라 「단어가 있는가」를 재게 되고, 신설 시점 실측으로 그 둘은 2건과 56건으로 갈린다. `--fix` 비대상. (lint.py 검사)

## §7-35. patterns 관측 폭 집계

**patterns 관측 폭 집계**: `type: concept` 중 `30_knowledge/patterns/` 하위(90_archive 제외)에서 **`## 프로젝트 사례` 절**(§2.5가 정본)을 갖지 않는 건수를 `{미보유}건 / 전체 {전체}건` 형태의 **INFO 1줄**로 집계한다(0이면 생략). **§7-34와 같은 등급·형태이고 이유도 같다** — 절 이름을 고치는 것은 그 절이 「관측 기록」인지 「쓰는 법」인지 읽어야 갈리는 판단이라 코드가 대신할 수 없고, WARN이면 점진 적용 대상 전부가 매 lint마다 경고를 내 실제 결함이 묻힌다(exit code 불변). **분모를 함께 낸다** — 신설 시점 실측 20/35는 「축이 고장났다」가 아니라 「이름이 아직 안 모였다」는 뜻이다. **꼬리가 붙은 이름을 보유로 세지 않는다**(줄 끝 앵커) — 통과시키면 이름을 하나로 모으는 이 축의 목적이 사라지고, 정확히 그 형태(`## 프로젝트 사례 (.NET)`)가 지금 집계를 갈라 놓은 원인이다. `--fix` 비대상. ## §4 분할 수행 절차 2·4번 (auto_split 내부 동작)

> 세션은 `--auto-split` 을 호출하고 5번으로 검증할 뿐, 아래 동작을 직접 수행하지 않는다.
> 구현은 `scripts/lint.py` 의 `PRESCRIPTIONS`·`auto_split()`·`relocate_sections()` 다.

> **두 경로 모두 「무엇을 어디로 나눌지」가 결정론이다** — index는 category·등록 순서로, 산문은 **스키마가 정한 `## ` 섹션 경계 + 크기순**으로 정해진다(§7-2 번복). 사람이 의미 단위로 나누는 것은 언제나 허용되지만, **그것이 없어도 처방은 돈다**. **단 본문이 정본 포인터뿐인 절은 이동 대상이 아니다** — 옮겨도 문서가 줄지 않고 같은 스텁이 하나 더 생길 뿐이라, 그 절을 후보에 두면 호출할 때마다 같은 스텁이 새 하위로 나가 조회 경로에 같은 라벨의 빈 파일이 쌓인다(그 절이 스텁인 것은 이동 자리에 포인터를 남기는 이 처방 자신과, 하위에 필수 섹션을 재현하는 규정의 정상 결과다 — 없앨 것은 그 재현이 아니라 그것을 다시 집는 경로다). 공유하는 것은 실행·검증·원복·기록 절차(아래 1~7번)이고, 산문의 승인 불요 근거는 §7 결과 처리의 예외 ②다(열거로 범위를 특정한다 — index의 결정론 근거와 별개다).

2. **신설 파일 생성** — 경로별로 다르다.

   - **산문 타입 하위 분리**: §2.3~§2.9의 타입별 허브+하위 구조 규정대로 하위 파일을 만든다(같은 폴더·같은 frontmatter 타입, 상단에 허브 복귀 링크). **「무엇을 어디로 나눌지」는 1번에서 이미 정해진다** — 자동 경로는 크기순으로, 사람이 손수 나눌 때는 의미 단위로. 여기서는 그 결과를 파일로 옮긴다.

   - **index 분할 (sub-index 생성)**:

     - **2단계(category)**: `index-personal.md`·`index-work.md`(기존 category 기준 — 새 분류 금지) + `type: index`·`## 기능별 인덱스` 헤딩.

     - 무엇이 어떤 형태여야 하는지의 정본은 위 표 규정.

4. **등록(도달 경로 확보)** — 신설 파일이 어디서도 링크되지 않으면 조회 경로 밖이다.

   - **산문 타입**: convention은 `conventions.md` 하단 `## 하위 문서`에 **wikilink + 담당 범위 1줄**(§2.9 — 그 한 줄로 절차 K가 어느 하위를 열지 판정한다), guide는 허브의 `## 하위 문서`**에 등록하고 `--build-index`를 돌린다(§2.6 — 인덱스 행은 `index-guides.md` 통합 표로 파생되므로 수기 등록이 아니지만, 생성기를 돌리지 않으면 신설 하위가 그 표에 오르지 않는다. 라벨은 `index_label`에 한/영 병기)**, feature·entity·concept은 **허브 개념이 없는 타입**이라 아래 「재분할 일반 규칙」 ③을 따른다 — 분할한 페이지들이 서로 상호 링크하고, **그 기능·기술·패턴을 가리키는 상위 참조**(허브 `## 기능 목록`·`index.md` 기능별 인덱스·관련 지식 링크) **중 실제로 이 페이지를 등록한 곳 전부**에 신설 페이지를 추가한다(상위 참조가 진입 파일 역할을 한다).

   - **index 분할**: `index.md` 상단에 sub-index 파일 목록 명시(§7-15가 미등록 WARN — 절차 K·Query의 도달 보장).
