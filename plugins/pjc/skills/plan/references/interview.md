# 인터뷰

> `plan/SKILL.md`의 「Step 2. 요구 인터뷰 (1문1답)」이 발동 조건을, 이 파일이 절차를 담는다.
> **사용자에게 보여주고 답을 받는 서식이 여기 모인다** — 인터뷰(2-1~2-6)와 Step 6의 「승인 제시」, 그리고 그 둘을 `ask` 로 옮기는 「중계 모드」다.

## 인터뷰 절차

### 2-1. 가설과 인터뷰 확신도부터 밝힌다

- **질문을 낼 때마다 다시 적는다** — 2-5의 정지 판정이 라운드별 인터뷰 확신도의 변화를 입력으로 쓰므로, 처음 한 번만 적으면 그 판정이 설 자리가 없다.

```
현재 이해: <한 문장>
인터뷰 확신도: <0-100>%
부족한 부분: <70% 미만일 때만 — 무엇을 모르는지>
```

**인터뷰 확신도가 무엇인가** — **지금 이 이해로 plan 을 써서 사용자가 고치지 않고 승인할 확률**이다. 가늠하는 것은 **남은 갈림길 수**이고, 갈림길은 *답이 갈리면 만들 것이 달라지는 질문*이다 (취향을 묻는 질문은 갈림길이 아니다 — 어느 답이든 만들 것이 같다).

| 남은 갈림길 | 인터뷰 확신도 | 그 상태 |
|---|---|---|
| 0 | 95% 이상 | 다음 세 질문의 답을 예측할 수 있다 — 2-5 의 정지 조건 |
| 1 | 80대 | 하나만 물으면 된다 |
| 2~3 | 60~70대 | **70% 미만이면 「부족한 부분」을 함께 적는다** |
| 무엇을 물어야 할지 모른다 | 50 이하 | 요청이 아직 형태를 갖추지 않았다 — 2-5 의 후퇴 제안 대상 |

- **숫자를 세밀하게 조정하지 않는다** — 이 값은 절대 크기가 아니라 **라운드 간 변화**로 쓰인다(2-5). 72 와 75 를 가르는 근거는 없고, 그 근거를 만들려 하면 재지 못하는 것을 재는 척도가 된다.

### 2-2. 한 번에 한 질문, 추측을 붙여서

```
Q: <초점이 하나인 질문>
GUESS: <내 가설과 그렇게 생각하는 근거>
```

- **`GUESS:`를 반드시 붙인다** — 사용자가 "그건 아니고"라고만 답해도 진전이 생기고, 맞으면 "응"으로 끝난다. 추측 없는 질문은 사용자에게 설계를 통째로 떠넘긴다.
- **답을 받은 뒤에 다음 질문을 만든다** — 앞 답이 뒤 질문을 바꾸므로 미리 목록을 짜 두면 죽은 질문을 묻게 된다.
- **`GUESS:`를 맞을 것 같은 쪽으로만 내지 않는다 — 인터뷰마다 최소 한 번은 사용자가 반박할 것 같은 쪽으로 낸다** — 맞을 것 같은 추측만 내면 사용자는 동의만 하게 되고, 그 동의는 확인이 아니라 통과다.

**선택지를 목록으로 낼 때** — 아래 셋은 같은 결함의 세 얼굴이다: **어느 것을 추천했는지 목록만 보고는 모른다.**

- **`GUESS:`가 지목하는 것을 선택지 이름과 글자 그대로 같게 쓴다** — 같은 안을 목록에서는 「현행 유지」로 근거 서술에서는 「그대로 두는 안」으로 부르면 사용자가 둘을 대조해야 하고, 그 대조가 어긋나면 **고른 것과 고르려던 것이 갈린다**. 이름을 다듬고 싶으면 목록 쪽 이름을 고치고 서술을 거기 맞춘다.
- **추천 표기는 선택지 이름에 붙인다** — 목록 밖 산문에만 적으면 목록을 읽는 순간에는 그 정보가 없다. 표기는 이름 뒤 `(권장)` 하나로 통일하고 **왜 그것인지는 그 선택지의 설명에 둔다** — 설명 첫머리에 넣은 `GUESS:`는 이름 옆에서 보이지 않는다.
- **추천하는 선택지를 맨 앞에 둔다** — 순서가 곧 우선순위로 읽히므로, 표기는 뒤에 두고 배치는 앞에 두면 서로 다른 신호를 준다.

### 2-3. 근거로 결정되는 것은 묻지 않는다

- **코드·`AGENTS.md`·위키·기존 컨벤션으로 답이 정해지는 항목은 자체 확정한다** — 명명 규칙, 기존 패턴 준수, 디렉터리 위치 같은 것을 물으면 사용자는 "알아서 해"라고 답하게 되고 질문 예산만 소모된다. 확정한 것은 plan의 Decisions에 `Source: <확인한 파일:라인>`과 함께 적는다.
- **단 `AGENTS.md`에 아키텍처 선언이 없으면 그것은 자체 확정 대상이 아니다** — 코드 구조를 보면 「지금 어떻게 돼 있는가」는 알 수 있지만 **그것이 의도였는지 누락이었는지는 코드에 없다.** 말없이 기본값을 적용하면 그 구분이 영영 생기지 않는다(`../SKILL.md`).
- **묻는 것은 근거만으로 결정할 수 없는 갈림길뿐이다** — 제품 방향, UX 선택, 비가역 데이터 형식, 범위의 크기.

### 2-4. "해야 할 것"과 "실제 원하는 것"을 가른다

사용자가 표준 용어("확장성", "깔끔한 구조", "베스트 프랙티스")로 답하면 한 번 더 묻는다:

> "정당화할 필요가 없다면, 실제로는 무엇을 원하시나요?"

- **이 질문이 필요한 이유** — 표준 용어는 무엇을 만들지 결정해 주지 않는데도 답변으로는 완결돼 보여, 그대로 받으면 계획이 추상적으로 흐른다.

### 2-5. 언제 멈추는가

**"다음에 물을 세 질문의 답을 내가 예측할 수 있는가?"** 예이면 인터뷰를 끝낸다.

- **인터뷰 확신도가 세 라운드 연속 오르지 않으면 인터뷰를 멈추고 그 사실을 말한다** — 그때는 질문이 모자란 것이 아니라 요청이 아직 형태를 갖추지 않은 것이라, 더 물으면 사용자가 답을 즉흥으로 만들어 낸다. 낼 것은 다음 질문이 아니라 무엇이 빠진 것 같다는 판단과 한 발 물러서자는 제안이다.

### 2-6. 의도 재진술과 확인

인터뷰가 끝나면 아래를 채워 보여주고 명시적 동의를 받는다.

```
- 결과:        <무엇이 만들어지는가>
- 사용자:      <누가 쓰는가>
- 지금 하는 이유: <왜 지금인가>
- 성공의 모습:  <끝났을 때 무엇이 참인가>
- 제약조건:    <지켜야 하는 것>
- 범위 밖:     <이번에 하지 않는 것>
```

- **"좋아 보여"·"뭐든 괜찮아"는 동의가 아니다** — 그런 답에는 재진술 중 확신이 낮은 항목 하나를 다시 묻는다.

## 승인 제시

`plan.md`를 쓴 뒤 **화면에** 아래를 낸다. **파일만 쓰고 「승인해 주세요」로 끝내지 않는다** — 사용자가 파일을 열어야 판단이 서면 승인 요청이 아니라 검토를 떠넘긴 것이다.

```
계획 요약 — <회차 제목>

T1: <한 줄>
T2: <한 줄>
…

승인 필요 항목: <있으면 나열, 없으면 「없음」>

[Y] 승인 / [E] 수정 요청 / [N] 중단
```

- **task당 한 줄이고 동사로 끝낸다** — 「승인 서식」이 아니라 「승인 서식을 신설한다」.
- **근거·실측·함정은 옮겨 적지 않는다** — 여기는 **무엇을 몇 개 하는가**만 보이는 자리다. 단 `## 승인 필요 항목`은 줄이지 않고 그대로 싣는다.

## 계획 불필요 판정과 면제 표식

인터뷰 도중 요청이 `SKILL.md`의 「이 스킬을 건너뛰는 경우」 목록에 해당하는 것으로 좁혀지면 계획을 쓰지 않는다. 그때 `guard-write`의 plan 존재 게이트를 여는 것이 면제 표식이다.

**순서를 지킨다 — 표식은 사용자 승인 뒤에만 낸다.**

1. 무엇을 고칠 것인지 **파일 경로까지** 확정한다
2. `A) 바로 수정 / B) 계획부터`를 제시한다
3. 사용자가 A를 고르면 표식 한 줄을 출력한다 — 대상이 여럿이면 가운뎃점으로 잇는다

   ```
   [PLAN-EXEMPT] <경로> · <경로>
   ```

   경로는 플레이스홀더가 아니라 **실제 경로**를 적는다.
4. 같은 turn 에서 곧바로 편집한다 — 표식은 그 turn 의 도구 호출 시점에 이미 transcript 에 실려 있다

- **승인 없이 표식을 내지 않는다** — 그렇게 정한 근거는 `docs/harness-conventions.md` 의 「`guard-write`의 PLAN-EXEMPT 면제 경로」 판정 3축이 정본이다(**그 문서는 하니스 레포에만 있어 다른 레포 세션에서는 열리지 않는다** — 규칙만으로 판정하고 근거를 찾아 나서지 않는다).
- **적은 파일만 열린다** — 훅은 표식 줄에서 파일명과 직속 부모 디렉터리 이름을 함께 본다. 작업 중 다른 파일이 필요해지면 다시 묻고 새 표식을 낸다.
- **표식을 내지 못하면 계획을 쓴다** — 사용자가 B 를 고르거나 대상이 여러 곳으로 번지면 Step 1 로 간다.

## 중계 모드

`pjc:chain-plan` 코디네이터가 Karina 워커 탭에 띄운 세션에서 이 스킬이 돌 때의 예외다. 인터뷰는 코디네이터가 사용자와 이미 끝냈고, 이 세션 화면은 아무도 보지 않는다.

- **판정: Skill args 첫 줄 또는 이 세션 첫 프롬프트의 `할 일:` 다음 줄이 `[chain-plan 중계]` 이면 중계 모드다** — 배정 머리의 첫 줄은 항상 `[오케스트레이션 배정]` 이고 spec 은 `할 일:` 아래에 온다. 두 자리를 다 보는 것은 args 로 넘기는 것을 빠뜨려도 머리로 잡히게 하기 위해서다.
- **표식 아래의 재진술 6항목(2-6 서식)을 인터뷰 결과로 쓰고 Step 1 → Step 3 으로 간다(Step 2 생략)** — 같은 질문이 사용자에게 두 번 가지 않게 한다. 아래 `<CLI>` 는 spec 의 `CLI:` 줄 값, `<핸들>` 은 배정 머리의 핸들이다.
- **표식은 있는데 재진술 6항목이 비었으면 채우지 않고 `failed` 로 보고한다** — 인터뷰 없이 채우면 Step 2 「사용자가 응답할 수 없는 실행」이 막는 추측 확정이 된다.
- **spec 에 `인계:` 줄이 있으면 Step 1 에서 그 파일을 Read 한다(없으면 첫 계획이라 넘어간다)** — 앞 계획의 결과가 뒤 계획으로 가는 길이 이 파일뿐이다.
- **spec 에 `실측 요지:` 가 있으면 Step 3·4 의 출발점으로 쓰되 다시 잰다 — 거기 적힌 다른 회차의 task 는 이 plan 에 넣지 않는다** — 원 세션이 잰 뒤 앞 회차가 코드를 바꿨고, 다른 회차 task 를 흡수하면 코디네이터의 승인 대조 ①이 되돌린다. 재진술 `범위 밖` 의 `(보류 — Deferred)` 항목은 `## Deferred / Follow-up` 에 적는다(서식 `deferred-rules.md`).
- **같은 경우 plan 의 마지막 task 로 「인계 파일에 `## plan <N>` 절을 추가하고 커밋한다」를 넣는다** — 절에 담을 것은 바꾼 파일·새 심볼·API · 내린 결정과 근거 · 뒤 계획이 지킬 제약 · 미해결 사항이다. task 로 두면 다른 task 처럼 검증·커밋되고 압축 뒤에도 `plan.md` 에 남는다.
- **갈림길은 외부 계약(공개 API·스키마·UX 동작)이 갈리는 것만 묻는다 — 그 밖의 판단은 스스로 정해 `plan.md` 의 `## Decisions` 에 근거와 함께 적는다** — 인터뷰는 코디네이터가 끝냈고, 사소한 질문마다 멈추면 체인이 자동으로 가지 않는다.
- **재진술의 제약조건·범위 밖과 어긋나는 해석은 승인 단계에 올리지 않는다 — `../SKILL.md` Step 4 의 회피 설계로 풀고, 회피 설계가 없을 때만 plan 을 쓰는 도중에 `ask` 로 확정한다** — 승인 제시에서야 드러나면 코디네이터가 그 항목을 판정하느라 체인이 거기서 선다(2026-10-02 Karina plan 2/2 — 워커가 스스로 고른 설계가 승인 항목 둘을 만들었고 약 3시간 멈췄다).
  - **재진술 `결과` 를 넘는 요청 밖 작업(기준 `../SKILL.md`「Step 5. plan.md 작성」)이 필요해 보이면 그 작업 없이 목표가 되는 설계부터 찾고, 없을 때만 `Q:` 머리에 `[요청 밖]` 을 달아 `ask` 한다** — 코디네이터는 그것을 판정하지 않고 사용자에게 넘긴다. 답이 보류면 `## Deferred / Follow-up` 에 적는다.
- **사용자 응답을 기다리며 turn 을 끝내는 모든 자리는 `ask` 로 묻는다** — 위 외부 계약 갈림길 질문 · 「계획 불필요 판정」의 A/B · Step 1 의 `AGENTS.md` 저장 승인 · 검증 명령 부재 · `[면제 ③]` 이 여기다. 워커 화면의 질문에는 아무도 답하지 않는다. **`AskUserQuestion` 도 화면 질문도 쓰지 않는다** — 화면에서 답을 받으면 코디네이터에 보낸 질문이 열린 채 남고 그 답이 체인 기록에서 빠진다. 본문은 2-2 의 `Q:`/`GUESS:` 그대로이고, Bash 도구 `timeout` 600000 으로 부른다:

  ```
  <CLI> orchestration ask --from <핸들> --timeout-ms 540000 --question "$(cat <<'EOF'
  Q: …
  GUESS: …
  EOF
  )" 2>/dev/null
  ```

- **본문은 위처럼 작은따옴표 heredoc 치환으로 넘긴다** — `ask`·`reply` 는 파일·stdin 입력이 없고, 본문의 백틱·`$`·따옴표가 셸에서 변조된다.
- **만료 응답(`answered:false`·`status:"pending"`)이면 `ask --resume <questionId>` 로 같은 질문을 이어 간다 — 다시 묻지 않는다** — 새로 `ask` 하면 같은 질문이 코디네이터에 둘 쌓인다. 시한 9분은 Bash 도구 상한 10분보다 짧게 잡은 것이다 — 도구가 먼저 끊으면 `questionId` 가 출력되지 않는다.
- **이어 가기 전에 `<CLI> orchestration check --json 2>/dev/null` 로 코디네이터의 대기 신호(`status` 유형, 제목 `사용자 확인 대기 중`)를 본다 — 신호가 있으면 사용자 판단을 기다리는 중이라 상한 없이 이어 가고, 신호 없는 만료가 3회 연속이면 `worker_done --outcome failed`(사유: 코디네이터 무응답)로 멈춘다** — `ask` 는 막는 호출이라 무응답과 사용자 대기를 그 사이의 신호로만 가를 수 있다. 3회는 같은 수단을 세 번 반복해도 닿지 않을 때 멈추는 수다.
- **새 `ask` 직전과 답을 받은 직후에 같은 `check` 로 남은 신호를 ack 해 비운다** — `check` 는 ack 전까지 같은 배치를 다시 주므로, 앞 질문의 신호가 남으면 다음 질문의 무응답을 사용자 대기로 읽어 상한이 사라진다. 배치에 다른 유형이 섞였으면 그것을 처리한 뒤 ack 한다.
- **Step 6 승인 제시는 화면 대신 같은 `ask` 본문으로 보내고 `Y` / `E: <수정 요청>` / `N` 을 받는다 — 서식은 위 「승인 제시」에 `DB 변경: <목록 | 없음>` 줄과 `실측 요지 대비: <spec 실측 요지의 초안 중 빠진 것 — 근거 | 없음 | 실측 요지 없음>` 줄을 더한 것이다** — 코디네이터는 그 본문의 task 줄·`승인 필요 항목`·`DB 변경`·`실측 요지 대비:` 줄을 체인 승인과 대조해 답한다. 초안은 다시 재서 빠질 수 있으나 근거가 없으면 누락과 갈리지 않는다. `E` 면 고쳐 다시 보내고, `N` 이면 `failed` 로 끝낸다.
- **답이 사용자의 답을 옮긴 것이든 체인 승인 위임 답(`Y (체인 승인 위임 — …)`)이든 코디네이터 판정 답(`… (코디네이터 판정 — <근거>)`)이든 사용자 응답·승인으로 본다 — 외부 계약 갈림길·Step 1 의 `AGENTS.md` 저장 승인·`[면제 ③]` 의 답도 같다** — 위임 답은 사용자가 체인 시작 때 이 계획을 포함해 승인한 것을, 판정 답은 사용자가 체인에 맡긴 목표·제약 안에서 코디네이터가 정한 것을 전한다.
- **중계 모드는 회차를 나누지 않는 것이 기본이다 — 그래도 나누면 남은 회차를 `worker_done` 의 `남은 일` 에 `[다음 회차]` 로 싣는다** — 계획 하나가 체인의 한 단위이고, 남긴 회차를 받을 세션이 없다. 워커 화면의 인계 프롬프트는 아무도 보지 않아, 거기만 두면 남은 회차가 사라진다. 코디네이터는 그 표식을 보고 다음 계획을 띄우지 않는다.
- **`pjc:implement` 「멈추는 넷」 ①(실행 시점 승인 항목)은 `failed` 대신 `ask` 로 승인을 요청한다 — 본문은 무엇을·왜·영향 범위·되돌리는 방법이다** — 코디네이터가 그것을 사용자에게 잇는다(`../../chain-plan/SKILL.md`「답하는 기준」). `Y` 면 실행한다. `N` 이면 실행하지 않고 그 항목에 의존하지 않는 task 를 끝낸 뒤, 의존 task 가 남으면 `--outcome failed`(사유: 거절된 항목·남은 task), 남지 않으면(push 등) `succeeded` 의 `승인 필요 항목` 에 싣는다 — 미완인 계획 위에 다음 계획이 뜨지 않게 한다.
- **멈추는 자리는 묻지 않고 `failed` 로 보고한다** — 같은 지적 3회 · 쓰기 실패 · `pjc:implement` 「멈추는 넷」 ②~④ · 요구 미확정 · **코디네이터 무응답**(신호 없는 만료 3회) · 구현 중에 새로 드러난 plan 에 없던 기능 변경 · **spec `DB 변경` 줄의 목록 밖 변경이 필요할 때**(실행하지 않고 사유에 필요한 변경을 적는다). 실행 정지(②~④ — 실패 카운터이고, ③ 의 인증정보는 `ask` 본문으로 건넬 수 없다)와 요구 미확정은 판정의 근거(목표·제약)가 없고, 구현 중의 기능 변경·목록 밖 DB 변경은 목표가 바뀌거나 사용자 몫이라 코디네이터가 대신 정할 수 없다. 계획 승인 전에 드러난 것은 정지가 아니라 승인 제시 `ask` 로 코디네이터에게 간다. 체인은 거기서 멈추고 재개는 사용자가 다시 부른다.
- **intent 의 `Problem` 은 spec 의 「원문:」 블록을 인용하고 `Author:` 에 「코디네이터 인터뷰 경유」를 적는다** — 이 세션이 받은 원문은 사용자 발화가 아니라 spec 이다.
- **`plan-reviewer` 전달물에 「중계 모드 — 인터뷰는 코디네이터 세션에서 사용자와 수행됨 · 원문은 spec 의 「원문:」 블록」 1줄을 싣는다** — 리뷰어는 확정 요구가 원문의 재진술뿐이면 지적한다.
- **`plan.md` 의 `## Next Steps` 에 실제 값(CLI 이름·task id·dispatch id·핸들·DB 목록)을 채운 아래 블록을 적고 「구현 중에 이 블록은 지우지 않는다」를 붙인다** — 압축 뒤 워커가 다시 읽는 것은 `implement/SKILL.md` 와 `plan.md` 뿐이라 배정 머리와 spec 에만 있는 것은 압축을 넘지 못한다:

  ```
  - 최종 보고 텍스트를 내기 전, 같은 turn 에서: <CLI> orchestration send --type worker_done --task-id <id> --dispatch-id <id> --outcome succeeded --subject "<한 줄>" --from <핸들> --body "$(cat <<'BODY'
    (한 필드 한 줄) 결과: … · 사용자용 요약: <무엇이 바뀌었나 2~3줄> · 확인 방법: … · 남은 일: … · 승인 필요 항목: … · HUMAN-VERIFY·미검증: …

    )"
  - 사용자에게 묻는 자리: <CLI> orchestration ask --from <핸들> --timeout-ms 540000 --question … (화면 질문 금지 · 만료마다 check 로 대기 신호(`사용자 확인 대기 중`) 확인 — 신호 없는 만료 3회면 아래 failed, 사유 코디네이터 무응답 · ask 직전·답 직후 check 로 신호 비움)
  - 실행 시점 승인(「멈추는 넷」 ①): 위 ask 로 무엇을·왜·영향 범위·되돌리는 방법을 보내고 계속 — N 이면 의존 task 가 남을 때만 failed

  - 회차를 나눴으면 남은 회차를 worker_done 남은 일에 [다음 회차] 로
  - DB 변경 승인 목록: <spec 의 DB 변경 줄 값> — 목록 밖은 실행하지 않고 failed
  ```
