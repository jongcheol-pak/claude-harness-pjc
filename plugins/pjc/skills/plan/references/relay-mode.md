# 중계 모드

> `../SKILL.md` 머리의 중계 판정이 맞을 때만 **Step 1 전에** 읽는다 — `pjc:chain-plan` 워커에서만 걸리는 예외라 일반 세션이 읽는 `interview.md` 에 두지 않는다. 여기서 가리키는 `interview.md` 의 절(「인터뷰 절차」 2-2·2-6 · 「승인 제시」 · 「계획 불필요 판정과 면제 표식」)은 `../SKILL.md` 도 직접 가리킨다.

## 중계 모드

`pjc:chain-plan` 코디네이터가 Karina 워커 탭에 띄운 세션에서 이 스킬이 돌 때의 예외다. 인터뷰는 코디네이터가 사용자와 이미 끝냈고, 이 세션 화면은 아무도 보지 않는다.

- **판정: Skill args 첫 줄 또는 이 세션 첫 프롬프트의 `할 일:` 다음 줄이 `[chain-plan 중계]` 이면 중계 모드다** — 배정 머리의 첫 줄은 항상 `[오케스트레이션 배정]` 이고 spec 은 `할 일:` 아래에 온다. 두 자리를 다 보는 것은 args 로 넘기는 것을 빠뜨려도 머리로 잡히게 하기 위해서다.
- **표식 아래의 재진술 6항목(`interview.md` 2-6 서식)을 인터뷰 결과로 쓰고 Step 1 → Step 3 으로 간다(Step 2 생략)** — 같은 질문이 사용자에게 두 번 가지 않게 한다. 아래 `<CLI>` 는 spec 의 `CLI:` 줄 값, `<핸들>` 은 배정 머리의 핸들이다.
- **`AGENTS.md` 에 아키텍처 선언이 없으면 재진술 제약조건에 실린 선언을 쓰고, 거기도 없으면 아래 `ask` 로 묻는다** — `../SKILL.md` Step 1 은 그것을 Step 2 의 질문으로 확정하는데 중계 모드는 Step 2 를 건너뛰고, 코디네이터가 인터뷰에서 확정해 제약조건에 싣는다(`../../chain-plan/SKILL.md`「인터뷰」). `../../AGENTS-BOUNDARY.md`「AGENTS.md 최소 생성」이 말하는 「Step 2의 답」 자리도 이것이 대신한다.
- **표식은 있는데 재진술 6항목이 비었으면 채우지 않고 `failed` 로 보고한다** — 인터뷰 없이 채우면 Step 2 「사용자가 응답할 수 없는 실행」이 막는 추측 확정이 된다.
- **spec 에 `인계:` 줄이 있으면 Step 1 에서 그 파일을 Read 한다(없으면 첫 계획이라 넘어간다)** — 앞 계획의 결과가 뒤 계획으로 가는 길이 이 파일뿐이다.
- **spec 에 `실측 요지:` 가 있으면 Step 3·4 의 출발점으로 쓰고, 거기 적힌 다른 회차의 task 는 이 plan 에 넣지 않는다** — 다른 회차 task 를 흡수하면 코디네이터의 봉투의 task 줄 대조가 되돌린다. 재진술 `범위 밖` 의 `(보류 — Deferred)` 항목은 `## Deferred / Follow-up` 에 적는다(서식 `deferred-rules.md`).
  - **실측 요지 항목을 다시 재는 범위는 셋으로 가른다 — 겹치는 항목만 다시 재는 것이 기본이다** — 잰 뒤 앞 계획이 바꾸지 않은 자리는 다시 재도 같은 값이 나온다. **근거가 붙지 않은 항목은 그 항목만 잰다.**
    - ⓐ spec 에 `실측 기준:` 이 없거나, 이어받기 워커이거나, `git diff --name-only <실측 기준>` 이 실패하면 전부 다시 잰다 — 무엇이 바뀌었는지 가를 기준이 없다.
    - ⓑ 그 diff 가 실측 요지의 바뀌는 파일과 겹치면, 겹친 파일을 근거로 둔 항목만 다시 잰다 — 앞 계획이 이 레포에서 바꾼 파일은 이 diff 에 들어 있다.
    - ⓒ `근거로 정한 것:` 의 ① 의존이 「없음」이 아니면, 그 의존이 가리키는 자리(인계 파일의 바꾼 파일·API 로 보강)를 근거로 둔 항목만 다시 잰다 — 레포 밖(다른 레포·데이터·외부 API) 의존은 ⓑ 의 diff 에 보이지 않는다.
  - **다시 재지 않은 항목은 Investigation Log 행으로 옮기고(명령 열에 그 항목의 근거, 출처 `실측 요지(기준 <sha>)`) 델타 명령과 그 출력을 한 행 더 적은 뒤, Step 3 의 호출자·테스트 Files 보강과 삭제 복구 경로, Step 4 의 acceptance 착수값만 잰다** — 실측 요지는 서브에이전트가 낸 task 초안·파일이라 그 셋을 보장하지 않는다.
- **같은 경우 plan 의 마지막 task 로 「인계 파일에 `## plan <N>` 절을 추가하고 커밋한다」를 넣는다** — 절에 담을 것은 바꾼 파일·새 심볼·API · 내린 결정과 근거 · 뒤 계획이 지킬 제약 · 미해결 사항이다. task 로 두면 다른 task 처럼 검증·커밋되고 압축 뒤에도 `plan.md` 에 남는다.
- **갈림길은 외부 계약(공개 API·스키마·UX 동작)이 갈리는 것만 묻는다 — 그 밖의 판단은 스스로 정해 `plan.md` 의 `## Decisions` 에 근거와 함께 적는다** — 인터뷰는 코디네이터가 끝냈고, 사소한 질문마다 멈추면 체인이 자동으로 가지 않는다.
  - **외부 계약 질문은 `Q:` 머리에 `[외부 계약:추가]`(기존 계약을 바꾸지 않는 새 접점) 또는 `[외부 계약:변경]`(기존 이름·인자·출력·기본값을 바꾸거나 지움)을 달고, 선택지 하나에 `(권장)` 을 붙인다** — 코디네이터가 추가형 프로그램 접점을 체인 승인 위임으로 답한다(`../../chain-plan/references/delegation.md`「외부 계약 위임」).
- **재진술의 제약조건·범위 밖과 어긋나는 해석은 승인 단계에 올리지 않는다 — `../SKILL.md` Step 4 의 회피 설계로 풀고, 회피 설계가 없을 때만 plan 을 쓰는 도중에 `ask` 로 확정한다** — 승인 제시에서야 드러나면 코디네이터가 그 항목을 판정하느라 체인이 거기서 선다(2026-10-02 Karina plan 2/2 — 워커가 스스로 고른 설계가 승인 항목 둘을 만들었고 약 3시간 멈췄다).
  - **재진술 `결과` 를 넘는 요청 밖 작업(기준 `../SKILL.md`「Step 5. plan.md 작성」)이 필요해 보이면 그 작업 없이 목표가 되는 설계부터 찾고, 없을 때만 `Q:` 머리에 `[요청 밖]` 을 달아 `ask` 한다** — 코디네이터는 그것을 판정하지 않고 사용자에게 넘긴다. 답이 보류면 `## Deferred / Follow-up` 에 적는다.
- **사용자 응답을 기다리며 turn 을 끝내는 모든 자리는 `ask` 로 묻는다** — 위 외부 계약 갈림길 질문 · `interview.md`「계획 불필요 판정과 면제 표식」의 A/B · Step 1 의 `AGENTS.md` 저장 승인 · 아키텍처 선언 부재 · 검증 명령 부재 · `[면제 ③]` 이 여기다. 워커 화면의 질문에는 아무도 답하지 않는다. **`AskUserQuestion` 도 화면 질문도 쓰지 않는다** — 화면에서 답을 받으면 코디네이터에 보낸 질문이 열린 채 남고 그 답이 체인 기록에서 빠진다. 본문은 `interview.md` 2-2 의 `Q:`/`GUESS:` 그대로다. **명령·시한·Bash 도구 timeout·만료 시 `--resume`·보고 `--body` 필드는 배정문 `진행:` 2·3 이 정본이다(`../../chain-plan/SKILL.md`「spec 서식」)** — 송신(배정문)과 수신(체인 보고)이 둘 다 chain-plan 이라, 여기는 그 위에 얹는 워커 쪽 규칙만 둔다:

  ```
  <CLI> orchestration ask --from <핸들> <진행 2 의 시한 플래그> --question "$(cat <<'EOF'
  Q: …
  GUESS: …
  EOF
  )" <진행 2 의 리다이렉트>
  ```

- **본문은 위처럼 작은따옴표 heredoc 치환으로 넘긴다** — `ask`·`reply` 는 파일·stdin 입력이 없고, 본문의 백틱·`$`·따옴표가 셸에서 변조된다.
- **만료 응답(`answered:false`·`status:"pending"`)이면 `ask --resume <questionId>` 로 같은 질문을 이어 간다 — 다시 묻지 않는다** — 새로 `ask` 하면 같은 질문이 코디네이터에 둘 쌓인다. 시한을 Bash 도구 상한보다 짧게 잡는 것은 도구가 먼저 끊으면 `questionId` 가 출력되지 않기 때문이다.
- **이어 가기 전에 `<CLI> orchestration check --json 2>/dev/null` 로 코디네이터의 대기 신호(`status` 유형, 제목 `사용자 확인 대기 중`)를 본다 — 신호가 있으면 사용자 판단을 기다리는 중이라 상한 없이 이어 가고, 신호 없는 만료가 3회 연속이면 `worker_done --outcome failed`(사유: 코디네이터 무응답)로 멈춘다** — `ask` 는 막는 호출이라 무응답과 사용자 대기를 그 사이의 신호로만 가를 수 있다. 3회는 같은 수단을 세 번 반복해도 닿지 않을 때 멈추는 수다.
- **새 `ask` 직전과 답을 받은 직후에 같은 `check` 로 남은 신호를 ack 해 비운다** — `check` 는 ack 전까지 같은 배치를 다시 주므로, 앞 질문의 신호가 남으면 다음 질문의 무응답을 사용자 대기로 읽어 상한이 사라진다. 배치에 다른 유형이 섞였으면 그것을 처리한 뒤 ack 한다.
- **Step 6 승인 제시는 화면 대신 같은 `ask` 본문으로 보내고 `Y` / `E: <수정 요청>` / `N` 을 받는다 — 서식은 `interview.md`「승인 제시」에 `DB 변경: <목록 | 없음>` 줄과 `실측 요지 대비: <spec 실측 요지의 초안 중 빠진 것 — 근거 | 없음 | 실측 요지 없음>` 줄을 더한 것이다** — 코디네이터는 그 본문의 task 줄·`승인 필요 항목`·`DB 변경`·`실측 요지 대비:` 줄을 체인 승인과 대조해 답한다. 초안은 다시 재서 빠질 수 있으나 근거가 없으면 누락과 갈리지 않는다. `E` 면 고쳐 다시 보내고, `N` 이면 `failed` 로 끝낸다.
- **답이 사용자의 답을 옮긴 것이든 체인 승인 위임 답(`Y (체인 승인 위임 — …)`)이든 코디네이터 판정 답(`… (코디네이터 판정 — <근거>)`)이든 사용자 응답·승인으로 본다 — 외부 계약 갈림길·Step 1 의 `AGENTS.md` 저장 승인·`[면제 ③]` 의 답도 같다** — 위임 답은 사용자가 체인 시작 때 이 계획을 포함해 승인한 것을, 판정 답은 사용자가 체인에 맡긴 목표·제약 안에서 코디네이터가 정한 것을 전한다.
- **중계 모드는 회차를 나누지 않는 것이 기본이다 — 그래도 나누면 남은 회차를 `worker_done` 의 `남은 일` 에 `[다음 회차]` 로 싣는다** — 워커 화면의 인계 프롬프트는 아무도 보지 않아, 거기만 두면 남은 회차가 사라진다. 코디네이터는 그 표식을 보고 같은 계획의 이어받기 워커를 띄운다(`../../chain-plan/references/continuation.md`「이어받기」).
  - **이 계획의 남은 회차만 적는다 — spec `다른 회차:` 의 계획은 `[다음 회차]` 로 적지 않는다** — 그 계획은 체인이 따로 돌린다.
  - **spec 머리(또는 args)에 `이어받기: <k>` 가 있으면 이어받기 워커다 — 작업 task 는 `실측 요지:` 항목뿐이고(인계 절 task 는 그대로), 인계 절 이름은 `## plan <N> 이어받기 <k>` 다** — 원 계획의 나머지는 앞 워커가 이미 커밋했다.
- **`pjc:implement` 「멈추는 넷」의 「파괴적·외부 비가역 작업」(실행 시점 승인 항목)은 `failed` 대신 `ask` 로 승인을 요청한다 — 본문은 무엇을·왜·영향 범위·되돌리는 방법이다** — 코디네이터가 그것을 사용자에게 잇는다(`../../chain-plan/SKILL.md`「답하는 기준」). `Y` 면 실행한다. `N` 이면 실행하지 않고 그 항목에 의존하지 않는 task 를 끝낸 뒤, 의존 task 가 남으면 `--outcome failed`(사유: 거절된 항목·남은 task), 남지 않으면(push 등) `succeeded` 의 `승인 필요 항목` 에 싣는다 — 미완인 계획 위에 다음 계획이 뜨지 않게 한다.
- **멈추는 자리는 묻지 않고 `failed` 로 보고한다** — `pjc:implement` 최종 리뷰의 같은 지적 3회 · 쓰기 실패 · `pjc:implement` 「멈추는 넷」의 「동일 원인 3회 실패」·「인증정보가 필요한 신규 외부 서비스」·「같은 수단을 3회 반복」 · 요구 미확정 · **코디네이터 무응답**(신호 없는 만료 3회) · 구현 중에 새로 드러난 `pjc:implement` 「plan 승인이 덮지 않는 변경」 · **spec `DB 변경` 줄의 목록 밖 변경이 필요할 때**(실행하지 않고 사유에 필요한 변경을 적는다). 실행 정지(동일 원인·같은 수단은 실패 카운터이고, 인증정보는 `ask` 본문으로 건넬 수 없다)와 요구 미확정은 판정의 근거(목표·제약)가 없고, 구현 중의 승인 범위 밖 변경·목록 밖 DB 변경은 목표가 바뀌거나 사용자 몫이라 코디네이터가 대신 정할 수 없다. 계획 승인 전에 드러난 것(계획 리뷰의 남은 지적 포함 — `../SKILL.md` Step 6)은 정지가 아니라 승인 제시 `ask` 로 코디네이터에게 간다. 체인은 거기서 멈추고 재개는 사용자가 다시 부른다.
- **intent 의 `Problem` 은 spec 의 「원문:」 블록을 인용하고 `Author:` 에 「코디네이터 인터뷰 경유」를 적는다** — 이 세션이 받은 원문은 사용자 발화가 아니라 spec 이다. **이어받기 워커면 intent 를 새 파일(슬러그 끝 `-이어받기-<k>`)로 쓰고 `Proposed outcome` 에는 이어받을 항목만 담으며 원 계획의 intent 경로를 가리킨다** — 결과 전체를 담으면 두 리뷰어가 앞 워커가 끝낸 항목을 누락으로 세고, 같은 슬러그면 원 intent 를 덮어쓴다.
- **`plan-reviewer` 전달물에 「중계 모드 — 인터뷰는 코디네이터 세션에서 사용자와 수행됨 · 원문은 spec 의 「원문:」 블록」 1줄을 싣는다** — 리뷰어는 확정 요구가 원문의 재진술뿐이면 지적한다. 이어받기 워커면 「이어받기 <k> — 이 회차 몫은 실측 요지 항목뿐, 나머지는 앞 워커 커밋」을, 실측 요지 항목 중 하나라도 다시 재지 않았으면 「재측정 생략 — 근거는 Log 의 델타 행」을 덧붙인다.
- **`plan.md` 의 `## Next Steps` 에 실제 값(CLI 이름·task id·dispatch id·핸들·DB 목록)을 채운 아래 블록을 적고 「구현 중에 이 블록은 지우지 않는다」를 붙인다** — 압축 뒤 워커가 다시 읽는 것은 `implement/SKILL.md` 와 `plan.md` 뿐이라 배정 머리와 spec 에만 있는 것은 압축을 넘지 못한다:

  ```
  - 최종 보고 텍스트를 내기 전, 같은 turn 에서: <CLI> orchestration send --type worker_done --task-id <id> --dispatch-id <id> --outcome succeeded --subject "<한 줄>" --from <핸들> --body "$(cat <<'BODY'
    <배정문 진행 3 의 --body 필드를 한 필드 한 줄로 그대로 옮긴 것>
    BODY
    )"
  - 사용자에게 묻는 자리: <배정문 진행 2 대로 완성한 ask 명령 — 시한·Bash timeout·리다이렉트·만료 시 --resume 를 실제 값으로> (화면 질문 금지 · 만료마다 check 로 대기 신호(`사용자 확인 대기 중`) 확인 — 신호 없는 만료 3회면 아래 failed, 사유 코디네이터 무응답 · ask 직전·답 직후 check 로 신호 비움)
  - 실행 시점 승인(「멈추는 넷」의 파괴적·외부 비가역 작업): 위 ask 로 무엇을·왜·영향 범위·되돌리는 방법을 보내고 계속 — N 이면 의존 task 가 남을 때만 failed
  - 그 밖의 승인이 필요한 정지(동일 원인 3회 실패·인증정보·같은 수단을 3회 반복 등): 첫 항목의 send 에 --outcome failed, --body 에 사유·남은 task
  - 회차를 나눴으면 이 계획의 남은 회차만 worker_done 남은 일에 [다음 회차] 로(다른 체인 계획은 적지 않는다)
  - DB 변경 승인 목록: <spec 의 DB 변경 줄 값> — 목록 밖은 실행하지 않고 failed
  ```
