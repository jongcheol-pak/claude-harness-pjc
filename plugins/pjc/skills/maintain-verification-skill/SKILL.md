# Maintain a verification skill

> 출처는 Cursor pstack 의 maintain-verification-skill 이다 — 고정 위치 `https://github.com/cursor/plugins/blob/d1715e03a8b1a2f03fdbe336d40c4a56b81f3c8f/pstack/skills/maintain-verification-skill/SKILL.md`. Copyright (c) 2026 Lauren Tan · MIT(`https://github.com/cursor/plugins/blob/d1715e03a8b1a2f03fdbe336d40c4a56b81f3c8f/pstack/LICENSE`). 한글로 옮기며 대상 위치를 Claude Code 프로젝트 스킬로, PR 절차를 pjc 의 `implement/references/pr-flow.md` 로 바꿨다.

기능 지도는 앱이 바뀌는 순간 낡는다(*"A feature map rots the moment the app changes."*). 이 스킬은 `/pjc:create-verification-skill` 이 만든 스킬(또는 기능 지도를 가진 다른 프로젝트 검증 스킬)의 유지 루프다. 엄밀함의 단위는 문장이 아니라 **기능**이다 — 모든 기능 파일을 소스로 덮고 모든 기능을 실제로 조작하되, 불릿 하나하나를 터미널로 재지는 않는다.

## 결과

셋 중 하나를 고르고, 어느 것인지 말한다.

- **clean** — 모든 기능이 소스와 실제 조작으로 덮였고 고칠 것이 없다. 브랜치도 PR 도 없다.
- **changed** — 증명된 문서·하네스·지도 수정을 PR 하나로 낸다.
- **blocked** — 덮기를 끝내지 못했거나 증명된 수정을 안전하게 내지 못했다. 무엇이 막았는지 정확히 말한다.

## 편집 범위

**검증 스킬 자기 폴더만 고친다** — 그 SKILL.md · `features/` · 그 스킬이 가진 `helpers/` 스크립트. 실행 중에 제품 코드를 고치지 않는다 — 지도가 적은 동작을 앱이 더는 하지 않으면, 그것은 지도 드리프트(지도를 고친다)이거나 제품 회귀(보고하고, 문서로 덮지 않는다)다.

## 진행

0. **대상을 찾는다** — 본문에 Launch·Drive 절과 기능 지도를 가진 프로젝트 스킬(보통 `.claude/skills/verify-*/`, `AGENTS.md` 의 `Verify (앱 조작)` 줄이 가리키는 것)이다. 후보가 여럿이면 어느 것인지 묻고, 없으면 대상을 지어내지 않고 멈춰 `/pjc:create-verification-skill` 을 안내한다.
1. **색인을 정리한다** — 지도 `features/README.md` 를 읽고 같은 폴더의 파일과 대조해 빠진 항목·남는 항목·중복·죽은 링크를 고친다. 가볍게 — 따로 목록을 생성하지 않는다.
2. **소스 웨이브** — 기능 파일마다 읽기 전용 `Explore` 서브에이전트 하나를 **한 메시지에서 동시에** 띄운다. 각자 「이 사용자 기능이 소스에서 어떻게 동작하는가」를 설명하고, 인용과 함께 드리프트로 보이는 곳을 짚고, 실제 조작용 조작법 하나를 돌려준다. **서브에이전트는 앱을 조작하지 않고 파일을 고치지 않는다.** 반환 형태: 기능 요약 / 소스 진입점 / 드리프트 후보 또는 없음 / 조작법 하나.
3. **대조한다** — 모든 기능 파일에 요약이 돌아왔는지 본다. 겹치는 조작법은 가능한 한 적은 앱 상태로 합친다. 인용된 드리프트는 표본으로 확인하고, 깨끗하다는 주장은 다시 증명하지 않는다. 최근 변경 이력(`git log`)에서 지도에 없는 사용자 표면을 훑되, 빠졌다고 부르려면 구체적인 소스 경로가 있어야 한다.
4. **실제 조작** — 소스가 깨끗해 보여도 **반드시** 한다. 조작은 이 세션 하나가 맡고, 검증 스킬 자신의 Launch 모델을 따른다 — 서버·UI 는 오래 사는 인스턴스 하나를 차례로, 수명이 짧은 CLI 는 조작마다 격리된 새 세션(어느 쪽인지는 그 스킬의 Launch 절이 정한다). 모든 기능을 적어도 한 번 조작하고, 어떤 실패가 나든 불변식 셋을 지킨다.
   - **놀라운 일이 있은 뒤에는 Doctor 를 다시 돌리기 전까지 그 인스턴스를 조작하지 않는다** — 첫 조작 전, 세션이 단위면 새 세션마다, 조작이 실패한 뒤마다 Doctor 를 돈다. Doctor 가 못 보는 실패(프로세스는 정상인데 UI 가 끼인 상태)면 기대하지 말고 알려진 상태로 되돌리거나 다시 띄운다.
   - **지금까지 남긴 증거는 어떤 정리 뒤에도 남는다** — 가정하지 말고 그 이름 댄 위치에서 확인한다.
   - **조작이 띄운 것은 그 조작이 쓸모를 다한 뒤 남지 않는다** — 세션이 끼었든 끝났든 공유든, 실패한 시도의 잔여를 치운다(공유 인스턴스는 인스턴스가 아니라 잔여를 치운다).
   - Doctor 가 스킬 드리프트 때문에 실패하면 그것도 드리프트다 — 편집 범위 안에서 고치고, 그 수정이 무효로 만든 것만 다시 띄워 한 번 더 시도한 뒤에야 `blocked` 로 부른다.
   - 닿지 못한 기능은 구체적인 전제 조건(인증·권한·OS·외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable` 이다. 지도가 그 전제를 빠뜨렸으면 그것이 드리프트다.
   - 분류(5)에서 나온 하네스 수정은 내기 전에 다시 실제로 조작한다. 마지막 정리는 그 재증명까지 포함한 이번 실행의 마지막 조작 뒤에 한다(증거는 그 스킬대로 남는다).
5. **분류한다** — 사용자 관점 설명이 틀렸거나 빠졌으면 **지도 드리프트** → 고친다. 동작은 하는데 하네스가 조작하지 못하면 **하네스 공백** → 고친다(생성 때와 같은 헬퍼 규칙 — 실행 가능 · 호출 방법을 본문에 · `helpers/` 아래). 앱 동작이 실제로 깨졌으면 **제품 공백** → 사용자에게 기록하고 이 PR 에는 넣지 않는다. 「변경 검증」 절이 `../create-verification-skill/SKILL.md` 2단계의 형식(화면 시나리오 입력 · 레포 루트를 인자로 받는 Launch)을 따르지 않으면 **형식 드리프트** → 그 형식으로 고치고, 고친 Launch 는 4 의 실제 조작에서 다른 worktree 경로로 한 번 돌려 증명한다 — 옛 형식이면 `pjc:implement`·`pr-verifier` 가 계획의 시나리오와 BASE 실행을 그 스킬로 돌리지 못한다.
6. **내거나 멈춘다** — changed 면 고친 파일을 모두 다시 읽은 뒤:
   - `../implement/references/pr-flow.md`「적용 판정」 의 앞 두 조건(GitHub 원격 · `gh auth status` exit 0)이 참이면 같은 파일 「브랜치」 표를 따르되 `<슬러그>` 를 `verify-<app>-map` 으로 둔다(브랜치 `pjc/verify-<app>-map` — 같은 이름이 있으면 `-2`·`-3`). `git add -- .claude/skills/verify-<app>` 뒤 경로 한정 로컬 커밋 `git commit -m "문서: 검증 스킬 verify-<app> 지도 보정" -- .claude/skills/verify-<app>` 를 하고(`add` 가 없으면 색인 정리·하네스 공백 수정이 새로 만든 파일이 커밋에서 빠진다 · `git check-ignore -q --no-index .claude/skills/verify-<app>/SKILL.md` 가 0 이면 그 폴더가 무시 경로인데 `add -f` 로 추적된 것이라 `git add -f --` 를 쓴다 — `--no-index` 가 없으면 추적된 파일은 늘 1 이 나온다(2026-10-18 실측)) 「PR 열기」 1~4 로 PR 하나를 연다. 본문 `## 검증` 에 덮은 기능 수와 실제로 조작한 기능을 적는다.
   - 앞 두 조건 중 하나라도 거짓이면 브랜치를 바꾸지 않고 같은 로컬 커밋만 하고 그 사실을 보고한다.
   - clean·blocked 는 PR 이 없다 — 결과와 덮은 범위를 정직하게 보고한다.

실행 메모(덮은 기능 · 닿지 못한 기능의 전제 · 확인된 드리프트 · 결과)는 레포 밖 임시 위치에 짧게 남기고 커밋하지 않는다.
