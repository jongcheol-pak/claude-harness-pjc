# `block-destructive` 판정 근거

> `block-destructive.ps1`이 **무엇을 왜 차단하는가**의 정본이다. 스크립트는 판정 로직만 담고, 정규식은 `destructive.json`이, 그 정규식이 그 모양인 이유는 이 파일이 담는다. 셋을 함께 고친다 — 정규식만 바꾸고 이 파일을 두면 다음 회차가 낡은 근거를 따른다.

> **이 파일의 내용은 v1.225.0 이전 `block-destructive.ps1`의 주석을 옮긴 것이다** — 문면을 요약하지 않고 이동만 했다(이관은 이동이지 요약이 아니다).

## 차단과 경고를 가르는 기준

> **이 절은 코드 주석의 이관본이 아니다** — 위 서두가 말하는 이관의 예외이고 규약 서술로 새로 쓴 것이라, 주석으로 되돌릴 대상이 아니다.

**판정은 「비가역성」이 아니라 「영향 범위 × 오탐 비용」이다.** `destructive.json`의 `why` 한 줄들은 *"히스토리 재작성"*처럼 비가역성을 사유로 적는데, 그것만으로는 실제 배치가 설명되지 않는다 — 두 명령의 복구 가능성은 배치와 **반대**다.

| 명령 | 무엇을 잃는가 | 복구 경로 | 취급 |
|---|---|---|---|
| `git reset --hard` | **커밋 안 된** 워킹트리·인덱스 변경 | **없다** — reflog는 커밋된 것만 담는다 | `guard-bash`의 `warn-external-ops` **경고** (실행은 통과) |
| 히스토리 재작성(`destructive.json` 4·5번) | 커밋된 이력의 SHA | `refs/original/`·reflog에 **남는다** | 이 hook의 **차단**(exit 2, 우회 변수 없음) |

**복구 가능성만 보면 역전인데도 이 배치가 옳은 이유는 셋이다.**

1. **영향 범위** — `reset --hard`는 로컬 워킹트리 하나에서 끝난다. 히스토리 재작성은 그 범위가 원격·협업자·이미 갈라진 브랜치 전체이고, 대개 강제 push가 뒤따른다(그 push는 1~3번이 별도로 차단한다).
2. **오탐 비용** — `reset --hard`는 일상 명령이라 차단하면 정상 작업이 매번 막힌다. 히스토리 재작성은 비일상 명령이라 차단해도 잃는 것이 거의 없다.
3. **차단은 금지가 아니라 행위자 전환이다** — 차단 메시지가 *"사용자에게 명시적 확인을 받은 뒤 직접 실행하도록 보고하세요"*로 끝나고 이 hook은 **Bash 도구만** 검사하므로, 사람이 터미널에서 치는 경로는 열려 있다. 차단이 막는 것은 **모델의 단독 판정**이지 그 작업 자체가 아니다.

**그래서 승인으로 뚫리는 우회 변수를 두지 않는다** — 자율 루프에서 「승인받으면 통과」를 만들면 루프가 스스로 승인 서사를 지어 통과할 수 있고, 그때는 마지막 방어선이 사라진다(위 절의 *"CLAUDE_HARNESS_QUICK도 무시합니다"*가 같은 취지다).

### 새 패턴을 어느 쪽에 넣을지 판정하는 순서

1. **영향 범위가 로컬 단일인가** — 워킹트리·단일 파일에서 끝나면 경고 후보, 원격·협업자·저장소 전체에 걸리면 차단 후보.
2. **일상 명령인가** — 정상 작업에서 자주 쓰이면 차단의 오탐 비용이 크므로 경고로 내린다.
3. **사람이 대신 칠 수 있는가** — 그러면 차단의 대가가 작다. 모델만 도달하는 경로면 차단이 곧 기능 상실이므로 경고가 맞다.

**셋이 갈리면 경고로 둔다** — 미탐은 사용자가 즉시 관측하지만, 오탐은 정상 작업을 막으면서 결함으로 보이지 않는다.

## PreToolUse hook - PowerShell 버전

```
 PreToolUse hook - PowerShell 버전
 Bash 도구 호출 시 파괴적 명령 차단.
 exit 2 = block (Claude에게 차단 사유 전달).

 차단 대상: 파일 시스템 파괴(rm -rf 등), git 히스토리 파괴,
   DB 데이터 삭제(DROP/TRUNCATE/WHERE 없는 DELETE/스키마 삭제/migration reset/ORM 대량삭제).

 ⚠️ 한계: 이 hook은 **Bash 도구로 실행되는 명령**만 검사한다.
   ORM 대량 삭제 코드(예: RemoveRange, deleteMany)를 소스 파일에 '작성'만 하는 경우는
   Write/Edit 도구라 여기서 안 잡힌다. 그런 코드는 pjc:plan 승인 게이트 +
   완료 리뷰가 검토한다 (CLAUDE.md "DB 데이터 삭제는 승인 필수" 참조).

 ⚠️ RemoveRange 는 **DB 컨텍스트 단서를 동반할 때만** 잡는다 (회차 66 오탐 수정).
   종전 정규식 `\.RemoveRange\(` 는 수신자를 가리지 않아 **PowerShell 리스트 조작을
   EF Core 로 오차단**했다 — 실해: `$lines.RemoveRange($idx, 2)` 가 막혀 같은 편집을
   다른 수단으로 다시 짰다(2026-09-12, 두 세션에서 관측).
   현행은 `db|context|dbset` 로 시작하는 식별자 뒤에 **점이 두 번** 오는 형태만 본다
   (`context.Users.RemoveRange(`). 점 하나짜리 `$dbLines.RemoveRange(` 는 미매치다.

   남는 미탐: **단서 없는 진짜 EF Core 호출**(지역 변수에 DbSet 을 받아 곧바로 부르는
   형태). 그 자리는 pjc:plan 승인 게이트와 완료 리뷰가 받는다 — 바로 위 한계와 같은
   취지이고, 차단을 넓혀 오탐을 되살리는 것보다 낫다는 판단이다.
   골든이 양방향을 잰다 — 오탐 통과 케이스와 **차단 유지 음성 대조** 케이스가 짝이다.
   음성 대조가 없으면 이 수정은 차단을 통째로 지운 것과 골든상 구분되지 않는다.

 ⚠️ 한계 (정규식 접근의 본질적 미탐 — 의도된 트레이드오프):
   명령치환·변수 간접 참조는 잡지 못한다 — 예: rm -rf $(echo /), X=/; rm -rf $X.
   문자열 평가를 하지 않는 정규식으로는 불가하며, 1차 방어선은 Claude Code 권한 시스템이다.
   (hook-cases.json에 '[알려진 미탐]' 케이스로 문서화 — 이 동작이 바뀌면 회귀로 검출됨.)
   변수 간접 중 **같은 명령줄 대입**(X=/; rm -rf $X)은 guard-bash의 warn-dangerous-assignment가
   실행 전에 경고로 알린다 — 알림이지 차단이 아니며, 이 hook의 차단 범위는 그대로다.

 ⚠️ 이 hook은 항상 동작합니다 (끌 수 없음).
   - 파괴적 명령 차단은 사용자 안전 보장의 마지막 방어선입니다.
   - 환경변수 CLAUDE_HARNESS_QUICK도 무시합니다.
   - 이 동작을 변경하지 마세요.
```

## heredoc 파일-리다이렉트 본문 스트립 (모든 검사 전, v1.98.0)

```
 ---- heredoc 파일-리다이렉트 본문 스트립 (모든 검사 전, v1.98.0) ----
 'cat <<EOF > m.sql … DROP TABLE …; EOF'처럼 heredoc이 '파일로 리다이렉트'되면 본문은 기록될
   데이터일 뿐 실행되지 않는다 — Split-TopLevel이 개행에서 본문을 별도 sub로 쪼개 $patterns
   (DROP TABLE 등)에 오탐되던 것을 막는다(마이그레이션 SQL '작성'까지 차단되던 오탐 수정).
 반면 실행자로 파이프되는 heredoc(psql <<SQL … / bash <<EOF …)은 본문이 실제 실행되므로 보존한다.
 스트립 조건(T1 리뷰 B1 반영): '>' 존재만으로 판정하면 'bash <<EOF > log.txt'(본문 실행 + stdout만
   파일로)가 스트립돼 위험 본문이 비가시화되는 우회가 생긴다 — heredoc을 소비하는 명령이
   데이터-싱크(cat + '>' 리다이렉트, 또는 tee)일 때만 스트립한다. 그 외 명령(bash/psql/python 등
   실행자)은 '>'가 있어도 본문을 보존해 검사한다(허용목록 방식 — 모르는 명령은 보존이 기본).
```

```

 주의: rm/Remove-Item/rmdir 계열의 '재귀 삭제'는 옵션 순서·따옴표·글롭 변형이 많아

   → 이 패턴 배열이 아니라 아래 '컴파운드 검사'에서 플래그·대상을 분해해 판정한다.
```

**회차 44 보완 — `git push` 후치·결합 단문자 `-f`.** 종전 두 패턴은 `push\s+-f` 와 `--force` 계열만 받아 `git push origin main -f` · `git push -uf origin main` 이 exit 0 이었다. 새 패턴은 `push\b` 뒤 같은 명령 안 어디서든 **공백으로 시작하는 단문자 옵션 묶음에 `f` 가 있으면** 잡는다(`\s-[a-zA-Z]*f[a-zA-Z]*(\s|$)`). `--force…` 는 `-` 다음이 글자가 아니라 이 패턴 밖이고(기존 패턴이 잡는다), `feature-f` 처럼 인자 안의 `-f` 는 앞에 공백이 없어 안 걸린다.

## &&, ||, ;, |, 개행 으로 분리 — 단, 따옴표 안의 구분자는 분리하지 않는다(quote-aware).

```
 &&, ||, ;, |, 개행 으로 분리 — 단, 따옴표 안의 구분자는 분리하지 않는다(quote-aware).
 (단순 -split '[;|&]'는 grep "DELETE FROM x;" 처럼 따옴표 안의 ;에서 명령을 쪼개
  따옴표가 깨지고, 그러면 데이터 인자 제거가 작동하지 못해 오탐이 난다.)
 개행도 최상위 구분자다(H1) — Bash 도구는 여러 줄 명령이 흔한데, 개행을 분리하지 않으면
  둘째 줄의 파괴 명령이 ^앵커 패턴(chmod 등)을 벗어나고 컴파운드 윈도우 계산도 빈 문자열이
  되어(선행 \n 매치) 'ls\nrm -rf /'가 통째로 미탐이었다. 따옴표 안 개행(멀티라인 커밋 메시지
  등 데이터)은 그대로 보존된다.
```

**회차 44 보완 — 도구별 따옴표 규칙.** 분리기는 bash 규칙(큰따옴표 안 `\"` 는 이스케이프)으로 읽는데 PowerShell 도구 입력에서는 `\` 가 리터럴이고 이스케이프는 백틱이다. 그래서 `echo "C:\"; Remove-Item C:\ -Recurse -Force` 가 PowerShell 도구로 오면 `"C:\"` 뒤 `;` 가 인용 안으로 읽혀 분리되지 않고, echo 스트립(`echo … .*$`)이 뒤 삭제 명령까지 지워 exit 0 이었다(실측). `tool_name -eq 'PowerShell'` 일 때만 `\` 이스케이프를 끄고 백틱을 대신 소비한다 — Bash 도구의 같은 문자열은 종전대로(그쪽은 정말 인용이 안 닫힌 명령이다).

## 줄-이음(PowerShell 백틱+개행, bash 백슬래시+개행)은 셸이 한 명령으로 잇는다 — 개행 분리 '전에'

```
 줄-이음(PowerShell 백틱+개행, bash 백슬래시+개행)은 셸이 한 명령으로 잇는다 — 개행 분리 '전에'
  전역 1회 공백으로 합쳐, 이어진 명령(rm -rf \<개행>/)이 두 sub로 갈라져 미탐되는 것을 막는다.
 줄-이음은 백슬래시/백틱 '직후' 개행만 해당한다(D2). 중간에 공백이 있는 '\ <개행>'는 bash에서
  줄-이음이 아니라 '이스케이프된 공백 + 명령 종결 개행'이므로 결합하지 않는다 — 결합하면 다음 줄
  명령(chmod 등)이 앞 명령과 한 논리 줄로 붙어 ^앵커 패턴을 벗어나 미탐된다. 그래서 \s* 없이 \r?\n.
```


## 설치본 하니스 자산 삭제 차단

`patterns` 의 마지막 3행은 **`.claude/` 하위**의 판정 데이터(`scripts/rules/*.json`) · hook 스크립트(`scripts/*.ps1`) · 등록표(`hooks/hooks.json`) 삭제를 막는다.

**왜 삭제도 막아야 하는가** — 쓰기는 `guard-harness` 가 이미 막는데 **삭제만 뚫려 있었다**(회차 53 실측: `rm`·`Remove-Item` 6형태 전부 `rc=0`). 그리고 그 파일이 사라지면 그것을 읽던 hook 의 판정이 조용히 꺼지므로, **삭제가 곧 무력화**다 — 쓰기 차단만으로는 사슬의 절반만 잡는다.

**왜 설치본만인가** — 레포 안 원본은 git 이 추적해 **복구 경로가 있다.** 설치본에는 없다. 그리고 이 레포에서 작업하는 세션이 자기 원본을 정리하는 것은 정상 작업이라, 그것까지 막으면 개발이 멈춘다.

**왜 다른 hook 인가** — 쓰기는 `Write`/`Edit` 도구라 `guard-harness`(PreToolUse · Write 매처)가 보고, 삭제는 셸 명령이라 `block-destructive`(Bash 매처)가 본다. **도구가 다르면 매처도 다르다** — 한 hook 에 몰 수 없다.

**삭제 동사는 `delCmdAlt` 7형태 + `unlink` 다** — `rm|Remove-Item|ri|rmdir|rd|del|erase|unlink`. ⚠ **로더는 문자열 `{dangerTarget}` 하나만 치환하므로**(`block-destructive.ps1:40`) `{delCmdAlt}` 는 쓸 수 없고 **리터럴로 적어 넣는다.** 그래서 `delCmdAlt` 에 별칭이 늘어도 이 세 패턴은 따라가지 않는다 — 늘릴 때 여기를 함께 본다.

**`{dangerTarget}` 은 쓰지 않는다** — 그 값은 `/`·`/etc`·`~`·`C:\Windows` 같은 **범용 위험 루트** 목록이고, 이 패턴의 대상은 `.claude/` 하위의 **경로 고정 리터럴**이라 개념이 다르다. 끼워 넣으면 매치 대상이 뒤바뀐다.

**경로 구분자는 `[\\/]` 다 — `[\/]` 로 적으면 백슬래시 경로를 통째로 놓친다.** PowerShell 정규식이 `\/` 를 이스케이프된 `/` 로 읽어 **슬래시만** 매치하기 때문이고, Windows 표기(`Remove-Item C:\Users\...\rules\harness-hooks.json`)가 그대로 통과한다. 회차 53 이 실제로 그렇게 넣었다가 완료 리뷰가 잡았다 — `post-write-rationale.md` 의 제외 정규식이 이미 같은 함정을 문서로 남긴 자리다. **json 문자열로 적을 때는 한 겹 더 필요하다**(`"[\\\\/]"`).

**디렉터리 형태도 함께 막는다** — `scripts/rules`·`scripts`·`hooks` 세 이름으로 끝나는 삭제는 파일 하나 지우는 것과 **결과가 같다**. 단 **캐시 루트 전체 삭제(`~/.claude/plugins/cache/pjc-harness`)는 통과시킨다** — `install.ps1` 의 재설치 경로가 실제로 수행하는 정상 동작이다.

**이 판정은 「개발 레포 경로에 `.claude` 세그먼트가 없다」는 전제 위에 있다** — 레포를 `~/.claude/` 아래 클론하면 자기 원본 삭제도 막힌다.
