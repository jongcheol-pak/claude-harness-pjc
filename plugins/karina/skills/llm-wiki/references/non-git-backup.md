# 비 git vault 사전 백업 (`karina:llm-wiki`)

> **`<vault>/.git` 이 없거나 커밋이 0건(`git log -1` 실패)일 때만 읽는다** — 그 밖의 vault 는 체크포인트 커밋이 보호한다(`wiki-ops-rules.md` 「체크포인트 커밋」). `../SKILL.md` 「사전 준수 사항」의 비 git 조건 줄과 `schema-budget.md` §8 「비 git vault 사전 백업」 헤딩이 여기를 가리킨다.

- **취지**: vault가 git 저장소가 아니면 모든 덮어쓰기·삭제가 되돌릴 수 없다. 글로벌 지침은 이 경우 "사전 백업 또는 사용자 확인"을 요구하므로, 승인 문답 없이 자율 동작을 유지하려면 **사전 백업**으로 요건을 충족한다.
- **git 여부 확인**: 세션의 첫 쓰기 절차 시작 전 1회, `<vault>/.git` 존재로 판단한다. git 관리 vault면 이 절 전체가 해당 없음(git이 이력 보존을 담당). **단 이 면제는 git 이력이 실제 보호를 제공할 때만 유효하다** — vault에 커밋이 하나도 없으면(`git log -1` 실패 — `git init`만 한 상태) `git checkout` 복구가 무력해 보호가 0이므로 **면제를 적용하지 않고 비 git vault로 취급해 사전 백업을 그대로 수행한다**(사후 커밋 권유만으로는 이미 덮어쓴 파일을 복구할 수 없다). 커밋은 있으나 워킹트리가 dirty하면 직전 커밋까지의 보호는 있으며, 미커밋 누적은 「git 자동 반영」이 커밋으로 해소한다. **§4 분할 직전 상태 잡기도 git vault에서는 사본이 아니라 체크포인트 커밋이다** **`--auto-split`·`--fix`·복구 직전에 커밋 1회를 두는 것으로 그 전제를 성립시켰으므로**(`references/wiki-ops-rules.md` 「체크포인트 커밋」) 예외가 필요 없어졌다. 비 git vault에서는 종전대로 사본을 뜬다. **그리고 이 면제가 말하는 "git이 담당한다"를 실제로 집행하는 것은 「git 자동 반영」**(`references/wiki-ops-rules.md` — 변경이 생긴 절차마다 커밋, 세션 끝에 push 1회)**이다** — 그 규약이 없던 때는 커밋을 사용자에게 권하기만 해서 면제의 전제가 자주 거짓이었다.
- **백업 대상·시점**: 비 git vault에서 수정·삭제할 **기존 파일**을, 각 파일의 그 세션 **최초 수정·삭제 직전**에 `90_archive/backup/{YYYY-MM-DD}/` 하위로 vault 상대 경로를 유지해 복사한다(예: `20_projects/personal/proj-a.md` → `90_archive/backup/2026-07-02/20_projects/personal/proj-a.md`). 같은 파일의 같은 세션 2회째 수정은 재복사하지 않는다(세션 시작 시점 상태 1부만 보존). **신규 파일 생성은 백업 불필요**(덮어쓰기가 아님).
- **복사 시 목적지에 파일이 이미 있으면 덮어쓰지 않는다**(decisions 롤오버 schema-types §2.8과 동일 규정) — 같은 날짜에 **다른 세션**이 먼저 떠 둔 원백업(그날 최초 상태, 가장 가치 있는 복구 지점)을 그 세션의 현재본으로 덮어써 유실하는 것을 막는다.
- **삭제(절차 C) 백업은 분리**: 프로젝트/파일 삭제 백업은 `90_archive/backup/{YYYY-MM-DD}-deleted/` 하위에 둔다 — 삭제는 원본이 vault에서 사라져 그 백업이 **유일 사본**이므로, 아래 정리·복구 규칙이 수정 백업과 달라야 한다.
- **§4 분할 착수 직전 상태(index 2·3단계 + 산문 타입 하위 분리 + 롤오버)도 분리**: **git vault면 체크포인트 커밋**이 그 상태를 잡는다(`references/wiki-ops-rules.md` 「체크포인트 커밋」 · `pass` 당 1회 · 실패하면 착수하지 않는다). **비 git vault면 사본을 `90_archive/backup/{날짜}-{시각}/` 하위에 둔다**(schema-budget §4 분할 수행 절차 1번·5번의 원복 기준 — 구현은 `lint.py`의 `_presession_dir`). 세션 사전 백업 폴더 `{YYYY-MM-DD}/`를 그대로 쓰면 위 미덮어쓰기 규정에 걸려 사본이 만들어지지 않고, 남아 있는 것은 그 세션 *최초 변경 직전*(=주 작업 이전) 상태라 그것으로 되돌리면 **주 작업까지 유실**된다 — 그래서 시각을 붙여 갈라 둔다. **시각까지 붙이는 두 번째 이유는 pass 격리다** — 한 번의 `--auto-split`이 본 pass와 재점검 pass를 돌리므로 둘이 같은 폴더를 쓰면 1회째 결과가 「원본」으로 보존된다(git vault에서 이 격리를 담당하는 것이 「`pass` 당 1회」 커밋이다). **아래 누적 금지 규칙이 이 폴더도 회수한다**(`-deleted`·`-pre-restore` 같은 보존 특례를 두지 않는다).
- **백업 누적 금지(집행 지점 포함)**: **git vault는 `--fix` 백업도 만들지 않는다** — 사전 백업이 면제인 것과 같은 이유이고, 보호는 직전 체크포인트 커밋이 담당한다(`lint.py`의 `apply_fixes`가 그 분기를 갖는다). **비 git vault는 `90_archive/backup/{YYYY-MM-DD}/`를 만들고**, 그대로 두면 쌓이므로 **다음 `--fix` 실행 시작 시 접미사 없는 이전 날짜 폴더**(`{YYYY-MM-DD}/`)**와 위 분할 사본**(`{날짜}-{시각}/`)**을 제거**한다(**집행 주체는 `scripts/lint.py`의 `cleanup_backups`** — `--fix`가 새 백업을 만들기 **전에** 1회 호출한다. 나중에 하면 방금 만든 오늘 백업을 지울 판정을 다시 하게 된다). **제거 시점을 그 세션 종료 시가 아니라 다음 실행 시작 시로 두는 이유**: `--fix` 변경이 미커밋인 채 세션이 끝나면 git 복구(`checkout`은 미커밋을 되돌리지 못한다)와 백업이 동시에 없어져 복구 수단이 0이 된다 — 한 세션분을 남기면 복구 창이 유지되면서 누적은 1개로 상한된다. **「git 자동 반영」이 도입된 뒤에도 이 규칙은 유지된다** — 커밋 실패 시 보고 후 계속하므로 미커밋 상태가 여전히 가능하고, 그 한 경우를 위해 복구 창이 필요하다. **문자 접미사 폴더(`-deleted`·`-pre-restore`)만 이 규칙의 대상이 아니다** — 유일 사본·복구 재백업이라 지우면 복구가 영구 불가해진다. **시각 접미사(`{날짜}-{시각}/`)는 대상이다** — 분할 사본은 원본이 vault에 그대로 있는 수정 백업 성격이라 보존 특례가 없다. **옛 이름 `-presplit` 폴더는 코드가 보존한다** — 더 이상 생성되지 않으므로 남은 것은 과거 잔여물이고, 그 삭제는 사용자 판단이라 검사기가 자동으로 걷지 않는다.
- **정리(자동, 승인 불필요)**: 위 누적 금지 규칙 하나가 정리를 전담한다(집행 주체는 `cleanup_backups`) — **접미사 없는 `{YYYY-MM-DD}/`와 시각 접미사 `{날짜}-{시각}/`을 다음 `--fix` 시작 시 회수**한다. 방치하면 vault가 비대해진다. 단 **`-deleted`(삭제 백업)·`-pre-restore`(복구 재백업) 문자 접미사 폴더는 정리에서 제외**한다. "삭제해도 정보 손실 없음"이라는 전제는 **수정 백업에만** 성립한다(원본이 vault에 최신으로 존재하므로). **삭제 백업은 원본이 vault에 없어 그 백업이 유일 사본이므로 자동 삭제하면 복구가 영구 불가**해진다(31일 뒤 "그 프로젝트 복구" 요청 시 수단이 이미 없음). 날짜는 추정하지 말고 확인 후 사용한다(확인 불가면 정리는 건너뛴다 — 백업 자체는 날짜 무관하게 수행).
- **lint 관계**: `90_archive/` 하위는 lint 검사에서 자동 제외되므로 백업 파일이 WARN을 만들지 않는다(schema-lint §7).
- **복구(백업 소비)**: 백업본으로 되돌리는 절차는 절차 L(`references/procedures-ops.md`) — 날짜 폴더에서 사본 확인(없으면 복구 불가 사실대로 보고) → 현재본과 차이 제시 → 사용자 확인 → **복구 직전 상태를 별도 폴더 `90_archive/backup/{YYYY-MM-DD}-pre-restore/`로 재백업**(당일 원백업 `{YYYY-MM-DD}/`을 **덮어쓰지 않는다** — 덮어쓰면 복원하려던 좋은 버전이 사라져 복구가 무효가 된다) → 원위치 복사 → lint 권고 + log 기록. 백업은 이 절차의 존재로 "만들기만 하는 사본"이 아니라 발견 가능한 복구 수단이 된다.
