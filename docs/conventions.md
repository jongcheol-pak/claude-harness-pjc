## 스크립트로 파일을 고칠 때

- **PowerShell `-replace` 의 대체 문자열은 `${name}` 을 삼킨다.** 그 자리의 `$` 는 **정규식 그룹 참조**라, 치환해 넣으려는 코드에 `${head}` 같은 변수 보간이 있으면 **빈 문자열로 바뀌어** 구문이 조용히 붕괴한다. 파싱 오류가 엉뚱한 줄을 가리켜 원인 찾기에 시간이 든다. **대체 문자열에 `${...}` 가 있으면 `-replace` 가 아니라 `.Replace()` 를 쓴다** — 앵커 탐색(`-notmatch [regex]::Escape(...)`)에는 그대로 써도 된다. 삼키는 것은 **대체** 쪽이다.
- **여기서 쓰는 헬퍼가 대상 셸 전부에 있는지 본다.** `ProcessStartInfo.ArgumentList` 는 .NET Framework 에 없어 **Windows PowerShell 5.1 에서 null** 이고, `.Add()` 가 던지는 예외를 같은 함수의 `catch` 가 삼키면 **그 축이 통째로 0건이 된다 — 경고도 판정불가 표시도 없이.** hook 은 pwsh 7 이 없으면 5.1 로 폴백하는데 골든은 자식을 `pwsh` 로 띄우므로 **케이스가 원리상 이 결함을 볼 수 없다.** 문자열 `Arguments` 는 양쪽에 다 있다. 이런 축은 **두 셸 대조 기록이 유일한 그물**이다.

**정본은 conventions — 스크립트로 파일을 고칠 때의 「스크립트로 파일을 고칠 때」이다** — 본문 3091자를 옮겼다(§7-2 발동 처방).

## 크기·개수를 잴 때

- [2026-09-11] **문서 예산의 단위가 바이트에서 «문자 수»로 바뀌었다 — 옛 실측 기록의 `B` 표기와 섞어 읽지 말 것.** 한글이 40~45% 섞인 규약 문서는 **B/문자가 1.25~1.99**로 군마다 갈려, 바이트로 재면 같은 정보량이 어느 파일에 있느냐로 다른 비용이 된다. 전환으로 실질 상한이 그만큼 올라 **초과·임박이 그 자리에서 전부 사라졌다**(검사기 99.8% → 69.9% · `DESIGN.md` 99.9% → 53%) — 처방이 아니라 단위 재산정이다. **표의 숫자는 유지하고 단위 표기만 바꿨으므로**, 근거 열에 남아 있는 `B` 값은 과거 실측 기록이고 판정 기준이 아니다. **예외 하나: `AGENTS.md` 주입 상한은 바이트로 남는다** — SessionStart 가 바이트로 자르므로 재는 단위가 곧 실제 동작이다. (실측)

- [2026-09-10] **acceptance 에 `grep -cE` 로 교대 패턴을 쓰면 안 된다 — GNU grep 은 ERE 에서도 `\|` 를 교대 연산자로 해석한다.** 패턴이 「또는 빈 문자열」이 되어 **전 줄이 매치된다**(실측 455/460 줄). 「옛 표기가 0건인가」류 판정이 통째로 무의미해지는데 **숫자가 나오므로 통과처럼 보인다.** 리터럴을 셀 때는 `grep -cF -e '...' -e '...'` 를 쓴다. (실측)

- [2026-10-19] **Git Bash 의 grep 에 `[①-⑤]` 같은 한글·기호 문자 범위를 쓰면 0 이 나온다 — 로캘이 C 라 멀티바이트 문자 범위를 해석하지 못한다.** 면제 표 행 수를 `grep -c "^| [①-⑤] |"` 로 쟀더니 실제 5행이 0 으로 나왔다. **숫자가 나오므로 「없음」으로 읽힌다.** 멀티바이트 문자는 범위 대신 교대로 쓴다 — `grep -cE '^\| (①|②|③|④|⑤) \|'`. (실측)

- [2026-08-20] **폴더 규모를 `du`로 재면 실제 바이트보다 크게 나온다** — 작은 파일이 많은 잔여 폴더에서 `du -shc`가 9.7MB, 실제 `Measure-Object Length` 합계가 2.01MB로 **4.8배** 벌어졌다(블록 4KB 단위 집계). 삭제 승인처럼 사용자가 규모를 보고 판단하는 자리에서는 실제 바이트로 보고할 것.

- [2026-08-15] **예산·임계를 잴 때 `wc -c`(바이트)를 문자 수로 읽지 말 것 — 한글 문서에서 판정이 통째로 뒤집힌다.** vault `conventions.md`가 "19,105자 / 12,000자 = 159% 초과"로 하니스 대장에 등재됐으나 **실측 10,287자(86%)** 였다 — `wc -c`가 낸 값은 바이트이고 한글은 UTF-8에서 3바이트라 **약 1.85배** 부풀려 보인다(공백·ASCII 혼재 비율에 따라 변동). 위키 예산은 전부 **문자 수** 기준이므로 `python -c "print(len(open(f,encoding='utf-8').read()))"`로 재고, 문서에 값을 적을 때는 **단위를 함께 적는다**(`10,287자` / `18,552B`). 이 오판으로 초과하지도 않은 파일의 분리 작업이 한 회차 착수될 뻔했다(결과적으로는 신규 3건 유입으로 분리가 정당해졌지만 근거는 틀렸다).

## 병행 세션·커밋

- [2026-09-20] **`git commit -m "…"` 의 메시지 본문에 백틱을 넣으면 셸이 명령 치환한다 — 메시지는 Bash 에서 `-m "$(cat <<'MSG' … MSG)"`, PowerShell 에서 작은따옴표 문자열을 `-m` 뒤에 바로 넘긴다** — `-F`(파일·stdin)나 변수 `-m $msg` 는 치환은 피하지만 `guard-bash` 가 제목을 읽지 못해 task 체크박스 검사를 건너뛴다(대장 등재 미탐). 정본은 레포 `AGENTS.md` 「병행 세션의 커밋」 줄과 `docs/harness-conventions.md` 같은 절, 워커 쪽은 `implement/SKILL.md` 「커밋」이다. 규칙이 어느 문면에도 없던 동안 같은 사고가 두 번 났다. (실측)

- [2026-09-11] **`.github/` 가 전역 `~/.gitignore_global` 에 걸려 추적되지 않는 일이 있다 — 그리고 디렉터리를 먼저 풀지 않으면 그 안 파일의 예외가 효력이 없다.** CI 워크플로를 새로 만들었는데 `git add` 가 조용히 아무것도 담지 않았다. 전역 설정은 이 레포 것이 아니므로 건드리지 않고 **레포 `.gitignore` 에 예외를 넣어** 되살린다 — 이때 `!.github/workflows/checks.yml` 만 적으면 통하지 않고 `!.github/`·`!.github/workflows/` 를 함께 풀어야 한다. (실측)

- [2026-09-10] **병행 세션 커밋은 `git commit -- <경로>` 를 쓴다** — `git add <경로>` 로 한정해도 상대가 staged 해 둔 것이 함께 들어간다. 근거·재발 이력(회차 54·55)·`git add -p` 와의 상충은 레포 `AGENTS.md` 「병행 세션의 커밋」이 정본이다 — 그쪽은 기계 축이 재고 있어 낡지 않는다 (실측)

- [2026-10-19] **`git commit -- <경로…>` 에서 `-m` 은 `--` 앞에 둔다 — `--` 뒤의 인자는 전부 경로로 읽힌다.** `git commit -- <경로> -m "$(cat <<'MSG' … MSG)"` 로 썼더니 메시지 전체가 경로로 해석돼 `did not match any file(s) known to git` 으로 커밋이 실패했다. 순서는 `git commit -m "…" -- <경로…>` 다. (실측)

- [2026-10-19] **`guard-bash` 는 커밋 제목의 `T<N>` 을 보고 plan 의 그 task 하위 항목이 전부 `[x]` 인지 확인한다 — 하위 항목 일부만 끝낸 중간 커밋(예: vault 쪽 하위 항목 전에 레포 쪽만 커밋)은 막힌다** — 하위 항목을 다 끝낸 뒤 그 task 의 커밋을 한 번에 하거나, 남은 하위 항목을 먼저 끝낸다. 체크박스만 먼저 `[x]` 로 바꾸는 것은 검증 전 `[x]` 금지(글로벌 「문서·기록」)에 걸린다. (실측)

## 위키 vault를 다룰 때

- [2026-10-04] **vault 페이지를 편집한 뒤 줄바꿈은 하네스 레포 규약(CRLF)이 아니라 그 파일의 원래 형상과 vault `.gitattributes` 의 `eol` 을 따른다** — 이 vault 는 `*.md text eol=lf` 인데 레포 습관대로 CRLF 로 되돌리자 커밋마다 git 이 「CRLF will be replaced by LF」 경고를 냈다. 정본은 스킬 `wiki-ops-rules.md` 「셸 경유 편집 규약」이다. (실측)

- [2026-09-17] **`log.md` 에 이력을 적을 때 `>>` 로 파일 끝에 붙이면 «아카이브 인덱스» 구역에 들어간다** — 그 파일은 `## 최근 변경` 다음에 `## 아카이브 인덱스` 가 오는 구조라, 끝에 append 하면 항목이 롤오버가 훑지 않는 구역에 놓여 **아카이브로 넘어가지 않는다.** lint 가 `log 이력 항목 오배치` 로 잡지만 **잡힐 때까지 조용히 쌓인다**(실측 5건 누적). 새 항목은 `## 최근 변경` **바로 아래에 삽입**한다 — 최신이 위로 오는 순서이기도 하다. (실측)

- [2026-09-17] **처방 스크립트(`--auto-split`·`--fix`)를 부르기 «직전마다» 절차 커밋을 먼저 한다 — 안 하면 스크립트가 거부한다.** 착수 직전 체크포인트 커밋이 `git add -A` 라 그 시점의 **모든** 미커밋 변경을 담으므로, 편집만 해 두고 처방을 부르면 그 편집이 통째로 체크포인트에 들어가고 절차 본 커밋에는 그 뒤 손댄 것만 남는다(같은 날 ingest 두 번에서 관측 — 체크포인트 6파일 대 본 커밋 2파일). **커밋 시점 규정이 「절차가 끝날 때 1회」에서 「호출 직전마다 1회 + 절차 끝 1회」로 내려간 이유가 이것이다.** ⚠ **한 절차가 스크립트를 두 번 부르는 자리가 있다** — lint 절차(F-2)가 `--auto-split` 뒤에 `--fix` 를 부르고 스크립트가 둘의 동시 실행을 금지하므로, 그 사이에도 커밋이 필요하다. **선행 처방이 미커밋을 남기는지는 재점검 pass 가 도는가로 갈리므로**(돌면 그 진입 체크포인트가 앞 pass 결과를 담아 깨끗해진다) 매번 재지 말고 **언제나 커밋한다** — 남지 않았으면 커밋할 것이 없어 무해하다.

- [2026-09-11] **`llm-wiki` 의 절차 이름·번호·쓰기 범위를 바꾸면 글로벌 `~/.claude/CLAUDE.md` 의 vault 예외를 «함께» 확인한다 — 어느 검사기도 이 결합을 잡지 못한다.** 정합 검사기의 포인터 도달성은 repo 안만 보는데 글로벌 지침은 repo 밖이라, 스킬 쪽 절차 이름이 바뀌어도 그것을 가리키는 글로벌 예외 조항은 낡은 채 남는다. **결합의 방향은 「면제」다** — `llm-wiki` 는 승인 문답 없이 자동 동작하는데 그것을 막는 것이 글로벌의 절대 금지·승인 필수 규칙이고, 면제는 **규칙을 소유한 쪽만** 줄 수 있다(글로벌 「지침 우선순위」 1 — 절대 금지는 스킬로 완화 불가). **없으면 스킬이 멈추는 필수 예외는 둘이다** — ⓐ 「절대 금지」의 **기록의 해석 기준 + 큐 유실 방지 폴백**(없으면 「질문 작업에서 파일 수정」이 절차 K 의 큐 append 를 막아 **발견이 유실**된다) ⓑ 「1단계」의 **대량 수정/삭제 vault 예외**(없으면 5파일·100줄 임계에 걸려 절차 A·B·J 가 중간에 멈춘다 — 한 번에 여러 페이지를 만드는 것이 그 절차들의 정상 동작이다). 나머지(push 예외·조회 순서·백업 요건·메모리 정책)는 없어도 스킬이 정상 동작한다. 레포 정본은 `docs/harness-conventions.md` 「llm-wiki ↔ 글로벌 지침 결합」 (문서 대조)

- [2026-08-13] **`updated`와 `synced_commit`은 다른 축이다.** `updated`는 「언제 손댔나」, `synced_commit`은 「어디까지 담았나」다. 날짜만 보고 stale을 판정하면 **조용한 프로젝트를 낡은 위키로 오인**한다 — 실제로 「6~7월에 멈춘 허브 8개」 중 7개는 레포도 그때 이후 안 바뀌었다.

## 규약 개정 요청을 받을 때

- [2026-08-27] **이 레포에서 규약을 근거로 규약 개정 요청을 거부하면 순환 논증이다** — *"규약을 고치자"* 에 *"규약이 금지한다"* 로 답하는 형태다. 하니스 스킬·위키 스키마 개선이 곧 규약 개정이므로, 그 자리에서 규약을 제약으로 쓰면 **자기 개정 경로가 닫힌다**. 갈림선은 **「규약을 지키며 하는 작업」 ↔ 「규약 자체를 고치는 작업」**이고 후자에서 규약은 제약이 아니라 **편집 대상**이다. 판정이 갈리면 **① 현행 규약 안의 안 ② 규약을 함께 고치는 안**을 둘 다 제시하며, ②에는 **정본 파일·절 / 딸린 기계 검사 / 파생 서술(포인터·복제 쌍)** 셋을 함께 적는다. 계기는 대장 중복 정리 세션에서 낸 세 선택지가 **셋 다 현행 규약을 고정한 채 범위만 물은** 것이었다.
  - **규약이 그대로 유효한 자리는 둘뿐이고 둘 다 "못 한다"가 아니다** — 안전 임계 hook(개정 경로가 이미 규정돼 있다)과 기계 검사와 짝인 값(동반 갱신 대상). 글로벌 지침의 절대 금지 4가지·승인 필수 항목은 이 절의 대상이 아니다.
