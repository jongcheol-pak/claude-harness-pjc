- **`-Resume`이 스킵하지 *않는* 범위**: 상태는 **필터 집합 + HEAD 커밋 + 검증 자산 내용 해시**로 격리된다(디렉터리 이름에 각인 — `scope.txt`로 확인 가능). 그래서 **다른 필터·다른 커밋·러너나 시나리오나 hook을 고친 뒤의 판정은 재사용되지 않는다** — 조건이 다르면 상태가 애초에 보이지 않아 그 그룹을 다시 돌린다. 이 격리가 없던 v1.159.0 개발 중에 **`-Filter`로 2그룹만 돌린 뒤 무필터 `-Resume`을 실행하자 12그룹을 전부 건너뛰고 `112/112 OK (FAIL 0)` exit 0**이 나왔다(419케이스가 조용히 빠졌고 부분 실행 경고도 없었다). **내용 해시를 함께 넣는 이유**: HEAD만 각인하면 *"전체 실행 → kill → 코드 수정 → `-Resume`"* 에서 **낡은 코드로 낸 판정**이 재사용되고 스코프 줄은 유효한 것처럼 보인다(커밋이 그대로이므로). 스킵이 일어나면 출력에 `[RESUME] … (스코프 filter=…|head=…|assets=…)`가 찍히므로 재사용 사실과 범위를 그 줄로 확인한다.
- **`-Filter`는 단일 문자열 콤마도 받는다**(`-Filter "a,b"`). v1.159.0 이전에는 배열 전달만 동작해 `"a,b"`가 통째로 한 이름이 되어 **매칭 0건 실패로만 드러났다**.
- **고아 콘솔 프로세스는 자동 회수된다 — 그래도 느려지면 그것부터 센다** — `session-end-cleanup-lib.ps1`이 **SessionStart·SessionEnd** 두 시점에서 부모가 죽은 `more.com`·`find.exe`를 걷는다(회수 사실은 화면에 안 뜨고 `hook-events` jsonl에만 쌓이므로 그 파일을 직접 읽어 확인한다). **자동 회수가 닫지 못하는 경우가 둘 있다** — ⓵ **커널에 갇힌 프로세스**: `Stop-Process`가 성공을 반환하고 `taskkill`이 *"실행 중인 인스턴스 없음"*이라 답하는데도 CPU가 계속 증가한다(핸들 0·스레드 1·커널 모드 93% — 2026-08-20 `find.exe` 12개 실측). 회수는 이를 `Unkillable`로 계상하고 마커를 남겨 재시도만 멈춘다. ⓶ **회수 시점 사이**: 세션이 크래시로 끝나면 SessionEnd가 발화하지 않아 다음 SessionStart까지 남는다. 진단은 `Get-CimInstance Win32_Process -Filter "Name='more.com' OR Name='find.exe'"`로 세고, 부모가 죽었는데 남아 있으면 위 ⓵ 상태다. **애초에 생기지 않게 하는 쪽이 본류다** — `find /` 류 전역 탐색은 Bash 도구 10분 캡 안에 끝나지 않아 실행하는 순간 고아가 확정되므로 `warn-global-find` 경고가 실행 전에 알린다. 2026-08-19에는 이 장치가 없어 전체 실행이 37분에서 2시간 이상으로 늘었고(고아 `more.com` 54개, 각 누적 CPU 20,000초+) 「멈췄는가」를 반복 판정하는 데 시간을 썼다.
- **격리 폴더는 부모 하나 아래 모이고, 중단이 남긴 것은 3일 뒤 걷힌다 (v1.184.0)** — 러너는 실행마다 두 곳을 만든다: **작업 폴더** `%LOCALAPPDATA%\pjc-hook-evals\run\<접미>`(시나리오 픽스처가 놓이는 곳으로, **반드시 임시 폴더 밖이어야 한다** — `guard-write`가 temp 하위를 무조건 통과시키므로 픽스처가 temp 안에 있으면 차단 시나리오가 통째로 무력화된다)와 **격리 홈** `%TEMP%\pjc-hook-evals\run\<접미>`. 같은 임시 쪽 부모에 `state`(`-Resume` 상태)와 `scratch`(temp 완화 경로 픽스처)가 나란히 있다.
  - **정상 종료는 자기 폴더를 지운다**(순차 경로와 자식의 `finally`). 남는 것은 **kill·타임아웃으로 그 자리에 닿지 못한 실행분**이며, 걷는 코드가 없던 시절 2026-08-20 시점에 평면 폴더 80개가 쌓여 있었다.
  - **코디네이터가 기동할 때 3일 경과분을 정리한다**(`eval-paths.ps1`의 `Invoke-EvalSweep`). 대상은 셋이다 — 현행 `run\` 하위 · **부모 폴더 도입 이전에 최상위에 흩어져 만들어지던 평면 이름**(`pjc-hook-evals-<접미>`, 구 `-Resume` 상태 루트 `pjc-hook-evals-state` 포함) · 단수형 `pjc-hook-eval-scratch`. **v1.184.0의 첫 실행이 지운 59개는 대부분 이 평면 축**이었으므로, 오래 안 돌린 기계에서 큰 숫자가 뜨는 것은 정상이다. 1건 이상이면 `[SWEEP] …` 한 줄이 뜨고 0건이면 무출력이다. **`state`·`scratch`는 대상이 아니다** — 실행 간 재사용되어 수명이 다르다. 자식은 정리하지 않는다(13개가 동시에 훑으면 서로의 진행 중 폴더를 건드린다).
  - **왜 3일인가 — 잔여 폴더 이름의 그룹명이 "어느 그룹이 죽었는지"를 알려주는 진단 창이기 때문이다.** 즉시 지우면 그 정보가 사라지고, 동시 실행 중인 다른 러너의 픽스처를 지우는 사고 위험도 생긴다. 사흘보다 오래 보려면 그 전에 복사해 둘 것.
- **소요 시간을 완료 판정에 쓰지 말 것** — 같은 스위트가 **19분 6초 ↔ 27분 14초로 실측**된 만큼 wall-clock 편차가 크다. 완료는 `결과: N/N OK` 라인과 exit 0으로만 판정한다. 같은 이유로 **성능 비교는 같은 세션에서 두 모드를 연속 측정**해야 한다(교차 세션 비교는 근거가 못 된다).
- **현행 케이스 수 757이 회귀 기준선이다 — 케이스를 추가·삭제하면 이 값을 함께 갱신할 것.**
  이 숫자는 기계 대조되지 않으므로(`docs/harness-conventions.md`의 예산 표는 파일 바이트만 추적한다)
  **문서를 갱신하지 않으면 드리프트를 막을 장치가 없다.** 실제로 v1.182.0·v1.190.0·v1.194.0이
  케이스를 늘리고 이 줄을 지나쳐 뒤늦게 드러났다. **회차별 증감 서사는 git 커밋 본문이 정본이다.**

- **hook 개명 대응표 — v1.225.0이 hook 을 통폐합하며 바꾼 이름이다.** 옛 이름으로 검색하는 세션을 위해 남긴다: `pre-bash-dispatch`·`warn-external-ops`·`require-task-checkbox`·`warn-commit-secrets` → `guard-bash` / `require-plan-for-write` → `guard-write` / `protect-harness`·`guard-agents-content` → `guard-harness`. **뒤 셋 중 `warn-external-ops`·`require-task-checkbox`·`warn-commit-secrets`는 hook 이름으로는 v1.225.0에 삭제됐지만 `guard-bash`가 방출하는 rule 이름으로는 살아 있다**(`guard-bash.ps1`의 rule 배열).

### 실행 절차 (정본)

**전경에서 그냥 돌린다.**

```
pwsh -NoProfile -ExecutionPolicy Bypass -File plugins/pjc/hooks/evals/run-hook-evals.ps1
```

- **v1.225.0에서 분리 실행·`Monitor` 폴링 절차가 사라졌다** — 무상태 그룹(313케이스)이 한 자식에서 순차로 돌아 전체 wall-clock을 혼자 결정하던 것을 `stateless-<N>` 8샤드로 나누고 동시 상한을 논리 코어의 절반으로 올렸다. 실측 **422초**(744케이스, 2026-09-03)로 Bash 도구의 10분 캡 안에 들어온다.
- **그래도 완료는 시간이 아니라 `결과: N/N OK` 라인과 exit 0으로 판정한다** — 아래 「소요 시간을 완료 판정에 쓰지 말 것」이 그대로 유효하다. 시간은 성능 축이고 편차가 크다.
- **10분 캡에 걸리면** `-Filter <hook>`로 좁혀 원인을 먼저 찾고, 전체 판정은 `-MaxParallel <N>`을 올려 다시 돌린다. 캡을 넘기는 상태가 지속되면 그것 자체가 회귀 신호다.
- **실행 중 검사 대상 파일을 편집하지 않는다** — 러너는 시작 시점의 파일을 읽으므로, 도중에 고치면 FAIL이 「내 수정이 만든 결함」인지 「옛 파일과 새 파일을 섞어 읽은 경합」인지 갈리지 않는다.

### ⚠ 우회 변수 오염 — 실행 전에 `CLAUDE_HARNESS_QUICK`을 지울 것

**환경에 `CLAUDE_HARNESS_QUICK=1`이 남아 있으면 골든은 돌긴 하는데 41건이 FAIL한다.** 그 변수가 `guard-write`·`guard-harness`를 통째로 우회시켜 「차단 기대」 케이스가 전부 통과(exit 0)하기 때문이다.

- **어떻게 들어오는가**: 사용자가 세션 시작 전에 그 변수를 설정하면 Claude가 띄운 프로세스가 그것을 **상속**한다.
- **해소**: 실행 직전에 `$env:CLAUDE_HARNESS_QUICK = $null; $env:CLAUDE_HARNESS_ALLOW_SECRET = $null` (bash에서는 `unset`).
- **판정**: FAIL이 「차단 기대인데 exit 0」 형태로 무더기로 나오면 이것부터 의심한다 — 개별 케이스 결함이면 그런 패턴이 나오지 않는다.

### ⚠ 코디네이터가 취합 전에 죽으면 state 에서 직접 집계한다

**결과 라인이 안 나왔는데 격리 `state\<접미>\*.jsonl` 파일들이 모두 최근 시각으로 남아 있으면 러너는 완주한 것이다** — 코디네이터가 판정을 끝에 일괄 출력하므로 그 직전에 죽으면 화면 결과만 사라진다. 그때는 jsonl 의 `"ok":false` 개수로 판정한다.

그 경우 jsonl 을 직접 집계한다 — 각 줄이 한 케이스의 판정이다:

```python
import json, glob, collections
tot = collections.Counter()
for f in glob.glob(r'<state>\<접미>\*.jsonl'):
    for line in open(f, encoding='utf-8'):
        if line.strip():
            o = json.loads(line); tot[str(o.get('status')).upper()] += 1
print(tot)
```

**단 이 집계는 「그룹이 전부 기록됐는가」를 먼저 확인해야 유효하다** — 일부 그룹의 jsonl 이 없으면 그만큼이 조용히 빠진 채 개수만 맞아 보인다(위 「커버리지 판정」과 같은 함정).

### 케이스 설계 규칙

회차마다 같은 함정을 밟아 온 자리다. 케이스를 더할 때 아래를 확인한다.

- **축마다 단독 양성 + 델타 음성을 함께 둔다** — 한 축만 양성으로 걸면 나머지가 죽어도 전건이 통과한다.
  차단 범위를 넓히는 변경은 `AGENTS.md` `## DO NOT` ②가 **델타 음성으로 오차단 0 실증**을 요구한다.
- **대조 문자열은 라벨이 아니라 대상 본문에서 고른다** — 라벨에도 있는 문자열로 재면 그 절이 통째로
  빠져도 통과한다. 주입 케이스는 주입 본문을, 차단 케이스는 차단 사유 문구를 쓴다.
- **대상이 사라진 음성 어서션은 공허하다** — `-ExpectNotContains`가 가리키던 문자열이 어디에도 없어지면
  그 케이스는 무조건 통과한다. 대상을 없앤 회차가 그 대조 문자열도 함께 교체한다.
- **경계값은 쌍으로 건다** — `29/30`·`13/14`처럼 임계 양쪽을 각각. `-ge` ↔ `-gt` off-by-one을 잡는 유일한 그물이다.
- **변이로 확인한다** — 판정을 뒤집어 FAIL을 관측한 뒤 복원한다. 변이에도 PASS하는 케이스는 회귀 고정용이라 정상이다.
- **한 픽스처의 실측을 원리로 일반화하지 않는다** — 「원리상 잴 수 없다」는 결론이 픽스처 조건 하나 때문이었던 전례가 있다.
- **날짜를 재고 경과 일수는 재지 않는다** — 일수는 매일 늘어 픽스처가 다음 날 깨진다.

### 커버리지 판정 — 개수만 보지 말 것

**`N/N OK (FAIL 0)`은 그 자체로 무회귀의 증거가 아니다.** 병렬화 회차에 **순차 531/531 ↔ 병렬 502/502**가 나왔는데 둘 다 exit 0이었다 — 29건이 조용히 빠진 것이 개수만 보면 통과로 읽혔다(원인: 증분 기록이 `Assert-Case`만 후킹했고 일부 시나리오는 `$results.Add()`를 직접 호출한다). 러너 자체를 고칠 때는 **`[PASS|FAIL|PENDING] + 케이스명`을 정렬해 diff 0줄**을 확인한다(FAIL 라인의 출력 head는 GUID 임시 경로가 실려 실행마다 달라지므로 제외).

### 구조 (v1.159.0)

- `run-hook-evals.ps1` — 코디네이터(그룹 병렬 디스패치 · 판정 취합 · `-Sequential` 순차 경로)
- `run-scenario.ps1` — 자식(그룹 1개를 자기 격리 홈에서 실행 · 판정을 JSON 라인으로 증분 기록 + 완주 시 전량 덤프)
- `eval-common.ps1` — 공용 격리 구성·헬퍼(`Invoke-Hook`·`Assert-Case`·`New-*Json`·`Test-HookSelected`)
- `filter-spec.ps1` — `-Filter` 유효 이름 목록 + 정규화 규칙(부작용 없음 — 코디네이터와 `eval-common`이 함께 읽는다)
- `eval-paths.ps1` — 격리 폴더 경로 계산(`Get-EvalRoot`) + 잔여 정리(`Invoke-EvalSweep`). `filter-spec.ps1`과 같은 이유로 분리돼 있다(양쪽이 필요로 하는 것을 복제하면 갈린다)
- `scenarios/*.ps1` 15개 — 케이스 본문(코디네이터를 모른다). 케이스 정본은 `hook-cases.json` + 이 15개.
- **그룹은 19개다**(무상태 8샤드 + 시나리오 11) — 대부분 시나리오가 독립이지만 `guard-harness-installed`와 `hook-event-log`는 `$vdCache`를 공유하고 후자가 격리 홈의 이벤트 로그 적재를 관찰하므로 **한 프로세스로 묶어** 분리 전 관찰 조건을 유지한다.
